# Engine (`engine/`)

Commands: `pixi run engine-install | engine-test | engine-check | golden-fixtures | engine-bench-data | engine-bench | engine-parity-large | engine-bench-browser` (tasks set cwd = `engine`).

The TypeScript engine of the target architecture (`architecture/`), built bottom-up. It holds the **value layer, the metamodel, the record-graph store, the op applier, the working copy, the snapshot reader and the state digest** — all of sub-project A — and, from sub-project B, the **steps layer, the read surfaces and the service** (the CT-4 dispatcher and its scheduler), and, from sub-project C, the **artifact set and the first evaluations** (criteria search and navigation, which the app's `criteria` and `navigation` surfaces take from the engine by default) and the **built-in validators** with the **custom rules** (`src/rules/`); the server never imports it, and the frontend imports its TYPES only — the sandbox's worker (`sandbox/README.md`) is its one host, and the frontend's shell (`frontend/src/lib/engine/README.md`) talks to it over a `MessagePort`.

- **`src/` has no DOM and no Node dependency** (`lib: ["ES2023"]`, `types: []`), is erasable-syntax-only, and imports with `.ts` specifiers, so a worker, Node and vitest all run the sources unbuilt.
- **`src/value/`** reproduces the Python core's view of JSON values. A `number` is always a Python `int`; every `float` is a `PyFloat`; integers past 2^53 are `bigint`. `parseJson`/`parseLines` route each line: a regex pre-scan sends lines holding a float, a 16-digit integer, a bare `Infinity`/`NaN` or `-0` to the exact parser and everything else to native `JSON.parse`, many lines to a call — which is why `parseLines` refuses a line holding more than one document instead of shifting every document after it. `parseExact(text, {floatConstants: true})` reads a bare `NaN` / `Infinity` / `-Infinity` as the `PyFloat` it stands for (as `json.loads` does) instead of keeping its text, which a rule-set document needs to tell `Infinity` from `"Infinity"`. `pyDumps` is `json.dumps(ensure_ascii=False, allow_nan=False)` byte for byte (`{allowNan: true}`: `allow_nan=True`, the non-finite floats written bare); `pyContains` is `needle in haystack` over code points; `pyFloatRepr`, `pyRepr`, `cmpCodePoint` and `pyKey` mirror `repr(float)`, `repr(str)`, `str` ordering and the uniqueness signature (`_frozen`). `pyLower` / `pyStrip` are `str.lower()` / `str.strip()` of Python 3.14 whatever Unicode version the host carries (Node's `toLowerCase()` differs at 28 code points, `trim()` from `strip()` at 6): generated tables — `lower-tables.ts`, written by `pixi run golden-fixtures`, never by hand — plus Python's final-sigma rule, held to `py_lower.json` over every code point. `pyCasefold` is `str.casefold()`: the same per-code-point lowercase with no final-sigma context, except at the code points whose casefold differs (ß → ss, ligatures, iota-subscript forms, Cherokee to upper case, ς → σ, µ → μ), listed by the generated `casefold-tables.ts` (`tests/golden/casefold_tables.py`). The search criteria's "JavaScript" coercion is Python's `str()` and `float()` in fact (`core/search/criteria.py`'s `_js_str` / `_to_number`): `jsStr` mirrors `_js_str`, `pyReprValue` the `repr` it and `_to_number` fall back to for a container (and `pyStr` Python's `str()` of any value: a string itself, else its `repr`), and `toNumber` `_to_number` itself, throwing `PyOverflowError` where `float(int)` raises `OverflowError`. `pyFloatOf` is `float(str)`: every Unicode decimal digit and `str.isspace()` code point past ASCII becomes its ASCII digit or a space — an ASCII code point, control characters included, is untouched, so `float()`'s own leading/trailing strip (the six classic whitespace characters, narrower than `str.isspace()`) still governs what parses — before the grammar runs and underscores are dropped for `Number()`. Its digits and whitespace come from `digit-tables.ts` (generated, `tests/golden/coerce_tables.py`), held to `py_coerce.json`. `translatePyRegex(pattern, mode)` is `re.search` / `re.fullmatch` (a criterion's `matches`, a pattern facet) in JavaScript. It answers `ok` with a `test(subject)`, `invalid` where `re.compile` certainly refuses the pattern (which then never matches), or `unsupported` with a one-line reason: anything outside its subset is `unsupported`, never guessed, and its caller sends the call to the server. A recursive-descent parser that follows `re`'s own over code points emits a `u`-flag `RegExp` source (never a string replacement over the pattern) and leaves nothing to JavaScript's semantics: the dot is `[^\n]`, `^` / `$` / `\A` / `\Z` / `\z` are look-arounds (`$` also before a final newline), `\w \d \s` and their negations are explicit classes, `\b` / `\B` look-arounds over the `\w` class, named groups become numbered ones, the whole is anchored natively (`^[\s\S]*?(?:…)` for a search, `^(?:…)$` for a full match) because V8 also tries a `u` search between the halves of a surrogate pair, where every look-around sees no neighbour, and IGNORECASE is not JavaScript's `i` (its folding differs at `İ` and `ı`, and with the host's Unicode) but `re`'s: a cased literal, or a class holding a cased member, becomes the class of every code point whose `re` lowercase is a member's lowercase or one of `re`'s extra equivalents. Outside the subset: flags other than leading `(?i)` / `(?m)` / `(?s)`, possessive quantifiers, atomic, conditional and comment groups, `\N{…}`, a class Python reads as a future set operation or a nested set, a look-behind of varying width, a repeated look-around, a back-reference under `(?i)`, in a look-behind or to a group that may not have matched (JavaScript matches an unset group as empty, `re` fails it), a class past U+FFFF under `(?i)`, a count past 65535 and a translation past 4 MiB. The classes and the case data come from `regex-tables.ts` (generated, `tests/golden/regex_tables.py`, which also asserts the two properties of `re`'s case data the translation leans on); the answers are held to `py_regex.json`, patterns × subjects in both modes plus a few patterns against every code point. Translations are memoized per pattern and mode, the 256 used last.
- **`src/metamodel/`** — `Metamodel.fromJSON(doc)` takes the `GET /metamodel` document (validated by the server; the engine parses no YAML and runs no `check_metamodel`) and builds every lookup of the Python `Metamodel` up front, under the same names in camelCase. `Multiplicity.parse` mirrors the Python parser, error text included.
- **`src/model/`** is the store: one fixed-shape record per entity (`ElementRec`, `RelRec`), adjacency and containment parents as arrays of record references ON the records, and `Model` as the single mutation boundary, with the Python method set and error texts (`ModelError.kind` is `key` / `value` for `KeyError` / `ValueError`). The engine never mints ids: `createElement(typeName, id)` and `connect(…, id)` take them. Entity order is state: each record has an `ord`, `elements()` / `relationships()` iterate in it, and a record restored WITH its old `ord` goes back to its old place (the Python core always appends). `IndexSet` keeps by-type, uniqueness, references and root order; adjacency order is unspecified, so anything observable sorts by code point. Uniqueness buckets are keyed by a 53-bit hash of the `pyKey` text and confirmed by the exact text at query time; that text is kept (`keyText`) for every member of a bucket of two or more, written as the element is filed and refreshed by every rekey — even one that keeps its hash, as a property edit, a re-parenting or a key relationship can move the text without moving the hash — so `uniqKey`, `uniqGroupOf` and the uniqueness validator read a group without serializing its members again, and `verifyConsistent` holds the texts to a rebuild's. Entity order has an epoch, `orderEpoch`, moved by every re-sort of either map: a `Map` iterator that crosses a re-sort reads the whole map again, so whatever holds one across a write must take a fresh one when the epoch moves. `loadElement` / `loadRelationship` + `rebuildIndexes()` are the bulk path — non-strict like `build_model_from_dicts(strict=False)`, the same refusal texts as `SnapshotError` — and stricter than Python in two places: an id shared by an element and a relationship, and an array-index property key (`"0"`) at any depth, which a JavaScript object cannot keep in insertion order. Committed state enters through `insertElement` / `insertRelationship` / `overwrite`, which check no type (a model may hold one its metamodel no longer has) and take `rev` as given instead of counting it.
- **`src/ops/`** — `applyBatch(model, ops, {restore, idFor, dirty})` is the port of `routes/ops.py::_apply_batch` for the six model ops, in the wire's shapes: temp ids resolved through `idMap` in ids, ends and property values (strings and lists, never inside a dict), `id` hints, restore mode, merge patches, the cascade read before it happens, first-touch changed/deleted sets kept disjoint, the `recreated` sets (the changed ids the batch deleted and created again), inverse units and `inverseOps()`. `idFor` decides a created entity's id and is the identity by default — a staged entity lives under its temp id. `dirty`, a `DirtyCollector`, receives the dirty-set hooks exactly where `_apply_one` fires them (see `src/validation/`); without one the applier fires nothing. A refusal is an `OpError {status: 422, detail}` with the server's text, the quote-stripping of `_error_detail` included (`No element with id 'ghost`). One deliberate difference from the server: an op carrying an array-index property key at any depth is refused. A refused batch leaves NO trace on either side — `rewind(model, result)` puts every touched entity back from its first-touch before-image (properties, `rev`, `ord`), and the server's `_rollback` is its port. A record that outlived the batch still has the `ord` of its image and is rewritten in place; anything else under a touched id is removed and the image inserted at its old `ord`.
- **`src/working/`** — `WorkingCopy` owns a `Model`, the committed `rev` and state digest, the staged batches and the committed image of every entity they touched (`committedElement` / `committedRelationship`, `isStaged`). `stage(ops)` applies a batch in place; `unstage('all' | {batch} | {entity, incident?})` and `applyDelta(delta, own?)` are both a rebase — rewind every staged batch newest first, change committed state, replay in order — and a batch that no longer applies is parked in `conflicts()`, never dropped. `applyDelta` follows CT-2 (`applied` / `duplicate` / `gap`), reads the delta's entities with the bulk loader's checks before anything moves, writes them through the committed-state methods (the ids the delta names in `recreated_*` go out first and are appended, as the server's dict did; a record that would change its type or its ends WITHOUT being named does not fit), folds the digest per entity and sets `diverged` on a mismatch or on a delta that does not fit; for the user's own commit it drops the committed batches and rewrites their temp ids in the rest (`remapOp`). The `(id, rev)` hash is the engine's own (`src/snapshot/`); the `entityHash` option replaces it, which is how tests hold it to another implementation. `verifyDigest()` recomputes the digest from every COMMITTED entity — the model's, with the committed image standing in wherever a staged batch has been — and sets `diverged` on a mismatch. Every operation returns a change set, whose `structural` says it may have moved more than properties: it names a relationship, a deleted element or an element absent when it began (presence is asked BEFORE a rebase rewinds, of the ids the staged batches and the change name), or it is an own commit with minted ids — a rebase over-reports what it touched, so a staged relationship makes any peer delta structural, which costs a refresh, never a stale tree. `stage(ops, {coalesce: true})` with ONE property update merges it into the first staged (never parked) op of the same kind and id — `{...old, ...new}`, later keys win, a `null` stays — as a new batch object under the old batch id: the op is first tried alone on top (a bad patch throws and cannot park the batch holding the earlier edits) and rewound, then the working copy rebases FROM that batch (the private `rebase` takes the index to start at; the batches below it stand). Never in place: an update bumps `rev` once per key and re-places a deleted key, so an in-place merge would leave a state no replay of `staged()` gives (key order and `rev`s included), which the seeded invariants hold. `adoptStaged(batches)` replays batches under their ids on a working copy with nothing staged or parked (a re-bootstrap carrying the user's edits), parks the refused ones and numbers the next batch past the highest id. A `duplicate` delta that comes with `own` naming a batch still staged or parked drops them all the same — the echo of a commit can arrive before its answer. `stagedVersion` moves whenever `staged()` or `conflicts()` come to hold other batch objects (a stage, a merge, a remap, a drop, a park; a plain rebase keeps them). `stagedDiff()` pairs each committed image with the record now, in first-touch order; `touchedIds(from?)` lists the ids those images hold, elements then relationships, or the ids the batches from `from` on touched; `mergePoint(op)` is the index of the batch a coalesced `op` would merge into (the batches from there on are the ones it replays), -1 when it would stage alone. `stage(ops, {dirty})` hands a `DirtyCollector` the hooks of the batch applied, or of a merge's trial run on top. `probeStaged(onWorking, onCommitted)` looks at the staged batches as the server's preview takes them and leaves no trace: it rewinds them, replays them in order into one collector — the dirty set `S` of the staged ops applied as ONE batch to committed state — and runs `onWorking(S)`; rewinds again and runs `onCommitted()` on committed state; replays once more. The entries and committed images are rebuilt from the replays, never through the staged-version tracking, so `staged()`, `conflicts()`, `stagedVersion`, the entity lines, the index dump and the digest are all as they were; parked batches are not touched. A replay cannot be refused (the same batches on the same states); if one ever is, it throws a plain `Error` with the staged batches put back, or, when even that fails, still listed and the replica diverged, for the next replica to adopt them.
- **`src/snapshot/`** — `sha256` is FIPS 180-4 in plain TypeScript, synchronous because the digest fold cannot wait for WebCrypto; `entityHash(id, rev)` is CT-3's hash (the first 8 bytes over `utf8(id) ‖ 0x00 ‖ ascii(rev)`, the UTF-8 written by hand, a lone surrogate as U+FFFD), `modelDigest(model)` the port of `state_digest.model_digest`, and both are `WorkingCopy`'s default. `openSnapshot(chunks, metamodel, onProgress?, options?)` reads a `datarover.snapshot/v2` text from inflated bytes cut anywhere and returns `{header, workingCopy}` at the header's `rev` and `state_digest` — adopted, not checked: `verifyDigest()` is the check, whenever the caller chooses. Bytes are decoded by the host's `TextDecoder` (`fatal`, the byte order mark kept so that it fails the format check), reached through a typed `globalThis` lookup in `utf8.ts` because a declared global would collide with the host typings of any project that compiles these sources; `LineSplitter` cuts on LF alone; lines are parsed and loaded 500 at a time through `parseLines`, the first `elements` of them as elements, so the text is never held whole — 500 being the largest batch that stays a short step (at 2,000 the worst batch took 36 ms at M, _measured_). `options.pause` is asked after every loaded batch and every step of the index build (`rebuildIndexSteps`, reported through `options.onIndex`); only a returned promise is awaited, so an open with room left in its slice pays no microtask, and a throw ends the open. The pause sits in the batch loop, not the chunk loop, and a chunk is decoded in pieces of 64 KiB: a snapshot served from a cache arrives as a few large chunks, and awaiting a chunk that is already there resolves in microtasks, which is no yield to the host. Anything that does not start with `{"format":"datarover.snapshot/v2"` is refused at its first bytes. A refusal is a `SnapshotError`: the server's two texts (`snapshot v2 header carries no valid entity counts`, `snapshot v2 holds N entity lines, its header promises E + R` — the count is checked BEFORE the last lines are parsed, which is what gives a cut text the server's answer), the bulk loader's own, or the engine's for what the server's decoder never looks at (`rev`, `state_digest`, the ids, invalid UTF-8, a line that is not one JSON document, named by its number). Like the server's reader it takes a last line without its LF and CRLF line ends.
- **`src/steps/`** — a `Steps<T>` is a generator that cuts a long operation into steps of about a millisecond at M, each `yield` saying where it stands (`{done, total}`). Every long operation exists once, in that form, and its synchronous name drains it (`drain`): `IndexSet.rebuild` / `Model.rebuildIndexes` (`rebuildIndexSteps`, 1,024 entity visits a step), `WorkingCopy.verifyDigest` (`verifyDigestSteps`, 2,048 entities a step), `RootOrder.reset` — so no caller of the one-shot forms changed. A steps generator publishes nothing before its last step (`diverged`, the root order), so abandoning one leaves no trace; it holds iterators over the model across its yields, so the model must stay still between two of them, and each user says who keeps it still: the index build runs only while a replica is opening, a scan is protected by the service's queue, and the digest check is dropped and restarted after any transition. `sortedInSlices(items, compare, run = 2048)` is a stable bottom-up merge sort in steps (runs sorted natively, then merge passes into a second buffer, a step every `run` items written; the order `Array.prototype.sort` gives); it costs about twice the native sort and no step over 2 ms at M (_measured_), and serves the root sort of the index build and the hit sort of a search.
- **`src/read/`** — the read surfaces, a port of `routes/read.py` (and `routes/elements.py::get_element`) rule for rule. A read is `(model, placements, params)` → the route's HTTP response BODY, in pydantic's field order (`{id, type_name, properties, rev}`, `{items, total}`, …), as a plain call or a `Steps` generator; it reads the model and nothing else. `READS` maps the `lib/api` names (`getElement`, `getElementsBatch`, `listElementsPage`, `listElementRelationships`, `getModelSummary`) to them, and `readScans(method, params)` says which calls run in steps. `toWire` deep-copies a value into plain JSON-able data — a `PyFloat` as its number, a `bigint` as the nearest double, which is what a client's `JSON.parse` of the server's body gives — so nothing of the replica leaves; `readOps` reads ops as the server reads what a client sends: through `JSON.stringify` (an integral double is an `int`, `NaN` `null`, `-0` `0`) and the exact parser, then a shape check whose refusal is a 422 `ops[i]…` in the engine's words. `ViewPlacements` holds the element ids each loaded view places (an unknown, empty or absent view places nothing). An unknown element is the model's `ModelError` (`key`); page bounds (`limit` 1–500, `offset` ≥ 0) and parameter types refuse with `ReadError(422)` in the engine's own texts, because FastAPI, not the route, enforces them and no fixture can hold them — `too many ids: N (max 500)` is the route's own. `getModelSummary` answers `issue_counts: null` and `undo_depth: 0`, `model_rev` being the caller's. The tree (`tree.ts`: `getTreeItemsBatch`, `listContainmentRoots`, `listExcludedRoots`, `listContainmentChildren`): a child belongs to its FIRST containment parent (`parents[0]`, relationship order — a relationship restored under its old id goes last, so it does not win its child back), counts once however many parallel edges hold it, and levels sort by `(displayName, id)`, both by code point; roots come off the maintained root order, the excluded pool is that order minus the ids `ViewPlacements` holds for `view_id` (whatever a view places that is not a root changes nothing) with `total` counted over the whole walk. Search (`search.ts`, `listElementsPage` with a `q` that is not blank) is a full scan in steps — no trigram index (AD-13) — of `searchScore` over every element in state order, 512 a step: the query is `pyLower(pyStrip(q))`; a name (`nameOf`) is lowered with `pyLower` and scored by `nameScore` — exact 1000, prefix 100, word boundary 30, substring 10 — plus `len(query) / len(lowered name)` counted in code points of the LOWERED name (U+0130 lowers to two); the boundary test runs on the lowered name (U+212A lowers to `k`) as an occurrence walk that tries every start, overlapping ones included, which is what the route's regular expression does; then +5 / +2 for the id, +1 for the type (memoized per type), +0.5 per other string property (every `name`-cased key skipped). The additions happen in the route's order, in doubles, so equal scores are equal doubles and nothing is rounded. Hits sort by `(-score, id)`, ids by code point, through `sortedInSlices`; `total` is every hit; nothing is kept between pages (the server keeps nothing either).
- **`src/search/`** — a port of `core/search/criteria.py` and of `POST /model/search`. `readCriteria(raw, path)` reads the eight criterion shapes as pydantic reads canonical JSON: `type` required (a group holds leaves only), the defaults filled (`names`, `criteria`, `rel_types` to `[]`, a property's `value` to `""`, `datatype` to `null`), `relTypes` and `rel_types` both taken — the alias winning when both are given — unknown keys ignored, an absent key defaulted but a `null` taken only where the field allows one (`datatype`); what pydantic would coerce (`"3"` or `true` for a count) is a 422 `<path>[i].<key>: …` in the engine's words. `compileCriteria` translates every `matches` pattern, group members included, BEFORE any entity is matched: a pattern `translatePyRegex` answers `unsupported` refuses the whole call with 501 `reaches an unsupported pattern` (the shell then asks the server), one it answers `invalid` never matches, as `_safe_regex` has it. What the host cannot run although Python can is that same 501, mid-scan too, its detail never the source: a `RangeError` — a pattern nested past the translator's stack, or a subject past the backtracking stack of the translated `RegExp` (about 8M code units of `(a)*$`, fewer the more groups it holds) — and V8's `SyntaxError` `Regular expression too large` (a literal of 50,000 `k`, or 40,000 under `(?i)`), which V8 throws on a pattern's first run because it compiles lazily, apart for one-byte and two-byte subjects; `compileCriteria` therefore runs each translation once on `''` and on `'Ā'`, so that it refuses before the first step whatever the model holds. Nothing else is caught. `matchElement` / `matchRelationship` are the matchers line for line: text ops over `jsStr` of the value (missing and `null` are `""`), `contains` over `pyLower` of both and never splitting a surrogate pair (Python's `in` counts code points), numeric ops over `toNumber` — whose `PyOverflowError` for an int past the double range reaches the service as the route's 500 `int too large to convert to float` — with NaN on either side never matching; type names compare exactly (a subtype is not its parent) in `entity_type`, `rel_types`, `connected_to_type` and `endpoint_type`; a relationship count counts a self-loop once; an empty group matches; an element-only criterion on a relationship query, and the reverse, matches. `nameProp` is `name_prop`: a non-empty STRING only (never a list's first entry, unlike `nameOf`), `name` first, then every other `name`-cased key in property order. `searchModel` is the route body: `target` required, `criteria` default `[]`, `limit` 1–500 default 500, `offset` ≥ 0; every entity of the target in state order, criteria ANDed in order (an earlier one that fails keeps a later one from running, as `all()` does), 512 a step; the page is cut after matching and `total` counts every match; the body is `{target, elements, relationships, total}`, the other list empty.
- **`src/artifacts/`** — `ArtifactSet`, the project's artifacts in two layers: the committed ones the shell hands in (`setCommitted` replaces the layer, `put(changed, deletedIds)` upserts then removes) and over them the staged overlay mirrored from the frontend's buffer, one entry per id (`setStaged` replaces it). `resolve(id)` answers `{id, kind, name, payload}` or `null`: a staged `delete` hides the id, a staged `create` (under its temp id) is itself, a staged `update` lays its `name` / `payload` — whichever it carries — over the committed artifact and names nothing when none is under it, and otherwise the committed artifact answers; `size` counts the ids that resolve. `readArtifacts` (`WireArtifact`: `{id, kind, name, artifact_rev, payload, rules?}`, unknown keys ignored) and `readStagedArtifacts` (`WireStagedArtifact`: `{op: 'create', id, kind, name, payload, rules?}`, `{op: 'update', id, name?, payload?, rules?}`, `{op: 'delete', id}`) read a list as `readOps` does — `JSON.stringify`, then the exact parser, so a payload's `1` is an `int` and `1.5` a `PyFloat` — and refuse a malformed entry with a 422 `<where>[i].<key>: …` in the engine's words before anything moves. `rules` is a rule set's parse, `POST /rules/parse`'s body read strictly as a `RulesParse` (`{ok: true, document}` or `{ok: false, errors}` with at least one `{message}`; other keys ignored): committed, absent or `null` carries none; staged, it may be `'pending'` while the shell's parse is out. The document text is not parsed here. The set keeps, per rule set, the parse a `'pending'` entry stands on (`lastWorkingParse`): the last one a staged payload brought — an update with no payload records none — or else the committed one, which a committed artifact arriving does not overwrite while a staged payload stands over its id; an entry that stops carrying a payload (a discard) resets it to the committed parse, and an id gone from both layers is forgotten. The set holds what the readers made, never what was handed in, and replaces entries rather than changing them, so a resolved payload stays as it was however the set moves after; it is read, never mutated. `version` moves whenever a layer comes to hold other entries — one added, removed, or replaced by one not alike (the same fields in the same order, values exact: `2` and `2.0`, `0.0` and `-0.0` differ; a committed layer's order counts) — and stays when a call hands it the same entries again (a push of what it holds, an identical staged buffer). The service's set is not tied to a replica: it survives `close` and `open`, as the view placements do.
- **`src/navigation/`** — a port of `core/navigation` and of `POST .../artifacts/navigation/evaluate`. `readNavigation(raw, path)` reads a definition as pydantic reads canonical JSON: `kind` required on every definition, start and step, `op` on a set, the defaults filled (`direction` `out`, `types` / `target_types` / `criteria` / `steps` `[]`, `exclude_visited` `true`, a snippet `{}`), unknown keys ignored, criteria through `readCriteria`, and what pydantic checks but nothing uses checked all the same — `schema_version` an int on a path and a set, a path's `name` and every step's `comment` a string or `null` (a set has no `name`: pydantic ignores one), a `true`, `1.0` or `"3"` version refused where pydantic coerces it; the core's own texts where it has them (non-empty `children`, more than 10 steps, an operand without exactly one of `ref` / `definition`, a snippet with both), a 422 `<path>…: …` in the engine's words otherwise. A snippet is not read past its `ref` / `definition`: set or not is all that matters. `resolveRefs(defn, fetch)` inlines every operand's ref depth first — a ref already on the path is `RefCycleError` (`navigation reference cycle through 'x'`), a diamond is fine — and `navigationFetch(artifacts)` is the fetch the route uses: `ArtifactSet.resolve`, so a staged create, update or delete is what a ref sees, and anything but a `navigation` is `RefNotFoundError` (`unknown navigation artifact 'x'`). `navigationHasScript` is true when a script step with a snippet set is anywhere in the resolved tree. `evaluateSteps(mm, model, defn, limits, rowElements, meter?)` is `evaluate.py` line for line in steps: ids sorted by code point (`sortedInSlices` past 1,024), a hop's relationships counted once each (`either` counts a self-loop once) and charged to the budget before any is examined, parallel edges one continuation, a property hop through an element-typed property to the distinct STRING values naming an element (any other item, a dict or a list included, is skipped) and through a scalar one to a `PropertyValue` per scalar item in list order, a script step pruning (one with a snippet never gets here), a fresh budget per set operand, a truncated start set marking the path truncated. A `PropertyValue`'s `key` is `(type, value)`, so `True`, `1` and `1.0` stay three; `bigint` and `number` ints share one. `Meter` counts the units of a whole call — an edge or a property value examined, an element gathered, matched or expanded, a set member combined, a chain collected, an id sorted — and ends a step every 1,024; `evaluateNavigationCore` drains it. `scopeSteps` is a scope's ids alone, with no budget and no chain cap: a table's scope rows. - **`src/validation/`** — a port of the Python core's six built-in validators and of its scoped pipeline (`core/validation/`), held to `validation_kinds.json`. `Validators` holds them for one metamodel, in pipeline order — type conformance, multiplicity, facets, endpoint typing, containment, uniqueness — with their memos per type name, so one is built per metamodel and reused; `FacetPatterns` likewise. `validateScoped(model, ids, validators, patterns, rules?)` is `ValidationPipeline.validate(model, Scope(ids))`: each id once, its first occurrence deciding the order; an element through every element hook, a relationship through every relationship hook, an id naming nothing skipped; then every global hook, in validator order; `check` stamped with the validator's name. Every issue is an error; a dangling reference, a second containment parent and a cycle are `structural`, the rest `conformance`. The messages are the core's texts: a value through `repr` (`pyReprValue`); a uniqueness identity through `repr` of the FROZEN value (`pyReprFrozen`: a list as a tuple, a dict as its key-sorted pairs, a missing key as `None`), rendered from the reported element's OWN key — `1`, `1.0` and `True` share a group — with its key relationships' endpoint ids sorted by code point, the group's primary being its member with the least `ord`; a facet bound is a float and renders as one (`5.0`) while the value goes through `str()` (`pyStrNumber`: `100000000000000000000`, `1e+20`); `max_length` counts code points; an enum member must be a string; a `date` is what `datetime.date.fromisoformat` accepts (`pyIsoDate`, CPython's parser over the UTF-8 bytes: `YYYY-MM-DD`, `YYYYMMDD`, `YYYY-Www[-D]`, `YYYYWww[D]`, ASCII digits, the calendar and ISO week 53 checked, and — since the parser never looks for the end — the two bytes past an eight-byte date not read at all, so `20240101xx` passes).   `LiveIssues(wc, {seed?, sweepStep?, sweepSkip?, rules?})` (`live.ts`) keeps an `IssueStore` over a working copy's WORKING state; nothing else may write to the working copy while it wraps it. It holds two compiles, `rules = {working, committed}` (W and C, both `EMPTY_RULES` unless given): W is the working layer's rule sets, the ones the store's issues are found with, C the committed layer's; with nothing staged they are the same. Its `stage`, `unstage` and `applyDelta` are the working copy's, each revalidating before it returns the ids whose verdict it may have moved, by three rules: a stage takes its applier's hooks, the server's own dirty set; a rebase (`unstage`, `applyDelta`) takes `addNeighbourhood` on the state before over every id it may touch — `touchedIds()`, plus every id a delta names or deletes — and on the state after over those and the ids its change set names, both passes carrying the ends of every relationship among them (from the model, the committed image of one staged away, or the delta's own `source_id` / `target_id`), since a relationship absent on one side cannot name its ends there and they move groups all the same; a merged edit (`coalesce`) takes its trial run's hooks and the rebase rule over the id it names and every batch it replays — from `mergePoint(op)` on, `touchedIds(at)` — since those batches may overwrite part of it or park; an edit that asks to merge and does not pays its hooks only. Every one of those dirty sets is then widened by W's reach (`expandScope`) on the state AFTER the transition — a stage after its hooks, as `_finalize` does, a rebase or a merged edit after its neighbourhoods — and revalidated with W: the premise of `src/rules/` holds because each dirty set holds every element whose properties or incident relationships moved, and the seeded invariants hold it with rules of two-hop atoms in play, the store equal to a fresh sweep after every action. The containment chain past its first link is the one input no rule reaches (the core shares it), which is why the seeded invariants compare stores without cycle issues. `version` moves when a splice changes the store's content (not when it only re-files an owner), on every applied delta (origins move with the rev), on every `setRules` (`rules_status` or the tags may have moved) and when the store becomes unusable. The sweep, `sweepSteps()`, is a `Steps<boolean>` whose state lives on the object, never in the generator: its first step takes the total, the entities then (`done: 0`), each later one walks on — elements in state order, then relationships — and validates and splices the next `sweepStep` entities (`SWEEP_STEP`, 512), a complete change of its own, so it resumes across any transition and any generator picks it up. It holds a live iterator per map, with the `orderEpoch` it was taken at, and the set of ids it has validated since it began (O(model), as a list of every id would be): the iterator passes over an entity in the set, at most `sweepSkip` (16 × `sweepStep`) a step, and validates any other. An entity deleted since is not reached (the transition that deleted it dropped it from the store); one the map holds between two steps is reached before the iterator ends, wherever it sits — made by a transition (validated twice, harmlessly), put back at its old place by an unstage, put back at the map's END by a refused batch's rewind (which validates nothing: the entity is as it was, but may never have been swept), or made again by a probe's replay (a staged create under the same id). A re-sort would make a live iterator read the whole map again, so when one moves the epoch the sweep takes a fresh iterator and passes over the set's members from the start. The progress counts the entities validated, short of the total until the last step, which alone reports `done === total` (entities made meanwhile can take the count past it); that step sets `seeded` and releases `whenSwept()`. The walk ends as long as each step's `sweepSkip` outruns what lands behind the iterator between two steps: the entries a probe's or a rebase's replay appends (one per staged create), or the whole map after a re-sort. `restartSweep()` sweeps again from the start, in place: the store keeps what it holds meanwhile. `setRules({working, committed})` swaps both compiles, moves `rulesVersion` and `version` and drops the origins; it validates nothing. When W's ordered list of rule identities changes, `appliesPopulation(model, old W, new W)` joins the rescan queue after the ids still queued, each once — a rename or anything that leaves W's rules as they were queues nothing. The same generator drains the queue after any sweep due, `sweepStep` ids a step, each a `revalidate` with W as it is at that step, and yields `RESCAN_STEP` (a `SweepStep` marked `rescan: true`) in place of progress, so a rescan reports none and never moves `seeded`, which still means a sweep has ended. `settled` is false while the queue holds ids; `whenSettled()` resolves when it empties or the store becomes unusable, and `whenSwept()` waits for the rescan too. A sweep or rescan step that throws — a validator's bug: a pattern the host fails is caught as `unusable` — splices nothing and leaves its ids due, the sweep's pulled ones first in its next step and a rescan's still queued, and releases both waits, since nothing drives the steps until a caller starts a generator again. A `PatternUnusable` anywhere — `FacetPatterns` refusing a pattern at construction, or the host failing one mid-run, which is sticky — sets `unusable = 'pattern'`, empties the store, ends the sweep (`false`) and moves `version`; the transition itself still answers. `origins()` runs `probeStaged`, once per `(rev, stagedVersion, rulesVersion)` and not at all with nothing staged: `hooks` is the probe's dirty set (the server's `base_dirty`), `S` (`dirty`) is `hooks` widened by W's reach on the working state, and while W and C differ, every element a changed rule applies to — the rules one identity list holds more often than the other, both ways (ΔPop) — with its issues validated on the working state with W (`working`) and on the committed one with C (`committed`); `previewDirty` is `hooks` widened by C's reach and `preview` its issues on the working state with C, which is `working` itself when W and C hold the same rules in the same order. An element of ΔPop that neither W nor C reaches from `hooks` has the same inputs on both states, so its issues with W and with C are found on the working state alone and kept (`deltaOf`) for one rev and one pair of rule sets: a keystroke's probe does not pay for ΔPop again. With nothing staged in the model, `S` is ΔPop alone, empty when W = C. `tagScope()` is what the panel's tags read: every owner whose issues may differ between the two states, with its committed issues. The exact probe finds it (`S`, with `committed`); from there, while the store is seeded and settled, the rev and the rule sets hold and W's identities are C's, each transition adds the ids it dirties, with the store's issues from just before it revalidates them — no transition had dirtied them since the probe, so those were their committed issues (the dirty sets are exact, and each owner's issues are found independently of the rest of a scope) — and a keystroke's list runs no probe. A delta, a `setRules`, W ≠ C or a store not seeded or not settled drops it, and the next read probes; `resetTagScope()` drops it too. The three bodies (`bodies.ts`) answer as the routes do — `validateBody` and `previewBody` through `origins()`, whose `S` is part of their answer, `issueListBody` through `tagScope()` — so each throws `PatternUnusable` when the store is unusable: `issueListBody` is `GET /model/issues` over the working store, an issue whose owner the tag scope names `on_server` while a committed issue of that owner with the same `(severity, message, target_ids, category)` is left to match it and `uncommitted` past that, every other one `on_server`, and no `resolved` (the live list never shows a fixed issue), its `rules_status` W's — so a new rule's issues read `uncommitted` and a removed rule's are gone; `validateBody` is the staged branch of `POST /model/validate` — the store's issues of owners outside `S`, then `S`'s working issues tagged the same way, then the committed ones left unmatched as `resolved`, in their order; `previewBody(live, strict)` is the model half of `POST /commits/preview` over `preview`, all `on_server` — C's rules, as the server's preview never assigns a staged rule set — `would_block` being `strict` and a conformance issue the ops can be held to (`attributable_issues`): owned inside `hooks`, or any rule's, warnings included. - **`src/rules/`** — a port of `core/validation/rules/` (the rule grammar, compile, reach and the validator), line for line, held to `rules_compile.json`, `rules_eval.json` and `rules_reach.json`. The engine parses no YAML: the server parses each rule set once (`POST /rules/parse`, and `rules` on `GET /artifacts/payloads`) and hands on the definition as a JSON document in TEXT, which `readRuleSet` (`document.ts`) reads with the exact parser — bare `NaN` / `Infinity` as floats, integers past 2^53 as `bigint`, every float a `PyFloat` — and then strictly, against the grammar pydantic enforces: an unknown key, a wrong type, zero or two property tests (chosen by the key being there, so `equals: null` is a test), a `null` on a test other than `equals` / `not_equals`, an empty `all` / `any`, `count` without a bound, a relationship atom without exactly one non-null `exists` / `count`, more than 200 rules, a duplicate name or nesting past eight levels (a `where` one) all throw `RulesUnreadable`, the one way out, never a guess; where pydantic reads an explicit `null` as absence (`to`, `where`, `when`, `message`, a relationship's `exists` / `count`, a count bound) so does the reader, and absent defaults are filled. Each `Rule` keeps its `identity`, its entry as the document wrote it (`pyDumps` with `allowNan`). `compileRuleSets(sources, mm)` (`compile.ts`) compiles `RuleSource`s in the order given — `ruleSources(set, layer)` (`sources.ts`) lists them by name then id, both by code point: the committed layer's rule sets with their committed parse, or the working layer's, a staged payload's parse laid over, `'pending'` standing on the set's last parse and a `'pending'` create with none left out. A failed parse is one skip for the whole set (`rule` empty, `reason` the parse error's message); a disabled rule is dropped before the drift check; the drift check walks `when` then `then` and reports the first mismatch — an unknown `applies_to`, a property the DECLARED type lacks (a subtype's does not count), an unknown relationship type, an unknown `to`, a `where` checked against `to`'s properties and not at all without one — with `repr` (`pyRepr`), skipping the rule whole. A document the reader refuses, or a rule set that arrived without its parse, marks the compile `unreadable`: its rules are missing and it must not be used. A `CompiledRule` carries its `appliesTypes` (`elementDescendants(applies_to)`), `check` `rule:<name>` and reach `paths`; `rulesByType` lists them per exact type in compile order, and `identities` the compiled rules' identities. `appliesPopulation(model, …compiled)` is every element a rule applies to: types sorted, each type's ids sorted. `evaluate.ts` is `validator.py`: `pyRuleEq` is Python `==` with a `bool` equal only to a `bool` (numbers compare exactly across `int`, `bigint` and `PyFloat`, `NaN` never; `None` equals `None`, which a list item can be); a value is missing when absent, `null` or `[]`, and missing fails every test but `exists`; a list holds when any item does, `contains` on a list being membership and on a string a substring test (`pyContains`) with a string operand; the bounds need a number that is not a `bool`; a relationship atom counts the element's own adjacency of the type's descendants, the far element filtered by `to`'s descendants and `where`. An issue is `conformance` with the rule's severity and check, its message the rule's own when not empty, else `Rule '<name>' violated` plus `: <description>`, quotes literal. `RulesValidator` counts a rule that throws under its check and merges the run's counts into the compile's `evalErrors` once, in its global hook; nothing it runs can throw (every comparison is total, nesting is capped and a record cannot hold a dangling end), so `eval_errors` never moves on either side. `reach.ts`: `derivePaths` gives a root-first path of steps per relationship atom, a `where` extending its atom's path; `expandScope(model, compiled, dirtyIds)` walks, from the dirty ids that are current elements, every suffix of every path backwards (an `outgoing` step through `el.in`, an `incoming` one through `el.out`), keeps each element reached whose type the rule applies to, frontier sorted by code point, first-seen order — never filtering on the far types, so a retype on the path cannot hide an owner. Its premise: a rule's verdict on an owner reads the owner and its paths, so if a transition moves the verdict, some path of the owner, on the state before or after, first meets an element the transition dirtied (the stage hooks and the neighbourhood rule add both ends of every relationship they touch and every element they change), and the prefix up to it is on the after state too; walking back from the dirty set on the AFTER state therefore reaches the owner.
- **`src/service/`** — `Scheduler` (`scheduler.ts`) runs engine work on the host's thread in slices. One pump, two lanes, each in arrival order: the _control_ lane (the replica's own transitions) runs in any state and first; the _model_ lane runs while the scheduler is open. A job is a `read` (one call), a `transition` (one call that changes the model, never interrupted — a transition may run up to 100 ms, AD-23) or a `scan` (a `Steps` generator that `run()` makes). A transition waits for every read that arrived before it and holds everything behind it; at each slice boundary of a running scan, the reads queued before the first transition are answered and other scans are skipped over, never started — so a scan never sees the model move under its iterators (probe: a `Map` iterator that crosses a `clear()` and refill reads everything again, and `Model.elements()` does exactly that on the first ordered read after a rewind). `cancel(id)` removes a queued job or drops a running scan at its next step, unanswered; closed (`setOpen(false)`), the model lane keeps its jobs and a scan that was mid-flight goes back to the head to start over, `run()` called again. The pump reads the injected clock after every unit — a read, a transition, one step — and at `SLICE_TARGET_MS` (8, half of CN-3's 16 ms chunk: at M a collector pause of 5–8 ms lands inside a step now and then) calls `onSliceEnd`, awaits `yieldToHost()` and starts a new slice — `onSliceEnd` also runs when the pump runs out of work, the end of that slice; messages are handled on those host turns only, never inside a unit. Idle and open, it gives its two background slots one step each in turn: the digest check (`setBackground`), whose `restartBackground()` drops its steps in flight (they published nothing) so a new run starts at its next idle step, and the sweep (`setSweep`), whose steps resume across any transition — `restartBackground` leaves it alone and closing only pauses it. A slot empties when its task ends. `pause()` lends the slice clock to work outside the pump (a snapshot open): `undefined` while the slice has room, else the host's turn. The pump starts on a microtask, so every job one message brings is queued before any runs.
  `createService(port, deps)` (`service.ts`) is the CT-4 dispatcher over one `Port` (`{post, onMessage}`: a `MessagePort` in a worker, `portPair()` in tests); `deps` is `HostDeps` plus `inflate`, since `src/` holds no timer, clock or gzip. A request `{id, method, params}` is answered `{id, ok, result | error: {status, detail}}` exactly once, or never once `{cancel: id}` came; a message without an id or a method is ignored. Errors: `OpError` / `ReadError` keep their status, a `ModelError` `key` is 404 with `errorDetail`'s quote-stripped text, `value` 422, a `SnapshotError` 422, an unknown method 404 `No method 'x'`, anything else 500 with its message. The replica is `opening`, `ready` or `diverged`. `open {project_id, metamodel}` discards any replica or open in flight (the heap never holds two) and starts `openSnapshot` over `deps.inflate` of a `ByteQueue` that `chunk {bytes}` feeds, with the scheduler's `pause` (which also stops a discarded open at its next batch); `end` answers the header once the replica is read and indexed — or the open's 422, which `chunk` and `end` then answer until the next `open`, a header of another project included — and the replica stays `opening`; `adoptStaged` (a control-lane transition) carries a re-bootstrap's staged batches over; `applyTail {text}` queues one transition per delta at once (control lane while opening, model lane after) and makes an opening replica `ready`, the scheduler open and the background digest check set; `applyDelta {text, own?}` is a model-lane transition, a 409 unless `ready`; `close` drops everything but the view placements, the artifacts and the queued model jobs. A delta or a tail crosses as the text the shell received and is read by `readDeltaText` / `readTailText` with the exact parser (AD-26: `JSON.parse` would lose `1.0` and integers past 2^53, which the digest cannot see); a commit response reads alike, `model_rev` standing for `rev`. Events: `replica {state, rev}`; `progress {task, done, total}` for `parse`, `index`, `tail`, `verify`, `sweep` — a task's first (`done` 0, which is how a restarted digest check or sweep shows) and last reports at once, the rest at most once a slice, from `onSliceEnd`; `changed {rev, staged_version, issues_version, artifacts_version, …ids, structural}` after every transition of a `ready` replica that changed something, which also restarts the digest check when an entity or the staged list moved. A delta whose digest disagrees, or a digest check that ends false, makes the replica `diverged`: the scheduler closes, so reads and edits posted meanwhile wait, and are answered from the replica the shell opens next (`close`, `open` … `end`, `adoptStaged` with what `staged` returned, `applyTail`). The method table (`METHODS`) is built from a few kinds, so the message handler has no per-method branch: `now` (answered at once, in any state — `open`, `chunk`, `close`, `staged`, `conflicts`, `setViewPlacement`, `dropViewPlacement`, and the artifact context: `setArtifacts {artifacts}`, `putArtifacts {changed, deleted_ids, staged?}` — the committed layer moves, then `staged`, when given, replaces the overlay — and `setStagedArtifacts {entries}`, each answering `null` and reading the whole call before the set moves), `later` (`end`), `read` (every `READS` name, a `scan` job when `readScans` says so; `getModelSummary` is handed the committed `rev` as `model_rev`), `evaluate` (every `EVALUATIONS` name, always a `scan` job over the ready model, the placements and the service's `ArtifactSet`; each `run()` reads the working copy's `rev` and `stagedVersion` into the context with the service's `TableOrderCache`, which no model-lane transition can move while the scan runs, and which `close`, a new `open` and a divergence clear), `inspect` (`stagedDiff`) and `transition` (`stage`, `unstage`: their params are read at arrival, so a malformed request is refused before it queues), plus the three replica methods above and the three that answer from the issue store, below. Reads, `stagedDiff`, `stage` and `unstage` wait in the model lane for `ready`, so an edit made during a re-bootstrap lands after the adopted batches. `stage` reads its ops through `readOps` and always asks the working copy to coalesce; it answers `{batch, coalesced, changes, elements, relationships}`, the last two the post-state of what `changes` names as changed, both `null` past 500 entities. Every result and event is a copy built by the `wire*` functions — over a direct port pair nothing is cloned, and an uncopied result would hand out the replica's own property bags.
  The issue store: when the tail makes the replica `ready`, the service compiles the rule sets of its `ArtifactSet` against the replica's metamodel — W from `ruleSources(set, 'working')`, C from `ruleSources(set, 'committed')` — builds a `LiveIssues` over its working copy holding them, and puts its sweep in the sweep slot, reporting `progress sweep` from `done` 0 to `done === total` for every run, a re-sweep's included, and nothing for a rescan's steps (their `SweepStep` says `rescan`; the scheduler's `BackgroundTask` hands `progress` what the steps yield); `close`, a new `open` and a divergence drop it with the replica. From then on `stage`, `unstage`, `applyDelta` and a ready replica's tail go through it, so each revalidates what it may have moved before it answers; while opening, `adoptStaged` and the tail go to the working copy alone, and the first sweep covers them. Rules follow the artifact methods, which stay `now` (a `now` method never interleaves with a transition, and every sweep or rescan step reads the rule sets as they are then): after `setArtifacts`, `putArtifacts` or `setStagedArtifacts` has moved the set, W and C are compiled again — each only when its sources changed, compared as the ordered `(id, name, parse)` of its rule sets, a parse by its document text or its first error — and handed to the store (`setRules`); a rescan it queued puts the store's steps back in the sweep slot. An artifact method that moved the set's `version` (`artifacts_version`, which the shell follows to re-page its tables), or the store's, posts one bare `changed` at once, both versions as they stand — a ready replica only: the first `changed` after `ready` carries the moves made before it. The compiles are kept with the store, so a replica opened again — after a rebind, under another metamodel whose drift differs — compiles afresh, though the artifacts outlive `close` and `open`. `issues_version` is a per-service counter that never goes back: it moves by what the store's `version` moved (a splice that changed the store's content, an applied delta, a rule-set change, the store become unusable). A transition's `changed` carries it; at a slice's end, if it moved since the last `changed` posted — sweep or rescan steps, or a probe that met an unusable pattern — the service posts a bare `changed` (the current `rev` and `staged_version`, no ids, `structural: false`), which neither restarts the digest check nor counts as a transition. Three methods answer from the store, in the routes' bodies (`bodies.ts`): `getModelIssues {}` (`issueListBody`) and `previewCommit {base_rev, batch_ids, strict}` (`previewBody`, the model half, with C's rules alone, as the server's preview) are model-lane transitions that post no `changed` — they may probe, a rewind and replay, so they wait for a running scan and are never answered at its slice boundary, as a read would be; `validateModel {batch_ids}` is a transition that restarts the sweep, answered by a second one, queued once that sweep and any rescan have ended (`whenSwept`), that builds `validateBody` — refused 409 `replica is not ready` if the replica was closed, replaced or diverged meanwhile, or if a sweep or rescan step threw. None is answered while a rescan is due: a call that finds the store not `settled` waits for it (`whenSettled`) and then queues its answering transition, which checks `settled` again and waits again if an artifact method started another rescan in between; `close`, a new `open`, a divergence and a sweep or rescan step that threw refuse a waiting call as they refuse a waiting `validateModel`, 409 `replica is not ready`, which the shell answers from the server, and a cancelled one is never answered. Steps that threw leave the sweep slot with their ids still due; the next `getModelIssues` or `previewCommit` puts them back in it before it waits or answers from the store as it stands (as `validateModel` and a rule-set change always do), so no call waits on steps nothing drives and a stalled sweep does not leave the store short of `seeded` for good, while a step that throws again only leaves the slot until the next such read, moving no `issues_version`. Each refuses first what the engine must not answer, with 501 for the client to take to the server: `reaches an unsupported pattern` (the store is `unusable`) and `reaches unreadable rules` (W or C is `unreadable`: a document the reader refuses, or a rule set that arrived without its parse, which only an older shell or a skewed bundle sends); then, with 409, what the shell retries at the server: `stale base_rev` (`previewCommit`'s `base_rev` is not the replica's `rev`) and `stale staged batches` (`batch_ids` are not `staged()`'s ids, in order) — both checked in the transition that answers. An answer whose body probed anew (`live.probes` moved, with batches staged) restarts the digest check, since a probe rebuilds the committed images it walks; `getModelIssues` over a kept tag scope probes nothing. A probe whose replay cannot even put the staged batches back diverges the replica, and the call is refused 409 `replica is not ready`. A direct call reads the store as it stands, partial until the first sweep has ended.
