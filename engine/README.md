# Engine (`engine/`)

Commands: `pixi run engine-install | engine-test | engine-check | engine-bench-data | engine-bench | engine-bench-browser | engine-xlsx-sample` (tasks set cwd = `engine`).

The TypeScript engine of the target architecture (`architecture/`), built bottom-up. It holds the **value layer, the metamodel, the record-graph store, the op applier, the working copy, the snapshot reader and the state digest** — all of sub-project A — and, from sub-project B, the **steps layer, the read surfaces and the service** (the CT-4 dispatcher and its scheduler), and, from sub-project C, the **artifact set and the first evaluations** (criteria search and navigation, which the app's `criteria` and `navigation` surfaces take from the engine by default) and the **built-in validators** with the **custom rules** (`src/rules/`); the server never imports it, and the frontend imports its TYPES only — the sandbox's worker (`sandbox/README.md`) is its one host, and the frontend's shell (`frontend/src/lib/engine/README.md`) talks to it over a `MessagePort`.

- **`src/` has no DOM and no Node dependency** (`lib: ["ES2023"]`, `types: []`), is erasable-syntax-only, and imports with `.ts` specifiers, so a worker, Node and vitest all run the sources unbuilt. Node-only code lives in `node/`.
- **`src/value/`** reproduces the Python core's view of JSON values. A `number` is always a Python `int`; every `float` is a `PyFloat`; integers past 2^53 are `bigint`. `parseJson`/`parseLines` route each line: a regex pre-scan sends lines holding a float, a 16-digit integer, a bare `Infinity`/`NaN` or `-0` to the exact parser and everything else to native `JSON.parse`, many lines to a call — which is why `parseLines` refuses a line holding more than one document instead of shifting every document after it. `parseExact(text, {floatConstants: true})` reads a bare `NaN` / `Infinity` / `-Infinity` as the `PyFloat` it stands for (as `json.loads` does) instead of keeping its text, which a rule-set document needs to tell `Infinity` from `"Infinity"`; `{controlCharacters: false}` refuses a raw U+0000–U+001F inside a string with a `SyntaxError`, as `json.loads` does (by default one is taken as it stands). `pyDumps` is `json.dumps(ensure_ascii=False, allow_nan=False)` byte for byte (`{allowNan: true}`: `allow_nan=True`, the non-finite floats written bare; `{ascii: true}`: `ensure_ascii=True`, every code unit above U+007E written `\uXXXX`; `{spaced: true}`: the `", "` and `": "` separators when `indent` is omitted; all three together are bare `json.dumps(value)`); `pyContains` is `needle in haystack` over code points; `pyFloatRepr`, `pyRepr`, `cmpCodePoint` and `pyKey` mirror `repr(float)`, `repr(str)`, `str` ordering and the uniqueness signature (`_frozen`). `pyEq(a, b)` is Python `==`: bool, int, `bigint` and `PyFloat` are one number line (`true == 1 == 1.0`, an int against a float exact, NaN equal to nothing), a list equals a list element-wise, a dict a dict with the same keys in any order, other kinds are unequal; it runs on an explicit stack, since a plain recursion overflows at 10,000 nested lists, and is held to `py_eq.json` in both orders. `pyLower` / `pyStrip` are `str.lower()` / `str.strip()` of Python 3.14 whatever Unicode version the host carries (Node's `toLowerCase()` differs at 28 code points, `trim()` from `strip()` at 6): generated tables — `lower-tables.ts`, written by `scripts/engine_tables.py`, never by hand — plus Python's final-sigma rule, held to `py_lower.json` over every code point. `pyCasefold` is `str.casefold()`: the same per-code-point lowercase with no final-sigma context, except at the code points whose casefold differs (ß → ss, ligatures, iota-subscript forms, Cherokee to upper case, ς → σ, µ → μ), listed by the generated `casefold-tables.ts` (`scripts/engine_tables.py`). The search criteria's "JavaScript" coercion is Python's `str()` and `float()` in fact (`core/search/criteria.py`'s `_js_str` / `_to_number`): `jsStr` mirrors `_js_str`, `pyReprValue` the `repr` it and `_to_number` fall back to for a container (and `pyStr` Python's `str()` of any value: a string itself, else its `repr`), and `toNumber` `_to_number` itself, throwing `PyOverflowError` where `float(int)` raises `OverflowError`. `pyFloatOf` is `float(str)`: every Unicode decimal digit and `str.isspace()` code point past ASCII becomes its ASCII digit or a space — an ASCII code point, control characters included, is untouched, so `float()`'s own leading/trailing strip (the six classic whitespace characters, narrower than `str.isspace()`) still governs what parses — before the grammar runs and underscores are dropped for `Number()`. Its digits and whitespace come from `digit-tables.ts` (generated, `scripts/engine_tables.py`), held to `py_coerce.json`. `translatePyRegex(pattern, mode)` is `re.search` / `re.fullmatch` (a criterion's `matches`, a pattern facet) in JavaScript. It answers `ok` with a `test(subject)`, `invalid` where `re.compile` certainly refuses the pattern (which then never matches), or `unsupported` with a one-line reason: anything outside its subset is `unsupported`, never guessed, and its caller sends the call to the server. A recursive-descent parser that follows `re`'s own over code points emits a `u`-flag `RegExp` source (never a string replacement over the pattern) and leaves nothing to JavaScript's semantics: the dot is `[^\n]`, `^` / `$` / `\A` / `\Z` / `\z` are look-arounds (`$` also before a final newline), `\w \d \s` and their negations are explicit classes, `\b` / `\B` look-arounds over the `\w` class, named groups become numbered ones, the whole is anchored natively (`^[\s\S]*?(?:…)` for a search, `^(?:…)$` for a full match) because V8 also tries a `u` search between the halves of a surrogate pair, where every look-around sees no neighbour, and IGNORECASE is not JavaScript's `i` (its folding differs at `İ` and `ı`, and with the host's Unicode) but `re`'s: a cased literal, or a class holding a cased member, becomes the class of every code point whose `re` lowercase is a member's lowercase or one of `re`'s extra equivalents. Outside the subset: flags other than leading `(?i)` / `(?m)` / `(?s)`, possessive quantifiers, atomic, conditional and comment groups, `\N{…}`, a class Python reads as a future set operation or a nested set, a look-behind of varying width, a repeated look-around, a back-reference under `(?i)`, in a look-behind or to a group that may not have matched (JavaScript matches an unset group as empty, `re` fails it), a class past U+FFFF under `(?i)`, a count past 65535 and a translation past 4 MiB. The classes and the case data come from `regex-tables.ts` (generated, `scripts/engine_tables.py`, which also asserts the two properties of `re`'s case data the translation leans on); the answers are held to `py_regex.json`, patterns × subjects in both modes plus a few patterns against every code point. Translations are memoized per pattern and mode, the 256 used last.
- **`src/metamodel/`** — `Metamodel.fromJSON(doc)` takes the `GET /metamodel` document (validated by the server; the engine parses no YAML and runs no `check_metamodel`) and builds every lookup of the Python `Metamodel` up front, under the same names in camelCase. `Multiplicity.parse` mirrors the Python parser, error text included.
- **`src/model/`** is the store: one fixed-shape record per entity (`ElementRec`, `RelRec`), adjacency and containment parents as arrays of record references ON the records, and `Model` as the single mutation boundary, with the Python method set and error texts (`ModelError.kind` is `key` / `value` for `KeyError` / `ValueError`). The engine never mints ids: `createElement(typeName, id)` and `connect(…, id)` take them. Entity order is state: each record has an `ord`, `elements()` / `relationships()` iterate in it, and a record restored WITH its old `ord` goes back to its old place (the Python core always appends). `IndexSet` keeps by-type, uniqueness, references and root order; adjacency order is unspecified, so anything observable sorts by code point. Uniqueness buckets are keyed by a 53-bit hash of the `pyKey` text and confirmed by the exact text at query time; that text is kept (`keyText`) for every member of a bucket of two or more, written as the element is filed and refreshed by every rekey — even one that keeps its hash, as a property edit, a re-parenting or a key relationship can move the text without moving the hash — so `uniqKey`, `uniqGroupOf` and the uniqueness validator read a group without serializing its members again, and `verifyConsistent` holds the texts to a rebuild's. The text itself is `uniqKeyText(mm, parentsOf, el, specs)` (`uniq-key.ts`: the type, the first parent's source id, then the key's property values and, per key relationship, `keyEndpoints` — the sorted endpoint ids of exact-type edges — or every property without a key), which `IndexSet` calls with the model's metamodel, the records' own parents and its memo of key specs; `specs` is one map per metamodel. `Structure` (`structure.ts`) is what validation reads of containment parents and uniqueness groups under one metamodel — `parentsOf`, `groupOf` (the group, itself included, or `null` when the element is alone) and `keyOf` — and `liveStructure(model)`, memoized per model, answers it from the records and the indexes: `null` for an element alone in its bucket, `[el]` when its bucket is shared by different keys. `candidateStructureSteps(model, mm)` answers it under another metamodel, in steps of 2,048 entity visits and a last step at its total, into side maps: the relationships in state order give each target the ones `mm` makes containment (so parents are in `ord` order, as a rebuild would push them), then the elements in state order are grouped on their exact `uniqKeyText` under `mm` and those parents, so a group never mixes keys and an element alone has `null`. It writes no record field, and nothing may write the model between two steps. Entity order has an epoch, `orderEpoch`, moved by every re-sort of either map: a `Map` iterator that crosses a re-sort reads the whole map again, so whatever holds one across a write must take a fresh one when the epoch moves. `loadElement` / `loadRelationship` + `rebuildIndexes()` are the bulk path — non-strict like `build_model_from_dicts(strict=False)`, the same refusal texts as `SnapshotError` — and stricter than Python in two places: an id shared by an element and a relationship, and an array-index property key (`"0"`) at any depth, which a JavaScript object cannot keep in insertion order. Committed state enters through `insertElement` / `insertRelationship` / `overwrite`, which check no type (a model may hold one its metamodel no longer has) and take `rev` as given instead of counting it.
- **`src/ops/`** — `applyBatch(model, ops, {restore, idFor, dirty})` is the port of `routes/ops.py::_apply_batch` for the six model ops, in the wire's shapes: temp ids resolved through `idMap` in ids, ends and property values (strings and lists, never inside a dict), `id` hints, restore mode, merge patches, the cascade read before it happens, first-touch changed/deleted sets kept disjoint, the `recreated` sets (the changed ids the batch deleted and created again), inverse units and `inverseOps()`. `idFor` decides a created entity's id and is the identity by default — a staged entity lives under its temp id. `dirty`, a `DirtyCollector`, receives the dirty-set hooks exactly where `_apply_one` fires them (see `src/validation/`); without one the applier fires nothing. A refusal is an `OpError {status: 422, detail}` with the server's text, the quote-stripping of `_error_detail` included (`No element with id 'ghost`). One deliberate difference from the server: an op carrying an array-index property key at any depth is refused. A refused batch leaves NO trace on either side — `rewind(model, result)` puts every touched entity back from its first-touch before-image (properties, `rev`, `ord`), and the server's `_rollback` is its port. A record that outlived the batch still has the `ord` of its image and is rewritten in place; anything else under a touched id is removed and the image inserted at its old `ord`.
- **`src/working/`** — `WorkingCopy` owns a `Model`, the committed `rev` and state digest, the staged batches and the committed image of every entity they touched (`committedElement` / `committedRelationship`, `isStaged`). `stage(ops)` applies a batch in place; `unstage('all' | {batch} | {entity, incident?})` and `applyDelta(delta, own?)` are both a rebase — rewind every staged batch newest first, change committed state, replay in order — and a batch that no longer applies is parked in `conflicts()`, never dropped. `applyDelta` follows CT-2 (`applied` / `duplicate` / `gap`), reads the delta's entities with the bulk loader's checks before anything moves, writes them through the committed-state methods (the ids the delta names in `recreated_*` go out first and are appended, as the server's dict did; a record that would change its type or its ends WITHOUT being named does not fit), folds the digest per entity and sets `diverged` on a mismatch or on a delta that does not fit; for the user's own commit it drops the committed batches and rewrites their temp ids in the rest (`remapOp`). The `(id, rev)` hash is the engine's own (`src/snapshot/`); the `entityHash` option replaces it, which is how tests hold it to another implementation. `verifyDigest()` recomputes the digest from every COMMITTED entity — the model's, with the committed image standing in wherever a staged batch has been — and sets `diverged` on a mismatch. Every operation returns a change set, whose `structural` says it may have moved more than properties: it names a relationship, a deleted element or an element absent when it began (presence is asked BEFORE a rebase rewinds, of the ids the staged batches and the change name), or it is an own commit with minted ids — a rebase over-reports what it touched, so a staged relationship makes any peer delta structural, which costs a refresh, never a stale tree. `stage(ops, {coalesce: true})` with ONE property update merges it into the first staged (never parked) op of the same kind and id — `{...old, ...new}`, later keys win, a `null` stays — as a new batch object under the old batch id: the op is first tried alone on top (a bad patch throws and cannot park the batch holding the earlier edits) and rewound, then the working copy rebases FROM that batch (the private `rebase` takes the index to start at; the batches below it stand). Never in place: an update bumps `rev` once per key and re-places a deleted key, so an in-place merge would leave a state no replay of `staged()` gives (key order and `rev`s included), which the seeded invariants hold. `adoptStaged(batches)` replays batches under their ids on a working copy with nothing staged or parked (a re-bootstrap carrying the user's edits), parks the refused ones and numbers the next batch past the highest id. A `duplicate` delta that comes with `own` naming a batch still staged or parked drops them all the same — the echo of a commit can arrive before its answer. `stagedVersion` moves whenever `staged()` or `conflicts()` come to hold other batch objects (a stage, a merge, a remap, a drop, a park; a plain rebase keeps them). `stagedDiff()` pairs each committed image with the record now, in first-touch order; `committedElementsInOrder()` / `committedRelationshipsInOrder()` walk committed state in state order whatever is staged, without a rewind: the model's records under no touched id, each as a view sharing its property bag, merged by `ord` with the non-null committed images (sorted once when the walk begins), so an entity a staged batch deleted and created again under its id comes at its committed place with its committed properties, and a rewired relationship on its committed ends; they read the model live, so a caller keeps it still while it walks (a scan does). `touchedIds(from?)` lists the ids those images hold, elements then relationships, or the ids the batches from `from` on touched; `mergePoint(op)` is the index of the batch a coalesced `op` would merge into (the batches from there on are the ones it replays), -1 when it would stage alone. `stage(ops, {dirty})` hands a `DirtyCollector` the hooks of the batch applied, or of a merge's trial run on top. `probeStaged(onWorking, onCommitted)` looks at the staged batches as the server's preview takes them and leaves no trace: it rewinds them, replays them in order into one collector — the dirty set `S` of the staged ops applied as ONE batch to committed state — and runs `onWorking(S)`; rewinds again and runs `onCommitted()` on committed state; replays once more. The entries and committed images are rebuilt from the replays, never through the staged-version tracking, so `staged()`, `conflicts()`, `stagedVersion`, the entity lines, the index dump and the digest are all as they were; parked batches are not touched. A replay cannot be refused (the same batches on the same states); if one ever is, it throws a plain `Error` with the staged batches put back, or, when even that fails, still listed and the replica diverged, for the next replica to adopt them.
- **`src/snapshot/`** — `sha256` is FIPS 180-4 in plain TypeScript, synchronous because the digest fold cannot wait for WebCrypto; `entityHash(id, rev)` is CT-3's hash (the first 8 bytes over `utf8(id) ‖ 0x00 ‖ ascii(rev)`, the UTF-8 written by hand, a lone surrogate as U+FFFD), `modelDigest(model)` the port of `state_digest.model_digest`, and both are `WorkingCopy`'s default. `openSnapshot(chunks, metamodel, onProgress?, options?)` reads a `datarover.snapshot/v2` text from inflated bytes cut anywhere and returns `{header, workingCopy}` at the header's `rev` and `state_digest` — adopted, not checked: `verifyDigest()` is the check, whenever the caller chooses. Bytes are decoded by the host's `TextDecoder` (`fatal`, the byte order mark kept so that it fails the format check), reached through a typed `globalThis` lookup in `utf8.ts` because a declared global would collide with the host typings of any project that compiles these sources; `LineSplitter` cuts on LF alone; lines are parsed and loaded 500 at a time through `parseLines`, the first `elements` of them as elements, so the text is never held whole — 500 being the largest batch that stays a short step (at 2,000 the worst batch took 36 ms at M, _measured_). `options.pause` is asked after every loaded batch and every step of the index build (`rebuildIndexSteps`, reported through `options.onIndex`); only a returned promise is awaited, so an open with room left in its slice pays no microtask, and a throw ends the open. The pause sits in the batch loop, not the chunk loop, and a chunk is decoded in pieces of 64 KiB: a snapshot served from a cache arrives as a few large chunks, and awaiting a chunk that is already there resolves in microtasks, which is no yield to the host. Anything that does not start with `{"format":"datarover.snapshot/v2"` is refused at its first bytes. A refusal is a `SnapshotError`: the server's two texts (`snapshot v2 header carries no valid entity counts`, `snapshot v2 holds N entity lines, its header promises E + R` — the count is checked BEFORE the last lines are parsed, which is what gives a cut text the server's answer), the bulk loader's own, or the engine's for what the server's decoder never looks at (`rev`, `state_digest`, the ids, invalid UTF-8, a line that is not one JSON document, named by its number). Like the server's reader it takes a last line without its LF and CRLF line ends.
- **`src/steps/`** — a `Steps<T>` is a generator that cuts a long operation into steps of about a millisecond at M, each `yield` saying where it stands (`{done, total}`). Every long operation exists once, in that form, and its synchronous name drains it (`drain`): `IndexSet.rebuild` / `Model.rebuildIndexes` (`rebuildIndexSteps`, 1,024 entity visits a step), `WorkingCopy.verifyDigest` (`verifyDigestSteps`, 2,048 entities a step), `RootOrder.reset` — so no caller of the one-shot forms changed. A steps generator publishes nothing before its last step (`diverged`, the root order), so abandoning one leaves no trace; it holds iterators over the model across its yields, so the model must stay still between two of them, and each user says who keeps it still: the index build runs only while a replica is opening, a scan is protected by the service's queue, and the digest check is dropped and restarted after any transition. `sortedInSlices(items, compare, run = 2048)` is a stable bottom-up merge sort in steps (runs sorted natively, then merge passes into a second buffer, a step every `run` items written; the order `Array.prototype.sort` gives); it costs about twice the native sort and no step over 2 ms at M (_measured_), and serves the root sort of the index build and the hit sort of a search.
- **`src/read/`** — the read surfaces, a port of `routes/read.py` (and `routes/elements.py::get_element`) rule for rule. A read is `(model, placements, params)` → the route's HTTP response BODY, in pydantic's field order (`{id, type_name, properties, rev}`, `{items, total}`, …), as a plain call or a `Steps` generator; it reads the model and nothing else. `READS` maps the `lib/api` names (`getElement`, `getElementsBatch`, `listElementsPage`, `listElementRelationships`, `getModelSummary`) to them, and `readScans(method, params)` says which calls run in steps. `toWire` deep-copies a value into plain JSON-able data — a `PyFloat` as its number, a `bigint` as the nearest double, which is what a client's `JSON.parse` of the server's body gives — so nothing of the replica leaves; `readOps` reads ops as the server reads what a client sends: through `JSON.stringify` (an integral double is an `int`, `NaN` `null`, `-0` `0`) and the exact parser, then a shape check whose refusal is a 422 `ops[i]…` in the engine's words. `ViewPlacements` holds the element ids each loaded view places (an unknown, empty or absent view places nothing). An unknown element is the model's `ModelError` (`key`); page bounds (`limit` 1–500, `offset` ≥ 0) and parameter types refuse with `ReadError(422)` in the engine's own texts, because FastAPI, not the route, enforces them and no fixture can hold them — `too many ids: N (max 500)` is the route's own. `getModelSummary` answers `issue_counts: null` and `undo_depth: 0`, `model_rev` being the caller's. The tree (`tree.ts`: `getTreeItemsBatch`, `listContainmentRoots`, `listExcludedRoots`, `listContainmentChildren`): a child belongs to its FIRST containment parent (`parents[0]`, relationship order — a relationship restored under its old id goes last, so it does not win its child back), counts once however many parallel edges hold it, and levels sort by `(displayName, id)`, both by code point; roots come off the maintained root order, the excluded pool is that order minus the ids `ViewPlacements` holds for `view_id` (whatever a view places that is not a root changes nothing) with `total` counted over the whole walk. Search (`search.ts`, `listElementsPage` with a `q` that is not blank) is a full scan in steps — no trigram index (AD-13) — of `searchScore` over every element in state order, 512 a step: the query is `pyLower(pyStrip(q))`; a name (`nameOf`) is lowered with `pyLower` and scored by `nameScore` — exact 1000, prefix 100, word boundary 30, substring 10 — plus `len(query) / len(lowered name)` counted in code points of the LOWERED name (U+0130 lowers to two); the boundary test runs on the lowered name (U+212A lowers to `k`) as an occurrence walk that tries every start, overlapping ones included, which is what the route's regular expression does; then +5 / +2 for the id, +1 for the type (memoized per type), +0.5 per other string property (every `name`-cased key skipped). The additions happen in the route's order, in doubles, so equal scores are equal doubles and nothing is rounded. Hits sort by `(-score, id)`, ids by code point, through `sortedInSlices`; `total` is every hit; nothing is kept between pages (the server keeps nothing either).
- **`src/search/`** — a port of `core/search/criteria.py` and of `POST /model/search`. `readCriteria(raw, path)` reads the eight criterion shapes as pydantic reads canonical JSON: `type` required (a group holds leaves only), the defaults filled (`names`, `criteria`, `rel_types` to `[]`, a property's `value` to `""`, `datatype` to `null`), `relTypes` and `rel_types` both taken — the alias winning when both are given — unknown keys ignored, an absent key defaulted but a `null` taken only where the field allows one (`datatype`); what pydantic would coerce (`"3"` or `true` for a count) is a 422 `<path>[i].<key>: …` in the engine's words. `compileCriteria` translates every `matches` pattern, group members included, BEFORE any entity is matched: a pattern `translatePyRegex` answers `unsupported` refuses the whole call with 422 `pattern <repr> uses <reason>, which is not supported`, one it answers `invalid` never matches, as `_safe_regex` has it. What the host cannot run although Python can is that same 422 with the fixed reason `a construct this browser cannot compile`, mid-scan too: a `RangeError` — a pattern nested past the translator's stack, or a subject past the backtracking stack of the translated `RegExp` (about 8M code units of `(a)*$`, fewer the more groups it holds) — and V8's `SyntaxError` `Regular expression too large` (a literal of 50,000 `k`, or 40,000 under `(?i)`), which V8 throws on a pattern's first run because it compiles lazily, apart for one-byte and two-byte subjects; `compileCriteria` therefore runs each translation once on `''` and on `'Ā'`, so that it refuses before the first step whatever the model holds. Nothing else is caught. `matchElement` / `matchRelationship` are the matchers line for line: text ops over `jsStr` of the value (missing and `null` are `""`), `contains` over `pyLower` of both and never splitting a surrogate pair (Python's `in` counts code points), numeric ops over `toNumber` — whose `PyOverflowError` for an int past the double range reaches the service as the route's 500 `int too large to convert to float` — with NaN on either side never matching; type names compare exactly (a subtype is not its parent) in `entity_type`, `rel_types`, `connected_to_type` and `endpoint_type`; a relationship count counts a self-loop once; an empty group matches; an element-only criterion on a relationship query, and the reverse, matches. `nameProp` is `name_prop`: a non-empty STRING only (never a list's first entry, unlike `nameOf`), `name` first, then every other `name`-cased key in property order. `searchModel` is the route body: `target` required, `criteria` default `[]`, `limit` 1–500 default 500, `offset` ≥ 0; every entity of the target in state order, criteria ANDed in order (an earlier one that fails keeps a later one from running, as `all()` does), 512 a step; the page is cut after matching and `total` counts every match; the body is `{target, elements, relationships, total}`, the other list empty.
- **`src/artifacts/`** — `ArtifactSet`, the project's artifacts in two layers: the committed ones the shell hands in (`setCommitted` replaces the layer, `put(changed, deletedIds)` upserts then removes) and over them the staged overlay mirrored from the frontend's buffer, one entry per id (`setStaged` replaces it). `resolve(id)` answers `{id, kind, name, payload}` or `null`: a staged `delete` hides the id, a staged `create` (under its temp id) is itself, a staged `update` lays its `name` / `payload` — whichever it carries — over the committed artifact and names nothing when none is under it, and otherwise the committed artifact answers; `size` counts the ids that resolve. `readArtifacts` (`WireArtifact`: `{id, kind, name, artifact_rev, payload, rules?}`, unknown keys ignored) and `readStagedArtifacts` (`WireStagedArtifact`: `{op: 'create', id, kind, name, payload, rules?}`, `{op: 'update', id, name?, payload?, rules?}`, `{op: 'delete', id}`) read a list as `readOps` does — `JSON.stringify`, then the exact parser, so a payload's `1` is an `int` and `1.5` a `PyFloat` — and refuse a malformed entry with a 422 `<where>[i].<key>: …` in the engine's words before anything moves. `rules` is a rule set's parse, `POST /rules/parse`'s body read strictly as a `RulesParse` (`{ok: true, document}` or `{ok: false, errors}` with at least one `{message}`; other keys ignored): committed, absent or `null` carries none; staged, it may be `'pending'` while the shell's parse is out. The document text is not parsed here. The set keeps, per rule set, the parse a `'pending'` entry stands on (`lastWorkingParse`): the last one a staged payload brought — an update with no payload records none — or else the committed one, which a committed artifact arriving does not overwrite while a staged payload stands over its id; an entry that stops carrying a payload (a discard) resets it to the committed parse, and an id gone from both layers is forgotten. The set holds what the readers made, never what was handed in, and replaces entries rather than changing them, so a resolved payload stays as it was however the set moves after; it is read, never mutated. `version` moves whenever a layer comes to hold other entries — one added, removed, or replaced by one not alike (the same fields in the same order, values exact: `2` and `2.0`, `0.0` and `-0.0` differ; a committed layer's order counts) — and stays when a call hands it the same entries again (a push of what it holds, an identical staged buffer). The service's set is not tied to a replica: it survives `close` and `open`, as the view placements do.
- **`src/navigation/`** — a port of `core/navigation` and of `POST .../artifacts/navigation/evaluate`. `readNavigation(raw, path)` reads a definition as pydantic reads canonical JSON: `kind` required on every definition, start and step, `op` on a set, the defaults filled (`direction` `out`, `types` / `target_types` / `criteria` / `steps` `[]`, `exclude_visited` `true`, a snippet `{}`), unknown keys ignored, criteria through `readCriteria`, and what pydantic checks but nothing uses checked all the same — `schema_version` an int on a path and a set, a path's `name` and every step's `comment` a string or `null` (a set has no `name`: pydantic ignores one), a `true`, `1.0` or `"3"` version refused where pydantic coerces it; the core's own texts where it has them (non-empty `children`, more than 10 steps, an operand without exactly one of `ref` / `definition`, a snippet with both), a 422 `<path>…: …` in the engine's words otherwise. - **`src/script/`** — `parseScriptResult(text, entry)` (`result.ts`) parses one embedded call's harness answer exactly (`parseExact` with `floatConstants`; a transform's by `parseOrdered`, which reads an object that holds an array-index key as a `Map` so that its keys keep their order, the document's `OrderedValue`) into a `ScriptResult` `{payload, error, reads, stdout}`: `decode_call_payload` and `decode_reads` of `core/script/runner.py` for the entry (`value`, `step` or `transform`), a malformed payload a `runtime` error `malformed … result payload` that keeps the call's `stdout`, a malformed read-set `null` ("depends on everything"), read keys distinct, a tag the guest invented kept, lengths counted in code points; an answer that is not the harness's envelope throws. `PENDING` is the result of a call no fill has answered. A transition's keys are the union over the state before it and the state after, for the ids it touched, a superset of the oracle's and equal to them where no containment moves. Held to `script_touched.json`. `deletedKeys(metamodel, ids, images, into?)` gives the keys of an entity a transition removed from its image instead (an element touches `el` and its type's `scan`s, a relationship its ends' `out` and `in`, and for containment `children` and `parent`), which with `touchedKeys` over the state after gives the same keys the two states give, for every `script_touched.json` case. `snippetFetch(artifacts)` and `resolveTransformSource(artifacts, transform, label)` (`snippets.ts`) read `code_snippet` artifacts, staged first; the transform's source resolves strictly, every failure a 422: `<label>: unknown transform snippet <ref>` for a ref that names no snippet, `<label>: transform code does not parse` for inline code the scan can see does not parse, and `<label>: transform code does not define a one-argument top-level transform(doc)` (`<label>: snippet <ref> does not define …` for a saved one, which is not parsed first) when no top-level `def transform` takes one argument — any of several, as `derive_entry_points` accepts it (`entryArities` of `arity.ts`, every top-level `def` of the name, `null` for what the scan can read as a syntax error; a file that fails to parse for a reason the scan cannot see is refused as above when the guest reports it, as the call runs). `BridgeDispatcher(model, recordOps, limits?)` (`bridge.ts`) is `core/script/bridge.py` op for op: `dispatch(requestText)` parses the request with `parseExact` and answers text written with `dumpDefault` (`json.dumps` in Python's default style), so a reply is byte-identical to the server's, errors included (`KeyError: `, `ReadOnlyError: ` and the rest of the oracle's texts, `RuntimeError: ` for anything else; a request that is not a JSON object answers `{"id": null, "error": "ValueError: …"}`). It only reads the model; a write dict is recorded verbatim in `ops`, under the op and byte caps. `projectRoots(model, ids)` projects the elements of a call's roots, an absent id left out. Held to `script_bridge.json`, whose replies are compared as text. Scripts run the core's facade in Pyodide, pinned `314.0.7` (a dev dependency). `host.ts` holds the types a host and its callers share (`ScriptBatch`, `RawScriptResult`, `ScriptRun`, `Bridge`, `ScriptHost`, `ScriptHostFactory`, `AbortSignalLike`); `RawScriptResult` is `{text}`, the harness's own answer for one call as the JSON text Python's `json.dumps` wrote, so a host that fails a call writes the same shape. `guest.ts` is everything that talks to the interpreter, against the structural `Interpreter` type (it names no Pyodide type): `createGuest(py, transport, limits = DEFAULT_HARNESS_LIMITS, restored = false)` is `prepareGuest(py)` (sets `_dr_facade` and `_dr_harness` (`HARNESS_SOURCE`), both text, and runs `GUEST_BOOTSTRAP`, which execs `HARNESS_SOURCE` into the interpreter's `__main__` and defines `_dr_batch(code, entry, calls_text, roots_texts, console)`; nothing in it names a JS value, so an image of the interpreter can be taken after it) and then the binding: `_dr_transport_text`, the harness's caps (`HarnessLimits`: `stdoutChars` 262144, `reprChars` 65536, `readMemoMax` 4096), `_dr_limits` and two JS hooks; `restored: true` skips `prepareGuest` (the image holds it) and reseeds `random`. `run(batch, roots, hooks?)` calls `_dr_batch` once. An embedded batch (`value`, `step`, `transform`) is `_dr_open` once (the facade, then the module, in a fresh namespace; interpreter state — `sys.modules`, `builtins`, `__main__` — persists across batches, `K-105`) and `_dr_call` per call in one session: the module's top-level output goes to the first call's `stdout`, a failed boot answers every call `{"payload": null, "error": <boot error>, "reads": null, "stdout": ""}`, and the harness catches whatever a call raises (any `BaseException` but `MemoryError`) as that call's `runtime` error, so the next call runs. A console batch (`entry: 'script'`, or `console: true` on the batch) is `_dr_run` per call, each on a namespace of its own, answering `{stdout, result_repr, truncated, error?}`. The bootstrap has no `except`: a `MemoryError` leaves `run` as a Python error, as it leaves the server's guest. `GuestHooks.callStart(i)` and `callEnd(i, text)` fire around each stretch in which a script's code runs, in order: the module-level code of an embedded batch as `-1` (a console batch has none), then each call; `text` is what the call answers. Whatever raises a `KeyboardInterrupt` in the bootstrap's own code between the hooks is absorbed there (the call answers a `runtime` error the pool replaces), so a stop never lands in the next call. A call's `docText` is a transform's document as JSON text, embedded in the calls text as written, where `doc` is a `Value` dumped (an object holding an array-index key would lose its order as one); the fill passes `docText`. `roots[i]` is the JSON text of call `i`'s `projectRoots` (`transform` sends none), which the facade's read memo takes, so a script that reads only its row makes no trip. Everything crosses the interpreter as text and is never re-serialized: the request is written by `dumpDefault`, each result comes back as the text Python's `json.dumps` wrote, so `1.0`, `1` and `2**60` stay a float, an int and exact. The one JSON layer the guest itself parses is `_dr_batch`'s reply, an array holding only result strings, which `JSON.parse` returns as written. The guest holds a Python proxy only for the duration of a call and destroys it. `facade.generated.ts` embeds `FACADE_SOURCE` from `core/script/facade_src.py` and `scripts/engine_tables.py` rewrites it; `harness.generated.ts` embeds `HARNESS_SOURCE` from `core/script/harness_src.py` and is frozen. `script_parity.json` records the oracle's answer to each of its cases (`test/script/parity.ts`: `loadParity`, `parityModel`, `parityBatch`, `parityRoots`, `expectParity`), and `test/script/guest.test.ts` holds the guest to those bytes in one in-process Pyodide, the `determinism` group apart (it needs pinned clocks and a fixed hash seed). **The pool** (`pool.ts`, `worker-main.ts`, `wire.ts`, `bridge-buffer.ts`, `host-error.ts`) is the one script host of every platform, written against `WorkerPort` (`post`, `onMessage`, `onError`, `terminate`) and `WorkerSpawner(buffers)`, never a Worker: `createPool(spawn, {cap, spareIdleMs?, limits?, now, onViolation?}): ScriptHost`. **One worker runs one batch, and that isolation holds in the browser only.** A worker boots (Pyodide and the guest, no user code), waits as a spare, is given the `run` of one batch and is terminated when that batch answers, fails or is disposed; it never runs a second, so no Python or JS state of one script (`__main__`, `sys.modules`, `builtins`, the worker's global scope, `K-105`) reaches another. In a browser the worker is a Web Worker in the cross-origin sandbox, which is the boundary: a script there reaches nothing but its own worker's scope. On the Node port the worker is a `worker_threads` thread in the host's process, and Pyodide's `js` module gives a script the worker's `process` (`js.process.getBuiltinModule('node:fs')`, `process.kill`), so a script can rewrite files later workers load or end the host: **the Node host runs trusted code only (tests, benches) until the headless service gets a process boundary** (sub-project E; `K-106`). The worker refuses a second `run` itself, but that is hygiene: the boundary is that the pool never sends one. What a worker posts is untrusted beyond its own batch (a script can post any message through Pyodide's `js` module): the pool reads it per worker, in the phase that worker is in, and whatever it forges can change only the answer of the batch it holds. **Messages.** Pool → worker: `init {reply, interrupt, limits, snapshot?, make?}` (the two `SharedArrayBuffer`s (the interrupt one of 8 bytes, see **Limits and stops**), the `HarnessLimits` the guest is made with; `snapshot` an `ArrayBuffer` to boot from, `make: true` to make one), `run {batch: WireBatch, roots: string[]}`. Worker → pool: `ready {ms, boot}`, `snapshot {bytes}` (the maker only), `failed {message}`, `bridge {text}`, `more`, `call-start {i}`, `call-end {i, text}`, `done {results, trips, ms}`, `csp-violation {directive, blocked}`; there is no run id. A `booting` worker may say `ready` or `failed`; a spare only `failed`; a running worker anything but `ready`, within the rules of **Limits and stops** and of the reply channel (a `bridge` only with no reply in flight, a `more` only while chunks of a reply are pending: the reply state is 0 and no chunk is pending at an honest request, and a chunk has been copied and the state reset at an honest `more`; anything else ends the worker); `csp-violation` (strings only) goes to `onViolation` in every phase, a wrong-shaped one is dropped. Any other message, or one of the wrong shape, ends the worker: a booting one is a failed boot, a spare is dropped, a running one fails its batch. `done` is valid with one `{text: string}` per call and a finite `ms`, and the pool takes the FIRST valid one: it ends the worker and answers, and nothing the worker says after that is read. `trips` is counted by the pool (one per `bridge` message it answered) and the `trips` the worker posts is ignored. **The snapshot.** Booting Pyodide cold takes about 1.9 s in Node; from a memory image it takes about 0.2 s. The pool's first spawn also starts a **maker** (`init {make: true}`, PoolOptions `snapshots` default `true`): a worker that boots cold with `_makeSnapshot: true`, runs `prepareGuest` (the facade and harness sources as text, `GUEST_BOOTSTRAP`: the harness's Python side and `_dr_batch`, with nothing of the host), takes `makeMemorySnapshot()` (about 30 MB), posts it as `snapshot {bytes}` with the buffer transferred, and is ended by the pool. The maker serves no batch: it never binds a transport, the pool never sends it `run` (a message from it other than `snapshot`, `failed` or `csp-violation`, or an empty or non-`ArrayBuffer` image, gives the snapshot up), and it holds no slot of the cap, so the first run is served by an ordinary cold worker booting beside it. The pool keeps the bytes and gives every worker spawned after that a copy of its own (`bytes.slice(0)`, transferred in `init.snapshot`): no worker shares bytes with the pool or another worker, and a script that overwrites what its worker was booted from (Pyodide's config keeps it, reachable as `pyodide_js._api.config._loadSnapshot`) changes nothing for the next one. While the maker works no spare is started (a worker starts only for a waiting run, or for `boot()`/`prewarm()`/`warmed()` when nothing is alive), so the first spare is the first from an image; `boot: 'cold'` then means a worker booted without the image and `'snapshot'` one that restored it. **What may and may not be in the image.** `_makeSnapshot` makes Pyodide wrap `jsglobals` in a path-recording proxy and serialize every JS value Python holds a reference to, and it refuses any that is not reachable by a path from `jsglobals` (`Can't serialize object`); so the maker sets only strings before the image (`_dr_facade`, `_dr_harness`) and holds no proxy, and everything that is a JS value or depends on the pool is bound after the restore, in `createGuest(py, transport, limits, restored = true)`: `_dr_transport_text`, `_dr_call_start`/`_dr_call_end`, the harness caps and `_read_memo_max`, `_dr_limits`, and the interrupt buffer (`setInterruptBuffer`), then `random.seed()` (the image froze `random`'s state). **If an image cannot be made or used,** every worker boots cold for the pool's life and `PoolOptions.onWarning(message)` is called once (`script workers boot cold: …`; default none): a maker that says `failed`, crashes, cannot be spawned or sends something else; or a worker that was given the image and reports `boot: 'cold'` or fails to boot (its run, if one waited, is served by a cold worker). The worker itself falls back in place: an `init` with `snapshot` that fails to restore or to bind (the private API missing, bytes that are not an image) boots cold in the same worker and says `ready {boot: 'cold'}`, which is how the pool learns. `snapshots: false` boots every worker cold without a maker (what `pool-protocol.test.ts` uses, so its spawn counts stay exact). **Determinism.** Every worker pins its own scope first (`worker-main.ts`, `pinScope` on `WorkerScope.globals`, never a test process's): `Date.now` to `1750000000000`, `Date`'s local getters to UTC and `getTimezoneOffset` to `0` (Emscripten's `localtime` reads those, not `TZ`, so `datetime.now()` is UTC as on the server), `crypto.getRandomValues` to fill `0x42` over the argument's bytes; Pyodide gets `env: {PYTHONHASHSEED: '0'}` on every boot (cold, maker, restore), which makes `hash` and set order fixed; `random.seed()` runs after a restore. In Node, Pyodide fills `os.urandom` through `node:crypto`'s `randomFillSync` and not `crypto.getRandomValues`, so `node/serve-worker.ts` pins that too, in the worker thread alone. The `determinism` group of `script_parity.json` holds these, on cold and on restored workers (`test/script/snapshot.test.ts`). Pyodide's snapshot API is private and is pinned with the Pyodide version (`architecture/constraints.md` CN-4): moving the pin needs `snapshot.test.ts` green. **A run.** `run(batch, bridge)` joins a FIFO; it takes a ready spare or waits for one. When it gets a worker the pool computes each call's roots through THAT run's `bridge.roots` (the call's elements and its `inputs.e.ids` elements, once each, as `trusted_runner.py` does; `'[]'` for a `transform`, a console run, or nothing to project) and posts `run`; each `bridge` message is answered synchronously in the message handler through that run's `bridge.dispatch` and the worker's reply buffer (`more` writes the next chunk), so two runs in flight never see each other's bridge. A batch that fails after it started (a `failed` message, an `error` event, a bad message, a bridge that throws) RESOLVES with one host-made `runtime` error per call, `hostErrorText(batch, kind, message)` (`host-error.ts`: the harness's own call-error shape, `{payload, error, reads, stdout}` for an embedded call and `{stdout, result_repr, truncated, error}` for a console run, the error `{kind, message, traceback: null}`, written with `dumpDefault`; `hostErrorResults` makes one per call); a boot that failed REJECTS the run that was waiting for it with the boot error. **Limits and stops** (`pool.ts`, `interrupt.ts`). `RunLimits = {callMs, batchMs, graceMs, bootMs} & HarnessLimits` (`DEFAULT_RUN_LIMITS`: 10,000, 30,000, 1,500, 30,000 ms, then the harness's caps), all in `PoolOptions.limits`. The pool times a batch from outside, in windows the worker reports: a window is a stretch in which a script's code runs, `call-start {i}` to `call-end {i, text}`, for each call and, before them in an embedded batch, `i = -1` for the module-level code (which the server times as part of its boot). Nothing else in the worker runs script code, so a worker that is between windows has nothing to stop. _Timers of a run_, all cleared together when its worker ends (`end(slot)`): the **deadline** of a window, armed by its `call-start` for `min(callMs, batchMs − elapsed)` (elapsed from the `run` post; a `call-start` with none left ends the worker at once, every call not ended answering `timeout`, as a dead session fails the calls after it); the **grace**, armed at the deadline (and at a cancel) for `graceMs`; and the **watchdog**, armed once at the `run` post for `batchMs + graceMs`, which nothing a worker says re-arms, so a worker that posts nothing, forges its messages or never ends a call is still ended (hard stop, `timeout`). `call-end` disarms the deadline and the grace. The **soft stop** at the deadline raises Pyodide's interrupt (`KeyboardInterrupt` in Python bytecode: it breaks `while True: pass`, and does not wake `time.sleep`, stop a long C call such as `sum(range(10**10))`, or survive `except BaseException` or `signal.SIG_IGN`); the interrupt can be lost, because Pyodide's `_Py_CheckEmscriptenSignals_Helper` (`pyodide.asm.mjs`) reads the flag and then clears it without an atomic step, so a store between the two never reaches Python; the pool therefore raises it again every `retryMs` (100 ms) until the call ends, which is required, not an optimization (`CN-4` says to re-check it when the Pyodide pin moves), and it can re-interrupt a script's own `KeyboardInterrupt` cleanup that runs longer than that (the effect stays in that script's own batch); the harness answers the call as its own `runtime` error, the pool replaces that answer by `timeout` (`execution exceeded the wall timeout of 10s`, with `callMs` in seconds, as the server writes it), and the batch goes on in the same worker. A call whose window the pool stopped answers `timeout` whatever the worker says, even a success that came before the stop took effect; every other call is what the worker said (a `KeyboardInterrupt` a script raises itself is its `runtime` error). The **hard stop** is the grace running out: the worker is terminated, every call not ended answers `timeout`, calls that ended keep their answers (the pool keeps the `text` of each `call-end` for this), and the run resolves; the batch is not re-queued, which bounds the cost of a runaway script, and the pool refills the slot by the rule above. A stopped module-level window ends the worker at its `call-end` (every call would carry the boot error): all `timeout`. _The interrupt buffer_ is two `Int32` (`interrupt.ts`): slot 0 is Pyodide's flag, slot 1 says which window the worker is in and whether the pool stopped it, moved by compare-and-swap so that exactly one of "the worker ended the window" and "the pool stopped it" happens: the pool raises the flag only after winning the swap, and a worker that ended a stopped window waits for the flag store and clears it, so a stop is never raised after its call ended and never reaches the next call, and the pool knows which calls it stopped. A script can write this buffer (Pyodide's config reaches it) but only changes its own batch: the grace is armed whether or not the swap was won, so the hard stop never depends on what the worker says; when the swap is lost the worker's own word is read at the grace, because timers run before queued messages and a pool thread busy past the grace would otherwise end a worker whose `call-end` is merely queued, and a worker whose word says it ended gets one more grace (a forged word, only one). The worker registers the flag with `setInterruptBuffer` after every boot, cold or restored. **Cancel:** `run(batch, bridge, signal)`; aborting while the run is queued removes it (it answers `cancelled` for every call, no worker is spawned or used for it, and the worker already booting for it is kept as a spare), and so does a signal aborted on arrival; aborting a running run stops its current call softly (`cancelled`), arms the grace and ends the worker when that call ends or the grace runs out (at once when no window is open), every call not ended answering `cancelled` (`the run was cancelled`), the calls that ended keeping their answers; a call already stopped by its deadline stays `timeout`. **Crashes:** a worker that fails or dies mid-run (`failed`, an `error` event, a bad message) answers what it had not ended as `memory` (`guest exceeded its memory budget`) when the text the worker itself gave names a `MemoryError` or an allocation, heap or memory-limit failure, else `runtime` with that text; a cancelled run answers `cancelled`. The harness re-raises `MemoryError` on purpose, which reaches the pool as that `failed`. _Boot:_ a worker (or the maker) that has not said `ready` (`snapshot`) within `bootMs` is ended and treated as a boot failure (what waited on it fails, nothing respawns on its own; the maker's end is the permanent cold fallback). Every host-made answer is written by `hostErrorText`/`hostErrorResults`. There is no per-worker memory limit: a wasm memory that cannot grow is the `MemoryError` above, and in a browser a worker that dies takes only itself. **Spares.** A worker starts for each run that waits, up to `cap` (the most alive at once, booting, spare or running). Once anything asked (`run`, `boot`, `prewarm`, `warmed`) the pool is _hot_: whenever the image is ready (at once when images are off, where the spares boot cold) and no boot is failing, it fills every free slot with a spare, so `cap` workers are alive, and a finished batch's slot is refilled the same way. No spare starts while the maker works, so none boots cold behind it. The maker holds no slot. Spares beyond one end after `spareIdleMs` (default 30,000) with no run waiting, and that ends the hot state: nothing refills what the shrink ended, and the pool keeps one spare ahead of the runs that wait, until the next `run`, `boot`, `prewarm` or `warmed` makes it hot again. The refill trigger is demand, never the trim, or the shrink would undo itself. `prewarm()` makes the pool hot and starts a boot when none is ready or booting. `warmed(signal?)` does the same and resolves `{spares}` once the image is settled and `cap` spares are ready. It rejects when a boot failed or a ready spare died and none is booting (also at the call, since nothing spawns until asked), on abort, and on dispose, and the idle shrink is held while one waits (it proceeds once the wait settles); the service exposes it as `scriptWarm`, which the bench awaits before its timer and which tells a runaway case that no run's worker still holds a slot. A hot pool keeps `cap` interpreters resident (about 90 MB each, `architecture/constraints.md` CN-4). **A boot that fails** fails one waiting run (or, with none waiting, the pending `boot()`s) and stops every spawn nobody asked for until a worker boots: a run, `boot()` or `prewarm()` asks, so a pool that cannot boot spawns once per waiting run and never on its own; `warmed()` asks too. `boot()` resolves with a ready spare's boot time, at once when one is up (and makes the pool hot), else starts one worker and resolves when any becomes ready; a rejection is never kept, so the next `boot()` or run boots again. `dispose()` ends every worker and rejects every pending run and boot (`script host is disposed`); a call after it rejects. `worker-main.ts` is `runWorker(scope, loadPyodide)` over `WorkerScope = {post(message, transfer?), onMessage, globals}`: on `init` it pins the scope, then (a `make` init posts the image instead, see above) loads Pyodide (from the image when one came), sets the interrupt buffer, makes the guest over a transport that arms the reply buffer, posts `bridge` and blocks in `readReply` (the one place that calls `Atomics.wait`; - **`src/evaluate/`** — `EvalContext` (`{model, artifacts, placements, working?, scripts}`, `artifacts` an `ArtifactSet`; `working` a `WorkingStamp` `{rev, stagedVersion, tableOrders}` — the committed revision a page reports and the staged version, under which `evaluateTable` keeps its orders in `tableOrders`; without it, rev 0 and nothing kept) and `EVALUATIONS`, the evaluations by `lib/api` name (`searchModel`, `evaluateNavigation`, `evaluateTable`, `exportTable`, `previewTableJson`, `runExporter`, `runExporterDraft`). An evaluation is always a `Steps` generator — the service runs it as a model-lane scan, whatever its params — and it reads its params, resolves its artifacts and translates its patterns before its first step, so a refusal (422) happens before any work and leaves nothing behind. Scripts: `ctx.scripts` (a `ScriptReader`) is required, and an evaluation that reaches a script reads through it. `evaluateFilled(pass, {runner, signal, cache?, transitions?, onProgress?, stdoutChars?, slices?})` (`fill.ts`) is how a reader is filled: a pass reads each call through the reader (the fill's memo, then the `CellCache`, else the miss is recorded and `PENDING` answered), a pass that recorded a miss is discarded, its misses run as one batch per `(code, entry)` in first-miss order, duplicates once, on the `BatchRunner` (one result text per call), and the pass runs again until none is recorded; the last pass's value is the answer, with `{rounds, calls}`. A pass that throws having recorded a miss is discarded like any other. Results are kept (memo and cache) only if `transitions()` is what it was when the pass that asked for them began: a round the model moved under is dropped and asked for again, and a moved counter clears the memo before the next pass. The memo is the fill's own, so a result the cache refuses (a timeout) runs again in the next fill. The texts of a call's inputs and document are read with `floatConstants`, a bare `NaN` or `Infinity` being the float `json.dumps` wrote. A text that is not an envelope is that call's `runtime` error `malformed call result`, never cached; a call's output is cut at `stdoutChars` as the oracle's session cuts it; a runner that answers the wrong number of texts rejects the fill. A pass that ended in another state than it began in (`transitions()` moved) is run again at once: its misses are not run, and nor is a pass that recorded none returned. The batches of a round run together under a signal of their own, so the first to fail aborts the others and the fill rejects with that failure once all have ended; an aborted `signal` rejects with its reason whatever the runners rejected with, before the next pass, and a round that finished after it keeps nothing. A round's settle (parse each text, fill the memo, `CellCache.put`) is steps of `SETTLE_STEP` (256) calls each, `settleRound`: `slices(run, signal)` runs them as model-lane work, absent they are drained at once. `run` makes the steps afresh on every start and returns at once if `transitions()` is not the round's stamp; the stamp is checked again at every resume, and the round is settled only if the steps ran to their end. A start that runs again after a restart skips what the memo already holds (the memo is cleared at the loop head whenever the stamp moved, so it holds only the round's state), so a call is settled once and a result is never kept in a state other than the one it was asked in. The memo has no byte bound: a table sorted by a script column holds every parsed result for the length of one evaluation (the cache's bounds apply to what outlives it).
- **`src/validation/`** — a port of the Python core's six built-in validators and of its pipeline, scoped and over the whole model (`core/validation/`), held to `validation_kinds.json`. `Validators` holds them for one metamodel, in pipeline order — type conformance, multiplicity, facets, endpoint typing, containment, uniqueness — with their memos per type name, so one is built per metamodel and reused; `FacetPatterns` likewise. `validateScoped(model, ids, validators, patterns, rules?, structure?)` is `ValidationPipeline.validate(model, Scope(ids))`: each id once, its first occurrence deciding the order; an element through every element hook, a relationship through every relationship hook, an id naming nothing skipped; then every global hook, in validator order; `check` stamped with the validator's name. With `rules` (a `CompiledRules`, below) it is `pipeline_for(compiled)`: a `RulesValidator` runs seventh, in every loop and in the globals. The run (`Run`: `{model, structure, patterns, out}`) reads containment parents (containment) and uniqueness groups (uniqueness) through `structure`, `liveStructure(model)` by default, and the rules' metamodel is the structure's; the model answers lookups and adjacency. The validators, the patterns and the structure must share one metamodel, or it throws. `validateSplit(model, ids, validators, patterns, rules, structure)` is the same pass split: `entity`, the entity hooks' issues, and `global`, each validator's global issues, one list per validator in list order (the rules' last); `entity` then every `global` list in turn is `validateScoped`'s answer. A scoped run reports every scoped element whose first-parent chain reaches a cycle, those hanging below it included. `WholeRun(model, validators, patterns, rules, structure)` is the run over the whole model (`ValidationPipeline.validate(model)`, `Scope.all()`), fed every element then every relationship in state order (`element`, `relationship`, in slices as the caller likes) and answering at `finish`: the entity issues, then each validator's global issues in validator order, from `validateWhole(run, out)`, the per-run whole-model global hook every validator with a global hook has. Two answer unlike a scoped run over every id: containment reports ONE cycle for the model, the first contained element whose chain reaches one, contained elements taken in the order their first containment parent comes in the relationships (the order the core's parents map is keyed in); uniqueness reports group by group, in the primaries' order, each member after its primary in `ord` order, every one rendering the key of the group's SECOND member (the one whose arrival put the key in the core's `duplicate_keys` as a rebuild fills it, so `1`, `1.0`, `True` all read `size=1.0`); the rules validator merges its evaluation failures at `finish`. Every issue is an error; a dangling reference, a second containment parent and a cycle are `structural`, the rest `conformance`. The messages are the core's texts: a value through `repr` (`pyReprValue`); a uniqueness identity through `repr` of the FROZEN value (`pyReprFrozen`: a list as a tuple, a dict as its key-sorted pairs, a missing key as `None`), rendered from the reported element's OWN key — `1`, `1.0` and `True` share a group — with its key relationships' endpoint ids sorted by code point, the group's primary being its member with the least `ord`; a facet bound is a float and renders as one (`5.0`) while the value goes through `str()` (`pyStrNumber`: `100000000000000000000`, `1e+20`); `max_length` counts code points; an enum member must be a string; a `date` is what `datetime.date.fromisoformat` accepts (`pyIsoDate`, CPython's parser over the UTF-8 bytes: `YYYY-MM-DD`, `YYYYMMDD`, `YYYY-Www[-D]`, `YYYYWww[D]`, ASCII digits, the calendar and ISO week 53 checked, and — since the parser never looks for the end — the two bytes past an eight-byte date not read at all, so `20240101xx` passes). Facet patterns are `re.fullmatch` through `translatePyRegex(…, 'fullmatch')`, each translated once and run on `''` and `'Ā'` when `FacetPatterns` is built: a pattern outside the translator's subset, or one the host cannot run (`beyondHost`, shared with the criteria), is kept with its reason (`regex.reason`, or `HOST_REFUSED`; a host failure mid-run is sticky), `test(pattern, value)` answers that `{reason}` in place of a verdict and `unusable()` lists those patterns — never a guessed answer. The facet validator reports each value of such a property as one `error` issue, `<name>: pattern '<p>' cannot be checked: <reason>`, owned by the entity. `wireIssue(i, origin)` is the routes' `IssueOut` (`{severity, message, target_ids, category, check, origin}`), `issueOwner` the first target, `issueKey` the multiset key `(severity, category, check, message, target_ids)`, `candidateKey` the metamodel diff's `(category, severity, check, message, sorted target_ids)`. `candidate.ts` validates the model under a candidate metamodel, the model half of `POST /metamodel/diff` and of a rebind's `POST /commits/preview` (`api/metamodel_candidate.py`, `routes/commits.py`), held to `metamodel_candidate.json`: `prepareCandidate(doc, rules)` reads the `GET /metamodel` document and builds its `Validators`, `FacetPatterns` and `rules(metamodel)` over that one `Metamodel` object (the pipeline's identity guard), throwing what `Metamodel.fromJSON` throws on a malformed document, and `UncheckablePattern` (`<type>.<property>: pattern '<p>' cannot be checked: <reason>`) for the first pattern of `unusable()`; `candidateScan(model, candidate, step = 512)` builds the candidate structure in steps, then feeds a `WholeRun` `step` entities a step, its progress one total over both phases, and answers the whole-model issues — the core's `candidate_issues`, a full run over a rebind view — never writing a record; `candidateDiff(current, candidate)` keys both sides by `candidateKey`, a key keeping its first position and its last issue as a dict built from the list does: `now_failing` in candidate order, `now_passing` in current order, `unchanged_count` the keys both hold, the error counts the raw lengths, every issue `on_server`; `rebindPreviewBody(issues)` is the rebind preview's body: every issue `on_server`, the structural ones also blockers, the rest counted, `would_block` false. `stagedRefusal(wc, candidate)` is the first refusal (`{status, detail}`) the server would answer applying the staged ops under the candidate (see the service's rebind preview), `null` when it admits them all. `DirtyCollector` is `core/validation/dirty.py`'s: an ordered set of ids (`ids` in first-insertion order) with the same hooks under camelCase names — `afterElementCreate`, `before`/`afterElementPropsChange`, `before`/`afterElementDelete` (over the applier's `containmentClosure`), `before`/`afterConnect`, `before`/`afterDisconnect`, `afterRelationshipPropsChange`, `addUniquenessGroupOf` — each adding exactly what the core's adds, every index set sorted by code point; a relationship type named in a uniqueness key (`out:` / `in:`, `keysOn`) re-keys the ends it names, so connecting, disconnecting or cascading it away also brings their old and new groups; fired from `applyBatch`, it collects the dirty set `_finalize` validates, held to `validation_dirty.json` in order. A rebase has no hook to fire, so `addNeighbourhood(model, ids, into)` over-approximates: per id, an element adds itself, its uniqueness group, its referencers, each outgoing relationship with its target and each incoming one with its source (each set sorted); a relationship itself, its ends and, for containment, its target's group; an id naming nothing itself — taken on the states before and after, it covers every entity whose verdict inputs moved. `IssueStore` is `ValidationState`: issues by owner, owners in insertion order; `replace(dirty, issues)` drops every dirty owner and files the new issues, an owner returning last, refuses an issue owned outside `dirty`, and says whether any owner's issues now differ (an owner that only moved does not count); `counts()` is kept as the store changes, severities in the order a walk of the store meets them. `storeListBody(store, rev, rulesStatus, tagOf?)` is `GET /model/issues`'s body over it — the first 5,000 issues in store order, `counts` exact, `truncated`, and the `rules_status` given, which `rulesStatusBody(compiled)` builds from a compile as the route does (`total`, `skipped` with `artifact_id, set_name, rule, reason`, `eval_errors`) — held with the store to `validation_steps.json`.
  `LiveIssues(wc, {seed?, sweepStep?, sweepSkip?, rules?})` (`live.ts`) keeps an `IssueStore` over a working copy's WORKING state; nothing else may write to the working copy while it wraps it. It holds two compiles, `rules = {working, committed}` (W and C, both `EMPTY_RULES` unless given): W is the working layer's rule sets, the ones the store's issues are found with, C the committed layer's; with nothing staged they are the same. Its `stage`, `unstage` and `applyDelta` are the working copy's, each revalidating before it returns the ids whose verdict it may have moved, by three rules: a stage takes its applier's hooks, the server's own dirty set; a rebase (`unstage`, `applyDelta`) takes `addNeighbourhood` on the state before over every id it may touch — `touchedIds()`, plus every id a delta names or deletes — and on the state after over those and the ids its change set names, both passes carrying the ends of every relationship among them (from the model, the committed image of one staged away, or the delta's own `source_id` / `target_id`), since a relationship absent on one side cannot name its ends there and they move groups all the same; a merged edit (`coalesce`) takes its trial run's hooks and the rebase rule over the id it names and every batch it replays — from `mergePoint(op)` on, `touchedIds(at)` — since those batches may overwrite part of it or park; an edit that asks to merge and does not pays its hooks only. Every one of those dirty sets is then widened by W's reach (`expandScope`) on the state AFTER the transition — a stage after its hooks, as `_finalize` does, a rebase or a merged edit after its neighbourhoods — and revalidated with W: the premise of `src/rules/` holds because each dirty set holds every element whose properties or incident relationships moved, and the seeded invariants hold it with rules of two-hop atoms in play, the store equal to a fresh sweep after every action. The containment chain past its first link is the one input no rule reaches (the core shares it), which is why the seeded invariants compare stores without cycle issues. `version` moves when a splice changes the store's content (not when it only re-files an owner), on every applied delta (origins move with the rev), and on every `setRules` (`rules_status` or the tags may have moved). The sweep, `sweepSteps()`, is a `Steps<boolean>` whose state lives on the object, never in the generator: its first step takes the total, the entities then (`done: 0`), each later one walks on — elements in state order, then relationships — and validates and splices the next `sweepStep` entities (`SWEEP_STEP`, 512), a complete change of its own, so it resumes across any transition and any generator picks it up. It holds a live iterator per map, with the `orderEpoch` it was taken at, and the set of ids it has validated since it began (O(model), as a list of every id would be): the iterator passes over an entity in the set, at most `sweepSkip` (16 × `sweepStep`) a step, and validates any other. An entity deleted since is not reached (the transition that deleted it dropped it from the store); one the map holds between two steps is reached before the iterator ends, wherever it sits — made by a transition (validated twice, harmlessly), put back at its old place by an unstage, put back at the map's END by a refused batch's rewind (which validates nothing: the entity is as it was, but may never have been swept), or made again by a probe's replay (a staged create under the same id). A re-sort would make a live iterator read the whole map again, so when one moves the epoch the sweep takes a fresh iterator and passes over the set's members from the start. The progress counts the entities validated, short of the total until the last step, which alone reports `done === total` (entities made meanwhile can take the count past it); that step sets `seeded` and releases `whenSwept()`. The walk ends as long as each step's `sweepSkip` outruns what lands behind the iterator between two steps: the entries a probe's or a rebase's replay appends (one per staged create), or the whole map after a re-sort. `restartSweep()` sweeps again from the start, in place: the store keeps what it holds meanwhile. `setRules({working, committed})` swaps both compiles, moves `rulesVersion` and `version` and drops the origins; it validates nothing. When W's ordered list of rule identities changes, `appliesPopulation(model, old W, new W)` joins the rescan queue after the ids still queued, each once — a rename or anything that leaves W's rules as they were queues nothing. The same generator drains the queue after any sweep due, `sweepStep` ids a step, each a `revalidate` with W as it is at that step, and yields `RESCAN_STEP` (a `SweepStep` marked `rescan: true`) in place of progress, so a rescan reports none and never moves `seeded`, which still means a sweep has ended. `settled` is false while the queue holds ids; `whenSettled()` resolves when it empties, and `whenSwept()` waits for the rescan too. A sweep or rescan step that throws — a validator's bug — splices nothing and leaves its ids due, the sweep's pulled ones first in its next step and a rescan's still queued, and releases both waits, since nothing drives the steps until a caller starts a generator again. `origins()` runs `probeStaged`, once per `(rev, stagedVersion, rulesVersion)` and not at all with nothing staged: `hooks` is the probe's dirty set (the server's `base_dirty`), `S` (`dirty`) is `hooks` widened by W's reach on the working state, and while W and C differ, every element a changed rule applies to — the rules one identity list holds more often than the other, both ways (ΔPop) — with its issues validated on the working state with W (`working`) and on the committed one with C (`committed`); `previewDirty` is `hooks` widened by C's reach and `preview` its issues on the working state with C, which is `working` itself when W and C hold the same rules in the same order. An element of ΔPop that neither W nor C reaches from `hooks` has the same inputs on both states, so its issues with W and with C are found on the working state alone and kept (`deltaOf`) for one rev and one pair of rule sets: a keystroke's probe does not pay for ΔPop again. With nothing staged in the model, `S` is ΔPop alone, empty when W = C. `tagScope()` is what the panel's tags read: every owner whose issues may differ between the two states, with its committed issues. The exact probe finds it (`S`, with `committed`); from there, while the store is seeded and settled, the rev and the rule sets hold and W's identities are C's, each transition adds the ids it dirties, with the store's issues from just before it revalidates them — no transition had dirtied them since the probe, so those were their committed issues (the dirty sets are exact, and each owner's issues are found independently of the rest of a scope) — and a keystroke's list runs no probe. A delta, a `setRules`, W ≠ C or a store not seeded or not settled drops it, and the next read probes; `resetTagScope()` drops it too. The three bodies (`bodies.ts`) answer as the routes do — `validateBody` and `previewBody` through `origins()`, whose `S` is part of their answer, `issueListBody` through `tagScope()`: `issueListBody` is `GET /model/issues` over the working store, an issue whose owner the tag scope names `on_server` while a committed issue of that owner with the same `(severity, message, target_ids, category)` is left to match it and `uncommitted` past that, every other one `on_server`, and no `resolved` (the live list never shows a fixed issue), its `rules_status` W's — so a new rule's issues read `uncommitted` and a removed rule's are gone; `validateBody` is the staged branch of `POST /model/validate` — the store's issues of owners outside `S`, then `S`'s working issues tagged the same way, then the committed ones left unmatched as `resolved`, in their order; `previewBody(live, strict)` is the model half of `POST /commits/preview` over `preview`, all `on_server` — C's rules, as the server's preview never assigns a staged rule set — `would_block` being `strict` and a conformance issue the ops can be held to (`attributable_issues`): owned inside `hooks`, or any rule's, warnings included. Both staged bodies are held to `validation_steps.json`, whose second session carries rule sets.
- **`src/rules/`** — a port of `core/validation/rules/` (the rule grammar, compile, reach and the validator), line for line, held to `rules_compile.json`, `rules_eval.json` and `rules_reach.json`. The engine parses no YAML: the server parses each rule set once (`POST /rules/parse`, and `rules` on `GET /artifacts/payloads`) and hands on the definition as a JSON document in TEXT, which `readRuleSet` (`document.ts`) reads with the exact parser — bare `NaN` / `Infinity` as floats, integers past 2^53 as `bigint`, every float a `PyFloat` — and then strictly, against the grammar pydantic enforces: an unknown key, a wrong type, zero or two property tests (chosen by the key being there, so `equals: null` is a test), a `null` on a test other than `equals` / `not_equals`, an empty `all` / `any`, `count` without a bound, a relationship atom without exactly one non-null `exists` / `count`, more than 200 rules, a duplicate name or nesting past eight levels (a `where` one) all throw `RulesUnreadable`, the one way out, never a guess; where pydantic reads an explicit `null` as absence (`to`, `where`, `when`, `message`, a relationship's `exists` / `count`, a count bound) so does the reader, and absent defaults are filled. Each `Rule` keeps its `identity`, its entry as the document wrote it (`pyDumps` with `allowNan`). `compileRuleSets(sources, mm)` (`compile.ts`) compiles `RuleSource`s in the order given — `ruleSources(set, layer)` (`sources.ts`) lists them by name then id, both by code point: the committed layer's rule sets with their committed parse, or the working layer's, a staged payload's parse laid over, `'pending'` standing on the set's last parse and a `'pending'` create with none left out. A failed parse is one skip for the whole set (`rule` empty, `reason` the parse error's message); a disabled rule is dropped before the drift check; the drift check walks `when` then `then` and reports the first mismatch — an unknown `applies_to`, a property the DECLARED type lacks (a subtype's does not count), an unknown relationship type, an unknown `to`, a `where` checked against `to`'s properties and not at all without one — with `repr` (`pyRepr`), skipping the rule whole. A document the reader refuses, or a rule set that arrived without its parse, is one skip for the whole set (`rule: ''`, the reason `rule set could not be read` or the reader's message); the other sets still compile. A `CompiledRule` carries its `appliesTypes` (`elementDescendants(applies_to)`), `check` `rule:<name>` and reach `paths`; `rulesByType` lists them per exact type in compile order, and `identities` the compiled rules' identities. `appliesPopulation(model, …compiled)` is every element a rule applies to: types sorted, each type's ids sorted. `evaluate.ts` is `validator.py`: `pyRuleEq` is Python `==` with a `bool` equal only to a `bool` (numbers compare exactly across `int`, `bigint` and `PyFloat`, `NaN` never; `None` equals `None`, which a list item can be); a value is missing when absent, `null` or `[]`, and missing fails every test but `exists`; a list holds when any item does, `contains` on a list being membership and on a string a substring test (`pyContains`) with a string operand; the bounds need a number that is not a `bool`; a relationship atom counts the element's own adjacency of the type's descendants, the far element filtered by `to`'s descendants and `where`. An issue is `conformance` with the rule's severity and check, its message the rule's own when not empty, else `Rule '<name>' violated` plus `: <description>`, quotes literal. `RulesValidator` counts a rule that throws under its check and merges the run's counts into the compile's `evalErrors` once, in its global hook; nothing it runs can throw (every comparison is total, nesting is capped and a record cannot hold a dangling end), so `eval_errors` never moves on either side. `reach.ts`: `derivePaths` gives a root-first path of steps per relationship atom, a `where` extending its atom's path; `expandScope(model, compiled, dirtyIds)` walks, from the dirty ids that are current elements, every suffix of every path backwards (an `outgoing` step through `el.in`, an `incoming` one through `el.out`), keeps each element reached whose type the rule applies to, frontier sorted by code point, first-seen order — never filtering on the far types, so a retype on the path cannot hide an owner. Its premise: a rule's verdict on an owner reads the owner and its paths, so if a transition moves the verdict, some path of the owner, on the state before or after, first meets an element the transition dirtied (the stage hooks and the neighbourhood rule add both ends of every relationship they touch and every element they change), and the prefix up to it is on the after state too; walking back from the dirty set on the AFTER state therefore reaches the owner.
- **`src/service/`** — `Scheduler` (`scheduler.ts`) runs engine work on the host's thread in slices. One pump, two lanes, each in arrival order: the _control_ lane (the replica's own transitions) runs in any state and first; the _model_ lane runs while the scheduler is open. A job is a `read` (one call), a `transition` (one call that changes the model, never interrupted — a transition may run up to 100 ms, AD-23) or a `scan` (a `Steps` generator that `run()` makes). A transition waits for every read that arrived before it and holds everything behind it; at each slice boundary of a running scan, the reads queued before the first transition are answered and other scans are skipped over, never started — so a scan never sees the model move under its iterators (probe: a `Map` iterator that crosses a `clear()` and refill reads everything again, and `Model.elements()` does exactly that on the first ordered read after a rewind). `cancel(id)` removes a queued job or drops a running scan at its next step, unanswered; closed (`setOpen(false)`), the model lane keeps its jobs and a scan that was mid-flight goes back to the head to start over, `run()` called again. The pump reads the injected clock after every unit — a read, a transition, one step — and at `SLICE_TARGET_MS` (8, half of CN-3's 16 ms chunk: at M a collector pause of 5–8 ms lands inside a step now and then) calls `onSliceEnd`, awaits `yieldToHost()` and starts a new slice — `onSliceEnd` also runs when the pump runs out of work, the end of that slice; messages are handled on those host turns only, never inside a unit. Idle and open, it gives its two background slots one step each in turn: the digest check (`setBackground`), whose `restartBackground()` drops its steps in flight (they published nothing) so a new run starts at its next idle step, and the sweep (`setSweep`), whose steps resume across any transition — `restartBackground` leaves it alone and closing only pauses it. A slot empties when its task ends. `pause()` lends the slice clock to work outside the pump (a snapshot open): `undefined` while the slice has room, else the host's turn. The pump starts on a microtask, so every job one message brings is queued before any runs.
  `createService(port, deps)` (`service.ts`) is the CT-4 dispatcher over one `Port` (`{post, onMessage}`: a `MessagePort` in a worker, `portPair()` in tests); `deps` is `HostDeps` plus `inflate`, since `src/` holds no timer, clock or gzip. A request `{id, method, params}` is answered `{id, ok, result | error: {status, detail}}` exactly once, or never once `{cancel: id}` came; a message without an id or a method is ignored. Errors: `OpError` / `ReadError` keep their status, a `ModelError` `key` is 404 with `errorDetail`'s quote-stripped text, `value` 422, a `SnapshotError` 422, an unknown method 404 `No method 'x'`, anything else 500 with its message. The replica is `opening`, `ready` or `diverged`. `open {project_id, metamodel}` discards any replica or open in flight (the heap never holds two) and starts `openSnapshot` over `deps.inflate` of a `ByteQueue` that `chunk {bytes}` feeds, with the scheduler's `pause` (which also stops a discarded open at its next batch); `end` answers the header once the replica is read and indexed — or the open's 422, which `chunk` and `end` then answer until the next `open`, a header of another project included — and the replica stays `opening`; `adoptStaged` (a control-lane transition) carries a re-bootstrap's staged batches over; `applyTail {text}` queues one transition per delta at once (control lane while opening, model lane after) and makes an opening replica `ready`, the scheduler open and the background digest check set; `applyDelta {text, own?}` is a model-lane transition, a 409 unless `ready`; `close` drops everything but the view placements, the artifacts and the queued model jobs. A delta or a tail crosses as the text the shell received and is read by `readDeltaText` / `readTailText` with the exact parser (AD-26: `JSON.parse` would lose `1.0` and integers past 2^53, which the digest cannot see); a commit response reads alike, `model_rev` standing for `rev`. Events: `replica {state, rev}`; `progress {task, done, total}` for `parse`, `index`, `tail`, `verify`, `sweep` and `scripts` — a task's first (`done` 0, which is how a restarted digest check or sweep shows) and last reports at once, the rest at most once a slice, from `onSliceEnd`; `changed {rev, staged_version, issues_version, artifacts_version, …ids, structural}` after every transition of a `ready` replica that changed something, which also restarts the digest check when an entity or the staged list moved. A delta whose digest disagrees, or a digest check that ends false, makes the replica `diverged`: the scheduler closes, so reads and edits posted meanwhile wait, and are answered from the replica the shell opens next (`close`, `open` … `end`, `adoptStaged` with what `staged` returned, `applyTail`). The method table (`METHODS`) is built from a few kinds, so the message handler has no per-method branch: `now` (answered at once, in any state — `open`, `chunk`, `close`, `staged`, `conflicts`, `setViewPlacement`, `dropViewPlacement`, and the artifact context: `setArtifacts {artifacts}`, `putArtifacts {changed, deleted_ids, staged?}` — the committed layer moves, then `staged`, when given, replaces the overlay — and `setStagedArtifacts {entries}`, each answering `null` and reading the whole call before the set moves), `later` (`end`), `read` (every `READS` name, a `scan` job when `readScans` says so; `getModelSummary` is handed the committed `rev` as `model_rev`), `evaluate` (every `EVALUATIONS` name, always a `scan` job over the ready model, the placements and the service's `ArtifactSet`; each `run()` reads the working copy's `rev` and `stagedVersion` into the context with the service's `TableOrderCache`, which no model-lane transition can move while the scan runs, and which `close`, a new `open` and a divergence clear), `inspect` (`stagedDiff`), `scanWorking` (`downloadModel`, `compareModel` and `proposeCr`: a `scan` job over the ready working copy itself, its steps made afresh on every start; `compareModel {file, created_at}` reads its params at arrival — `file` an `ArrayBuffer` (else 422 `file must be an ArrayBuffer`, a typed array included), kept, not detached, `created_at` a non-empty string (else 422 `created_at must be a string`) — and keeps one `UploadedFile` for every start; `proposeCr {crs, created_at}` reads its params at arrival too — `crs` through `readCrs`, else 422 `invalid change request: …`, `created_at` as `compareModel`'s — and keeps the change requests read for every start) and `transition` (`stage`, `unstage`: their params are read at arrival, so a malformed request is refused before it queues), plus the three replica methods above and the three that answer from the issue store, below. Reads, `stagedDiff`, `stage` and `unstage` wait in the model lane for `ready`, so an edit made during a re-bootstrap lands after the adopted batches. `stage` reads its ops through `readOps` and always asks the working copy to coalesce; it answers `{batch, coalesced, changes, elements, relationships}`, the last two the post-state of what `changes` names as changed, both `null` past 500 entities. Every result and event is a copy built by the `wire*` functions — over a direct port pair nothing is cloned, and an uncopied result would hand out the replica's own property bags. Bytes are the one thing an answer moves rather than copies: `Call.answer(result, transfer?)` hands `port.post` a transfer list, and `evaluate` and `scanWorking` pass `transferOf(result)` — `result.parts` when it is an array of `ArrayBuffer`s, as an export's is, else none — so over a `MessagePort` the file's parts go to the shell without a copy and the engine's are detached; nothing in the engine keeps them (each export slices fresh ones from its encoded bytes, and a download writes into fresh ones). No other answer, refusal or event carries a transfer list. An export is a scan like any evaluation: a `stage` posted while it runs waits for it, `{cancel}` drops it unanswered, and a `close` or a divergence under it sends it back to the model lane's head to start over on the next replica, answered once.
  Evaluation with scripts. `evaluate` always runs an evaluation as a fill, so one that reaches a script is answered: `answerLater` takes the call, `evaluateFilled` (`src/evaluate/fill.ts`) drives it, a pass is a model-lane scan (`modelScan`: `scheduler.submit`, resolved on its outcome, with a fresh `EvalContext` per start) and the runner is `runBatch`, the body of `scriptCalls` over a prepared batch, on the replica the call arrived on. A pass is one scan, so no transition of the model lane lands within one; the batches of a round run outside the scheduler, where `stage`, `unstage`, `applyDelta` and the tail land, and the settle of a round, which `fill` hands to `slices`, is a model-lane scan of its own under the call's id (`modelScan` over `start(); run()`), cancelled on an abort as a pass is. A running scan holds the model lane's transitions behind it, so none lands between its slices; what can move the model under one is the control lane (the transitions of a replica that is opening, and `discard` and `diverge`, which close the scheduler), which interrupts it at its next step: the scan goes back to the head of the lane, its generator is never resumed, and it starts over through `run()`, which pins the replica again (`start` answers 409 for another epoch) and checks the stamp. Whatever a settle put before a transition is in the cache when the transition's eviction runs, so eviction drops it, and a drop of the cache empties it. A pass is read at the state its scan started in: the scan's `run()` calls `scripts.begin()` (the `FillReader` a pass is given), and the fill reads `transitions` then, not when it queued the pass, so a transition queued ahead of the scan is the state the pass reads and one queued behind it, which the pump runs in the same slice before the fill hears of the scan's end, is not. A pass that recorded no miss is answered as it stands, whatever landed after it, so a `stage` posted behind an evaluation waits for it and the evaluation answers the state it ran on, and a stream of stages does not starve one; a pass that recorded a miss is run again, with no round, if a transition landed since, and a round is kept only if `transitions` still equals the scan's stamp. A pass that never calls `begin` (a test's, over an awaiting model) is taken to have begun when the loop started it and is checked against the counter at its end. A call that waits for a round answers with what a `stage` landing in it staged: the pass after the round reads the state it ends in. The call belongs to the replica its first scan starts on, which `run()` pins (`start` in `fill`) rather than the one it arrived on: a call that arrives while the replica is diverged, or before it is ready, waits in the model lane for the next one as any call does. That replica closed, replaced or diverged under it aborts the fill, takes its scan out of the lane and answers 409 `replica closed` (`replica is not ready` after a divergence); `{cancel: id}` aborts it, stops its batches (soft, then hard) and answers nothing. There is one `CellCache` for the service, emptied at `close`, a new `open` and a divergence, and `this.cells` is it where the host gave the service a script host, `null` otherwise. Without a script host a pass that needs a script run rejects 503 `no script host`; an evaluation that reaches no script is answered as ever. `transitions` is a counter that moves on every `stage`, `unstage`, `applyDelta` and delta of a tail whose `ChangeSet` names an entity, and on every drop of the cache: a fill keeps what a round answered only if it has not moved since the pass that asked for it began, which is what stops a result computed before a transition from entering the cache after that transition's eviction (the counter moves in the same synchronous step as the eviction). A transition that changed nothing moves nothing, so a round in flight across it is kept. A transition that is not `ready` evicts nothing and moves the counter when it names something. Eviction (`transit`) is the union of the touched keys of the state the transition leaves, over `wc.touchedIds()` and the delta's ids (the sets `LiveIssues` reads; a delta that moves nothing computes none) or, for a stage, over `touchedIds()` only when its ops delete something or it merges into a staged batch, and the keys of the state it makes, over its `ChangeSet`, which names the cascade: the contained elements and the incident relationships a delete removed. An entity gone from the state after is read from its committed image (`committedElement`, `committedRelationship`); one a staged batch created and a later stage deleted has none, and is in the state before. A transition whose `ChangeSet` names nothing evicts nothing, so a cell that depends on everything survives it; a transition that failed other than by leaving no trace (`OpError`, `SnapshotError`) drops the cache. `progress {task: 'scripts'}` sums the calls asked for and finished over every fill in flight, emitted at each batch result with `emit` (`progress()` holds until a slice ends, and a fill runs outside the pump), and ends `done === total` when the last fill ends, the count then starting anew; a fill of a replica that was dropped counts in no sum of the next replica, neither while it winds down nor once ended; an evaluation whose calls are all cached emits nothing.
  The issue store: when the tail makes the replica `ready`, the service compiles the rule sets of its `ArtifactSet` against the replica's metamodel — W from `ruleSources(set, 'working')`, C from `ruleSources(set, 'committed')` — builds a `LiveIssues` over its working copy holding them, and puts its sweep in the sweep slot, reporting `progress sweep` from `done` 0 to `done === total` for every run, a re-sweep's included, and nothing for a rescan's steps (their `SweepStep` says `rescan`; the scheduler's `BackgroundTask` hands `progress` what the steps yield); `close`, a new `open` and a divergence drop it with the replica. From then on `stage`, `unstage`, `applyDelta` and a ready replica's tail go through it, so each revalidates what it may have moved before it answers; while opening, `adoptStaged` and the tail go to the working copy alone, and the first sweep covers them. Rules follow the artifact methods, which stay `now` (a `now` method never interleaves with a transition, and every sweep or rescan step reads the rule sets as they are then): after `setArtifacts`, `putArtifacts` or `setStagedArtifacts` has moved the set, W and C are compiled again — each only when its sources changed, compared as the ordered `(id, name, parse)` of its rule sets, a parse by its document text or its first error — and handed to the store (`setRules`); a rescan it queued puts the store's steps back in the sweep slot. An artifact method that moved the set's `version` (`artifacts_version`, which the shell follows to re-page its tables), or the store's, posts one bare `changed` at once, both versions as they stand — a ready replica only: the first `changed` after `ready` carries the moves made before it. The compiles are kept with the store, so a replica opened again — after a rebind, under another metamodel whose drift differs — compiles afresh, though the artifacts outlive `close` and `open`. `issues_version` is a per-service counter that never goes back: it moves by what the store's `version` moved (a splice that changed the store's content, an applied delta, a rule-set change). A transition's `changed` carries it; at a slice's end, if it moved since the last `changed` posted — sweep or rescan steps — the service posts a bare `changed` (the current `rev` and `staged_version`, no ids, `structural: false`), which neither restarts the digest check nor counts as a transition. Three methods answer from the store, in the routes' bodies (`bodies.ts`): `getModelIssues {}` (`issueListBody`) and `previewCommit {base_rev, batch_ids, strict}` (`previewBody`, the model half, with C's rules alone, as the server's preview) are model-lane transitions that post no `changed` — they may probe, a rewind and replay, so they wait for a running scan and are never answered at its slice boundary, as a read would be; `validateModel {batch_ids}` is a transition that restarts the sweep, answered by a second one, queued once that sweep and any rescan have ended (`whenSwept`), that builds `validateBody` — refused 409 `replica is not ready` if the replica was closed, replaced or diverged meanwhile, or if a sweep or rescan step threw. None is answered while a rescan is due: a call that finds the store not `settled` waits for it (`whenSettled`) and then queues its answering transition, which checks `settled` again and waits again if an artifact method started another rescan in between; `close`, a new `open`, a divergence and a sweep or rescan step that threw refuse a waiting call as they refuse a waiting `validateModel`, 409 `replica is not ready`, which the shell answers from the server, and a cancelled one is never answered. Steps that threw leave the sweep slot with their ids still due; the next `getModelIssues` or `previewCommit` puts them back in it before it waits or answers from the store as it stands (as `validateModel` and a rule-set change always do), so no call waits on steps nothing drives and a stalled sweep does not leave the store short of `seeded` for good, while a step that throws again only leaves the slot until the next such read, moving no `issues_version`. Each refuses first, with 409, what the shell retries at the server: `stale base_rev` (`previewCommit`'s `base_rev` is not the replica's `rev`) and `stale staged batches` (`batch_ids` are not `staged()`'s ids, in order) — both checked in the transition that answers. An answer whose body probed anew (`live.probes` moved, with batches staged) restarts the digest check, since a probe rebuilds the committed images it walks; `getModelIssues` over a kept tag scope probes nothing. A probe whose replay cannot even put the staged batches back diverges the replica, and the call is refused 409 `replica is not ready`. A direct call reads the store as it stands, partial until the first sweep has ended. Two more answer under a candidate metamodel (`validation/candidate.ts`): `candidateIssues {metamodel}` (`candidateDiff` of the store against the working copy scanned under the candidate, with W compiled under it) and `previewCommit` with `rebind: {metamodel}` (`rebindPreviewBody` over the working copy scanned under the candidate, with C compiled under it; `would_block` always false). The second is the server's rebind preview where `stagedRefusal(wc, candidate)` is `null`: the server applies the staged ops under the candidate over the committed state, and the working copy applied them under its own metamodel, so a create of a type the candidate lacks or has abstract, a create or update naming a property the candidate does not give the entity's type (its type read from the batch's own creates, else the committed image), or any delete while a relationship type's containment differs between the two (the cascade may reach other elements) is refused as the server refuses the batch: 422 `Unknown element type 'X'`, `Cannot instantiate abstract type 'X'`, `'T' has no property 'p'`, or 409 `commit or unstage model edits before changing containment` for a delete (`stagedRefusal`, the first refusal in op order). Each prepares its candidate on arrival (`prepareCandidate`: an `UncheckablePattern` is 422 with its own text, naming the type, the property and the pattern; anything else it throws is 422 `metamodel: …`, as `open` answers a document `Metamodel.fromJSON` cannot read), then goes through `settled` — refusing as the others do, and checking `previewCommit`'s `base_rev` and `batch_ids` there — waits for the first sweep while the store is not `seeded` (`whenSwept`), and queues a model-lane scan of `candidateScan`. The scan's first step checks the call again, returns `MOVED` if the store is not `seeded` and `settled`, stamps the store as the probe caches it (the store itself, `rev`, `staged_version`, `rulesVersion`), prepares the candidate again if the rule sources moved, and refuses ops the candidate does not admit (`stagedRefusal`) before it scans; after its last step it compares the stamp: a store that moved, or has a rescan due, returns `MOVED`, and the call goes back through `settled` to wait and scan again. A transition that ran between the scan's queueing and its start is simply in the state it scans. So a rule-set change between its slices (an artifact method is `now`) is paired on both sides, never a fresh candidate with a stale store; a `close` or a divergence under it sends the scan to the lane's head and its `run()` finds the next replica's store, whose sweep it then waits for; a transition queued behind it (a stage, a delta) waits for it, as for any scan. The prepared candidate is kept across restarts while its layer's sources compile alike (`sameSources`). A cancel drops the call wherever it stands; the call is answered once.

The replay runs `buildRowsSteps` and `orderRowsSteps` drained, the core's `ValueError`s answered as the route answers them. `cell_text` records one page (`offset`, `limit`) of the core's cells in that order, with the step's `limits`, each as `cell_text` renders it, tagged; the replay renders `evaluateCellsSteps`' cells through `cellText`. `view` registers the element ids a view's nested folders place (`read._placed_element_ids`, the list the shell would register) and `drop_view` forgets them. `validate` runs `ValidationPipeline(default_validators())` over a scope — a list of ids, or `all_ids`: every element id in state order, then every relationship id — and records the issues as `IssueOut` bodies, which the replay compares as text with `validateScoped`'s; after a `rules` step it runs `pipeline_for` of the recorder's compile, and the replay passes its own. `rules` takes `(artifact_id, name, yaml)` sources, sorted by name then id as both sides compile them, and records `routes/rules.py::parse_result` per source, the compile's `rules_status` and each compiled rule's applies types and paths with the checks per type; the replay hands the sources in as committed rule-set artifacts carrying those parses, lists them with `ruleSources` and compiles them. `reach` records `expand_scope` over its ids. A `batch` or `undo` with `record_dirty` adds its `DirtyCollector`'s ids to its result, which the replay compares with the ids its own collector gathered; a `batch` with `expand` too records them widened by `expand_scope`, as `expand_dirty` widens them. `seed` gives the recorder a `Session` over its model, with the recorder's compile when a `rules` step ran, whose store the server's own sweep fills (`start_validation_sweep(sync=True)`); from then on every landed batch bumps `model_rev` and goes through `_finalize` as `POST /model/ops` does (reach widening included), a `rules` step lands as `POST /commits` lands a batch of rule-set ops alone — recompiled, `applies_population(old, new)` validated with the new rules and spliced, `model_rev` bumped — and `issues` records `routes/validation.py::list_issues`, `rules_status` included, which the replay answers from an `IssueStore` and a compile it keeps beside it, seeded and spliced the same way (`storeListBody`, `rulesStatusBody`). `preview` (with `strict`, the session's strict mode) and `validate_staged` send a step's ops to `routes/commits.py::preview_commit` and to the staged branch of `routes/validation.py::validate_model`, which apply, validate and roll back; the recorder holds both to leaving the model and the store as they were, and puts back any id a preview minted (creates carry `id` hints, so both sides name them alike). The replay clones the model into a `WorkingCopy`, gives it a `LiveIssues` seeded with a copy of its store and the compile as both W and C, stages the ops as one batch and answers `previewBody` / `validateBody`. `candidate` (`metamodel_candidate.json`, whose runs start from the smart-city model file, `replaySteps` loading `model_file` before step 0) diffs the store against the model under a candidate document with the rule sources recompiled for it, `candidateDiff` over `candidateScan`; `now_passing` is compared sorted by `candidateKey`, each store keeping its own order. `candidate.golden.test.ts` also replays it with the batch staged on a `WorkingCopy` over a swept `LiveIssues`, and with the rule set staged too, each under both hashes. `preview_rebind` (its second run) previews a rebind to a candidate ahead of staged ops, strict and not, and then over two batches the candidate refuses: the replay clones the model into a `WorkingCopy`, stages the ops as one batch and answers `rebindPreviewBody` over `candidateScan` with the committed rule sources recompiled for the candidate, compared in order — or, where the oracle recorded its 422, expects the same status and `stagedRefusal` to refuse; `test/service/candidate.test.ts` also answers each step through the service's `previewCommit` with `rebind`. `download` (`model_download.json`) is `GET /model/download`'s file: the replay drains `modelFileSteps` over a `WorkingCopy` of the model itself, or, with the step's `stage` ops, of a clone with them staged (the recorded file being the committed one all the same), and compares the joined parts with the UTF-8 of `result` byte for byte, a mismatch naming the first differing byte with the text around it on both sides. `insert_element` / `insert_relationship` put an entity in as committed state arrives (`Model.insert_element`), its type unchecked, so a scenario can hold a type its metamodel lacks. `engine/test/working/replica.golden.test.ts` feeds a `WorkingCopy` those deltas alone and expects the oracle's state, entity order included — through `ops_recreate` too (an entity created again under its id, unchanged in type and ends), which only the delta's `recreated_*` lists can express. `snapshot_v2` holds a snapshot text as the server encodes it, the texts no writer emits that the server reads alike (`same`) and the ones its decoder refuses in its own words (`refused`); `engine/test/snapshot/open.golden.test.ts` opens them all, cut into pieces as small as one byte. Every `observe()` of the golden runner computes its digest with the engine's own hash, so each fixture step holds it to `hashlib`. **Scripted scenarios** hold the answers of steps that run snippets (`nav_eval_scripted`): their steps carry `"scripted": true` and were recorded in a child process (`PYTHONHASHSEED=0`, `TZ=UTC`) whose Recorder has `TrustedRunner(deterministic=True)` (which pins the clock for the whole process, hence the child) and `Settings(snippet_sweep_sync=True)`, every step going to the child so a scripted read sees the model the steps before it left; a scripted step calls its route until the answer holds no pending cell, three times at most, and records that answer without `script_status` and `duration_ms`. `replayScripted(fixture, host, layer?)` (`test/golden/scripted-steps.ts`) is the async twin of `replaySteps`, built on `startReplay` (the same pieces, `begin` / `apply` / `fail` / `end`): a scripted `read` runs its evaluation through `evaluateFilled` with a `BatchRunner` over the Node host and a read-only bridge over the replay's model, the oracle's volatile keys dropped from the engine's answer too, and is compared as text like any read.
