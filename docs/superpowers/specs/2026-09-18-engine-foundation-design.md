# Engine foundation (sub-project A) — design

The first piece of the client-engine program (`architecture/program.md`): a standalone
TypeScript package that holds a model replica, applies ops with the server's exact
semantics, keeps a working copy, and is tested against golden fixtures generated by the
Python core. It runs in Node under vitest; nothing in the frontend or the server's
behaviour changes yet.

Contracts this design implements: CT-1 (snapshot v2), CT-2 (delta apply rule), CT-3 (state
digest), CT-5 (working copy), CT-7 (fidelity) in `architecture/contracts.md`.

## Goals

- `engine/`: value model, JSON parse and serialize, metamodel caches, record-graph store
  with indexes, mutation boundary, op applier with inverses, working copy, snapshot v2
  reader, state digest.
- Golden-fixture harness: scenarios driven through the real Python oracle, consumed by a
  generic vitest runner.
- Python side of the shared formats: snapshot v2 codec and state digest.
- Benchmarks at model M with the open budget of CN-3.

## Non-goals

- A worker, a `MessagePort`, the CT-4 message envelope, any frontend change (sub-project B).
- Navigation, search, tables, validators, rules, change-request diff/apply, metamodel diff,
  view validation (sub-project C).
- Views, the artifact family of the working copy, scripts.
- Metamodel YAML parsing and `check_metamodel`: the engine takes an already-validated
  metamodel as JSON; validity stays the server's job.
- A trigram or any other search index (AD-13).
- Minting real ids: the server mints them (CT-5.6).

## 1. Package

- `engine/` at the repo root: private ESM package `@data-rover/engine`, `exports` pointing at
  `./src/index.ts` (no build step), own `package.json`, `tsconfig.json`, `vitest.config.ts`,
  `eslint.config.js`, `.prettierrc`. Tool versions match `frontend/package.json`
  (TypeScript 6, vitest 3, eslint 10, prettier 3); prettier settings are copied verbatim
  minus the svelte plugin.
- `tsconfig.json`: `strict`, `lib: ["ES2023"]`, `types: []`, `moduleResolution: "bundler"`,
  `noUncheckedIndexedAccess`, `erasableSyntaxOnly` and `.ts` import specifiers
  (`allowImportingTsExtensions`), so Node can run the sources with type stripping and no
  build. The snapshot reader reaches the host's `TextDecoder` through a typed `globalThis`
  lookup in one file (`src/snapshot/utf8.ts`): a declared global collides with `@types/node`
  in the test project (`TS2300`, hidden only by `skipLibCheck` when it sits in a `.d.ts`) and
  would with the frontend's DOM typings in B. The hash writes its UTF-8 by hand. The compiler
  therefore enforces RC-4 (no DOM, no Node built-ins) for `src/`; `tsconfig.test.json` adds
  Node types for tests and benches.
- Inflating gzip is the host's job: the engine consumes inflated `Uint8Array` chunks.
- Layout:

  ```

  ```
- pixi, under the `frontend` feature with `cwd = "engine"`: `engine-install`, `engine-test`,
  `engine-check` (`tsc --noEmit`), `engine-lint`, `engine-format`, `engine-tidy`,
  `engine-bench`; under `core-dev`, `engine-bench-data` (`scripts/snapshot_v2.py`). `dr-test`
  depends on `engine-test`; `dr-tidy` on `engine-tidy`.
  `.gitignore` gains `engine/node_modules`.

## 2. Value model

| Python | Engine |
|---|---|
| `int` within ±(2^53 − 1) | `number` |
| larger `int` | `bigint` |
| `float` | `PyFloat` — a class holding one `number` |
| `bool` / `None` / `str` / `list` / `dict` | `boolean` / `null` / `string` / array / plain object |
| the strings `"Infinity"`, `"-Infinity"`, `"NaN"` | the same strings, as the oracle stores them |

- Invariant: `typeof v === 'number'` always means a Python `int`; a float is always a
  `PyFloat`, integral or not.
- `pyKey(v)` renders the canonical text of the uniqueness signature (`_frozen` in
  `core/model/indexes.py`): two values share a key exactly when their frozen forms are equal
  in Python — numerics collapse across kinds (`True == 1 == 1.0`, `-0.0 == 0`, a big integer
  equal to a float), a dict freezes to its key-sorted pairs (so `{}` equals `[]`). General
  Python equality (`pyEquals`) is sub-project C's need and is not built here.
- `pyRepr(s)` reproduces `repr(str)` (quote choice, escapes) for error messages.
- `cmpCodePoint(a, b)` orders strings by code point, not UTF-16 code unit.

### Parse

- Input is one line of CT-1 text. A regex pre-scan looks for a literal in value position
  that native `JSON.parse` would get wrong: a float (`\d+[.eE]`), an integer of 16 or more
  digits, a bare `Infinity` / `NaN`, or `-0` (an `int` 0 in Python, `-0` in JavaScript). A
  false positive inside a string only costs speed.
- No match: native `JSON.parse`, batched (many lines joined into one array parse). Every
  number it yields is a safe integer.
- Match: a hand-written exact parser for that line, producing `PyFloat`, `bigint`, and the
  bare literals `Infinity` / `-Infinity` / `NaN` as their source-text strings
  (`parse_model_json` parity).
- Exactness rests on one oracle fact: every float Python writes contains `.`, `e` or `E`.
- Measured on model M (Node 22, one pass): 18.5 % of lines take the exact path, none of them
  a false positive; line-routed parse 1.49 s against 2.50 s for an exact parse of the whole
  document and 0.59 s for the inexact native one; parse → serialize reproduced all 297,160
  lines byte for byte.

### Serialize

- `pyDumps(value, {indent})` reproduces `json.dumps(..., ensure_ascii=False, allow_nan=False)`
  with compact separators or `indent=2`, insertion key order, Python's float `repr`
  (`5.0`, `1e+16`, `1e-07`), Python's string escapes. A non-finite `PyFloat` throws.
- Test: parse → serialize is byte-identical for every line of the model M snapshot.

## 3. Metamodel

- `Metamodel.fromJSON(doc)` takes the `GET /metamodel` shape: `enums`, `elements`,
  `relationships` with `PropertyDef`, `Mapping` and the `source`/`target` shorthand already
  normalized by the server. Immutable; every cache is built in the constructor.
- Ported lookups, same names in camelCase, same results: element and relationship type by
  name (first name wins), ancestor chains (self first) and sets, subtype tests, effective
  properties (inherited first; on a name clash the ANCESTOR's definition stays — that is what
  the oracle's `_effective_props` does, whatever its comment says) and effective
  property-name sets, effective key (the nearest declared one wins; `[]` is declared) and
  `KeySpec` (`out:`/`in:` DSL), `isContainment` (any ancestor's flag), end constraints (with
  the never-violatable `0..*` filter), descendants, relationship types from / to.
- `Multiplicity.parse` (`n`, `lo..hi`, `*`), memoized.
- `extends` cycles are tolerated exactly as the Python caches tolerate them.

## 4. Store — the record graph

- `ElementRec {id, typeName, props, rev, ord, out: RelRec[], in: RelRec[], parents: RelRec[]}`
  and `RelRec {id, typeName, source: ElementRec, target: ElementRec, props, rev, ord}` are
  fixed-shape class instances. `parents` holds the containment relationships whose target is
  this element, in relationship-insertion order; the first one is the owner. Containment
  parent = relationship source. Records also carry index-owned bookkeeping: `uniq` and
  `rootName` on `ElementRec`; `outAt` / `inAt` on `RelRec`, its positions in `source.out` and
  `target.in`, so that removing an edge is O(1) on any degree.
- `ord` is a monotonic insertion sequence, sparse after churn; only its order matters.
  Entity order is state (CT-1). Iteration in state order is `Map` order, which is correct
  until a record is restored with an older `ord`; the store then re-orders the `Map` lazily,
  once, before the next ordered iteration.
- Adjacency arrays have unspecified order, as Python's sets do. Anything observable sorts.
  `debug/shuffleAdjacency` randomizes them in tests to expose a hidden dependence.
- Global indexes, maintained at the mutation boundary and rebuilt by `rebuildIndexes()`:
  by id (elements, relationships), by exact type, uniqueness, references, root order.
  - **Uniqueness**: key = `(typeName, owner id | null, signature)`; signature is the key-spec
    values (property values, then per relationship key the sorted endpoint ids of
    exact-type edges) or, for a type without a key, all properties. Groups are keyed by a
    hash of `pyKey(key)`; membership is confirmed with exact equality so a hash collision
    never fabricates a duplicate. Re-keyed on create, property change, containment-parent
    change, delete.
  - **References**: forward `entity → target ids` and reverse `target id → referencer ids`,
    for properties whose datatype is an element type; scalar or list of strings; a dangling
    target stays indexed.
  - **Root order**: sorted array of `(displayName, id)` with `cmpCodePoint`, binary-search
    insert and remove. `displayName` ports `core/model/naming.py` exactly (exact-case `name`
    first, then case-insensitive, list values contribute their first non-empty string, id
    fallback).
  - Per-type adjacency counts are computed from the arrays on demand; no counter index.
- `Model` mirrors the Python mutation boundary: `createElement`, `restoreElement`,
  `getElement`, `getRelationship`, `setProperty`, `deleteProperty`, `connect`,
  `restoreRelationship`, `disconnect`, `deleteElement`, `relationshipsFrom`,
  `relationshipsTo`, `containerOf`. `createElement(typeName, id)` and
  `connect(relType, sourceId, targetId, id)` take the id from the caller (the engine never
  mints one) and refuse one in use; `restoreElement` / `restoreRelationship` take an optional
  `ord` that puts the record back at its old place in state order. Committed state — a
  delta's entities, a rewind's before-images — enters through `insertElement` /
  `insertRelationship` / `overwrite`, which check no type (a model may hold one its metamodel
  no longer has) and take `rev` as given; `restore*` validate and delegate to them.
  - `setProperty` always bumps `rev`, same value included; `deleteProperty` of an absent key
    is a no-op. Values are replaced wholesale, never mutated in place.
  - `deleteElement`: contained children first (disconnect the containment edge, recurse,
    visited-set guard), then every remaining incident relationship, then the element.
  - An id is unique across elements and relationships.
  - A property key that is a canonical array index (`"0"`, `"42"`) cannot keep its insertion
    order in a JavaScript object. Bulk load rejects an entity carrying one, at any depth of
    its properties (`SnapshotError`); no metamodel in use declares such a name.
  - `ModelError {kind: 'key' | 'value', message}`; message text equals the oracle's
    (`No element with id 'x'`, `'T' has no property 'p'`, …). Fixtures assert it.
- Bulk load is non-strict like `build_model_from_dicts(strict=False)`: unknown types load.
  A duplicate id (across both kinds — stricter than the oracle, whose loader checks each kind
  alone), a `tmp_`-prefixed id, an abstract element type or a relationship with a missing
  endpoint is a `SnapshotError`, with the oracle's text where the oracle has one.
- `debug/dumpIndexes(model)` renders the canonical, sorted form the oracle dumps;
  `debug/verifyConsistent(model)` compares incremental indexes with a fresh rebuild, which it
  performs in place (a consistent model is left as it was).

## 5. Ops

- Op types mirror the model family of `src/data_rover/api/schemas.py` (`create_element`,
  `update_element`, `delete_element`, `create_relationship`, `update_relationship`,
  `delete_relationship`), including the optional `id` hint.
- `applyBatch(model, ops, {restore, idFor})` reproduces `routes/ops.py::_apply_batch`:
  - create: inverse (`delete_*`) recorded before the property loop; properties set one at a
    time, so an undeclared key fails mid-create and rolls back; `temp_id` must carry `tmp_`
    unless `restore`; a taken or reserved `id` hint fails.
  - update: patch keys checked up front; merge-patch at depth 1, `null` deletes; inverse is
    one update restoring prior values (`null` for keys that did not exist).
  - delete element: cascade snapshot before mutation — containment closure, and per closure
    element `sorted(outgoing) + sorted(incoming)` relationship ids; inverse unit recreates
    elements first, then relationships.
  - temp ids resolve through `idMap` in `source_id`, `target_id` and in property values
    (strings and lists of strings); an unknown temp id passes through.
  - `BatchResult`: `idMap`, first-touch-ordered changed and deleted id sets kept disjoint,
    first-touch before-images, inverse units, `inverseOps()` (units reversed, each unit front
    to back).
  - failure: the rollback is EXACT — `rewind(model, result)` puts every touched entity back
    from its first-touch before-image (properties, `rev`, `ord`), where the oracle's
    `_rollback` replays inverse ops and leaves `rev` bumped and restored entities last
    (`BACKLOG.md` `K-30`). A record that outlived the batch still has its image's `ord` and is
    rewritten in place; anything else under a touched id is removed, and the image inserted at
    its old `ord`. Then `OpError {status: 422, detail}` with the oracle's detail text, the
    quote-stripping of `_error_detail` included (`No element with id 'ghost`).
  - an op carrying an array-index property key, at any depth of `properties` or
    `properties_patch`, is refused like any other bad op (422, its own text).
- `idFor(tempId)` decides the id of a created entity: the identity in production (staged
  entities are keyed by their temp id); a `SequentialIdGenerator` mimic in fixture tests. It is
  called once per minted entity, in op order, never for a hinted or a reinstated one.

## 6. Working copy

- `WorkingCopy` owns a `Model`, the committed `rev` and digest, the staged batches, and
  `committedImage: Map<id, record image | null>` — the first before-image of every entity any
  staged batch touched. Committed reads are served from it; everything else reads the model.
- One mechanism, `rebase(change)`: rewind every staged batch (newest first) → run `change`
  → replay the remaining batches in order → park any batch that fails as a conflict
  (`conflicts()`), never drop it silently.
- `stage(ops)`: `applyBatch` in place with the identity `idFor`; returns the change set.
- `unstage(selector)`: `'all'`, `{batch}` (staged or parked), or `{entity, incident?}` — the
  staged ops that target the entity and, with `incident`, every staged relationship op with
  it at one end (the frontend's `revertStagedFor` / `revertStagedForElement`). A `rebase` that
  edits the staged list; a batch left empty disappears. A parked batch is not retried.
- `applyDelta(delta, own?)`: CT-2 apply rule (`prev_rev` equal → apply; `rev` not newer →
  ignore; otherwise report a gap). Inside the rebase: delete relationships, delete elements,
  upsert elements, upsert relationships. Records keep identity and `ord`; new ones append.
  Committed changes bypass the mutation boundary and take the server's `rev`. An entity that
  arrives under another type or other ends than the replica's record was deleted and created
  again within the commit (an apply-CR rewire): it is removed and appended, as the server's
  dict did; a re-creation that changes neither keeps its place (`K-31`). The delta's entities
  are read with the bulk loader's checks before anything moves (`SnapshotError`). The digest
  is updated per entity — the `(id, rev)` hash is injected as `entityHash` until plan 4's
  SHA-256 — and compared with `delta.state_digest`; a mismatch, or a delta that does not fit
  the replica, sets `diverged`.
  For an own commit, `own = {batchIds, idMap}` drops those batches and remaps temp ids in the
  rest (ids, endpoints, property values) before replay.
- Every operation returns a change set (element and relationship ids changed or deleted);
  sub-project B turns it into the CT-4 `changed` event.

## 7. Snapshot and digest

- `openSnapshot(chunks: AsyncIterable<Uint8Array> | Iterable<Uint8Array>, metamodel,
  onProgress?, options?)` → `{header, workingCopy}`: decode UTF-8, split lines across chunk
  boundaries, validate the header (`format`, counts), parse and bulk-load in order,
  `rebuildIndexes()`, check the counts, adopt `rev` and `state_digest` — adopted, not checked.
  - Decoding is `fatal` (a replacement character would be invisible to the digest; the server
    raises on the same bytes) and keeps a byte order mark, which then fails the format check.
    Lines are cut on LF alone; a CR before it stays on the line, where JSON reads it as white
    space. Like the server's reader, it takes a last line without its LF and CRLF line ends.
  - Whatever does not start with `{"format":"datarover.snapshot/v2"` is refused at its first
    bytes (`not a datarover.snapshot/v2 snapshot`): a v1 document is one endless line.
  - Header: the counts are checked as the server checks them, in its words (`snapshot v2
    header carries no valid entity counts`; a count past 2^53 is a `bigint` here and refused,
    where the server takes it — a documented gap). `rev`, `state_digest` (16 lower-case hex
    digits), `project_id` and `metamodel_id`, which the server's decoder never looks at, are
    refused in the engine's own words.
  - Lines are parsed and loaded 2,000 at a time through `parseLines`, the first `elements` of
    them as elements; `onProgress(done, total)` follows every batch. Every line is counted, a
    line past the promised ones is not parsed, and the count is checked BEFORE the last batch
    is parsed, so a text cut inside a line gets the server's answer (`snapshot v2 holds N
    entity lines, its header promises E + R`), not a JSON error.
  - `parseLines` refuses a batch that parses to another count than it has lines: the join
    trick lets a line holding two documents through (the server loads one entity more than
    its header promises; the engine would have dropped the last document). The reader names
    the line (`snapshot v2 line N: …`). Every refusal is a `SnapshotError`.
- `h(id, rev)` = the first 8 bytes of SHA-256 over `utf8(id) ‖ 0x00 ‖ ascii(decimal rev)`;
  the digest is the XOR over all entities, 16 lower-case hex digits. SHA-256 is implemented
  in pure TypeScript (WebCrypto is asynchronous). CRC32 is rejected: it is linear, so an
  XOR fold cannot see two same-length ids exchanging `rev`s.
- `WorkingCopy.verifyDigest()` recomputes the digest from committed state — the model's
  entities, with the committed image standing in wherever a staged batch has been — sets
  `diverged` on a mismatch and returns the verdict; B runs it after `ready`. The engine's
  `entityHash` is `WorkingCopy`'s default; the option stays, for tests.
- Python: `snapshot_codec.py` gains `encode_snapshot_v2` / a v2 branch in `decode_snapshot`
  (header sniffed from the first line); a new `api/state_digest.py` holds `entity_hash` and
  `model_digest`. The server's writers keep emitting v1 until B.

## 8. Golden fixtures

- `tests/golden/`: scenario modules plus a driver. A scenario builds a metamodel and an
  initial model with `SequentialIdGenerator`, then runs steps against the real oracle —
  `Model` methods directly, op batches through `routes/ops.py::_apply_batch`, undo through
  `inverse_ops()` in restore mode. After every step the driver records the op result
  (`id_map`, changed, deleted, inverse ops) or the error detail, the digest, and a
  fingerprint (SHA-256) of the model's v2 lines plus the canonical index dump; every n-th
  step, and the last, carries the lines and the dump themselves, and a step that changed
  nothing says so (`tests/golden/model_steps.py`).
- An op batch is applied to a deep copy of the oracle's model, kept only when the batch
  lands, so the oracle's inexact rollback never enters a fixture. Ops, before-images, inverse
  ops and changed entities travel as lines of the server's compact JSON text; the changed
  entities and deleted ids of each landed batch are the delta a replica test follows
  (`ops_batches`, `ops_churn`; `ops_recreate` is kept out of it, see `K-31`).
- Output: `engine/fixtures/golden/<scenario>.json`, committed. `pixi run golden-fixtures`
  regenerates. `tests/golden/test_fixtures_current.py` regenerates in memory and fails on any
  difference, so `core-test` guards against drift (the repo has no CI).
- Scenarios: metamodel caches (inheritance, overrides, keys, containment inheritance, end
  constraints, descendants, from/to, a tolerated cycle); every mutation with its error
  text; cascades (nested, diamond, cyclic, parallel edges); indexes after churn (unicode
  and astral names in root order, order after restore, uniqueness with and without keys,
  owner change, bool/int/float collisions, scalar, list and dangling references); op batches
  (temp ids in properties, id hints, restore mode, mid-batch rollback, first-touch order,
  same-value set); values (big ints, a seeded table of doubles with their `repr`, infinity
  tokens and bare literals, `NaN`, escapes); the smart-city example (load, index dump,
  digest); snapshot v2 round trip.

## 9. Tests and benchmarks

- Golden runner: loads each fixture, replays its steps through the engine with the
  sequential `idFor`, compares state, index dump, digest, results and errors.
- Unit tests: value layer, comparators, `pyRepr`, SHA-256 vectors, line splitter, parser
  pre-scan false positives.
- Working-copy invariants over seeded random op sequences (no oracle exists): stage then
  rewind reproduces the initial dump byte for byte, entity order included; rebase over a
  delta equals replaying the staged ops on a fresh replica; `verifyConsistent` holds after
  every step. Adjacency is shuffled in every test run.
- `engine-bench` at model M (`benchmarks/`, generated locally; a Python script converts
  `large.model.json` to v2): v2 open against the whole-document baseline in the same pass
  (AD-11), heap after GC, a 1,000-op batch, a rebase with 100 staged ops, a delta apply.
  The heap is weighed right after the open and before the document is read: V8 keeps the
  last text a regular expression ran over reachable. The bench checks itself — a replica
  off its digest stops the run. Measured 2026-09-18: open 2.30 s of 3 s, the same model as
  one document 3.14 s (2.26 s of it the exact parse), 231 MB of heap for one open replica.

the last:
