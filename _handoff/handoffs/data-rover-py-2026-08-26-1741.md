## Standing Constraints
- Memo is created INSIDE each public pass (`build_rows_ex`, `order_rows`,
  `evaluate_cells`) and is never a parameter of any public entry point —
  `/tables/evaluate` runs build+sort under `ScriptEvalContext.cache_only=True`
  then the window live; a shared memo would serve pruned/pending chains to
  the live pass. The plan pins this with an `inspect.signature` test.
- Navigations containing a `ScriptStep` bypass the memo (`NavMemo.scripted`)
  — their `evaluate()` calls have per-call side effects (`pending_misses`,
  warning deltas) a cache would skip.
- Thread `memo=` explicitly through the helpers, exactly like `script=` is
  threaded today — no ContextVar, no module global (the codebase's stance:
  per-request objects are explicit; see CLAUDE.md "construct one pipeline
  per request/thread").
- Store `tuple(result.chains)` + `truncated` in a frozen `MemoEntry`, never
  the `ChainResult` — consumers only iterate; an aliased mutable list would
  corrupt sibling rows.
- LRU bound `max_entries=64`: split rows are contiguous in build order so
  build/sort need one live entry; the window pass is <= 500 rows
  (`MAX_LIMIT` in `frontend/src/lib/state/table-editor.svelte.ts:86`).
- Key on `id(col)`; valid only because the pass owns the live `defn` for its
  whole duration. Document it in the module docstring (plan does).
- Commit messages end with the two trailer lines used in this repo (see the
  plan's commit steps).
- Dead end already ruled out this session: the frontend
  (`ColumnSourceEditor.svelte`, `TableGrid.svelte`, `ValueCell.svelte`) and
  `routes/tables.py` render exactly what the core returns — do not look for
  the original bug or the slowdown there.

## Known Issues, Not Yet Fixed
- The O(rows x fan-out) re-navigation described above — this is what the
  plan fixes. `src/data_rover/core/table/evaluate.py:213-235` (step-index
  branch) and `:328-362` (`_navigation_step_elements`).

  only (the expand slot carries no owner), so two elements reached with EQUAL
  values share step elements across their two rows — an over-approximation,
  documented in its docstring at `evaluate.py:336-347`. Accepted, not
