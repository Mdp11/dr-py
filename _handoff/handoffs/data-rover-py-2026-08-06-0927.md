## Standing Constraints
- **Approach 1 — one journal, materialized heads** — chosen over full event sourcing (rewrites hydration/snapshots) and federated per-type streams (no total order, no atomic cross-content commits). Do not relitigate; rationale in the spec.
- **Artifacts adopt the full lock→edit→commit flow** (user decision) — not instant-save-with-lock; history/diffs fall out of the journal.
- **Elements keep BARE lock resource ids; only new types get prefixes (`art:`, `folder:`, `mm`)** — the existing frontend lock badges key on element ids and must keep working.
- **The model applier (`routes/ops.py::_apply_one`) never receives an artifact op** — enforced at type-check time by the `ModelOpIn`/`ArtifactOpIn` split plus `assert_never`. Any frontend-driven backend change must preserve that.
- **`/model/ops` and `POST /model/validate` reject artifact ops permanently** — artifact edits go through `POST /commits` or legacy `PUT /artifacts` only.
- **The lease, not OCC, is the real concurrency control for artifacts.** `UpdateArtifactOp.artifact_rev` is an OPTIONAL precondition the client contract currently omits, so an editor that does not hold `art:<id>` gets last-writer-wins. The frontend MUST acquire the lease at edit start.
- **Plans are written one phase at a time, after the previous phase lands** — later phases need real code to reference. This is why only the Phase 1 backend plan existed.
- **The plan's own sample code is not trustworthy.** Across the 9 executed tasks, review found real defects in the plan's snippets in 6 of them, including one Critical. When you write the next plan, mark sample code as illustrative and tell the executor to follow intent over transcription.
- Execution discipline that worked and should be repeated: subagent-driven development, one task per commit, a task review after every task, a fix round for every Critical/Important, then one whole-branch review with a single fix wave.

## Known Issues, Not Yet Fixed
All diagnosed (verified by review), all deliberately deferred. The first three bear directly on the frontend plan:
- `src/data_rover/api/routes/commits.py:~520` — the empty-batch early return **skips the lock-token release step**, so an empty `POST /commits` carrying `lock_tokens` orphans those leases until TTL (300 s). The client's `commitStaged` clears its lease registry on any 200. Unreachable today (the UI disables Commit at `total === 0`); the frontend plan must not send one, or the backend must release first.
- `UpdateArtifactOp.artifact_rev` is optional and no client sends it → **no OCC on the commit path** (see Standing Constraints). Related: `artifact_rev` is NOT restored by apply-then-inverse (a recreated row restarts at 1), an ABA hazard for a client holding a pre-delete rev. Fix these two together if OCC is ever turned on.
- `src/data_rover/api/locking.py:~238` — `peer_leases` ignores lease MODE, so a peer's SHARED pin 409s a legacy PUT/DELETE that the conflict matrix would allow. Fail-safe direction; nothing takes shared `art:` pins today.
- `locking.verify_held` compares MODE only and never reads `RequiredLock.intent`, so an EDIT-intent exclusive lease satisfies a DELETE op at commit time. **Pre-existing Phase-4 behavior**, inert for artifacts; revisit when Phase 2's folder/containment pins land.
- `clone_project` silently drops all artifacts (`src/data_rover/api/routes/projects.py:~126-167`) — **Phase 3** fixes it.
- Root-level `View.artifacts` are dropped on API round-trip (`src/data_rover/api/schemas.py`, `ViewOut`/`ViewIn`) and `validate_view` never warns on dangling artifact refs — **Phase 2** fixes both.
- Task 7's completeness guard assumes no commit row can exist above this instance's `model_rev` — true single-instance only; same debt Phase 7 (Redis lock mirroring) already owns.
- Smaller, all cosmetic or unreachable: the `IntegrityError`→422 catch is type-scoped not constraint-scoped; the empty-commit response returns `commit_id=""`/`message=""` even when a message was supplied; `_artifact_diffs` deserializes both op lists even for artifact-free commits; the top-level `id` of update/delete artifact ops is not resolved through `id_map` (so `[create tmp_x, update tmp_x]` 422s — asymmetric with the model applier, but fails loudly); `ARTIFACT_OP_KINDS` (strings) and `split_ops` (isinstance) are two membership sources that will drift; the 5-member artifact-kind `Literal` is restated in two schema sites, neither derived from `ArtifactKind`; `LockTable.active_leases` iterates without the write mutex (pre-existing, `GET /locks` already does it).
