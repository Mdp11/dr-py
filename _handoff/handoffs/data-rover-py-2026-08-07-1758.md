## Standing Constraints
- **Frontend only.** The backend is done and merged; if a backend change seems needed, STOP and surface it — that is a scope change, same rule Phase 1's frontend plan used.
- **The wire contract is fixed and was designed for this plan to mirror.** Do not rename anything. Ops (`api/schemas.py`): `create_folder {temp_id, parent_id, name, index?}`, `rename_folder {id, name}`, `move_folder {id, to_parent_id, index?}`, `delete_folder {id}`, `place_element {element_id, folder_id, index?}`, `remove_element {element_id, folder_id}`, `move_element {element_id, from_folder_id, to_folder_id, index?}`, `place_artifact {artifact_id, artifact_kind, folder_id, index?}`, `remove_artifact {artifact_id, folder_id}`, `move_artifact {artifact_id, from_folder_id, to_folder_id, index?}`. Lock `type: "folder"`, resource prefix `folder:`, commit scope string `"view"`.
- **Element placements never target the root.** `VIEW_ROOT_ID = "root"`; an unplaced element renders at root, so "move to root" is `remove_element`, and placing an element at root 422s. Artifacts DO have a real root list and may sit in many folders (at most once per folder) — `folder:root` is a genuine lease target.
- **Folder ids, not name paths.** `Folder.id` is a uuid4 hex, assigned lazily server-side. This is what fixes the long-standing view-change-tracking caveat where a rename read as delete+create (spec:73).
- **`index` is carried on placement ops but sibling-FOLDER order is not user-controlled** (the tree renders alphabetically). Element order inside a folder IS user-meaningful. The backend concretizes `index` regardless so inverses restore byte-identical blobs — the client should send what the user did and not try to be clever.
- **No per-op OCC precondition.** The lease is the concurrency control, exactly as the client already treats `UpdateArtifactOp.artifact_rev` (Phase 1 Decision 3). Do not send a rev precondition on view ops.
- **Never send an empty commit** (Phase 1 Decision 6) — the backend's empty-batch early return skips lock release and orphans leases until TTL.
- Frontend commands must run through the pixi tasks (they set `cwd=frontend`); a bare `pixi run -e frontend npm test` fails with "Missing script".
- New public stores/API functions MUST be added to the `lib/state/index.ts` / `lib/api/index.ts` barrels. Zod schemas in `types.ts` are `const`s — a forward reference throws at module init (TDZ).
- Preserve the dense invariant comments in files you touch; extend in the same voice.

## Known Issues, Not Yet Fixed
- **`routes/locks.py`'s `expand_targets` degrades against a cold `session.view`** (`src/data_rover/api/routes/locks.py:84`): if `session.view` is `None` at `POST /locks` time, a DELETE-intent folder lease does not expand over the subtree, so the granted token is NARROWER than the holder believes and `GET /locks` under-reports. Two independent reviewers judged it safely deferrable — `create_commit` and `undo` both re-derive and verify against the resolved view, so the failure mode is a false 409 for the holder, never a silent stomp. Backend follow-up, not this plan.
- **`DELETE /view` clears `session.view` but leaves `ViewRow`**, so eviction resurrects the view (`src/data_rover/api/routes/view.py:115-118`). Pre-existing, deliberately out of scope. NOTE: the previous handoff claimed this route was unused by the frontend — that was WRONG. It is wired to a live button (`frontend/src/lib/components/Sidebar/ViewSelector.svelte:20` via `dropView`). It is no longer a data-loss path (commit/undo now hydrate from the durable row), but the frontend plan should decide what this button means once view edits are commits.
- **`create_commit` is ~300 lines with four near-identical unwind blocks** (`src/data_rover/api/routes/commits.py`). The final reviewer called it the most fragile function in the API package; the backend plan mandated the inline form. Worth refactoring before Phase 3 adds a fourth content family. Backend, not this plan.
- **Pre-existing flake**: `tests/model/test_search_index.py::test_string_properties_indexed_non_strings_ignored` fails ~0.8% of runs — it queries `"123"` while the element's own uuid7 id is trigram-indexed, so an id coincidence trips it. Unrelated to any of this work; re-run and move on. A real fix = query a string the uuid7 alphabet cannot produce.
- **Carried forward from the Phase 1 FRONTEND session, and these belong to THIS plan**: the denied-checkout editor is still typeable (user can type into an artifact editor whose lease was denied, then discover it cannot save), and there is no "Save as…" alternative offered on a denied tab. Same UX question will now apply to a denied folder lease.

## Deferred — Do Not Do
- **Retiring `PUT /view/snapshot`** — the spec's migration-window stance: it retires AFTER this frontend plan lands, as a separate backend cleanup. Keep it working for the whole of this plan.
- **View-scoped feed events for the legacy PUT** — peers still do not see legacy-PUT view changes live (pre-existing). The commit path's `scope: ["view"]` is the go-forward signal; deferred in the backend plan.
- **Renaming the view itself / multiple named views** — there is deliberately no op for `View.name` (the legacy PUT can still set it), and no UX ask for N views. Spec-deferred.
- **Revert across view ops** — the backend answers a clean 409 by design, the same boundary Phase 1 drew for artifacts. Do not build UI that implies otherwise.
- **OCC on view ops** — no per-op rev precondition, by decision (see Standing Constraints).
- **Phase 3 (import/export closure) and Phase 4 (metamodel lease + diff)** — separate plans; Phase 4 is independent and may be reordered.

## Open Questions
1. **What does the DnD gesture lease?** A drag that moves an element between folders needs EXCLUSIVE on both folders; the backend derives that itself at commit time, but the client must acquire *something* at drag start for fail-fast UX. Whole-subtree at drag start, or just the two endpoints? Watch the known `endGesture`-before-mutator ordering trap in `frontend/src/lib/components/Sidebar/ContainmentTree.svelte:1162`.
2. **When is a view edit staged vs committed?** Phase 1 chose "Save = stage, commit = DiffDrawer". A folder drag has no Save button — does every DnD drop stage an op silently into the commit batch (so the sidebar becomes dirty-until-commit), or does the view keep an autocommit feel? This is the biggest UX decision in the plan and it changes the whole task breakdown.
3. **What happens to the `DELETE /view` button** (`ViewSelector.svelte:20`) once view state is committable — remove it, turn it into a staged "delete all folders" batch, or leave it as the last legacy writer?
4. **Does this plan also fix the two carried-forward Phase 1 UX gaps** (denied-checkout editor still typeable; no "Save as…" on a denied tab), now that folder leases raise the same question, or do they stay deferred again?
