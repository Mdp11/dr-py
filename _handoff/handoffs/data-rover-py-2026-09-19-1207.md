## Standing Constraints
- **B's four owner decisions (2026-09-19), now in `architecture/`:** the store forks and the legacy half lives until F (AD-24 — server reads are committed-only, so server mode needs the overlay; one staged state must exist before C evaluates over it); the workspace blocks on the replica, no hybrid warm-up (AD-25); the 16 ms rule binds evaluation and background work, a transition is atomic under ≤ 100 ms per 1,000 ops at M (AD-23, CN-3); neighborhoods are out of B (no production caller, no graph view exists).
- **Plan 1 design choices and their reasons (spec §1):**
  - Rollback follows `rewind.ts`'s four-pass order, NOT reverse first-touch order — that can re-insert a relationship before its endpoint exists.
  - `recreated_*` are SEPARATE lists, not ids named in both `deleted_*` and `changed_*` — the frozen legacy store's `applyDelta` must be able to ignore them.
  - `prev_rev` is not stored on `Commit` — journal rows are contiguous and the tail route refuses a hole; only `state_digest` gets a column.
  - `/model/ops` and `/model/undo` stay silent on the feed — a replica heals through the `prev_rev` gap and the tail, and B's tests use that to exercise gap recovery.
  - Before-images enter the Python model only through new committed-state methods on `Model` (twins of the engine's `overwrite` / `insert*`), RC-8.
- **Dict order repair — a hazard found while designing, not in the spec:** read routes and table evaluation iterate `model.elements` WITHOUT `write_mutex`. An in-place `clear()` + `update()` shows them an empty dict between the two steps; building the ordered dict and rebinding the attribute is atomic, but first check for long-lived aliases of `model.elements` / `model.relationships` (`build_rebind_view` aliases them; `IndexSet` goes through `self.model`). The plan must pick one deliberately.
- **Measure the order repair at M before the plan is approved; if it is slow, ASK before optimizing** (standing rule across A and B: measure first, optimize only on a missed budget and only after asking).
