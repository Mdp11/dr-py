## Open Questions

1. **Callback or promise API?** `ConfirmDialog` today is callback-based
   (`onConfirm: () => void`) and every call site is a synchronous
   `if (!window.confirm(...)) return;`. Two routes:
   - **(a) Restructure each site** into "open the dialog → continue in `onConfirm`".
     Faithful to the component as built; nine separate restructurings, each adding
     a `$state` flag and a mounted `<ConfirmDialog>` to that component's markup.
   - **(b) Add a promise-returning imperative helper** (e.g. a
     `confirm({title, description, ...}): Promise<boolean>` backed by one
     app-level dialog instance) so call sites become
     `if (!(await confirm({...}))) return;` — a near-mechanical edit at all nine.
     More infrastructure up front, far less churn, and it is the only shape that
     rescues `TopBar` cleanly.

   Recommend **(b)**, but this is the user's call — it is an architectural
   addition, not a refactor.

2. **`TopBar.svelte:79-86` may not be convertible without a behaviour change.**
   `confirmDiscardChanges(message): boolean` returns a synchronous boolean and its
   caller `goHome()` uses it to gate a `goto(...)` navigation. Making it async
   changes `goHome` into an async flow. Confirm with the user that a one-frame
   delay before navigation is acceptable. (Checked: there is no `beforeunload`
   handler anywhere in `frontend/src/lib`, so nothing here is trapped by a browser
   API that genuinely requires a synchronous answer — the constraint is stylistic,
   not technical.)

3. **Should the rollout include tests per converted site?** The existing sites have
   no tests around their `window.confirm` guards. Adding one per site is real work;
   converting without tests means the gates are unverified. Ask which the user wants.
