## Standing Constraints
- **Engine = Rust → wasm32 (browser) + native (headless).** User decision: "We need to minimize costs, so rust it is", made AFTER I recommended TypeScript. Do not relitigate.
- **One engine, two hosts.** User: headless is essential (`GET /exports/run-by-name` for CI). Every surveyed product that split engines regretted it (Excel's client calc is officially an "estimate").
- **User scripts stay Python in Pyodide, facade unchanged.** User prefers Python; measured: 10k script cells = 1.7 s in-process Python store vs 2.7 s over a JS or Rust store with a naive JSON bridge (≈270 vs ≈165 µs/call); the store's language is irrelevant (2.74 vs 2.73 s) — the cost is Python-side JSON + FFI. So the Rust design needs a **batched / non-JSON bridge** and can use parallel script workers (replica is small). JS-language scripts would be ~11 ms but were not chosen.
- **"80 MB is normal"** = `benchmarks/large.model.json`: 170,340 elements / 126,820 relationships, compact JSON, 5.83 MB gzip-3. 320k elements is the stress size. Must feel fast at the normal size.
- **Pure web app; GCP ≈ $130/month for 20–30 concurrent users, scalable with budget.** Research: thin server ≈ $65–100/mo (Cloud Run 1 vCPU min=max=1 + Cloud SQL db-g1-small ≈ $90, or single VM ≈ $65); today's server-heavy design realistically $280–355 and RAM-bound (≈1.4 GB per hot 80 MB project: 0.5 GB model+indexes + 0.9 GB trigram index). An open WebSocket keeps a Cloud Run instance billed; 60-min WS cap ⇒ clients must reconnect; in-process locks/feed force max-instances=1 until moved to Postgres/Redis. Skip CDN/LB ($18.25/mo fixed) — egress is ≈ $2/mo.
- **Shape common to all options (already presented, not yet formally approved section-by-section):** browser holds full replica (snapshot straight from GCS signed URL + journal tail + WebSocket deltas) with the STAGED overlay inside the engine, so every evaluation sees committed + staged (fixes "commit first"); server never loads a model — commit gate is O(batch) against Postgres head rows (FKs for dangling refs, ancestor CTE for containment cycles), server derives inverse ops / `entity_states` itself (never accept client-supplied inverses: undo/revert/diff depend on them), snapshots streamed from head rows; conformance validation moves client-side (already non-blocking today).
- **Keep pessimistic locks + explicit commits + the existing journal/`model_rev`/feed** — it already matches Linear's sync protocol. No off-the-shelf sync engine (Zero, ElectricSQL, PowerSync, LiveStore): none fits locks + explicit commits and each adds an always-on service.
- **Script sandbox = cross-origin iframe + strict CSP** (`default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self'; worker-src 'self'` on a static-only origin). PROVEN in the spike: zero CSP violations, `crossOriginIsolated` true in iframe + worker, `setInterruptBuffer` stops a runaway script in 1.5 s and the loaded model survives. Pyodide itself is NOT a security boundary (two 2026 CVEs) — the origin is.
- **GCS gotchas:** store snapshots as `application/gzip` and inflate with `DecompressionStream`; never `Content-Encoding: gzip` (transcoding ignores Range, bills inflated size). Signed URLs defeat the HTTP cache — cache manually by `(project, rev)`.
- **Dead ends (don't retry):** Python core in Pyodide as the engine — passes the agreed thresholds only when the machine is in a fast state (open 6.9 s) and fails in a slow one (12.1 s open, 11.4 s table), no headroom; orjson in Pyodide — wasm heap 1279 MB; Pyodide memory snapshots fail once pydantic is loaded ("Unexpected hiwire entry").
- **Benchmark hygiene:** absolute timings on this PC drifted 1.5–1.9× between sessions with load ≈ 1. Only compare engines measured in the same pass; report medians.
- **No trigram search index client-side:** a full name scan is 32 ms (Rust) / 51 ms (JS) over 170k elements.
- **Rust facts from the spike:** raw C ABI + `serde_json` + `rustc-hash` was enough (288 KB wasm, 97 KB gz); open 0.90 s, 100 MB live / 201 MB wasm high-water with the naive one-allocation-per-string layout (an arena would roughly halve it); the Rust module and Pyodide are separate wasm instances and can only talk through JS.
- **Fidelity hazards to design for:** Python big ints vs `i64`/`f64`; float formatting (exports are contractually deterministic/byte-identical); `Infinity` parsing (see HEAD commit). The existing Python core (13.5k LOC + 56k LOC tests) is the oracle: generate golden fixtures from it.
- **Migration seam idea (presented, liked by nobody yet explicitly):** put the engine behind the API contract the frontend already uses (swap `fetch` for worker RPC) so the ~53k-line frontend mostly survives and migration goes route by route.
- **Root causes already diagnosed:** script exhaustion = 4 sweep workers × N distinct snippet codes guests vs pool of 6 → `unavailable` → abort after 3 → `failed` until next commit. Commit-first = refs resolve from committed DB rows.
