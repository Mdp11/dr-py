## Standing Constraints
- **K-23 (new, load-bearing):**
  - `_trigrams_of` entry ⇔ that element's trigrams are indexed, **an empty tuple `()`
    included**. Absence means exactly "bulk-loaded and not yet reached by the chunked search
    build". Never make it sparse again; deletion pops the entry explicitly
    (`on_element_deleted`), and `index_search_chunk` writes `()` too.
  - While `search_ready` is False, the property hooks must NEVER index a builder-owned
    element (one with no entry) — ownership is per element, not global.
  - `on_property_changed`'s per-value diff is exact ONLY for plain-string (or absent)
    old/new values with **no list- or tuple-valued `name`-keyed property** (any casing).
    `naming._name_str` accepts `(list, tuple)` and the guard must keep matching it exactly —
    every other case falls back to `_update_trigrams(eid, _element_trigrams(el))`.
    `IndexSet.verify_consistent()` is the oracle; every search test ends in it.
  - `on_properties_changed(entity)` now has zero `src` callers — it is the documented escape
    hatch for code that writes `entity.properties` directly. Keep it.
- **K-22:** `IndexSet.element_order` is maintained by the two ELEMENT hooks only (no property

## Known Issues, Not Yet Fixed
- **K-24's sort key is by element ID**, not insertion order — `evaluate.py:245` is
  `sorted(i for i in ids if ...)` over a set of id strings. So K-22's `element_order` does
  **not** answer it directly; the real questions are (a) whether any consumer depends on
  id order at all or merely on determinism, and (b) whether the `set(...)` +
  `sorted(...)` can be replaced by a maintained order (`element_order` gives insertion order
  in O(n) with no sort) — which would be a **visible row-order change** for untyped
  scopes, so it needs an explicit decision in the design section, not a silent swap.
- The remaining **~11 µs per-write floor** (guards, dict write, refs/rekey/roots — `_rekey`'s
  `_frozen(properties)` for keyless types is the largest at ~8 µs) and the applier's ~15 µs
  per op. Recorded in the spec's K-23 non-goals; nobody owns them.
- `_check_patch_keys` landed at 1.17 µs against the spike's projected ~0.3 µs — the code is
  optimal as specified; the residue is the pydantic attribute chain
  (`model.metamodel` → `_caches()`) the spike's monkeypatched variant bypassed. Accepted.
- `on_element_deleted` writes `_trigrams_of[id] = ()` (via `_update_trigrams`) and pops it on
  the next line — a redundant dict write/delete on the delete path. Correct, cosmetic only.
- Unowned, carried forward: `element_order` ~16 MiB resident per hydrated session;
  `ENTITY_STATES_MAX` is an entity-count cap (`api/commit_states.py:36`); snapshot blob GC
  (`content.py:229-233`); four tests call `schedule_periodic_snapshot` without `write_mutex`;
  `snapshot_job` row ahead of `models.model_rev` after `touch_model()`; `scripts/bench.py:208`
  pyright note; the validation sweep's other ~33 ms per element chunk.
- Program items K-24 → K-25 (`BACKLOG.md`).

## Deferred — Do Not Do
- **A bulk `restore_element(..., properties=...)`** for the replay tail — per-property hooks
  are the contract; K-23's leg 3 removed the cost instead (spec K-23 non-goals).
- **Diffing refs / rekey / roots per property** — ≤ 9 µs each; declined.
- **The `zip(s, s[1:], s[2:])` trigram idiom, and touching `_element_trigrams` or the chunked
  build's cost** — measured no faster; declined.
- **Per-field trigram storage** — multiplies the index's dominant memory cost; the substring
  check buys the same exactness. Declined.
- **Bypassing the hooks globally under `search_ready=False`** — hook-created elements must be
  indexed by the hooks (the build's id snapshot predates them); ownership is per element.
- **Narrowing `_update_trigrams_for`'s fallback guard** — widening it is always safe,
  narrowing it is a correctness hazard. A tuple-valued name already caused a real
  `verify_consistent` failure before `a9f187b`.
- Everything K-22/K-21/K-20/K-6 deferred: folding the sequence number into `uniq_groups`, a
  sequence field on `Element`, the per-sweep position-map hoist, comparing `element_order`
  numbers to a rebuild's, zstd, an `encoding` column, serialize-outside-the-mutex,
  posting-set shrinking, `entity_states` backfill, journal-based `GET /commits/{rev}/model`.
