## Known Issues, Not Yet Fixed
- **Minor 1 — cheap, fix now (diagnosed, reproduced by the reviewer):** a deferred edit blocks every settle-waiter until adoption or Retry. `isQuiet()` (`model-engine.svelte.ts:288-296`) requires `_provisional` and `_pending` empty, and a deferred entry sits in both (`:1095-1100`). So `stagedSettled` (`:332`), every `unstageAfter` (`:1237`), `previewStaged` (`checkout.svelte.ts:372`), `validateAll` (`model.svelte.ts:229`) and `_discardWith` (`checkout.svelte.ts:1013`) hang. Scenario: peer rebind freezes the replica → user commits a rename of e2 (lands) → renames e2 again (deferred) → opening the DiffDrawer runs `previewStaged` (`DiffDrawer.svelte:73`) which never resolves; Commit stays disabled (`:772`) so the `CommitPendingError` explanation never shows; Ctrl+E Validate and Discard of an unrelated element do nothing until adoption. No data loss. Reviewer's fix directions: have `isQuiet` ignore deferred entries and their pending counts (they are never in `captureStaged`), or have `previewStaged`/`validateAll` refuse early like `commitNow` does with `CommitPendingError`. Needs a failing-first test over `engineStore()` (freeze via `handReplicaFeed` rebind event, commit lands, same-entity edit deferred → `previewStaged()`/`stagedSettled()` resolve or refuse promptly; commit still refused while the answer is pending; the deferred edit still posts after adoption).
- **Minor 2 (backlog):** `sync.ts:1009-1015` drain second-failure `forget` → `onAbandoned` → `forgetBatches` → `postDeferred` (`model-engine.svelte.ts:944`) posts deferred edits while the replica is still `ready` and still holds the forgotten batch B; the update merges into B, `ask()` re-bootstraps, `resync` filters B via `r.abandoned` → update silently lost. Trigger: an own `applyDelta` failing twice with non-`EngineGoneError` errors while an edit is deferred (very rare). Fix direction: don't `postDeferred` from `forgetBatches` while the replica may still hold the batch; wait for the next ready.
- **Minor 3 (backlog):** two own-answer drop paths bypass `forget`: `handle`'s retried-gap branch (`sync.ts:1039-1041`) and `requeue`'s silent return when `!waits` (`:968-969`, reachable when the replica goes `off` while an own delta is handled). The batches stay in `run.held`, are adopted, stay hidden by `_landed` but never dropped; a same-entity update then stays deferred forever (makes Minor 1 permanent). Fix: `forget(r, [input])` on both paths.
- **Minor 4 (backlog):** three residual windows named in the fix report but in no open entry: (a) a keystroke made DURING the POST, held while `failed` and released at `ready` before the own drain (the narrowed K-44(b) window); (b) `unstage {entity}` can strip ops from a committed batch; (c) the source→target-only filter for the committed diff (see `final-fix-report.md` "Risks not ruled out").
