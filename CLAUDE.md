# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A reflective MBSE (Model-Based Systems Engineering) metamodel engine. Three data layers stack on each other:

- **Metamodel** (`*.metamodel.yaml`) — the schema: element types, relationship types, inheritance (`extends`), properties with datatypes/multiplicity/facets, allowed endpoint `mappings`, and `key`s for uniqueness.
- **Model** (`*.model.json`) — instance data: elements and relationships conforming to one metamodel.
- **View** (`*.view.json`) — an optional user-defined folder overlay that *references* model elements by id; it owns nothing.

It ships as a Python core + FastAPI backend and a SvelteKit single-page frontend, with a one-shot CLI to migrate a legacy metamodel/model format into the new one. Example artifacts live in `examples/` (`smart-city.*`).

## Target architecture

`architecture/` is the source of truth for where the system is GOING — computation in the browser against a full model replica, a thin server, a headless export host — with its decisions (`AD-n`), shared contracts (`CT-n`), constraints (`CN-n`), build order and migration rules (`MR-n`), and repo conventions (`RC-n`). Start at `architecture/README.md` before designing or planning anything that touches the engine, sync, evaluation, scripts or deployment. This file keeps describing what the code does TODAY; `architecture/program.md` says which parts of the target exist yet.

## Architecture — the parts that span files

### Core layering (`src/data_rover/core/`)

- **`metamodel/schema.py` — `Metamodel` is immutable with lazily-built derived caches** (`_Caches`: ancestor chains, effective properties/keys, containment flags, end constraints). Treat it as frozen after load; uploads replace the whole object. If you ever add a mutation path, reset `_cache` to `None` (see `model_copy`). All subtype/effective-property/containment queries go through its cached lookup methods — never re-walk `extends` chains by hand. On a property-name clash along `extends` the ANCESTOR's definition stays (`_effective_props` keeps the first name it sees walking root → leaf), while `key` resolves nearest-first and `key: []` counts as declared; the engine port mirrors both.
- **`model/model.py` — `Model` is the single mutation boundary.** Every create/connect/set_property/delete flows through its methods, which keep `self.indexes` (`IndexSet`, in/out relationship adjacency) in sync. Bulk loaders that populate the dicts directly must call `indexes.rebuild()`. `IndexSet.element_order` (element id → monotonic insertion sequence number; sorting ids by it reproduces `model.elements` order, and ONLY the order is meaningful — the numbers go sparse after churn, a restore re-inserts last) is maintained at that same boundary like `roots_order` and is how the uniqueness validator picks a duplicate group's insertion-first primary without enumerating the model; `verify_consistent` checks it as an order invariant, never by comparing numbers to a fresh rebuild. `relationship_order` is its twin over `model.relationships`, with its own counter, and is what keeps `containment_parents` in relationship insertion order when a relationship comes back under an old number. `set_property`/`delete_property` check the property name against `Metamodel.effective_*_property_names` (cached frozensets on `_Caches`, shared with `routes/ops.py::_check_patch_keys` — never a per-write list copy) and fire `IndexSet.on_property_changed(entity, prop, old_value)`, the single-property hook that diffs the search index from the changed value's text alone; `on_properties_changed(entity)` stays the whole-entity re-derivation for code that writes `entity.properties` directly. `delete_element` cascades through containment children. `insert_element` / `insert_relationship` / `overwrite` are the committed-state methods, the only way an entity is put back as it was: they check no type (a model may hold one its metamodel no longer has), take `rev` as given and fire the same hooks; handed the entity's old sequence number they give it its place back, and `settle_order()` then puts the dicts in that order by REPLACING them — read routes iterate them without `write_mutex`, so never refill one in place and never keep a reference to one across that call. Property values are **replaced wholesale, never mutated in place** — the API op-log's inverse patches alias prior values by reference and depend on this.
- **`validation/pipeline.py` — one sweep, many validators.** The pipeline iterates the model (or a `Scope` subset) once and hands each entity to every `Validator` (`type_conformance`, `multiplicity`, `facets`, `endpoint_typing`, `containment`, `uniqueness`). `default_validators()`/`default_pipeline()` stay these six and rule-free — core stays session-agnostic; `rules` is layered on top only by `api/rules.py` (see "Custom validation rules" below). Per-entity hooks must be O(entity) — use metamodel caches and `model.indexes`, not model scans. Whole-model checks go in `validate_global`. Validators carry mutable per-metamodel memo caches (`MetamodelMemo`, identity-keyed), so **construct one pipeline per request/thread**; never share across threads.

### Engine package (`engine/`)

The TypeScript engine of the target architecture (`architecture/`), built bottom-up. It holds the **value layer, the metamodel, the record-graph store, the op applier, the working copy, the snapshot reader and the state digest** — all of sub-project A — and, from B's third plan, the **steps layer, the read surfaces and the service** (the CT-4 dispatcher and its scheduler); the server never imports it, and the frontend imports its TYPES only — the sandbox's worker (below) is its one host, and the frontend's shell (below) talks to it over a `MessagePort`.

- **`src/` has no DOM and no Node dependency** (`lib: ["ES2023"]`, `types: []`), is erasable-syntax-only, and imports with `.ts` specifiers, so a worker, Node and vitest all run the sources unbuilt.
- **`src/value/`** reproduces the Python core's view of JSON values. A `number` is always a Python `int`; every `float` is a `PyFloat`; integers past 2^53 are `bigint`. `parseJson`/`parseLines` route each line: a regex pre-scan sends lines holding a float, a 16-digit integer, a bare `Infinity`/`NaN` or `-0` to the exact parser and everything else to native `JSON.parse`, many lines to a call — which is why `parseLines` refuses a line holding more than one document instead of shifting every document after it. `pyDumps` is `json.dumps(ensure_ascii=False, allow_nan=False)` byte for byte; `pyFloatRepr`, `pyRepr`, `cmpCodePoint` and `pyKey` mirror `repr(float)`, `repr(str)`, `str` ordering and the uniqueness signature (`_frozen`). `pyLower` / `pyStrip` are `str.lower()` / `str.strip()` of Python 3.14 whatever Unicode version the host carries (Node's `toLowerCase()` differs at 28 code points, `trim()` from `strip()` at 6): generated tables — `lower-tables.ts`, written by `pixi run golden-fixtures`, never by hand — plus Python's final-sigma rule, held to `py_lower.json` over every code point.
- **`src/metamodel/`** — `Metamodel.fromJSON(doc)` takes the `GET /metamodel` document (validated by the server; the engine parses no YAML and runs no `check_metamodel`) and builds every lookup of the Python `Metamodel` up front, under the same names in camelCase. `Multiplicity.parse` mirrors the Python parser, error text included.
- **`src/model/`** is the store: one fixed-shape record per entity (`ElementRec`, `RelRec`), adjacency and containment parents as arrays of record references ON the records, and `Model` as the single mutation boundary, with the Python method set and error texts (`ModelError.kind` is `key` / `value` for `KeyError` / `ValueError`). The engine never mints ids: `createElement(typeName, id)` and `connect(…, id)` take them. Entity order is state: each record has an `ord`, `elements()` / `relationships()` iterate in it, and a record restored WITH its old `ord` goes back to its old place (the Python core always appends). `IndexSet` keeps by-type, uniqueness, references and root order; adjacency order is unspecified, so anything observable sorts by code point. Uniqueness buckets are keyed by a 53-bit hash of the `pyKey` text and confirmed by the exact text at query time. `loadElement` / `loadRelationship` + `rebuildIndexes()` are the bulk path — non-strict like `build_model_from_dicts(strict=False)`, the same refusal texts as `SnapshotError` — and stricter than Python in two places: an id shared by an element and a relationship, and an array-index property key (`"0"`) at any depth, which a JavaScript object cannot keep in insertion order. Committed state enters through `insertElement` / `insertRelationship` / `overwrite`, which check no type (a model may hold one its metamodel no longer has) and take `rev` as given instead of counting it.
- **`src/ops/`** — `applyBatch(model, ops, {restore, idFor})` is the port of `routes/ops.py::_apply_batch` for the six model ops, in the wire's shapes: temp ids resolved through `idMap` in ids, ends and property values (strings and lists, never inside a dict), `id` hints, restore mode, merge patches, the cascade read before it happens, first-touch changed/deleted sets kept disjoint, the `recreated` sets (the changed ids the batch deleted and created again), inverse units and `inverseOps()`. `idFor` decides a created entity's id and is the identity by default — a staged entity lives under its temp id. A refusal is an `OpError {status: 422, detail}` with the server's text, the quote-stripping of `_error_detail` included (`No element with id 'ghost`). One deliberate difference from the server: an op carrying an array-index property key at any depth is refused. A refused batch leaves NO trace on either side — `rewind(model, result)` puts every touched entity back from its first-touch before-image (properties, `rev`, `ord`), and the server's `_rollback` is its port. A record that outlived the batch still has the `ord` of its image and is rewritten in place; anything else under a touched id is removed and the image inserted at its old `ord`.
- **`src/working/`** — `WorkingCopy` owns a `Model`, the committed `rev` and state digest, the staged batches and the committed image of every entity they touched (`committedElement` / `committedRelationship`, `isStaged`). `stage(ops)` applies a batch in place; `unstage('all' | {batch} | {entity, incident?})` and `applyDelta(delta, own?)` are both a rebase — rewind every staged batch newest first, change committed state, replay in order — and a batch that no longer applies is parked in `conflicts()`, never dropped. `applyDelta` follows CT-2 (`applied` / `duplicate` / `gap`), reads the delta's entities with the bulk loader's checks before anything moves, writes them through the committed-state methods (the ids the delta names in `recreated_*` go out first and are appended, as the server's dict did; a record that would change its type or its ends WITHOUT being named does not fit), folds the digest per entity and sets `diverged` on a mismatch or on a delta that does not fit; for the user's own commit it drops the committed batches and rewrites their temp ids in the rest (`remapOp`). The `(id, rev)` hash is the engine's own (`src/snapshot/`); the `entityHash` option replaces it, which is how tests hold it to another implementation. `verifyDigest()` recomputes the digest from every COMMITTED entity — the model's, with the committed image standing in wherever a staged batch has been — and sets `diverged` on a mismatch. Every operation returns a change set, whose `structural` says it may have moved more than properties: it names a relationship, a deleted element or an element absent when it began (presence is asked BEFORE a rebase rewinds, of the ids the staged batches and the change name), or it is an own commit with minted ids — a rebase over-reports what it touched, so a staged relationship makes any peer delta structural, which costs a refresh, never a stale tree. `stage(ops, {coalesce: true})` with ONE property update merges it into the first staged (never parked) op of the same kind and id — `{...old, ...new}`, later keys win, a `null` stays — as a new batch object under the old batch id: the op is first tried alone on top (a bad patch throws and cannot park the batch holding the earlier edits) and rewound, then the working copy rebases FROM that batch (the private `rebase` takes the index to start at; the batches below it stand). Never in place: an update bumps `rev` once per key and re-places a deleted key, so an in-place merge would leave a state no replay of `staged()` gives (key order and `rev`s included), which the seeded invariants hold. `adoptStaged(batches)` replays batches under their ids on a working copy with nothing staged or parked (a re-bootstrap carrying the user's edits), parks the refused ones and numbers the next batch past the highest id. A `duplicate` delta that comes with `own` naming a batch still staged or parked drops them all the same — the echo of a commit can arrive before its answer. `stagedVersion` moves whenever `staged()` or `conflicts()` come to hold other batch objects (a stage, a merge, a remap, a drop, a park; a plain rebase keeps them). `stagedDiff()` pairs each committed image with the record now, in first-touch order.
- **`src/snapshot/`** — `sha256` is FIPS 180-4 in plain TypeScript, synchronous because the digest fold cannot wait for WebCrypto; `entityHash(id, rev)` is CT-3's hash (the first 8 bytes over `utf8(id) ‖ 0x00 ‖ ascii(rev)`, the UTF-8 written by hand, a lone surrogate as U+FFFD), `modelDigest(model)` the port of `state_digest.model_digest`, and both are `WorkingCopy`'s default. `openSnapshot(chunks, metamodel, onProgress?, options?)` reads a `datarover.snapshot/v2` text from inflated bytes cut anywhere and returns `{header, workingCopy}` at the header's `rev` and `state_digest` — adopted, not checked: `verifyDigest()` is the check, whenever the caller chooses. Bytes are decoded by the host's `TextDecoder` (`fatal`, the byte order mark kept so that it fails the format check), reached through a typed `globalThis` lookup in `utf8.ts` because a declared global would collide with the host typings of any project that compiles these sources; `LineSplitter` cuts on LF alone; lines are parsed and loaded 500 at a time through `parseLines`, the first `elements` of them as elements, so the text is never held whole — 500 being the largest batch that stays a short step (at 2,000 the worst batch took 36 ms at M, *measured*). `options.pause` is asked after every loaded batch and every step of the index build (`rebuildIndexSteps`, reported through `options.onIndex`); only a returned promise is awaited, so an open with room left in its slice pays no microtask, and a throw ends the open. The pause sits in the batch loop, not the chunk loop, and a chunk is decoded in pieces of 64 KiB: a snapshot served from a cache arrives as a few large chunks, and awaiting a chunk that is already there resolves in microtasks, which is no yield to the host. Anything that does not start with `{"format":"datarover.snapshot/v2"` is refused at its first bytes. A refusal is a `SnapshotError`: the server's two texts (`snapshot v2 header carries no valid entity counts`, `snapshot v2 holds N entity lines, its header promises E + R` — the count is checked BEFORE the last lines are parsed, which is what gives a cut text the server's answer), the bulk loader's own, or the engine's for what the server's decoder never looks at (`rev`, `state_digest`, the ids, invalid UTF-8, a line that is not one JSON document, named by its number). Like the server's reader it takes a last line without its LF and CRLF line ends.
- **`src/steps/`** — a `Steps<T>` is a generator that cuts a long operation into steps of about a millisecond at M, each `yield` saying where it stands (`{done, total}`). Every long operation exists once, in that form, and its synchronous name drains it (`drain`): `IndexSet.rebuild` / `Model.rebuildIndexes` (`rebuildIndexSteps`, 1,024 entity visits a step), `WorkingCopy.verifyDigest` (`verifyDigestSteps`, 2,048 entities a step), `RootOrder.reset` — so no caller of the one-shot forms changed. A steps generator publishes nothing before its last step (`diverged`, the root order), so abandoning one leaves no trace; it holds iterators over the model across its yields, so the model must stay still between two of them, and each user says who keeps it still: the index build runs only while a replica is opening, a scan is protected by the service's queue, and the digest check is dropped and restarted after any transition. `sortedInSlices(items, compare, run = 2048)` is a stable bottom-up merge sort in steps (runs sorted natively, then merge passes into a second buffer, a step every `run` items written; the order `Array.prototype.sort` gives); it costs about twice the native sort and no step over 2 ms at M (*measured*), and serves the root sort of the index build and the hit sort of a search.
- **`src/read/`** — the read surfaces, a port of `routes/read.py` (and `routes/elements.py::get_element`) rule for rule. A read is `(model, placements, params)` → the route's HTTP response BODY, in pydantic's field order (`{id, type_name, properties, rev}`, `{items, total}`, …), as a plain call or a `Steps` generator; it reads the model and nothing else. `READS` maps the `lib/api` names (`getElement`, `getElementsBatch`, `listElementsPage`, `listElementRelationships`, `getModelSummary`) to them, and `readScans(method, params)` says which calls run in steps. `toWire` deep-copies a value into plain JSON-able data — a `PyFloat` as its number, a `bigint` as the nearest double, which is what a client's `JSON.parse` of the server's body gives — so nothing of the replica leaves; `readOps` reads ops as the server reads what a client sends: through `JSON.stringify` (an integral double is an `int`, `NaN` `null`, `-0` `0`) and the exact parser, then a shape check whose refusal is a 422 `ops[i]…` in the engine's words. `ViewPlacements` holds the element ids each loaded view places (an unknown, empty or absent view places nothing). An unknown element is the model's `ModelError` (`key`); page bounds (`limit` 1–500, `offset` ≥ 0) and parameter types refuse with `ReadError(422)` in the engine's own texts, because FastAPI, not the route, enforces them and no fixture can hold them — `too many ids: N (max 500)` is the route's own. `getModelSummary` answers `issue_counts: null` and `undo_depth: 0`, `model_rev` being the caller's. The tree (`tree.ts`: `getTreeItemsBatch`, `listContainmentRoots`, `listExcludedRoots`, `listContainmentChildren`): a child belongs to its FIRST containment parent (`parents[0]`, relationship order — a relationship restored under its old id goes last, so it does not win its child back), counts once however many parallel edges hold it, and levels sort by `(displayName, id)`, both by code point; roots come off the maintained root order, the excluded pool is that order minus the ids `ViewPlacements` holds for `view_id` (whatever a view places that is not a root changes nothing) with `total` counted over the whole walk. Search (`search.ts`, `listElementsPage` with a `q` that is not blank) is a full scan in steps — no trigram index (AD-13) — of `searchScore` over every element in state order, 512 a step: the query is `pyLower(pyStrip(q))`; a name (`nameOf`) is lowered with `pyLower` and scored by `nameScore` — exact 1000, prefix 100, word boundary 30, substring 10 — plus `len(query) / len(lowered name)` counted in code points of the LOWERED name (U+0130 lowers to two); the boundary test runs on the lowered name (U+212A lowers to `k`) as an occurrence walk that tries every start, overlapping ones included, which is what the route's regular expression does; then +5 / +2 for the id, +1 for the type (memoized per type), +0.5 per other string property (every `name`-cased key skipped). The additions happen in the route's order, in doubles, so equal scores are equal doubles and nothing is rounded. Hits sort by `(-score, id)`, ids by code point, through `sortedInSlices`; `total` is every hit; nothing is kept between pages (the server keeps nothing either).
- **`src/service/`** — `Scheduler` (`scheduler.ts`) runs engine work on the host's thread in slices. One pump, two lanes, each in arrival order: the *control* lane (the replica's own transitions) runs in any state and first; the *model* lane runs while the scheduler is open. A job is a `read` (one call), a `transition` (one call that changes the model, never interrupted — a transition may run up to 100 ms, AD-23) or a `scan` (a `Steps` generator that `run()` makes). A transition waits for every read that arrived before it and holds everything behind it; at each slice boundary of a running scan, the reads queued before the first transition are answered and other scans are skipped over, never started — so a scan never sees the model move under its iterators (probe: a `Map` iterator that crosses a `clear()` and refill reads everything again, and `Model.elements()` does exactly that on the first ordered read after a rewind). `cancel(id)` removes a queued job or drops a running scan at its next step, unanswered; closed (`setOpen(false)`), the model lane keeps its jobs and a scan that was mid-flight goes back to the head to start over, `run()` called again. The pump reads the injected clock after every unit — a read, a transition, one step — and at `SLICE_TARGET_MS` (8, half of CN-3's 16 ms chunk: at M a collector pause of 5–8 ms lands inside a step now and then) calls `onSliceEnd`, awaits `yieldToHost()` and starts a new slice; messages are handled on those host turns only, never inside a unit. Idle and open, it gives the background task (`setBackground`) one slice at a time; `restartBackground()` drops its steps in flight (they published nothing) so a new run starts at the next idle slice. `pause()` lends the slice clock to work outside the pump (a snapshot open): `undefined` while the slice has room, else the host's turn. The pump starts on a microtask, so every job one message brings is queued before any runs.
  `createService(port, deps)` (`service.ts`) is the CT-4 dispatcher over one `Port` (`{post, onMessage}`: a `MessagePort` in a worker, `portPair()` in tests); `deps` is `HostDeps` plus `inflate`, since `src/` holds no timer, clock or gzip. A request `{id, method, params}` is answered `{id, ok, result | error: {status, detail}}` exactly once, or never once `{cancel: id}` came; a message without an id or a method is ignored. Errors: `OpError` / `ReadError` keep their status, a `ModelError` `key` is 404 with `errorDetail`'s quote-stripped text, `value` 422, a `SnapshotError` 422, an unknown method 404 `No method 'x'`, anything else 500 with its message. The replica is `opening`, `ready` or `diverged`. `open {project_id, metamodel}` discards any replica or open in flight (the heap never holds two) and starts `openSnapshot` over `deps.inflate` of a `ByteQueue` that `chunk {bytes}` feeds, with the scheduler's `pause` (which also stops a discarded open at its next batch); `end` answers the header once the replica is read and indexed — or the open's 422, which `chunk` and `end` then answer until the next `open`, a header of another project included — and the replica stays `opening`; `adoptStaged` (a control-lane transition) carries a re-bootstrap's staged batches over; `applyTail {text}` queues one transition per delta at once (control lane while opening, model lane after) and makes an opening replica `ready`, the scheduler open and the background digest check set; `applyDelta {text, own?}` is a model-lane transition, a 409 unless `ready`; `close` drops everything but the view placements and the queued model jobs. A delta or a tail crosses as the text the shell received and is read by `readDeltaText` / `readTailText` with the exact parser (AD-26: `JSON.parse` would lose `1.0` and integers past 2^53, which the digest cannot see); a commit response reads alike, `model_rev` standing for `rev`. Events: `replica {state, rev}`; `progress {task, done, total}` for `parse`, `index`, `tail`, `verify` — a task's first (`done` 0, which is how a restarted digest check shows) and last reports at once, the rest at most once a slice, from `onSliceEnd`; `changed {rev, staged_version, …ids, structural}` after every transition of a `ready` replica that changed something, which also restarts the digest check when an entity or the staged list moved. A delta whose digest disagrees, or a digest check that ends false, makes the replica `diverged`: the scheduler closes, so reads and edits posted meanwhile wait, and are answered from the replica the shell opens next (`close`, `open` … `end`, `adoptStaged` with what `staged` returned, `applyTail`). The method table (`METHODS`) is built from a few kinds, so the message handler has no per-method branch: `now` (answered at once, in any state — `open`, `chunk`, `close`, `staged`, `conflicts`, `setViewPlacement`, `dropViewPlacement`), `later` (`end`), `read` (every `READS` name, a `scan` job when `readScans` says so; `getModelSummary` is handed the committed `rev` as `model_rev`), `inspect` (`stagedDiff`) and `transition` (`stage`, `unstage`: their params are read at arrival, so a malformed request is refused before it queues), plus the three replica methods above. Reads, `stagedDiff`, `stage` and `unstage` wait in the model lane for `ready`, so an edit made during a re-bootstrap lands after the adopted batches. `stage` reads its ops through `readOps` and always asks the working copy to coalesce; it answers `{batch, coalesced, changes, elements, relationships}`, the last two the post-state of what `changes` names as changed, both `null` past 500 entities. Every result and event is a copy built by the `wire*` functions — over a direct port pair nothing is cloned, and an uncopied result would hand out the replica's own property bags.
- **`bench/run.ts`** (`pixi run engine-bench`, input written once by `pixi run engine-bench-data` → `scripts/snapshot_v2.py`) measures model M in three passes: opening the snapshot against opening the same model as one document in the same pass, the digest check, the heap of one open replica, a 1,000-op batch staged and unstaged, a rebase of 100 staged batches, a delta — and the long operations driven step by step by hand (`stepped`), each with its total and its longest step: the index build (over the document model), the digest check, the broadest search (`q='a'`, hit sort included) and a rare one. It measures STEPS, not slices: there is no scheduler in it; the browser benchmark below bounds the slices. It weighs the heap BEFORE it reads the document: the last text a regular expression ran over stays reachable in V8, and there that is 77 MB.
  **`frontend/bench/`** (`pixi run engine-bench-browser`, which builds the sandbox first) is the same model in the browser: a bench page on `http://127.0.0.1:5173` (`bench/vite.config.ts`: the app's COOP / COEP plugin, and `benchmarks/large.snapshot.v2.gz` — the encoder's own bytes, which `engine-bench-data` writes with `--gzip` — served at `/data/snapshot.gz` with its length and no `Content-Encoding`) drives the BUILT sandbox through `frame.ts` and `client.ts`, and `bench/run.ts` (Node's type stripping) drives the page through `window.bench` with Playwright's default headless shell, e2e's browser: three passes, each in a fresh context, medians, a verdict against CN-3, never a failing exit. It measures the cold open (first byte asked to `replica ready`, split at the last chunk sent, `end`, and when `parse` and `index` began and ended by the engine's `progress` events), the digest check, `stage` / `unstage` / `applyDelta` and the reads THROUGH THE PORT (round trips, so upper bounds), and the longest slice FROM OUTSIDE: a loop posts `staged` — a `now` method, answered on the worker's next host turn — each when the last was answered, so its longest round trip bounds the longest time the worker took no message, main thread included. The heap is the WORKER's: Chromium runs with `--remote-debugging-port`, the `worker` target of `/json/list` whose `url` holds `engine-worker` is reached over its own `webSocketDebuggerUrl` with Node's `WebSocket`, `HeapProfiler.collectGarbage` then `Runtime.getHeapUsage`, after the digest check is done (before, it is 15–35 MB higher); `backingStorageSize` is shown beside `usedSize`, not added. A worker has no `performance.memory`, and `context.newCDPSession(frame)` needs an out-of-process frame the headless shell does not give. The page cannot compute a state digest, so the last row's delta carries a wrong one and ends the replica — after the rewind, apply and replay it times.
- **`src/debug/`** — `dumpIndexes` (the canonical index dump the fixtures compare), `verifyConsistent` (incremental indexes against a rebuild, performed in place) and `shuffleAdjacency` (tests shuffle between steps to expose a dependence on adjacency order).
- **Golden fixtures** — `tests/golden/scenarios/*.py` run the real Python core and `pixi run golden-fixtures` writes `engine/fixtures/golden/*.json`; `engine/test/**/*.golden.test.ts` read them. The same task writes one generated source, `engine/src/value/lower-tables.ts` (`tests/golden/lower_tables.py`, listed in `driver.GENERATED`). `tests/golden/test_fixtures_current.py` (part of `core-test`) fails when a committed fixture or that source differs from what the core produces now. The Python core is the oracle: fix the engine, never the fixture. Values a plain JSON reader cannot hold are tagged (`tests/golden/tagged.py` ↔ `engine/test/golden/load.ts`). Model scenarios are step lists run by `tests/golden/model_steps.py` (`Recorder`): every step records its result or error text, the state digest and a fingerprint of the entity lines plus `tests/golden/index_dump.py`'s dump, and every n-th step carries both in full; `engine/test/golden/model-steps.ts` replays them, a second time with every uniqueness key forced into one bucket. A `batch` step runs an op batch through `routes/ops.py::_apply_batch` on the recorder's own model, as a session does — a refused batch must leave no trace, the recorder fails the run when one does, and `ops_refused` refuses after every kind of touch — and records the outcome, the first-touch before-images, the inverse ops and the delta a replica would be sent; `undo` runs an earlier batch's inverse ops in restore mode. A `read` step calls the real route function behind a `READS` name on a `Session` built for the call, with EVERY argument passed (called directly, a route keeps its `Query(...)` objects as defaults), and records `model_dump(mode="json")`; the replay compares `JSON.stringify` of both, values and key order at once. `view` registers the element ids a view's nested folders place (`read._placed_element_ids`, the list the shell would register) and `drop_view` forgets them. `engine/test/working/replica.golden.test.ts` feeds a `WorkingCopy` those deltas alone and expects the oracle's state, entity order included — through `ops_recreate` too (an entity created again under its id, unchanged in type and ends), which only the delta's `recreated_*` lists can express. `snapshot_v2` holds a snapshot text as the server encodes it, the texts no writer emits that the server reads alike (`same`) and the ones its decoder refuses in its own words (`refused`); `engine/test/snapshot/open.golden.test.ts` opens them all, cut into pieces as small as one byte. Every `observe()` of the golden runner computes its digest with the engine's own hash, so each fixture step holds it to `hashlib`.

### Sandbox (`sandbox/`)

A static Vite site, its own npm package, always served as BUILT files (`vite preview`) on `http://localhost:5174` — another site than the app's `http://127.0.0.1:5173`. It hosts the engine in a module worker; the workspace embeds it through the shell (next section).

- **`src/page.ts`** (behind `index.html`, which holds one module script and nothing inline) creates the worker (`new Worker(new URL('./engine-worker.ts', import.meta.url), {type: 'module'})`), reports the worker's `error` event (`{type: 'worker-error', message}`) and every `securitypolicyviolation` (`{type: 'csp-violation', directive, blocked}`) to the parent at `APP_ORIGIN` (`src/origins.ts`, `VITE_APP_ORIGIN` at build time), then posts `{type: 'sandbox-ready', crossOriginIsolated}`. It hands the FIRST acceptable `connect` to the worker as `{type: 'port'}` with the port and keeps no reference to it, so it leaves the data path: `src/handshake.ts`'s `connectPort` accepts a message only from `APP_ORIGIN`, from `window.parent`, of type `connect` and carrying exactly one port; the "only once" rule is the page's. **`src/engine-worker.ts`** runs `createService` over the first port it is given and ignores any other.
- **`src/host.ts`** — the three things the engine cannot hold, and `portOf(port)`, the engine's `Port` over a `MessagePort` (setting `onmessage` starts the port, which queues whatever was posted before). `inflate` is a `DecompressionStream('gzip')` fed by a pump and read through a `getReader()` loop (not the stream's async iterator, which not every browser has); a failure of the STREAM — a truncated member, trailing bytes, not gzip — is rethrown as `SnapshotError('snapshot bytes do not inflate')`, because the stream's own errors carry an EMPTY message and the service answers anything but a `SnapshotError` with a 500 of that message; a failure of the SOURCE (the service's `ByteQueue`) is rethrown as it is, and the pump never rejects. `createHost()` gives `yieldToHost` as a post on a private `MessageChannel` resolving a FIFO of waiters — a macrotask with no clamp, where a nested `setTimeout(0)` is clamped to 4 ms from its fifth level (about 1.2 s over an open at M) — and `now` as `performance.now()`; its `close()` frees that channel (the worker never calls it; tests must). `host.ts` may use only what a window, a worker and Node 22 share, because the frontend's tests run it.
- **Policy.** `vite.config.ts` sets `Content-Security-Policy: default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self'; worker-src 'self'; frame-ancestors <app origin>`, `Cross-Origin-Embedder-Policy: require-corp` and `Cross-Origin-Resource-Policy: cross-origin` on `preview` AND `server`, so `vite dev` is never laxer than what ships. The app origin comes from `loadEnv(mode, process.cwd(), 'VITE_').VITE_APP_ORIGIN`, defaulting to `http://127.0.0.1:5173` like `src/origins.ts`'s own read of it — `loadEnv`, not `process.env`, because the config itself cannot read `import.meta.env`. `appType: 'mpa'`: a missing file is a 404, not the page again. `worker: {format: 'es'}`, `build.target: 'es2022'`.
- **Three tsconfigs** keep the page from seeing worker globals: `tsconfig.json` (the page: ES2023 + DOM), `tsconfig.worker.json` (the worker and `host.ts`: ES2023 + WebWorker), `tsconfig.test.json` (tests, `host.ts`, `handshake.ts` and the configs: DOM + `node`). The engine's sources come in through the imports (`../../engine/src/index.ts`), which is why `allowImportingTsExtensions` is on.

### Shell (`frontend/src/lib/engine/`)

The app's side of the replica: plain TypeScript, no runes, no `lib/state/*` import (it may import `lib/api/*`). `lib/state/replica.svelte.ts` wires it into the workspace, and `frontend/README.md` ("Replica (engine shell)") has the detail. The nine model reads can be answered by the replica, one switch per surface, every default `engine` — so the five read surfaces (elements, fuzzy search, incident relationships, containment tree, summary counts) come from the in-browser replica unless `dr.surfaces` says otherwise or the replica cannot serve them, with the server as fallback; a status-bar indicator (`data-testid="replica-indicator"`) shows its state.

- **`frame.ts`** — `connectFrame(deps?)` appends a hidden `<iframe>` of `SANDBOX_ORIGIN` (`origins.ts`, `VITE_SANDBOX_ORIGIN`, `http://localhost:5174` by default) with `allow="cross-origin-isolated"` and `sandbox="allow-scripts allow-same-origin"`, waits for `{type: 'sandbox-ready', crossOriginIsolated}`, and answers `{type: 'connect'}` with ONE transferred `MessagePort`; the link carries `isolated` and replays `csp-violation` reports to its `onViolation` listeners. A message counts only when `event.origin === SANDBOX_ORIGIN` and `event.source` is the frame's `contentWindow`. It refuses outright — `FrameError('same-host', 'open the app at http://127.0.0.1:5173')`, no frame built — when the app's hostname is the sandbox's: the two must be different sites (CN-17), which is why every doc says `127.0.0.1:5173`. No `sandbox-ready` within 10 s is a `timeout`; a `worker-error` before it is `worker`, after it ends the link. The window, location, frame factory and channel are injectable, because happy-dom's `postMessage` delivers no ports and an iframe there fetches for real.
- **`client.ts`** — `createEngineClient(port)` is the CT-4 client: ids from 1, an error answer rejects with `errorForStatus` of `lib/api/errors` (so `NotFoundError` / `ConflictError` / `ValidationError`, as after an HTTP call), events go to every `on` listener, an aborted signal posts `{cancel: id}` and rejects with an `AbortError`, `transfer` rides as the transfer list, and `dispose()` rejects everything pending or later with `EngineGoneError`. An `EngineLink` (`client`, `isolated`, `onViolation`, `dispose`) is what `sync.ts` is handed.
- **`cache.ts`** — `createSnapshotCache()`: IndexedDB `datarover-snapshots` v1, store `snapshots`, key path `project_id`, so one row per project (`{project_id, rev, bytes, size, used_at}`). A hit needs the descriptor's exact `rev` and returns a copy; a `put` happens only after the engine's `end` accepted the bytes and evicts least-recently-used rows of OTHER projects down to 64 MiB; a row the engine refuses is dropped. Every call resolves whatever the store does (AD-10): no `indexedDB`, a blocked open, an aborted transaction or a quota error is a miss or a no-op.
- **`sync.ts`** — `createReplicaSync({connect, api, cache, sleep, onStatus})`, the one place that knows the order of things. An open attempt: the snapshot descriptor (`null` → `off`, `no model`), the link (a `connect()` that rejects is phase `server` at once), the metamodel document (an `X-Metamodel-Id` other than the descriptor's restarts the attempt for free, three times), `open`, the bytes from the cache (one `chunk`) or streamed from the descriptor's `url` (each chunk transferred exactly — a view is copied first), `end` (its header must be the descriptor's; refused cached bytes are dropped and read again from the network, uncounted), `adoptStaged` on a re-bootstrap, the tail (incomplete fails the attempt), `applyTail`, `ready`. Three attempts, 1 s then 3 s apart; after the third `server` if this open was never ready (the link disposed), else `failed`. Every continuation checks a generation token that `stop()` and `open()` move, and every API call carries its own project's base URL (`replicaApi(root)`), so a late call never lands on the next project. Following: feed deltas, snapshot events and the user's own commit responses form ONE queue handled in `rev` order while `ready` (at most 1,000 wait otherwise, past that a catch-up is owed); a delta not past the replica drops without a call unless it is the user's own; `gap` or a snapshot event ahead runs a catch-up through the tail; an incomplete catch-up, `diverged: true`, or the engine's `replica {state: 'diverged'}` event re-bootstraps — `resyncing`, `staged` + `conflicts` read and joined by id, the cache row dropped, `close`, the attempts on the SAME worker adopting those batches; a catch-up whose tail FETCH throws tries once more after 1 s first. `feedReset(rev)` (the feed's `reset`: a `rev` bump with no journal row) is a snapshot event ahead, so the tail is incomplete and the replica re-bootstraps; a `reset` or a snapshot event in `off` restarts the open (`server` stays). `retry()` re-bootstraps a `failed` replica with a fresh budget of attempts, adopting the batches it still holds. `beginCommit()` opens a flight BEFORE the POST and the queue holds while any is open; `settle({text, rev, applied, rebound, idMap})` inserts the response at its place by `rev` (`applied: false` — `prev_rev` null — queues nothing), so the echo drops as covered (CT-2); `abandon()` just lets the queue go. A `rebind` event or a `rebound` settle FREEZES the replica (`frozen`, `metamodel changed at rev N`) and `metamodelAdopted()` re-bootstraps it onto the metamodel the UI now shows (AD-27). `call(method, params?, {signal?})` is a read answered by the replica, held in the shell until the phase is `ready` and its `rev` has reached `known` — the highest `rev` a `feedCommit`, an applied `settle`, a `feedSnapshot` or a `feedReset` handed it before the call (AD-28) — or at once in `frozen` / `failed`; with `{transition: true}` (the store's `stage` / `unstage`) it is held for the phase alone — posted in `ready` or `frozen`, never held for `known` nor by a commit in flight, held while `opening`, `resyncing` or `failed` so a re-bootstrap's batches are adopted first — in the SAME list as the reads, a held transition holding every call asked after it; no open, `off`, `server`, `stop()` or no link reject `EngineGoneError`. `on('changed', listener)` hands every engine `changed` event (`ChangedEvent`) to listeners kept on the sync, forwarded by each link it adopts until that link is dropped. `setViewPlacement` / `dropViewPlacement` keep a map the sync sends to every new link before any held read goes (`stop()` clears it); `placements.ts`'s `placedElementIds(view)` is what a view places. `ReplicaStatus` is `{phase: off|opening|ready|resyncing|frozen|failed|server, rev, progress: {task, done, total}, attempt, source, isolated, cspViolations, reason}`, a new object on every change; the replica's `rev` comes from the engine's answers and events, never from the shell's arithmetic.
- **Surfaces — `lib/api/engine-route.ts`, `surfaces.ts`, `seam.ts`.** The nine model reads of `lib/api` (`getElement`, `getElementsBatch`, `getTreeItemsBatch`, `listElementsPage`, `listElementRelationships`, `getModelSummary`, `listContainmentRoots`, `listExcludedRoots`, `listContainmentChildren`) keep signature and schema and pick a side through `route(surface, cfg, engineCall, serverCall)` over an INJECTED seam (`installEngineSeam`; `lib/api` imports nothing of `lib/engine`): no seam, an explicit `baseUrl` or `fetch` (a call that names its server — every MSW test of the server path), or the surface's side `server` → the server; else the engine, whose body passes the same zod schema, an `EngineGoneError` (`gone`) answered by the server instead and any other error the caller's; an optional `shadow` is handed `{surface, method, params, engine, again, server}` after every engine outcome, never awaited, its throws and rejections swallowed. Engine params are flat snake_case (`elementId` → `id`, `viewId` → `view_id`, an id list → `{ids}`) with omitted options left out; `signal` on the option bags reaches the engine as the call's signal and the server as `init.signal`, never the query string. The five surfaces (`surfaces.ts`): `elements` (`getElement`, `getElementsBatch`, `listElementsPage` without a query that is not blank), `search` (with one), `relationships`, `tree` (the tree items and the three containment reads), `summary`; `SURFACE_DEFAULTS` all `engine`, `readSurfaces(storage?)` overlays the JSON object in `localStorage['dr.surfaces']` (honoured in a build too; anything malformed gives the defaults), `anyEngineSurface`. `createEngineSeam(sync, surfaces, shadow?)` (`seam.ts`): a surface's effective side is `engine` iff its switch says so and the phase is neither `off` nor `server`; `call` is `sync.call`. The replica store installs it (below).
- **Shadow comparison — `shadow.ts`, `quiet.ts`.** Dev-only: `shadowEnabled(storage?)` is `import.meta.env.DEV && localStorage['dr.shadow'] === '1'` (absent from a build; a throwing storage or any other value is off). `createShadow({rev, quiet, report})` builds the seam's `shadow`: runs `server()` beside the engine's own outcome, compares by deep equality (object key order ignored, array order not) or, for two failures, the same kind (`ApiError.status`, else the error's `name`) — `summary` compares without `issue_counts`/`undo_depth`, since the engine always answers those `null`/`0`. Equal: nothing. Different: `await quiet()`, note `rev()`, run `again()` and `server()` once more, note `rev()` again — moved in between → repeat, three rounds at most, then give up silently (a replica that never rests is not a mismatch); a round whose `rev` held still decides it, reporting ONE line (`report`, `console.error` in the store) on a still-different round: `[shadow] <surface> <method> <params>: engine <short> ≠ server <short>`, each `short` cut at 300 characters. An `AbortError` from either side, or an `EngineGoneError` from the engine side (`again()`, or the engine's own outcome), at any point, ends the comparison silently — a `rev` gone to `null` on a `stop()` must never read as two stable, equal reads. `quiet.ts`'s `addQuietProbe(probe)` / `quiet()` is the small registry other stores add a "still settling" probe to. The replica store reaches `shadow.ts` only through a dynamic `import('../engine/shadow')` behind the same DEV check, so a build holds neither the module nor its `[shadow]` string.
- **The store — `lib/state/replica.svelte.ts`.** `startReplica()` opens the sync and installs `createEngineSeam(sync, readSurfaces())` into `lib/api`, with `sync.settled()` as a quiet probe; `stopReplica()` / `resetReplica()` uninstall both (every read goes to the server again). `subscribeReplicaStatus(listener)` hands every status change with the one before it. With staging on the engine, `startReplica()` also attaches the model store's engine half (`attachEngine(handle)`: the sync's `call` and `on('changed')`, this store's status, `subscribeReplicaStatus`) and `stopReplica()` / `resetReplica()` detach it before the sync stops; with staging on legacy it is never attached (it would move the structure rev on every applied delta, which the legacy half already moves). The switches are read once, at the first start; `resetReplica()` forgets them. In dev, with `dr.shadow` set and some surface on the engine, the seam is installed again with a shadow once the module has loaded (a seam replaced meanwhile is not overwritten). `handReplicaFeed` hands a `reset` event to `feedReset`; the realtime store then does a snapshot event's work minus presence and leases (`refreshSummary()` when ahead, the debounced issues refetch). With `summary` on the engine, `refreshSummary()` keeps the store's issue counts (the engine answers `null`) and asks `refetchIssues()`; `_modelRev` is the answer's either way. `registerViewPlacement` / `forgetViewPlacement` / `forgetViewPlacements` reach the sync: the view store registers the COMMITTED document's `placedElementIds` from `refreshView()` — the fetched one, never the staged ops on top, and before `setState`, since the tree refetches on `_view`'s identity — forgets the old view on a switch, a 404, no view or a failed load, forgets all in `clearViewState()`, and adds a quiet probe pending while a `refreshView()` is in flight. The three debounced searches (`Sidebar/Search.svelte`, `Navigation/ElementStartPicker.svelte`, `Snippet/ElementContextRow.svelte`) abort a superseded `listElementsPage` through its `signal`; an `AbortError` leaves the results as they were.
- **The model store — `lib/state/model.svelte.ts`, `model-shared.svelte.ts`, `model-legacy.svelte.ts`, `model-caches.ts`.** `model.svelte.ts` is a facade: it re-exports the shared half and, for every entity-half name, dispatches to `model-legacy.svelte.ts` or `model-engine.svelte.ts` by `getStagingSide()` (`replica.svelte.ts`, the `staging` switch in `lib/engine/surfaces.ts`) — `legacy` without a sync, `engine` iff the switch says so and the phase is neither `off` nor `server` (`failed`/`frozen` keep `engine`: a re-bootstrap carries the batches staged there); `resetModelStore` and `validateAll` touch both halves directly, since neither is one entity half's concern, and `setModelApiConfig` always sets the shared half's client config (the engine half has none). `model-shared.svelte.ts` holds what every entity half agrees on — the summary, `model_rev`, the structure-rev counter, the live issue map, rules status and the store error — and `applyDeltaShared(d, has)` is the shared half of a delta's application (the structural formula, the issue splice, the summary patch, `clearOverlay()`), taking a `has(id)` callback so its pre-remap "was this id already cached" check reads the CALLER's cache before the entity half's own remap runs (`structure: false` leaves the structure rev to the caller). `model-legacy.svelte.ts` is the server-mode entity half (the fetched-subset caches, the staged-edits buffer) — frozen, and deleted once the engine half is the only one (sub-project F). `model-engine.svelte.ts` is the engine half, a view over the replica: its caches (the legacy half's names) are filled through the `lib/api` seam — so they hold the staged edits — with none of the legacy guards and no temp-id short-circuit (a temp id the engine 404s is in `getMissingElementIds()`); `emit(op)` / `emitMany(ops)` (one batch, all or nothing) write the op into the caches at once (a create under its temp id with a lite tree item, a delete taking the row out of the tree items too), raise the entity's PENDING count, add a PROVISIONAL entry and post a `stage` transition; nothing the engine says overwrites a pending entity except the `stage` answer that brings its count back to zero (its post-state), so an answer never regresses a newer keystroke, and a refused stage (`getModelError()` `rejected`, the engine's text) reads its entities back and drops what it created. It keeps a mirror of the engine's `staged` / `conflicts` / `stagedDiff`, read again whenever a `changed` event's `staged_version` moves, whenever the replica becomes `ready` (after a re-bootstrap the cached elements the staged and parked batches touch, before and after, are read again: adopting says nothing) and after every `stage` answer; the staged-edit readers read the mirror's batches then the provisional entries, an entry leaving when a mirror read issued AFTER its answer lands — and no mirror read starts while an edit waits for its answer (its `changed` comes first), which is what keeps an op from counting twice; `getStagedBatchIds()` / `getStagedConflicts()` are the mirror's, `getStagedDiff()` the engine's committed images against its records. `stagedSettled()` resolves once every edit is answered and covered, no mirror read, cache re-read or unstage is in flight or owed; a detach releases it. The engine's `changed` event is the one path that refreshes it after a transition: deleted ids leave the caches and tree items, cached changed elements are re-read in one `getElementsBatch`, a changed relationship is left to the relationships list's refetch, `structural` moves the structure rev and the event's `rev` becomes `getModelRev()` when past it. Its `applyDelta` runs `applyDeltaShared` with `structure: false` (the structure rev moves on `changed` alone, once per structural delta), re-keys the caches, visit history and selection through `id_map`, and upserts the delta's entities except those a staged batch touches (the mirror's diff) — the replica replays the batch over the delta and re-reads them; a delta older than `getModelRev()` (the replica applied it already, e.g. through a tail catch-up ahead of the feed frames) moves no rev and no entity, only its issues (`applyDeltaShared`'s `rev: false`) and its `id_map` re-keying. The unstage family waits for the edits before it and posts one transition: `popLastStaged()` = `unstage {batch: last}` (a coalesced keystroke lives in its first batch), `revertStagedFor` = `{entity}` (parked batches stay), `revertStagedForElement` = `{entity, incident: true}` plus `{batch}` for each parked batch touching the element, `revertAllStaged` = `'all'`, `revertConflict(id)` = `{batch}`; `clearStaged()` does nothing. The facade's `emitMany`, `stagedSettled`, `getStagedBatchIds`, `getStagedConflicts`, `revertConflict` are, on the legacy side, a loop of `emit`, a resolved promise, `[]`, `[]` and a no-op. `model-caches.ts` holds the pure id-remap helpers (`remapElement`, `remapRelationship`, `remapCaches`) an entity half's `applyDelta` uses to resolve temp ids to canonical ones across its caches.
- **The notice and the block.** `getReplicaNotice()` (some surface on the engine, phase `server`, not dismissed) is a dismissible warning row — `ReplicaFallbackNotice.svelte`, its own `auto` row in `+page.svelte`'s grid — saying the engine could not start, so the tab reads from the server; `dismissReplicaNotice()` clears it until the next `startReplica()`. `isReplicaBlocked()` (some surface on the engine, phase `failed`, or a `retryReplica()` still running through `resyncing`) blocks the workspace behind `ReplicaFailedOverlay.svelte` — a fixed overlay under the progress overlay's z-index, its Retry button taking focus on mount — showing `Retrying…` disabled while `isReplicaRetrying()`; `retryReplica()` calls `sync.retry()`, the same in-place re-bootstrap that adopts the batches the sync still holds, never a reload. Both read `_status.phase`, so they move with `getReplicaStatus()`; with every switch on `server` neither ever fires, and the indicator alone says so.
- **Raw text.** A feed frame, a commit or revert response body and a tail body reach the engine as the text that arrived, never re-serialized (AD-26): `FeedConfig.onEvent(event, raw)` passes the frame's text, `ApiFetchInit.onText(text)` (on `commitChanges` / `revertToCommit`) hands over a 2xx body before it is parsed, and `lib/api/replica.ts` returns the tail's text with its three envelope fields read off for the shell. `OpsResponseSchema` keeps `prev_rev`. A feed commit event without its text is not handed to the replica.
- **Types only.** `$engine` (`../engine/src/index.ts`) and `$sandbox` (`../sandbox/src`) are aliases in `kit.alias` and again in `vitest.config.ts`; production code imports them with `import type` only, so the app bundle never holds the engine — ESLint's `no-restricted-imports` (`allowTypeImports`) refuses a value import everywhere but `**/__tests__/**` and `testing.ts`.
- **Tests** run the real engine and never mock it: `testing.ts`'s `connectInProcess()` is `createService` with the worker's own `$sandbox/host.ts` (`createHost`, `portOf`) over a Node `MessageChannel` — every link `dispose()`d in teardown, or the vitest worker never exits — and no test uses fake timers. The server is `__tests__/support/project-server.ts`: `fakeProject()` holds the smart-city example in an engine `Model` built from the engine's PUBLIC exports (the engine's own `test/**` helpers fail to load under this Vite root) and serves the descriptor, streamed gzip v2 snapshot bytes, the tail and the metamodel as MSW routes; `syncOver()` is a sync over it with a fresh `fake-indexeddb` (happy-dom has no `indexedDB` or `Worker`). The real handshake, isolation and CSP are e2e's.
- **e2e** — every spec imports `test` and `expect` from `frontend/e2e/fixtures.ts` (types such as `Page` still come from `@playwright/test`; `seed.setup.ts` keeps it whole), whose auto fixture runs the whole suite in engine mode with shadow on: engine mode is `SURFACE_DEFAULTS` (every surface on `engine`, no `dr.surfaces` set), and an init script on the CONTEXT sets `dr.shadow` = `1` once per tab (a `sessionStorage` marker, so a test that removes the key and reloads keeps it removed); a test FAILS on any `[shadow]` console line of any page of its context — the engine and the server answered one read differently. A context a test builds itself gets the same through `engineMode(context)` and `watchShadow(context)`; a `beforeAll`'s `browser.newPage()` gets neither. `engine-mode.spec.ts` holds the reads to the engine: with shadow on every surface's route is requested (shadow's second call), and with it off and a reload none of `/model/summary`, `/model/elements`, `/model/containment/` is while the same walk runs; an own commit shows in the tree and the search, a peer's in the open inspector; a legacy `POST /model/elements` passes the indicator through `resyncing` to `ready` at the new rev; and the app opened at `http://localhost:5173` (the sandbox's host) reads from the server behind `replica-notice`. `frontend/e2e/replica.spec.ts` runs the replica in the real sandbox against the real backend, with a second API client as the peer (`e2e/helpers/api-client.ts`: `peer`, `peerCommit` through locks and `POST /commits`, `silentBump` through `POST /model/ops`) and the indicator read through `e2e/helpers/replica.ts`: ready, isolated, no CSP violation and no console error; an own commit, a peer commit and a silent bump reach it (the bump is healed at the next delta — observed: through the tail, the phase staying `ready`); a reload opens from the cache unless the descriptor's snapshot moved. The iframe's `sandbox` attribute does not stop the module worker in Chromium. The console is watched from the picker on: the login page's session probe answers 401 by design. `isolation.spec.ts` pins one `iframe[title="Data Rover engine"]` of the sandbox origin per workspace, gone after a client-side navigation to `/projects`.

### Backend session & the delta protocol (`src/data_rover/api/`)

This is the central design and the thing most likely to surprise you. The model can be **~80 MB**, so the architecture is built to avoid copying it.

- **`session.py`** holds a process-wide `SessionRegistry` (one independent in-memory `Session` per project id, created lazily on first access). Each `Session` carries the metamodel, model, view, validation baseline, `model_rev`, and `op_log` for its project. Routes resolve the active `Session` per-request from the **`/api/v1/projects/{project_id}` path segment** via `deps.get_request_session`, which depends on `authz.require_membership` so the request is **authorized before the session is touched** (see Tenancy below); the no-arg `get_session()` returns the default project's session for internal/test callers. The **backend session is the source of truth; the client never holds the whole model** — except through the replica (see "Shell" above), which mirrors it in the browser for the five read surfaces.

### Tenancy & auth (`src/data_rover/api/`)

User/project/membership data lives in a **SQLAlchemy + Postgres** layer, separate from the in-memory model `Session`. Tests run hermetic **in-memory SQLite** (`tests/api/conftest.py`); production runs Postgres with the schema owned by **Alembic** (`alembic/`, `pixi run db-upgrade`).

- **`db.py`** — SQLAlchemy 2.0 (sync) engine lifecycle: `Base`, idempotent `init_engine` (in-memory SQLite → `StaticPool`; file SQLite/Postgres → default pool; SQLite gets `PRAGMA foreign_keys=ON`), `get_db` request dependency, `create_all`/`drop_all` (SQLite/dev + tests only — Postgres uses Alembic).
- **`db_models.py`** — `User`, `Project`, `Membership` + `Role` (`owner`/`editor`/`viewer`). FKs cascade (DB `ON DELETE CASCADE` + ORM `passive_deletes`); `role` is `native_enum=False` (VARCHAR+CHECK, portable across SQLite/Postgres). `User.id` is the external identity subject; `User` also carries the local-auth columns `password_hash` (nullable — header/importer users have none), `is_admin`, `is_active`, plus a partial-unique index on `email` excluding the `''` sentinel those passwordless users share.
- **`tenancy.py`** — service functions over the ORM (create/list/get/delete project, member CRUD, `upsert_user`); the single place queries live.
- **`identity.py`** — the **auth seam**: `IdentityProvider.identify(conn) -> Identity` (typed to `HTTPConnection`, the shared base of `Request`/`WebSocket`). Two providers, selected by `DATA_ROVER_IDENTITY_PROVIDER` (default **`cookie`**): `CookieIdentityProvider` (local auth — reads the session-JWT cookie) and `DevHeaderIdentityProvider` (trusts `X-User-Id`/`X-User-Email`, or `?x-user-id=`/`?x-user-email=` on a WebSocket — dev/gateway/tests only); swap via `set_identity_provider`. `get_current_user` is **dual**: the header provider auto-provisions on first sight (zero-setup), the cookie provider does **not** (admin-only provisioning, no self-signup) and 401s when the user is unknown or `is_active=False`.
- **`authz.py`** — `require_membership` (404 unknown project / 403 non-member / 403 viewer-attempting-write), `require_owner` (membership management), and `require_admin` (global-admin gate for the `/admin` routes). Writes are detected by HTTP method with a small allowlist of read-only POSTs (search/batch/validate); `/model/save` and `/model/apply-cr` are deliberately treated as writes, `/model/compare` is read-only (see comments).
- **`routes/projects.py`** — project + membership CRUD at `/api/v1/projects` (the only non-project-scoped data routes). All other data routers mount under `/api/v1/projects/{project_id}`. An admin sees **all** projects with a synthesized `role` (picker visibility, not membership — the data/feed routes still enforce `require_membership`).
- **Local auth (`auth.py` + `routes/auth.py`)** — `auth.py` holds the primitives: argon2 (`argon2-cffi`) `hash_password`/`verify_password`, PyJWT session-token `mint_token`/`decode_token` (carries `user_id` + `is_admin`), and `set_session_cookie`/`clear_session_cookie` (HttpOnly, SameSite=Strict, `Secure` per `auth_cookie_secure`). `routes/auth.py` mounts `/api/v1/auth/{login,logout,me,change-password}`; login is timing-equalized against user enumeration. No change-password UI exists yet — the endpoint is the only path.
- **`routes/admin.py`** — router-level `require_admin`; `/api/v1/admin/users` CRUD + `/api/v1/admin/projects/{id}/members` management. This is the only way to create login-capable users under cookie auth (last-admin/last-owner lockout guards live in `tenancy.py`).
- **`csrf.py` (`CSRFMiddleware`)** — defense-in-depth wired after CORS: on an unsafe method, **if** the session cookie is present, require the `X-Requested-With: data-rover` header (else 403). Cookie-less header-auth requests and login (no cookie yet) are exempt.
- **Dev seed & first admin** — `main._ensure_dev_seed` (gated by `settings.dev_seed`, SQLite-only) **only creates the schema** (`create_all`) — no model or user seeding. `_ensure_bootstrap_admin` is the **sole** user-seed path and runs **always** (independent of `dev_seed`): it create-or-promotes `DATA_ROVER_BOOTSTRAP_ADMIN_EMAIL`/`_PASSWORD` as a global admin — the first admin a fresh deploy logs in as. `_guard_prod_secret` refuses to boot the cookie provider with the insecure default `DATA_ROVER_JWT_SECRET` when `dev_seed=false`. The frontend is a real **login + project picker + admin console** (not single-user). Set `DATA_ROVER_DEV_SEED=false` in production.
- **`routes/ops.py` (`POST /model/ops`)** is the mutation path: clients send small op batches (mirroring `frontend/src/lib/state/ops.ts`). Ops are applied **in place** to the live model while inverse ops and first-touch before-images are collected; a mid-batch failure returns **422** after `_rollback(model, res)` has put every touched entity back from its before-image — properties, `rev` and place in insertion order — in the four passes of the engine's `rewind` (relationships out, elements out, elements in, relationships in), closed by `Model.settle_order()`. Every path that applies a batch and takes it back goes through it — `POST /commits/preview`, `POST /model/validate` with staged ops, `_CommitUnwind`, the persist failures of `/model/ops` and `/model/undo` — so none leaves a trace in any `rev`, in entity order or in the state digest. Each accepted batch bumps `model_rev` once and is appended to `op_log` for undo. `create_element`/`create_relationship` accept an optional **`id` hint** (CR/compare proposals carry the file's real ids): the applier reinstates the entity under it via `Model.restore_*` or 422s the batch when the id is taken, and the journal keeps only the canonical `temp_id`, so replay, undo and the commit diff never see the hint.
- **Rev conflicts**: clients echo `model_rev` as `base_rev`; a stale batch gets **409** and the client must reload.
- **The commit delta (CT-2)**: every landed batch — `POST /commits`, `/commits/revert`, `/model/ops`, `/model/undo` — answers with `prev_rev` (the `model_rev` before the bump), `state_digest` and `recreated_element_ids` / `recreated_relationship_ids` on `OpsResponse` / `CommitResponse` (`prev_rev` and `state_digest` are `null` on a response that applied nothing); `commit_event` carries the same four, and `Commit.state_digest` (nullable, Alembic `0015`) records the digest on the journal row. `Session.state_digest_value` is the CT-3 digest as an integer: `advance_state_digest(res)` folds a landed batch into it in O(batch) (`state_digest.fold_batch`: every before-image out, whatever the batch left behind in), and it is `None` — recomputed in one O(model) pass by the next `Session.state_digest()` — on a fresh or hydrated session and after `set_model` / `touch_model`. A rolled-back batch needs nothing, the rollback being exact; a path that takes a LANDED batch back (a persist failure, `_CommitUnwind` once `rev_bumped`) restores the value from before it. `/model/ops` and `/model/undo` stay silent on the feed: a replica sees the `prev_rev` gap at the next delta. `prev_rev` is kept, and the shell hands the response's text to the replica.
- **Replica routes (`api/replica.py`, `routes/replica.py`)** — pure rules over journal rows in `replica.py` (no FastAPI; queries stay in `content.py`), the routes in `routes/replica.py`, member-gated GETs and so viewer-allowed.
  - `GET /replica/tail?from_rev=` answers `{from_rev, head_rev, complete, deltas}` (`ReplicaTailOut`): a range is served whole or not at all. `content.commit_tail_marks` reads `(rev, expressible)` for `(from_rev, head]` as scalar SQL — a row is expressible with a `state_digest`, `entity_states`, and neither metamodel-id column set; a Python `None` in a JSON column is stored as JSON `null`, not SQL NULL, so the test is `IS NULL OR CAST(... AS VARCHAR) = 'null'` — and `replica.tail_is_complete` demands every revision present, each expressible, and `0 <= head - from_rev <= TAIL_MAX_REVS` (1,000). Anything else is `complete: false` with no row loaded, and the client re-bootstraps. `head_rev` is `session.model_rev` read under `write_mutex` (no journal writer sits between its bump and its `db.commit()` there, so every row up to it is durable), the same number the feed's `snapshot` event reports — which is how a `touch_model` hole at head is seen. Each delta is `replica.delta_from_commit`: `feed.commit_event` built from the RAW `entity_states` (non-null `after`s changed, null ones deleted, in the row's key order; `recreated` absent on old rows = none) and `scope_of_ops` over the raw ops — so it is the feed event field for field (`test_replica_tail.py` holds the two together; `create_commit`'s own scope expression is not refactored onto it). `/model/ops` and `/model/undo` rows, silent on the feed, are served here like any other.
  - `GET /replica/snapshot` (`SnapshotDescriptorOut`: `rev`, `metamodel_id`, `state_digest`, `elements`, `relationships`, `url`) names the snapshot a replica opens from, read off the `Snapshot` row's typed columns — it never touches the blob store. `replica.pick_snapshot` takes the newest v2 row at or below head and accepts it iff `tail_is_complete` over the same marks the tail route reads, so a client that follows a descriptor never meets an incomplete tail; ONE candidate suffices, as an older snapshot's range contains the newest one's. Lock-free fast path first; if it declines, it looks again under `write_mutex` (a second opener finds what the first wrote; a commit mid-flight in the fast path has landed) and only then writes a v2 snapshot at head through `write_snapshot` — a viewer-allowed GET that can fill that cache, holding the mutex ≈ 1.15 s at M plus the upload (measured). A failed write is a 503 `snapshot store unavailable`; no model is a 404 `No model loaded`. The descriptor's `state_digest` is the digest AT its `rev`, not the live one, and its `url` is a PATH (the request's own, last segment replaced), not an absolute URL.
  - `GET /replica/snapshots/{rev}` answers the stored bytes — `application/gzip`, `Cache-Control: no-store` (the shell caches the bytes itself), and NEVER a `Content-Encoding`, so no client library inflates them; 404 `no v2 snapshot at rev N` when the row is missing, is not v2, or its blob is gone. It depends on `require_membership` alone, so it never hydrates a project. It stands in for signed storage URLs: the descriptor's `url` is all a client follows. A v1 row is invisible to both routes.
  - `GET /metamodel` carries `X-Metamodel-Id` (`ModelRow.metamodel_id`, `""` without a row; CORS `expose_headers` lists it) so a client can pair the document with a descriptor's `metamodel_id`. It is read lock-free: a rebind landing between the two reads is healed by the `rebind_event` the client is already buffering.
- **Undo** (`POST /model/undo`) replays an op-log batch's inverses in restore mode (`Model.restore_element/restore_relationship` reinstate exact ids). `op_log` is capped at `OP_LOG_MAX` (1000 batches); past that, `GET /model/changes` reports `complete: false`.
- **Legacy direct-mutation routes** (`routes/elements.py`, `relationships.py`) bypass the op protocol, so they call `session.touch_model()` to invalidate `op_log`/validation and bump `model_rev`.
- **Table sorting is part of the definition** (`TableDefinition.sort`, a priority list of `{column, direction}` keys normalized on read by `core/table/evaluate.py::sort_keys`, never validated): there is no request-level sort, so `/tables/evaluate`, `/tables/export`, `/tables/json-preview`, `/tables/script-errors` and every exporter entry order rows the same way, and the order cache keys on the definition fingerprint alone. The script sweep's job key strips it (`api/script_sweep.py::sweep_fingerprint`) so one sweep serves every order.
- Reads are **paged/on-demand** (element pages, fuzzy search, containment tree children, BFS neighborhoods); load/save **stream** rather than materializing the serialized model as a string. Fuzzy element search (`GET /model/elements?q=`) draws candidates from the trigram index (`IndexSet.search_postings` / `search_candidates`, maintained at the mutation boundary like `roots_order`; ownership is per element — `_trigrams_of` holds an entry for every indexed element, an empty tuple included, so an element WITHOUT one is bulk-loaded and not yet reached by the chunked build, and the property hooks leave it to that build while `search_ready` is False instead of indexing it on first touch). The index is **not** built by `IndexSet.rebuild()` — it is the dominant cost of a bulk load and most `rebuild()` callers (rebind views/previews, apply-cr copies, history reconstructions) never search — so a bulk-loaded model starts with `search_ready=False` and `search_candidates` returns `None`, which is the scan fallback; `api/search_index_build.py` fills the live session's index in chunks under `write_mutex` after load/hydrate (`DATA_ROVER_SEARCH_INDEX_SYNC=true` in tests), and the rebind paths rebuild with `keep_search=True` because the indexed text is metamodel-independent. Queries under 3 chars — or so common the index cannot beat a scan — fall back to the scan too, and results are byte-identical to a full scan either way.
- **Full-model validation is a background sweep** (`api/validation_sweep.py`): load/upload/hydrate install an empty issue store and stream issues in chunk-by-chunk under the write-mutex; `GET /model/status` (non-hydrating — `SessionRegistry.peek`) reports hydration/sweep progress and the frontend polls it during project open. Containment roots are served from a maintained order index (`IndexSet.roots_order`) — never re-sort roots per request.
- **`GET /model/issues` (`routes/validation.py`)** is the cheap read of that maintained store — the frontend's Issues panel is LIVE off it and needs no Validate click to be populated (see frontend/README.md, "Validation issues"). The panel itself is a **closable singleton workspace tab** (kind `'issues'`, id `issues:panel`), opened from the top bar's Issues button and deduped by kind exactly like the metamodel tab; it persists across reloads. It is on a hot multi-client path (every connected client refetches after every peer commit, on every feed reconnect, and repeatedly while the sweep runs), so everything it does is under `session.write_mutex` — including `_ensure_validation_seeded`, so that N clients racing a nulled store (`Session.touch_model`, `metamodel_swap`) cannot each launch their own full pipeline run — and it slices `ValidationState.iter_issues()` lazily at `ISSUES_RESPONSE_MAX` (5000) rather than materializing the store. The cap bounds the server-side copy, not just the wire; `counts` stays EXACT past it (that is what makes the cap acceptable — the client renders a truncation notice, never a wrong number), and there is deliberately no paging: one flat panel list is the only consumer. `POST /model/validate` with no ops remains the full O(model) pipeline and stays reachable ONLY from an explicit user click — never from an open, commit, reload or rebind path.
- **Compare / Apply CR (`routes/change_request.py`)** — two **dry-run** routes that never mutate, journal or validate: `POST /model/compare` (raw other-model body parsed `strict=False`; returns the session→file `datarover.cr/v1` CR plus the file's counts; viewer-allowed, so a viewer can hand an editor a CR). Both raw-body routes — this one and `POST /model/upload` — read through `deps.read_capped_body`, which refuses a body over `max_request_body_bytes` (`DATA_ROVER_MAX_REQUEST_BODY_BYTES`, default 512 MiB, 0 disables) with **413**, never the routes' 422: a `Content-Length` over the cap is refused before a byte is read, but the header is client-supplied and absent on a chunked body, so the running total is enforced while streaming too. Compare is why it exists — it holds the raw bytes plus a second parsed model beside the live one and `POST /model/apply-cr` (`{crs: [...]}`, capped at `MAX_CRS_PER_REQUEST` = 20 at request-parse time — a schema bound like `MAX_EXPORTER_ENTRIES`, since each CR costs an O(model) copy plus a full index rebuild — applied **sequentially and transiently** via the pure `apply_change_request`; the first conflicting CR 409s with `{cr_index, conflicts, model_rev}`; the combined base→final CR (`diff_models`) is gated by `_gate_cr_result` and translated by `api/change_request_ops.ops_for_change` into a phase-ordered op batch — creates with `id` hints → updates → relationship deletes/rewires → element deletes — so `delete_element`'s cascade can never over-delete; an element type change is a 422). The client stages the batch through `state/stage-proposed.ts` (the snippet-run precedent) and commits it like manual edits; **Replace** is the compare CR fed straight to apply-cr. Both are rules-blind by design — staging → `POST /commits/preview` is the validation.

The frontend edits through the check-out/commit flow (staged-edit buffers committed via POST /commits — see frontend/README.md "State model"); the op shapes below are shared by both paths. **`frontend/README.md` documents the frontend architecture in depth — read it before touching `frontend/src/lib/state/`.**

### Durable persistence (`src/data_rover/api/`)

Model content is durable: the in-memory per-project `Session` is a **cache
over a durable journal**, hydrated on cache-miss and snapshotted on eviction.

- **`db_models.py`** adds content tables: `MetamodelRow` (versioned YAML blob),
  `ModelRow` (1:1 with `Project`; carries DB-authoritative `model_rev` + the
  swappable `metamodel_id`), `ViewRow`, `Commit` (PK `(project_id, rev)`; the
  durable op-journal — `ops`/`inverse_ops`/`id_map` as JSON, `author_id` SET
  NULL on user delete), `Snapshot` (PK `(project_id, rev)`; blob `key`; and, for a v2 blob, its header's fields — `format`, `metamodel_id`, `state_digest`, `elements`, `relationships`; all NULL on a v1 row, Alembic `0016`).
- **`storage.py` / `storage_gcs.py`** — the `SnapshotStore` seam. `GcsSnapshotStore`
  (real `google-cloud-storage`) is used in dev (pointed at `fake-gcs-server` via
  `DATA_ROVER_STORAGE_EMULATOR_HOST`) and prod; `MemorySnapshotStore` backs the
  hermetic test suite. One opt-in `integration`-marked test hits the emulator.
  `build_store_from_settings` passes `create_bucket=` **iff** an emulator
  endpoint is set, so the bucket is provisioned at backend boot in dev (docker
  compose owns containers only) while prod never calls `storage.buckets.create`.
  **`snapshot_codec.py`** is the ONE place that knows the blob format — `encode_snapshot` (v1,
  written by no server path, read until F)
  streams a gzip member (level 3) of the COMPACT document (`serialize.iter_model_json_compact`,
  one `json.dumps` per `SNAPSHOT_BATCH` = 2000 entities, byte-identical to a whole-document
  dumps; ~5 % of the indented save-file size), and `decode_snapshot` sniffs the gzip magic and
  falls through to plain `json.loads`, so every row written before compression (indented JSON
  under a `.json` key) still loads: the `.json.gz` key suffix is naming only, readers NEVER
  branch on it, and there is no migration, `encoding` column or backfill. The indented
  `iter_model_json` stays the `/model/save` + `/model/download` contract. `encode_snapshot_v2` writes the line-delimited `datarover.snapshot/v2` form (CT-1: a header line carrying the entity counts, the `metamodel_id` and the `state_digest` of `api/state_digest.py`, then one `serialize.iter_entity_lines` line per entity), and every writer emits it through ONE funnel, `hydration.write_snapshot`: it takes `write_mutex` itself for the whole stream (a v2 text torn by a concurrent commit would be refused by its own header counts — `persist_baseline` and the importer hold no mutex of their own), reads `metamodel_id` from `ModelRow` (`""` without one), writes the SESSION's digest into the header (`encode_snapshot_v2(state_digest=)`; `None` recomputes it) and mirrors the header onto the `Snapshot` row. `scripts/snapshot_v2.py` writes one from a model file, inflated, for the engine's benchmark; the engine's `openSnapshot` reads it; and `decode_snapshot` recognizes it by its first bytes, returns the same `{"elements", "relationships"}` document and raises `ValueError` on a line count that disagrees with the header.
- **`content.py`** — service functions over the content tables (the `tenancy.py`
  of model content). **`hydration.py`** — `hydrate_session` (nearest snapshot +
  replay commit tail through the restore-mode applier) and `persist_baseline`/
  `write_snapshot`. The op journal is (de)serialized via `schemas.OPS_ADAPTER`.
- **`SessionRegistry.get`** hydrates cold projects via an injected loader under a
  per-project init-once lock; **`evict`** snapshots-then-drops under the session's
  `write_mutex`. A contentless project still hydrates to an empty `Session`.
  A lifespan idle-sweeper evicts stale sessions
  (`DATA_ROVER_IDLE_EVICT_SECONDS`, 0 disables).
- **`POST /model/ops`** appends a `Commit` and bumps `models.model_rev` in
  lockstep with `session.model_rev`, under the write-mutex. **`POST /model/undo`**
  appends a *compensating* commit (journal stays append-only; `model_rev` moves
  forward). Upload routes (`metamodel`/`model`/`view`) persist their content so a
  project survives eviction; `/model/save` + `/model/download` remain read-only
  **export** conveniences.
  The every-`snapshot_every` **periodic snapshot** (`routes/ops.py::_maybe_periodic_snapshot`,
  shared by `/commits`, `/commits/revert`, `/model/ops`, `/model/undo`) is scheduled on a
  daemon thread (`api/snapshot_job.py`) that takes `write_mutex` itself, snapshots whatever
  rev it finds (any rev at or past the trigger bounds the replay tail equally), writes nothing
  for a session the registry no longer holds, and logs-and-drops failures; one job per session
  at a time. `DATA_ROVER_SNAPSHOT_SYNC=true` (the test conftest) runs it inline. The
  rebind-forced, evict and baseline snapshots stay synchronous — they are correctness, not
  bounding.
- **`Commit.entity_states`** (nullable JSON) is the full before/after state of every model
  entity a batch touched, captured by every journal writer (`POST /commits`, `/commits/revert`,
  `/model/ops`, `/model/undo`) via `api/commit_states.capture_entity_states` — the applier
  snapshots each entity on first touch (`_BatchResult.before_*`), the post-state is read off the
  live model right before `_persist_commit`, and a `recreated` key names the ids the batch deleted
  and created again (`_BatchResult.recreated_*`; absent from older rows). It exists because the inverse ops cannot render a
  `modified` diff entry (an update's inverse patch carries only the touched keys).
  `GET /commits/{rev}/diff` renders the model half from it and reconstructs the model at
  rev-1/rev **only** when it is `NULL` (rows older than the column, or a batch over
  `ENTITY_STATES_MAX` = 5000 touched entities). Baseline rows (`persist_baseline`, the importer)
  store `NULL` on purpose. The frontend's per-commit Diff calls this route; its two-revision
  Compare still uses `GET /commits/{rev}/model`, which stays O(model) by design.
- **`importer.py`** (`python -m data_rover.api.importer`) turns
  `(metamodel.yaml + model.json + view.json)` into a project's rev-0 baseline;
  the importer CLI / New Project wizard load `examples/smart-city.*` on demand (no autoload).

### Check-out/commit + locking (`src/data_rover/api/`)

Pessimistic leases gate every durable mutation; the legacy unlocked path (`/model/ops`, `/model/undo`) stays mounted for tests and scripts.

- **`locking.py` — `LockTable`** holds in-session TTL leases keyed by resource id (single-instance in-process, per-session). `acquire` is all-or-nothing. Conflict matrix: SHARED never conflicts; non-DELETE EXCLUSIVE conflicts only with another holder's EXCLUSIVE; DELETE EXCLUSIVE conflicts with ANY other holder's lease (including shared pins — that is how a pin blocks deletion). `expand_targets` turns a lock request into `RequiredLock`s, expanding DELETE-intent exclusives to the full containment subtree. `required_locks` derives the lock set from an op batch (delete → subtree; connect → EXCLUSIVE on source + SHARED pin on target); temp/just-created ids within the same batch need no lock. Leases are best-effort write-through mirrored to Redis (`lock_mirror.py` seam: Redis/Memory/Null impls, `DATA_ROVER_REDIS_URL`, empty ⇒ disabled; `lock_mirror_redis.py` isolates the client with 1s timeouts + 30s cooldown) and restored at session hydration with their ORIGINAL tokens, so a client's heartbeat keeps working across a backend restart. The mirror never participates in a conflict decision; a mirror failure degrades (warn), never fails a lock route.
- **`IssueCategory` on `core.validation.issue.Issue`** — two-tier commit gate: `STRUCTURAL` (dangling reference, containment cycle/two-parents) hard-fails at commit with 422; `CONFORMANCE` (endpoint typing, multiplicity, facets, uniqueness, scalar type) is counted and surfaced but never blocks a commit (engine stays inspectable). Default is `CONFORMANCE`; only the handful of structural call sites opt in.
- **`routes/locks.py`** — `POST /locks` acquires leases (all-or-nothing; 409 with conflict detail on failure); `POST /locks/release` releases by token; `POST /locks/renew` heartbeat-extends all leases under a token; `GET /locks` lists active leases for the project. Holder = authenticated user; times use `time.monotonic()` (same clock as the sweeper).
- **`routes/commits.py`** — `GET /open` returns `{model_rev, role, element_count, relationship_count, issue_counts}`; `POST /commits/preview` applies ops → validates the dirty set → rolls back (all under `write_mutex`), returning `conformance_error_count`, `structural_blockers`, and the full `issues` list without advancing `model_rev`; `POST /commits` is the durable lock-verified commit (see below).
- **Commit flow** (`POST /commits`): (1) stale-rev 409 before the mutex; (2) `_ensure_validation_seeded`; (3) under `write_mutex`: verify caller holds every required lock (409 if any expired/missing), apply batch (422 on mutation-boundary error), hard-reject structural blockers (422 + rollback), splice conformance issues into the issue store, bump `model_rev`, record batch in `op_log`, persist a `Commit` row with `message`/`validation_error_count`/conformance `issues` JSON (500 + full in-memory rollback on DB failure), release caller's locks. Returns `CommitResponse` with full element/relationship delta and commit metadata.
- **`Commit` row columns** — `message TEXT`, `validation_error_count INTEGER`, `issues JSON` on the `commits` table; fed by `_persist_commit` via the `_commit_id`/`_message`/`_validation_error_count`/`_issues` kwargs.
- **Lifespan sweepers** — a `lock-sweeper` daemon thread runs every `lock_sweep_seconds` (default 60) calling `LockTable.sweep_expired` on every registered session; `lock_ttl_seconds` (default 300) is the per-lease TTL refreshed on each `renew` call. Both settings are 0-disableable (tests use 0).
- **Evict-with-live-locks guard** — `SessionRegistry.evict` checks `lock_table.active_leases` under the `write_mutex` before removing the session; if any lease is live, eviction is skipped and the session stays registered.
- **`/model/ops` + `/model/undo`** remain mounted as the **legacy unlocked** path for tests and scripts. The frontend does not call them — it edits through the check-out/commit flow, and its `applyOps`/`undoOps` wrappers are test-only.
- **Artifact ops** — `create_artifact`/`update_artifact`/`delete_artifact` join the `OpIn` union: they flow through `POST /commits` (applied, lock-verified — `art:<id>` leases from the typed lock namespace in `locking.py`) and are dry-validated — no lock check, no persistence — by `POST /commits/preview`; `/model/ops` and `POST /model/validate` reject them permanently, and `POST /snippets/run` refuses a guest-proposed one outright (the facade has no artifact surface, so one could only be an injection channel). `api/artifact_ops.py`'s `split_ops` separates the union so they are applied to `ArtifactRow`s on the request's DB transaction, never to the in-memory model (materialized heads — model hydration replay SKIPS artifact ops entirely), with full-state inverses so `POST /model/undo` can replay them in restore mode (journaling a compensating forward commit) and `GET /commits/{rev}/diff` can render them journal-only, like the model half (`api/commit_diff.py`); `/commits/revert` answers a clean 409 for any range containing artifact ops. The kind registry lives in `api/artifact_kinds.py` (`ArtifactKindSpec`: adapter + derived metadata + `extract_deps`/`rewrite_refs`, which drive the import/export closure) — `navigation`, `table`, `code_snippet` and `exporter` are registered; `diagram`/`diagram_kind` stay unregistered and 422 on write. Commit staleness is **overlap-based with a completeness guard**: a stale `base_rev` 409s only when the batch's touched resources intersect the journal tail, but falls back to a strict 409 whenever the tail cannot fully account for the rev gap (something bumped `model_rev` without journaling) or contains an empty-ops/rebind commit; `/commits/preview` keeps strict equality (an empty `POST /commits` is a no-op early return, so a commit can never mint that always-conflict marker itself). Commit feed events carry a `scope` list (`model`/`artifact`). Legacy `PUT`/`DELETE /artifacts/{id}` stay mounted, bumping `artifact_rev` and emitting the same-shaped feed events as the op path. **Lease rule**: `POST /commits` is the only lock-VERIFIED artifact writer, but every other writer HONORS `art:` leases — the legacy PUT/DELETE and the artifact half of `POST /model/undo` all 409 while a peer holds one (the caller's own lease never blocks them) — because `UpdateArtifactOp.artifact_rev` is an optional precondition the current client contract omits, which makes the lease, not OCC, the real concurrency control.
- **Named views** — a project holds N views (`ViewRow`: `id`, `name` unique per project, `blob`, `view_rev`), all hydrated into `Session.views: dict[id, View]` (complete after hydration — a missing id is a client error, never a cold-cache miss). Selection is **per client**: `routes/views.py` exposes `GET /views` (summaries), `GET /views/{id}` (content + `validate_view` warnings), `POST /views` (`{name, view}` → 201; the row's `name` overwrites the document's; 409 duplicate name, 422 malformed), `PUT /views/{id}` (`{view, base_view_rev?}` — whole-document replace, the View menu's JSON editor Save; a differing `name` renames, 409 on a stale rev, duplicate name or a peer lease inside the view, folder ids colliding with another view's are reassigned) and `DELETE /views/{id}` (204; 409 while a PEER holds the view's `view:` lease or any `folder:` lease inside it). Add/replace/delete are DIRECT actions like `POST /metamodel` — under `write_mutex`, never journaled or undoable, broadcast as `view_event(created|updated|deleted)` so peers refresh their list (and refetch an updated active view); `GET /model/containment/roots/excluded?view_id=` scopes the excluded pool (absent → every root). The frontend remembers the active view per project in localStorage and stamps it on every staged op.
- **View ops** — folders carry stable uuid ids (`Folder.id`, healed lazily by `core/view/ids.ensure_folder_ids` at hydration/import — blob content needs no migration; `views.view_rev` is a real column). Every op of the ten-op `view.*` family (`create/rename/move/delete_folder`, `place/remove/move_element`, `place/remove/move_artifact`) carries a **`view_id`** (`str = ""` — the default exists ONLY so journal rows from before named views still parse; `POST /commits`/`/commits/preview` 422 an empty or unknown id via `view_ops.resolve_view`, and undo resolves an empty one to the project's SOLE view or 409s with push-back). The family flows through `POST /commits` only: `api/view_ops.py` applies each `group_by_view` group to the in-memory `session.views[view_id]` with exact inverses (apply-then-inverse restores a byte-identical blob — the invariant undo and `GET /commits/{rev}/diff` lean on; the diff renders view commits journal-only, prior names off the inverse half, each entry stamped with its `view_id`), then every touched view's blob is persisted (`content.upsert_view`) + `view_rev` bumped on the commit's transaction and reported as `CommitResponse.view_revs`. `/model/ops`, `/model/validate` and guest-proposed snippet ops reject the family (alongside the `metamodel.*` family — see "Live metamodel editing" below); model hydration replay skips it; `/commits/revert` answers 409 across it. Locks: `folder:<id>` leases (`LockTargetIn.type: "folder"`; DELETE intent expands over the folder subtree in the view that OWNS the folder; element placement ops lock only the containing folder) and, for a view's ROOT membership, the view's own `view:<id>` lease (`LockTargetIn.type: "view"`, `locking.container_resource`) — folder ids are uuids, unique across views, so only the root needed view scoping. The conflict backstop compares `folder:`/`view:` resources plus `viewel:<view_id>:<eid>`/`viewart:<view_id>:<aid>` placement-subject markers (the same element placed in two views is no conflict). Element placements never target the root (`VIEW_ROOT_ID = "root"`): an unplaced element renders there, so "move to root" is `remove_element`; artifact refs have a real root list and may sit in many folders. The client commits every `view.*` op through `POST /commits`.
- **Import/export** — `api/artifact_bundle.py` owns the `datarover.artifact-bundle/v1` envelope, the `extract_deps` BFS closure, and the stateless plan→confirm import (`POST /artifacts/{export,export/preview,import/plan,import}`): confirm re-derives the plan, builds fresh-id `create_artifact` ops (refs pre-rewritten to temp/reuse ids; the commit applier resolves the rest) and lands ONE commit via `create_commit` — no leases, 409-with-fresh-plan on any stale decision or apply-time clash (the 409 carries the applier's own detail, never a bare "stale"), and a no-op (never an empty batch) when nothing is created. `extract_deps` is a generic `{"ref": ...}` payload walk, so a REF-valued `transform` (an exporter entry's or a table's) is a bundle dependency it finds and pulls in, while an INLINE `transform` is plain data the walk never sees — an exporter/table using only inline transforms exports bundle-self-contained, one using ref transforms drags its snippet artifacts along. A client `copy_names` rename is vetted against the plan's per-kind taken-name pool (`derive_plan_ex().taken_names`) and rejected by name in `build_import_ops`, since a whole-plan 409 for it would re-derive byte-identically and loop forever. `importer.import_project(artifact_bundle=…)` lands baseline artifacts with id remap + view-blob ref rewrite, and its `trust_artifacts` flag splits its two callers: `clone_project` alone passes it (verbatim copy — unregistered `diagram` rows ride along, because that bundle never left this DB), while the wizard/CLI take the safe default and hold every artifact to what a normal write enforces (registered kind, adapter-valid payload, re-derived `entry_points`), reporting-and-skipping the rest exactly like `derive_plan` — so all three import-from-outside paths accept the same bundle. Duplicate `(kind, name)` inside a bundle is a skip (first wins) on every path; dangling refs, including refs to skipped artifacts, are always tolerated. Export/preview are viewer-allowed read-only POSTs. The frontend exposes this via the TopBar's Artifacts menu (`ArtifactsMenu.svelte` + `ExportArtifactsDialog`/`ImportArtifactsDialog`) and a per-artifact export button in each artifact editor's own toolbar (`ArtifactExportButton.svelte`), and the New Project wizard accepts an optional bundle file and surfaces any `ProjectOut.skipped_artifacts` in a warning panel before navigating to the new project.

### Realtime feed (`src/data_rover/api/`)

Server-to-client WebSocket feed.

- **`feed.py` — `FeedHub`** holds a per-`Session` set of `ClientConn`s (each with a bounded `asyncio.Queue`). `broadcast` is sync and thread-safe: it schedules enqueues on the event-loop thread via `loop.call_soon_threadsafe` so it is safe to call while holding the `write_mutex`. A client that falls behind has its queue drained, receives `CLOSE_SENTINEL`, and is dropped; its sender pump closes the socket with 4408 and the client reconnects. The event loop is captured lazily on the first WebSocket connect via `set_loop_if_unset`; `reset_loop` provides test isolation. The event builders (`snapshot_event`, `commit_event`, `reset_event`, `lock_event`, `presence_event`, …) return plain dicts serialized by `ws.send_json`.
- **`routes/feed.py` — `@router.websocket("/feed")`** mounts under the `/{project_id}` prefix. Authentication uses the `IdentityProvider` seam (typed to `HTTPConnection`, the shared base of `Request`/`WebSocket`): the default `CookieIdentityProvider` reads the session cookie the browser sends on the same-origin WS upgrade (no query params); `DevHeaderIdentityProvider` falls back to `?x-user-id=`/`?x-user-email=` query params (dev/tests). Close codes: 4401 (no identity), 4403 (non-member), 4404 (unknown project), 4408 (dropped-behind). On connect: capture the event loop, auth+authz over a short-lived DB session, register `ClientConn`, broadcast a presence-join, send an initial snapshot (current `model_rev` + active leases + connected users), then run a sender pump (`_pump`) alongside a receive loop that only observes disconnect. On disconnect: unregister and broadcast a presence-leave.
- **Broadcast hook sites** — commit delta + lock release after `POST /commits` (in `routes/commits.py`); lock acquire in `POST /locks` and release in `POST /locks/release` (in `routes/locks.py`); lock expiry in the lifespan lock-sweeper (`main.py`); `Session.announce_reset()` — a header-only `reset_event` (`{type, model_rev}`) for a `model_rev` bump that writes no journal row, fired by `set_model`, `touch_model` and `set_metamodel` unless they are passed `announce=False`. Two callers pass it and announce late, after their durable writes (in a `finally`, so a failed write still announces the bump): `routes/model.py::_install_model` after `persist_baseline`, and `POST /metamodel` after its rows are committed — an earlier event would send a replica to `GET /replica/snapshot` between the bump and those writes, to open from the rows they are about to replace (and, for an upload, to write a second snapshot). `POST /locks/renew` is silent (heartbeat only, no peer-visible state change).
- **`identity.py` (WS detail)** — `identify` is typed to `HTTPConnection`; on a WebSocket the cookie provider reads the session cookie and `DevHeaderIdentityProvider` reads `conn.query_params` instead of `conn.headers` (browsers can't set WS headers). See the auth section above.
- **Evict guard extension** — `SessionRegistry.evict` skips eviction while `session.hub.has_clients()` returns true (mirrors the live-leases guard); `feed_queue_max` setting controls per-client queue depth.

### Code execution (snippets) (`src/data_rover/core/script/`, `src/data_rover/api/`)

Server-run Python snippets against the live session model, sandboxed in WASM. Ground truth + full facade reference: `src/data_rover/core/script/README.md`.

- **Artifact kind** — `code_snippet` is a fifth `ArtifactKind` (`db_models.py`), payload validated by `core/script/schema.py`'s `SnippetDefinition` (`schema_version`, `language: "python"`, `code` capped at `SNIPPET_MAX_CODE_BYTES` = 64 KiB, `entry_points`). `entry_points` is **server-derived, never client-trusted**: `routes/artifacts.py`'s `_apply_derived_metadata` overwrites it from `core/script/lint.derive_entry_points` (AST-based) on every create/update — a snippet always gets `"script"` plus `"value"`/`"step"`/`"transform"` (`core/script/lint.py::_ENTRY_NAMES`) if it defines a matching one-arg top-level function. Inline runs (`SnippetRunIn.code`, no saved artifact) never populate `entry_points` at all.
- **`ScriptRunner` seam (`core/script/runner.py`)** — a `Protocol` (`run(model, RunRequest, RunLimits, *, record_ops, rev) -> RunResult`) that is deliberately sandbox-agnostic (`data_rover.core.*` + stdlib only). Two implementations: `api/script_runner.py`'s `WasmScriptRunner` (the only production choice — `wasmtime` is imported **nowhere else** in the repo) and `tests/script/trusted_runner.py`'s `TrustedRunner` (in-process `exec`, no sandbox at all — must never move to `src/`). `build_runner_from_settings` is the **RCE tripwire**: selecting `snippet_runner="trusted"` raises at boot unless `settings.dev_seed` is true, mirroring `main._guard_prod_secret`'s refuse-to-boot posture.
- **`WasmScriptRunner` mechanics (one-liner)** — a warm pool (`snippet_pool_size` pre-booted CPython-WASI/wasmtime guest instances, one shared `Engine` + cached `Module`) drives a newline-JSON bridge protocol per run, arming a per-run epoch deadline (wall-timeout kill) and memory cap on the guest's `Store` while it's parked on stdin; determinism shims pin the WASI realtime clock and `random_get` (paired with guest-env `PYTHONHASHSEED=0`) so identical code produces byte-identical output; guest death/traps are mapped to `ScriptError.kind` per the table in that module's docstring (`syntax`/`runtime`/`timeout`/`memory`). Every instance is discarded after one run (never returned to the pool) for a clean interpreter per snippet.
- **Routes (`routes/snippets.py`)** — `POST /snippets/{run,lint,format,cancel}` under the project prefix. `run`/`lint` read `session.model` **without** `session.write_mutex` (the bridge dispatcher only ever calls read accessors; writes are recorded op *proposals*, never applied) and report `stale = start_rev != end_rev` if a concurrent commit landed mid-run; both are in `authz._READ_ONLY_POST_SUFFIXES` alongside `cancel`, so viewers may run/lint/cancel their own runs. `cancel` is a **real registry + ownership check** (404 for unknown-or-not-yours) but the actual abort is a no-op (`_noop_cancel`) — a run only ends via `wall_timeout_s`. Concurrency is capped globally and per-user (`_ConcurrencyGuard`, fail-fast 429, no queuing) via `snippet_concurrency`/`snippet_per_user_concurrency`. Every run logs one audit line (`user`, `project`, `code_sha` prefix, `entry`, `duration_ms`, `ops` count, `outcome`). `format` (the editor's Reformat button) shells `ruff format` through `api/script_format.py` — ruff is a `[feature.api.dependencies]` runtime dep, and it parses and prints rather than executing, so no sandbox is involved; the call pins `indent-width=4` to match the editor's own `INDENT_WIDTH` and passes `--isolated` so a stray config file in the server's cwd cannot change the result. It answers **422** on unparseable code and **503** when ruff is absent (degraded, never 500), and is in `authz._READ_ONLY_POST_SUFFIXES` too, so viewers may format their own drafts.
- **Settings (`api/settings.py`)** — `snippet_runner` (`"wasm"`|`"trusted"`, default `"wasm"`), `snippet_guest_wasm_path`/`snippet_guest_lib_path` (vendor binary/stdlib, unfetched by default), `snippet_pool_size` (default 6 — 4 sweep workers + 2 interactive headroom), `snippet_concurrency`/`snippet_per_user_concurrency` (4/1), the embedded-evaluation knobs `snippet_eval_budget_s`, `snippet_cell_cache_max` (50 000 cells per SESSION, shared across all its tables) and the sweep's `snippet_sweep_workers` (4) / `snippet_sweep_ceiling_s` (600) / `snippet_sweep_timeout_abort` (3) / `snippet_sweep_sync` (false; test seam), and the `RunLimits` mirrors `snippet_wall_timeout_s`/`snippet_memory_bytes`/`snippet_stdout_bytes`/`snippet_result_repr_bytes`/`snippet_max_ops`/`snippet_max_op_bytes`/`snippet_page_limit` — all `DATA_ROVER_SNIPPET_*` env vars (standard `DATA_ROVER_` prefix).
- **Guest binary** — `spikes/code_exec/vendor/python.wasm` + stdlib are NOT committed; they are fetched **automatically** by `scripts/ensure_guest.sh`, a `[feature.api.activation]` hook that runs on every `pixi run -e api ...` / `-e core-dev ...` and short-circuits on two stat calls once vendored (that script is *sourced* by pixi — read its header before touching it; `exit` there breaks every task). Fetch by hand with `bash spikes/code_exec/fetch_python_wasi.sh [--force]` (idempotent). A failed fetch is deliberately non-fatal. Without the binary, `main._boot_script_runner` logs a warning and leaves the runner `None` (routes 503) rather than failing startup. The `integration`-marked test (`tests/api/test_snippets_wasm.py`) exercises the real sandbox end-to-end and needs the binary fetched first.
- **Frontend** — the snippet workspace tab, console, and ops staging live in `frontend/src/lib/{state/snippet-editor.svelte.ts,state/snippet-stage.ts,components/Snippet/}`; see `frontend/README.md` for the client-side architecture.
- **Embedded evaluation (`ScriptColumn`/`ScriptStep`)** — table columns and navigation steps evaluate a snippet's `value(elements)`/`step(el)` against the live model via `ScriptRunner.open_session` (one warm guest per distinct code, execs the facade + module once, then serves repeated entry-point calls), threaded through `core/script/embed.py`'s per-request `ScriptEvalContext` — which memoizes by `(code, entry, element_ids, inputs digest)`, collects `.warnings`, and enforces a shared `ScriptBudget` (`snippet_eval_budget_s`). A `ScriptColumn` may declare `inputs` (named backward-only `ColumnRef`s, `core/table/schema.py::ScriptInput`) handed to `value(elements, inputs)` as `dict[str, list]`; `core/table/script_inputs.py` resolves them per row to what the referenced cell holds and is the ONE `value()` call site (`evaluate_script_column`) — the resolved values are in the cache key, so invalidation needs nothing new, and a pending/errored input yields an uncached pending/error cell rather than a call. Non-fatal degradations (a snippet that raises pruning its chains, a returned id the model doesn't recognize) go out through a **structured** warning channel, not prose: `core/script/warnings.py`'s `ScriptWarningLog` aggregates by `(code, detail)` — `occurrences` counts how many times a kind fired, `total` sums the subject quantity it carries — capped at `MAX_SCRIPT_WARNINGS` (20) distinct kinds held at once (a kind already present keeps counting past the cap; only brand-new kinds are dropped). The wire form (`ScriptWarningOut`) ships codes and counts, never sentences; the frontend's `formatScriptWarning` (`frontend/src/lib/script/warnings.ts`) is the sole place that turns a code into user-facing copy, so the table's warnings badge/panel and the nav dock's tooltip render identical wording from the same data. **No request ever computes a whole table**: results live in a rev-stamped per-session `ScriptCellCache` (`core/script/cell_cache.py`), the whole-table passes in `/tables/evaluate` and `/tables/export` run CACHE-ONLY (a miss yields a synthetic `pending` cell rather than a guest call), and a background `SweepJob` (`api/script_sweep.py`, sort-less job key, sharded over `snippet_sweep_workers` guest sessions, with consecutive-`timeout`/`unavailable` abort guards and failed-job memory) fills the cache. Cells carry per-call read-sets and commits evict selectively via `api/invalidation.touched_keys` + `ScriptCellCache.evict_touched` (clear-all survives only on the no-op-delta paths); the guest facade memoizes reads for the session lifetime and hop/call frames inline element projections (trip collapse) — see `core/script/README.md`. Clients poll on `TablePageOut.script_status` (`ready` | `computing` | `failed`; a response that saw a pending cell can never report `ready`, and a TERMINAL sweep that still left holes — an LRU-evicted or never-cacheable cell — reports `failed`, since failed-job memory would otherwise hand the same dead job back to every poll forever), and export answers **`202 + Retry-After: 1`** while the sweep is in flight — the status code, not the body's `state`, is the retry signal. The stance stays **degraded, not failed**: a missing runner, a full concurrency slot, or a snippet error never 5xxs a table/nav route — it renders error cells or pruned-with-warning chains at 200. Embedded work draws one **global** slot (no per-user cap) per evaluate/export request from the guard console runs use (`api/snippet_concurrency.py`); sweeps draw from their own semaphore instead, which is why `snippet_pool_size` is 6 (4 sweep workers + 2 interactive headroom). `routes/tables.py`'s `TableOrderCache` cache-poisoning guard also declines to cache an order when anything went pending (that order is the degraded build order, and neither fingerprint nor `rev` changes on retry). Full mechanics (cache key/stamping rules, sweep lifecycle, the module-global "don't", settings table) are in `core/script/README.md`'s "Evaluation sessions" section.
- **Table export formats** — `POST /tables/export` takes `format: "xlsx" | "json" | "csv" | "jsonl"` (default `xlsx`) and branches only at its final render step, so the 202/completeness-probe preamble is shared. JSON rendering lives in `core/table/json_export.py` (pure; core needs no dependency for it, unlike the xlsx writer in `api/table_export.py`). CSV shares its cell display text with the xlsx writer through `core/table/cell_text.py`, so the two formats cannot drift. Per-column settings ride on the column itself as `json_export: JsonColumnOptions | None` (`key` / `item_key` / `value` / `group` / `single`) so reorder/insert/remove need no index remapping; on a grouped column `key` names the array at its home level while `item_key` names its own value inside each entry (blank = same as `key`). `single` renders an array cell as ONE value instead of an array — BOTH array kinds a navigation can yield per row, an `ElementsCell` and the `ValuesCell` a scalar property step reaches, since collapsing only one would ship `[5]` and `null` under the same setting (empty → `null`; more than one item → 422 naming the column, strict like `json_doc.key_column`, because the shape is a contract a consumer branches on) and, because `ColumnOverride` reuses `JsonColumnOptions`, is available per entry column in an exporter too. `group` rolls an `expand` column's rows back into an array, keyed off the `RowKey` expand slot — never off value comparison — and nests any column that transitively sources it; it is honored only on a VISIBLE EXPAND column and tolerantly ignored elsewhere. Failed and uncomputed cells render `{"$error": ...}` rather than `null` so a consumer can tell failure from emptiness. `POST /tables/json-preview` renders a bounded sample through the same function for the settings UI (whole-table passes cache-only, the sample window itself evaluated live, so a cold cache shows values rather than `$error` markers). The object shape's key is read through `_render_key_cell` with `single` FORCED on: a key is a scalar by contract, so a navigation/script cell holding exactly one element or value keys the document without the author flagging the column, and more than one is a 422 worded for `json_doc.key_column`. A JSON export can additionally set `json_split: JsonSplitOptions` (`enabled`, `filename_template`) to fan out into **one file per base element** instead of one combined document: `core/table/split.py` buckets rows by `RowKey` slot 0 (the base element for a scope/nav source, the chain origin for a chain) and renders each bucket through the same `render_json`, sitting ABOVE it as a pure partitioning/naming layer — never touched during evaluation. `filename_template` is a strict `${name}` template (`${name}` swapped for each base element's display name); the token's absence is a 422 at export time (`split.validate_template`), deliberately not at save time, so a stored-but-not-yet-fixed template never blocks saving or evaluating the table. Filenames are sanitized and length-capped, then deduplicated `_2`, `_3`, ... in row order; the result always ships as a zip (`ExportFiles.archive=True`), which is why `table_export_engine.py` (shared by both `/tables/export` and `/exports/run`) centralizes the zip builder alongside the 202-vs-ship completeness probe. An exporter entry's `json_doc: JsonDocumentOptions` (`shape: 'array'|'object'`, `key_column`, `pretty`, `on_error: 'emit'|'fail'` — never on a bare `TableDefinition`) shapes the `json`/`jsonl` document after rendering, applied render → shape → serialize in the shared engine, and is strict (422 at export time, never at Save) about a missing/duplicate/non-scalar object key or an `on_error: 'fail'` document still carrying an error cell. **`exporter`** is a sixth artifact kind (`core/table/exporter.py`): a named collection of `ExporterEntry` table refs (`ExporterDefinition.entries` capped at `MAX_EXPORTER_ENTRIES` = 50 — a schema bound like `SNIPPET_MAX_CODE_BYTES`: rejects at artifact save AND at `RunExportIn.definition` request-parse time, never as an export-time business rule, because a viewer-callable `RunExportIn.definition` draft run could otherwise chain N whole-table, O(model) exports into one synchronous request), each an independent presentation override (`ColumnOverride` by column index, `export_order`, `show_row_numbers`, `export_row_number`, `json_split`) over a table it does NOT own — `overridden_table` restates those fields onto a COPY of the table's `TableDefinition` (RENDER ONLY: evaluation, row order and script cache keys stay off the original), so one exporter artefact can export tables A/B/C under entirely different column sets and names without touching how A/B/C export standalone. Each entry also carries a `folder` — a per-entry template path inside the archive — and the definition as a whole carries `output: OutputOptions {mode, filename, manifest}`: `mode` is `"zip"` (default) or `"bare"` (ship the single produced file directly, no archive — a CONTRACT, not best-effort, so a run that produces more than one file 422s rather than silently falling back to zip under a consumer expecting one content type); `filename` templates the zip's own download name; `manifest` (default on, zip-mode only) adds a deterministic `manifest.json` recording what every entry rendered to. `POST /exports/run` (`api/routes/exports.py`) resolves every entry's table up front — a missing table 422s loudly naming the entries rather than shipping a partial zip — runs each through the shared engine, and zips the results: a split entry's files nest under `{entry's rendered folder}/{entry's rendered name}/`, and dedupe keys on the FULL archive member path (`_dedupe_path`'s `taken` set) scoped per folder, not on a bare root-level stem — two entries landing in different folders never force a suffix on each other, and a split entry's OWN produced member paths are reserved into `taken` too, so a plain sibling entry that renders into the split entry's folder collides instead of silently overwriting a zip member. A still-computing entry yields ONE aggregate 202 (`computing` wins over `failed` unless every entry is dead, `done`/`total` summed). `RunExportIn` takes exactly one of `artifact_id`/`definition` (422 otherwise) — a `definition` is a staged draft validated by the same `ExporterDefinition` schema and run through the identical guards, with `name` feeding the zip-stem fallback and the manifest's `artifact_name` (`artifact_id: null` marks a draft run); `GET /exports/run-by-name?name=` runs a committed exporter by name for CI (404 unknown, 409 with candidate ids on ambiguity, response contract shared via `_execute_export`); and the frontend's Export button ships dirty/uncommitted drafts inline while the add-table control is a searchable typeahead. **The `transform(doc)` snippet hook** is the customizability escape hatch — attaches at TWO independent presentation fields with the same no-bleed rule as every other `overridden_table` field: `ExporterEntry.transform` (an entry's own) and `TableDefinition.transform` (a table's own, for the standalone `POST /tables/export`) — both `SnippetSource | None`, a saved-snippet ref OR inline code like every other `SnippetSource`, JSON-family formats only (`json`/`jsonl`; set on an `xlsx`/`csv` entry or table → 422, since silently skipping a transform would ship untransformed data — a functional contract, not a presentation preference). `None` and an empty (`{}`, unconfigured) source both mean "no transform" — every gate on the field tests `is not None and not .is_empty`, never bare truthiness, so an unconfigured source never 422s an `xlsx`/`csv` entry or draws an interactive concurrency slot. Pipeline position inside `run_table_export` (`api/table_export_engine.py`): render → `on_error` check (on the freshly rendered per-row documents, BEFORE shaping — so a transform can never launder an error marker past the check by transforming it away) → shape → **transform** → serialize; on a split export it runs ONCE PER FILE, called with that file's already-shaped document. `jsonl`'s transform must return a `list` (each item one line) or 422s naming the entry. Entry-point derivation: `"transform"` is in `_ENTRY_NAMES` (`core/script/lint.py`) — a one-arg top-level `def transform(doc)` adds it to the server-derived `entry_points`, same as `value`/`step`; the STORED `entry_points` is advisory only and is re-derived from the code at resolution time for BOTH forms — both run routes (`routes/tables.py::_resolve_transform_source`, reused by `routes/exports.py`) 422 naming the entry when a ref doesn't resolve to a `code_snippet` artifact in the same project, or inline code fails to parse, or either form's code lacks a one-arg top-level `transform`. Execution is identical on both surfaces through the shared engine: `TransformHost` keys warm `SnippetSession`s by CODE STRING — one per DISTINCT transform code, shared across every entry/file in one export run that references it regardless of whether each references it by ref or inline, LRU-evicted past `_TRANSFORM_SESSION_CACHE_MAX` (8, sized for inline code making distinct-code-per-entry the common case rather than one snippet shared by many entries) — drawing exactly ONE global interactive concurrency slot for the whole run (`open_transform_host`/`api/snippet_concurrency.py`) and one shared `ScriptBudget`. `TransformUnavailableError` is the ONE exception to the export engine's degraded-not-failed stance: no runner constructed → 503, no free interactive slot → 429 (the snippet-console routes' precedent) — mislabeling either as 422 would call a transient condition a definition error. Any other transform failure (boot error, raise, timeout, unserializable/over-cap return) is a plain `ValueError` → 422 naming the entry — a machine consumer must never receive a half-transformed document at 200. Setting `snippet_transform_max_bytes` (default 8 MiB, `DATA_ROVER_SNIPPET_TRANSFORM_MAX_BYTES`) caps the document sent to the guest AND the document received back, independently, both directions over → 422. `POST /exports/run` records each entry's transform on `ManifestEntry.transform`: the artifact id for a ref source, `inline_transform_marker`'s content-addressed `inline:<sha256(code)[:12]>` for inline code (deterministic and wall-clock-free, so a rerun at the same rev stays byte-identical), `None` when the entry has no transform. **`POST /exports/preview-transform`** (`{entry}`, a viewer-allowed read-only POST) is the exporter entry's Test button: it renders the entry's table the way the export would (the entry's overridden layout + `json_doc` shape, `table_export_engine.render_json_sample`, which shares `json_key_column`/`shape_json_docs` with `run_table_export`) with script cells evaluated LIVE under the eval budget — a cache-only render would 422 a script-backed key column on a cold cache while the real export, which waits for the sweep, succeeds — and runs `transform(doc)` through `TransformHost.apply_ex` — the structured sibling of `apply`: the snippet's own failure (boot, raise, timeout) comes back as a typed `error` with traceback at **200**, while entry problems keep `/exports/run`'s 422 wording and no-runner/no-slot keep 503/429. The response is per FILE (`TransformPreviewOut.files[]`, each `filename`/`input`/`output`/`stdout`/`error`/`duration_ms`, the documents as pretty-printed text): an UNSPLIT entry is one file rendered from the `PREVIEW_MAX_ROWS` sample window (`truncated` = the table has more rows); a SPLIT entry is the FULL run — every row, every partition, named through the same `render_filenames` dedup as the export, one `transform(doc)` call per file, continuing past a file whose transform fails so each reports its own outcome — bounded by `PREVIEW_MAX_FILES` (200; `truncated` = more partitions exist) rather than by rows, because debugging one-file-per-element output means seeing every file, not the first. The frontend renders the single file flat and a split run as one collapsible per file, all collapsed, headed by the filename. That last field exists because **`CallResult.stdout`** carries each session call's prints (the WASM guest's `call_result` frame and the `TrustedRunner` both capture per call; module-level prints ride on the first call's stdout only); the embedded evaluators ignore it.

Every user-facing name/path in an exporter run — the zip filename, an entry's name, an entry's folder, a split partition's filename — renders through ONE `${token}` engine, `core/table/naming.py`: `NAME_TOKENS` (`name`/`rev`/`date`/`project`) covers the first three contexts, `SPLIT_TOKENS` adds `id` for the fourth, and `${name}` BINDS to something different per context (the artifact's own name for the zip filename, the table's name for an entry's name/folder, the partition's base-element display name for a split filename — see that module's docstring table for the full mapping, including that `${rev}`/`${date}`/`${project}` are the run's `session.model_rev`/UTC `YYYYMMDD`/project id, shared across every context in one run). The engine is deliberately two-phase: `validate_tokens` runs UP FRONT, so an unknown token is a 422 naming the offending entry before anything renders, while `substitute` itself never raises and leaves unknown tokens verbatim — safe to call on already-validated input. `sanitize_stem` (character cleanup) and `folder_segments` (path-segment rules — rejects absolute/empty segments, neutralizes `..`) are the zip-slip seam a rendered template crosses before becoming an archive member path; this is **strict-at-export, never-block-Save**, uniformly — a bad template, an absolute folder, a tokenless split template all 422 at `POST /exports/run` (naming the entry), never at the artifact's own Save, so a definition mid-edit is never rejected for a mistake only export-time rendering can even detect. `api/export_manifest.py`'s `build_manifest` is deliberately NO-WALL-CLOCK (no `generated_at`): the manifest's identity is `model_rev` plus the run's entries/overrides, so two runs at the same rev are byte-identical zips, matching `build_zip`'s own `ZIP_DATE_TIME`-pinned determinism.
- **Per-pass navigation memo (`core/table/nav_memo.py`)** — `build_rows_ex`, `order_rows` and `evaluate_cells` each construct their OWN bounded `NavMemo` (LRU, 64 entries) keyed by `(column identity, roots)` and thread it through `resolve_source_elements`/`_navigation_reached`/`_navigation_step_elements` like `script`, so the split rows of one root (contiguous in build order) re-navigate once instead of fan-out times. The memo is NEVER a public-entry-point parameter, never lives on a `Session`/`ScriptEvalContext`, and a navigation with a `ScriptStep` bypasses it (`NavMemo.scripted`) — the two guards that keep a result computed under `cache_only` (build/sort) from ever being served to the live window pass. Entries are immutable chain tuples; consumers only iterate.
- **Scope row sources (`core/navigation/evaluate.py::_scope_ids`)** — the ids a `Scope` selects (every `ScopeRows` table's rows — paid once per table per commit through `TableOrderCache` — and every `Scope`-started navigation's starts, paid on every page request) come back SORTED by id — the evaluator's "depth-first over SORTED element ids" paging-determinism contract, deliberately not insertion order. The untyped branch walks `model.elements` in insertion order and never builds an id set: production ids are time-ordered UUIDv7 and the importer's are sequential, so `sorted` sees a presorted run and finishes in O(n) comparisons (~24 ms at 320k elements), and an empty criteria list skips the matcher entirely. Never route it back through a `set` — the hash order is what makes the sort O(n log n).
- **Export overrides (`core/table/export_layout.py`)** — which columns an export contains, in what order, under what names: the ONE place that answers it, so the xlsx writer, the JSON renderer and the dialog's client mirror (`frontend/src/lib/table/export-layout.ts`) cannot drift. `ColumnExportOptions.include` is **tri-state** — `None` follows `hidden`, which is the whole no-migration guarantee: every table that exists today exports byte-identically until someone opens the dialog. `export_order` holds definition indices with **`-1` (`ROW_NUMBER_SLOT`)** standing for the row-number pseudo-column, and is **normalized defensively on read** (drop out-of-range/duplicates, drop `-1` when `show_row_numbers` is off, append what the list forgot) rather than validated into a 422 — a presentation setting must never block an export. It is an OUTPUT order: definition column order is structural (backward-only `ColumnRef`, positional expand slots) and is never permuted. `display_order` is its sibling for the GRID (`normalized_display_order`, same defensive normalization, `[]` = definition order): the frontend renders columns through it while cells/sort/refs keep definition indices, and an EMPTY `export_order` is completed in display order, so an export matches the grid unless the export dialog said otherwise. **RENDER ONLY** is the rule that keeps this contained — `export_definition` (which restates inclusion as `hidden` so `json_export`'s existing hidden-column and group-nesting logic is reused unchanged) reaches `render_json_ex` and nothing else; `build_rows_ex`/`order_rows`/`iter_export_rows`/the script context all keep the ORIGINAL definition, so cell values, row order and every script cache key are independent of export presentation.

### Live metamodel editing (`src/data_rover/api/routes/metamodel*.py`, `api/metamodel_ops.py`, frontend `state/metamodel-{editor,diagram,stage}.svelte.ts`)

The metamodel is edited as YAML **in the app** instead of by uploading a file, and both metamodel edits and diagram node positions flow through the **same check-out/commit pipeline** as model/artifact/view edits — there is no separate swap page. Two routes sit beside the commit flow as an ADDITIVE pair (`POST /metamodel/diff`, `POST /metamodel/lint`); there is no `POST /metamodel/rebind` and no `PUT /metamodel/layout`.

- **`GET /metamodel/raw`** (`routes/metamodel.py`) returns `{blob, source}`: the stored `MetamodelRow.blob` **verbatim** (`source: "stored"` — the author's comments and formatting are the point of this route) or, for a session whose metamodel never landed in a durable row (legacy/test setups, uploads that wrote no content row), a re-serialized `yaml.safe_dump` of the in-memory object tagged `source: "serialized"`. Degrading beats failing here; the client shows a chip saying the comments are gone.
- **`POST /metamodel/lint`** (`routes/metamodel_swap.py`) is parse + metamodel-schema check ONLY — no `Session` dependency (a cold project is not even hydrated), no model, no `write_mutex` — cheap enough for a debounced call per keystroke. It is **always 200** with `{ok, errors[]}`, carrying `line`/`column` off the YAML error's `problem_mark`; an undecodable body is just another bad candidate, not a 422. It is deliberately **NOT** in `authz._READ_ONLY_POST_SUFFIXES` (unlike `/metamodel/diff`), so a viewer gets a 403: only the owner-gated editing flow lints, and a viewer has nothing to lint.
- **The `metamodel.*` op family** (`schemas.py`'s `MetamodelOpIn` union, `METAMODEL_OP_KINDS`) joins `OpIn` with two members, applied by `api/metamodel_ops.py` (the fourth sibling of the model/artifact/view appliers — full-state inverses, no internal rollback, mirroring the artifact applier's split of responsibilities with `POST /commits`'s unwind):
  - `metamodel.rebind {blob}` — the author's full candidate YAML. At most one per batch (422 otherwise); `POST /commits` **hoists it to apply first** regardless of client order, so every other op in the batch validates against the **new** schema (the point of an atomic migration commit). Inverse carries the prior YAML blob (full-state, self-contained), persisted as a new immutable `MetamodelRow` at `prior_version + 1`. **Known limitation, by design, not a bug**: there is deliberately no "old-schema slot" — a model op that references a property the outgoing schema declared but the NEW one doesn't is rejected by `_check_patch_keys` because the swap already happened. So a **property-removal migration cannot be one commit**: the supported shape is unset the property on every affected element in commit N, then rebind (dropping it from the schema) in commit N+1 — two commits, not one atomic migration. The **ADD-a-mandatory-property** direction has no such limitation and IS atomic (rebind + populate in one commit), which is also the direction that actually risks an observable inconsistent state if it weren't atomic.
  - `metamodel.move_node {node, pos: {x,y} | null}` — a per-node write against `metamodel_layouts` (`pos: null` removes the key). Cheap and presentation-only: no metamodel swap, no revalidation.
- **`POST /commits`** treats a rebind-carrying batch specially: gates it on the **owner** role (`metamodel.move_node` alone only needs editor+); hard-verifies the singleton `mm` lease (unlike `POST /metamodel` and `DELETE /metamodel`, which only HONOR the lease — they are the only callers of `_peer_mm_conflict`); runs a **quiet-peers guard** that 409s if any *peer* holds a model-scope lease (the caller's own leases never block — a migration is expected to hold locks on the elements it fixes); replaces the usual dirty-scope validation splice with a full `Scope.all()` sweep (an O(model) cost); is **exempt from the strict-mode conformance hard-reject** (structural blockers still hard-reject as always — "the engine stays inspectable" through a migration); **forces a snapshot** at the new rev (so a replay tail never spans a rebind boundary); and broadcasts **`rebind_event`** instead of `commit_event` (peers get the reload banner — there is no applyable delta after a schema swap). A layout-only batch is a normal cheap commit: `commit_event` with `"metamodel-layout"` added to the `scope` vocabulary so an open diagram refetches positions. `POST /commits/preview` dry-runs the whole family (apply-swap → apply ops → full validate → unwind) side-effect-free.
- **Undo/revert/diff.** `POST /model/undo` replays `metamodel.move_node` inverses normally but **409s with push-back** on any batch that carried a `metamodel.rebind` — restore-mode model inverses are schema-checked at the core mutation boundary, and no single replay order is valid both before and after a schema swap without teaching the core a schema-independent restore mode. `/commits/revert` 409s across the whole family too. `GET /commits/{rev}/diff` renders the rebind's structural diff (recomputed from the two immutable `MetamodelRow` blobs, off the commit's `from_metamodel_id`/`to_metamodel_id` columns) beside a journal-only "N nodes moved" layout summary, independent of whether the commit also carried a rebind (`commit_diff.py`).
- **Hydration replay skips the whole family** (materialized heads: the metamodel comes from `ModelRow.metamodel_id`, positions from `metamodel_layouts`), and `/model/ops`, `POST /model/validate` and guest-proposed snippet ops reject it permanently, same stance as the artifact/view families.
- **The conflict backstop uses the single `mm` resource** for the whole family (not per-node markers): every metamodel writer already serializes on the exclusive `mm` lease, so a finer marker could never change an outcome.
- **Frontend** — a singleton `metamodel` workspace tab (`components/Metamodel/`, `state/metamodel-editor.svelte.ts`) with a CodeMirror YAML editor, a localStorage draft, debounced lint and on-demand preview; it composes the surface-agnostic `mm` lease module. The dirty buffer and the diagram's coalesced node moves are the **fourth staged family** (`state/metamodel-stage.svelte.ts`, beside model/artifact/view), committed through the same `commitStaged` as everything else — there is no Rebind button; a dirty draft becomes the batch's `metamodel.rebind` op and staged moves become its `metamodel.move_node` ops. See `frontend/README.md`'s "Live metamodel editing" section.
- **Diagram surface (metamodel diagram editor)** — the same tab toggles to an editable UML class diagram. It adds **no** mutation protocol: `state/metamodel-diagram.svelte.ts` turns every canvas gesture into `parseDraft → applyEdit → serializeDraft` over the current buffer and hands the text back through `editMetamodelBuffer`, so lease/lint/draft/preview are the YAML path's, unbranched; a drag stages a `metamodel.move_node` op instead of a live PUT. The edit core is `frontend/src/lib/metamodel/yaml-edit.ts` — a 22-member `YamlEditCommand` union over the `yaml` package's Document API, because the point of `GET /metamodel/raw`'s `stored` source is the author's comments and re-serializing a plain object would burn them; its `STRINGIFY_OPTS = {lineWidth: 0, flowCollectionPadding: false}` is load-bearing (drop `flowCollectionPadding` and an unedited round-trip of `examples/smart-city.metamodel.yaml` rewrites 126 of 455 lines — a test pins the byte-identity). `diagram-build.ts` derives endpoints from `rel.mappings` ONLY, never the `source`/`target` shorthand, which is a serialization mirror that can go stale. **Node positions are the one exception to "everything durable is journalled"** — they live in the shared `metamodel_layouts` blob, not in a `Commit` row's `ops`, and a rename's position migrates as two `metamodel.move_node` ops (`old → null`, `new → {x,y}`) landing in the SAME commit as the rename, so there is no wire moment where the blob and the draft's names disagree — a peer never observes a half-renamed layout. There is no rename-key deferral: positions only ever land atomically with the rename that caused them.

### Custom validation rules (`src/data_rover/core/validation/rules/`, `api/rules.py`)

User-defined cross-element rules ("if x has y, then z must have k"), authored as a small **declarative YAML** language and evaluated **natively as a seventh validator** — deliberately not Python-snippet rules, which would need a second async evaluation subsystem (sweep, read-set capture, rev-stamped caching) and an eventual-consistency validation UI.

- **`core/validation/rules/schema.py`** — the pydantic AST + `parse_rule_set(text)`, raising only `RuleSetError`. A rule is `{name, applies_to, severity, disabled, description?, when?, then, message?}`; conditions are `all`/`any`/`not`/property atoms (`exists`/`equals`/`not_equals`/`in`/`gt`/`gte`/`lt`/`lte`/`contains`)/relationship atoms (`type`, `direction`, optional `to`/`where`, `exists` xor `count`), nesting freely. Caps enforce wherever the payload PARSES, never at evaluation time: `RULES_MAX_YAML_BYTES` (64 KiB — a pydantic `max_length` on the string, so characters, matching the `SNIPPET_MAX_CODE_BYTES` precedent), `MAX_RULES_PER_SET` (200), `MAX_CONDITION_DEPTH` (8), and a null operand is refused for every test but `equals`/`not_equals` (`gt: null` would otherwise compile clean and then die per element). **YAML aliases are refused outright** (`_NoAliasLoader`): PyYAML memoizes anchors into a shared-reference DAG that loads in flat time and memory, but pydantic walks that DAG as a tree, so a few hundred bytes of nested aliases expands into gigabytes of validation work **under every one of those caps** — they all measure the source text.
- **`compile.py`** — `compile_rule_sets(sources, metamodel) -> CompiledRules`: parses every source, resolves each `applies_to` to its subtype closure, builds the type → rules dispatch map, and computes per-rule **drift verdicts**. A rule naming an unknown stereotype/relationship/property is **skipped whole** at compile — never evaluated half-blind — because the skip must not become an issue (an ownerless pseudo-issue could never be cleaned up incrementally); it surfaces instead as `rules_status` (below).
- **`validator.py`** — `RulesValidator(EntityValidator)` dispatches per element via the precomputed map. Rule issues are **always `IssueCategory.CONFORMANCE`** (a user rule must never block a commit — permanent by design), `check = "rule:<rule-name>"`, `target_ids[0]` = the evaluated element. `CompiledRules.eval_errors` is the one field that moves after publication: the validator accumulates a run's failure counts locally and folds them in once from `validate_global` by whole-object swap under a lock, so an unlocked `dict(compiled.eval_errors)` snapshot can never tear, and a rule that raises logs one traceback per `(check, exception type)` per run rather than one per failing element.
- **`reach.py`** — static reverse-path derivation + `expand_scope`: because the language is closed (no snippets), each rule's navigation shape is statically analyzable, so a mutation's dirty set is expanded backwards along every rule's reverse paths before the pipeline runs. **Over-approximation is safe; a too-small expansion is the only correctness hazard**, and the full background sweep is the healing backstop either way. The walk is deliberately **unfiltered by the paths' far-type closures**: those name the type an element must match for a rule to reach it, and a retype is precisely the mutation that flips a verdict *while making the element stop matching* — gating on the current type would never start the walk and would silently lose the owner's new violation. It pays extra adjacency hops instead.
- **Storage.** `validation_rules` is an artifact kind (`ArtifactKind.validation_rules`), payload `{schema_version: 1, yaml: "<verbatim text>"}` — the text, not parsed JSON, so author comments and formatting survive, mirroring the metamodel blob. Structural invalidity (unparseable YAML, schema violation) 422s at save; **metamodel drift does not** — the metamodel can change under a committed set regardless. No new artifact routes: commits/locks/bundles are already generic over the kind registry.
- **`api/rules.py`** — the ONE place the API layer builds rules-aware pipelines and widens dirty scopes: `session_pipeline` (fresh pipeline = `default_validators()` + a `RulesValidator` over the session's compiled rules — build fresh per run, never cache a pipeline/validator on the session), `load_compiled_rules`, `expand_dirty`, `rules_touched`, `applies_population`. `Session.compiled_rules` is an **immutable-swap** cache, rebuilt at **hydration**, on a **commit that touches a rules artifact** (create/update/delete detected off the transaction's staged rows), on **metamodel rebind**, on a **metamodel upload** (`POST /metamodel` recompiles against the new schema; `DELETE /metamodel` empties it), and on an **undo** that restores or removes a rules artifact. The legacy `PUT`/`DELETE /artifacts/{id}` path deliberately does **not** recompile — that write lands with the session's rules stale until the next hydration (`routes/artifacts.py` carries the trap note). A commit that touches a rules artifact widens the validation splice to the `applies_to` population of the **old ∪ new** compiled sets, so issues minted by a deleted or renamed rule drop too.
- **Rules-aware call sites:** commit/preview/revert, ops `_finalize`, undo, `POST /model/validate`'s staged and full branches, the metamodel-diff candidate side (compiled against the *candidate* schema so the diff shows rule flips), and the background sweep (re-checking `session.compiled_rules` per chunk, since a commit can swap it mid-sweep). One site stays deliberately **rules-blind** because it validates a caller-supplied candidate model rather than the session's: the validate route's inline branch (the compare/apply-cr proposals validate nothing at all — staging → `/commits/preview` does).
- **The strict-mode gate is scoped to the batch, not to the widened scope.** Dirty-set widening feeds the *validation* scope; it must not feed the commit gate. `POST /commits`' strict-mode hard-reject therefore filters to issues owned by the batch's OWN entities plus any `rule:` verdict — a pipeline run over a widened scope also re-reports built-in conformance issues (multiplicity, facets, uniqueness) on elements the batch never touched, and those can never be its doing. `POST /commits/preview`'s `would_block` applies the identical filter, since a preview promising a landing followed by a 422 is worse than either answer alone, while the reported `conformance_error_count` stays the unfiltered truth.
- **`GET /model/issues`** carries `rules_status: {total, skipped: [{artifact_id, set_name, rule, reason}], eval_errors}`, where `rule == ""` means the whole set failed to parse.
- **`POST /rules/lint`** (`routes/rules.py`) is the sibling of `/metamodel/lint`: no write mutex, no model iteration, cheap enough to debounce per keystroke. Parse failures and schema violations are `errors` (`ok: false`); **drift is a `warning` with `ok: true`** (compiled against `session.metamodel` when present). Deliberately NOT in `authz._READ_ONLY_POST_SUFFIXES`, so a viewer gets a 403 — only the editing flow lints. Always 200 for any well-formed envelope; 422 only for a malformed request body (missing/non-string `yaml`, an over-cap `yaml`).
- **Deliberately out of scope**: `else` branches; rules on relationship types; property tests on the relationship itself; value-vs-value joins; snippet-backed rules; per-element severity override/muting; STRUCTURAL user rules (permanently out); e2e coverage (joins the T-7 backlog list).

### Migration CLI (`src/data_rover/migration/`, `migration/README.md`)

`python -m data_rover.migration` converts the old JSON metamodel+model format to the new one (stereotype→element type, `owner`→`Owns` containment, `element_type`→`TypedBy`, datatypes inferred from real values). It never raises on invalid output so incomplete inputs stay inspectable; `--remove-inconsistencies` prunes model entities that would block frontend load.

## Conventions

- Tests live in `tests/<area>/` mirroring the source packages (`model`, `metamodel`, `validation`, `view`, `api`, `migration`). `pythonpath=src` is set in `pytest.ini`, so import as `from data_rover.core...`.
- Comments and docstrings are concise and present-tense: only for critical details that do not emerge from the code itself (invariants, concurrency rules, non-obvious contracts). No references to specs/plans/phases, and no historical narration — git history owns the past.
- API tests that hit data routes use the `client` fixture + `seed_default_project`/`AUTH_HEADERS`/`papi` helpers from `tests/api/conftest.py`: every project-scoped request needs an identity header and a seeded project (the helpers seed/​target the `default` project so `get_session()`-based setup lines up with the HTTP path). conftest **pins `DATA_ROVER_IDENTITY_PROVIDER=header`** so `AUTH_HEADERS` (`x-user-id`/`x-user-email`) authenticate; auth/admin tests that need cookie auth opt in via `pytestmark = pytest.mark.usefixtures("cookie_provider")`.
