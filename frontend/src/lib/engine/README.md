# Replica shell (`frontend/src/lib/engine/`)

The app's side of the replica: plain TypeScript, no runes, no `lib/state/*` import (it may import `lib/api/*`). `lib/state/replica.svelte.ts` wires it into the workspace, and `frontend/README.md` ("Replica (engine shell)") has the detail. The nine model reads can be answered by the replica, one switch per surface, every default `engine` — so the five read surfaces (elements, fuzzy search, incident relationships, containment tree, summary counts) come from the in-browser replica unless `dr.surfaces` says otherwise or the replica cannot serve them, with the server as fallback; a status-bar indicator (`data-testid="replica-indicator"`) shows its state. Two evaluations have a switch each beside them, `navigation` (`evaluateNavigation`) and `criteria` (`searchModel`), both `engine` by default too: a navigation or a criteria search reads the working copy, staged edits and staged artifacts included, and one the engine refuses with a 501 (a script, a pattern it cannot vouch for) is answered by the server and marked. `staging` (default `engine`) is its own switch: `staging: engine` FORCES the five read surfaces' switches (`READ_SURFACES`) to `engine` regardless of what `dr.surfaces` set for them, so overriding one of them to `server` needs `staging: legacy` alongside it; `navigation` and `criteria` are never forced, since the server never evaluated staged edits in either mode. The replica also STAGES: with `staging: engine` (the default, `STAGING_DEFAULT`) the user's edits are ops applied to the working copy, and the model store's engine half (`model-engine.svelte.ts`) is a view over its staged batches, mirrored for the synchronous readers — see "The model store" below and `frontend/README.md`'s "State model".

- **`frame.ts`** — `connectFrame(deps?)` appends a hidden `<iframe>` of `SANDBOX_ORIGIN` (`origins.ts`, `VITE_SANDBOX_ORIGIN`, `http://localhost:5174` by default) with `allow="cross-origin-isolated"` and `sandbox="allow-scripts allow-same-origin"`, waits for `{type: 'sandbox-ready', crossOriginIsolated}`, and answers `{type: 'connect'}` with ONE transferred `MessagePort`; the link carries `isolated` and replays `csp-violation` reports to its `onViolation` listeners. A message counts only when `event.origin === SANDBOX_ORIGIN` and `event.source` is the frame's `contentWindow`. It refuses outright — `FrameError('same-host', 'open the app at http://127.0.0.1:5173')`, no frame built — when the app's hostname is the sandbox's: the two must be different sites (CN-17), which is why every doc says `127.0.0.1:5173`. No `sandbox-ready` within 10 s is a `timeout`; a `worker-error` before it is `worker`, after it ends the link. The window, location, frame factory and channel are injectable, because happy-dom's `postMessage` delivers no ports and an iframe there fetches for real.
- **`client.ts`** — `createEngineClient(port)` is the CT-4 client: ids from 1, an error answer rejects with `errorForStatus` of `lib/api/errors` (so `NotFoundError` / `ConflictError` / `ValidationError`, as after an HTTP call), events go to every `on` listener, an aborted signal posts `{cancel: id}` and rejects with an `AbortError`, `transfer` rides as the transfer list, and `dispose()` rejects everything pending or later with `EngineGoneError`. An `EngineLink` (`client`, `isolated`, `onViolation`, `dispose`) is what `sync.ts` is handed.
- **`cache.ts`** — `createSnapshotCache()`: IndexedDB `datarover-snapshots` v1, store `snapshots`, key path `project_id`, so one row per project (`{project_id, rev, bytes, size, used_at}`). A hit needs the descriptor's exact `rev` and returns a copy; a `put` happens only after the engine's `end` accepted the bytes and evicts least-recently-used rows of OTHER projects down to 64 MiB; a row the engine refuses is dropped. Every call resolves whatever the store does (AD-10): no `indexedDB`, a blocked open, an aborted transaction or a quota error is a miss or a no-op.
- **`sync.ts`** — `createReplicaSync({connect, api, cache, sleep, onStatus, heldFallback?, onAbandoned?})`, the one place that knows the order of things. An open attempt: the snapshot descriptor (`null` → `off`, `no model`), the link (a `connect()` that rejects ends the attempts at once: `server` if this open was never ready, else `failed`), the metamodel document (an `X-Metamodel-Id` other than the descriptor's restarts the attempt for free, three times), `open`, the bytes from the cache (one `chunk`) or streamed from the descriptor's `url` (each chunk transferred exactly — a view is copied first), `end` (its header must be the descriptor's; refused cached bytes are dropped and read again from the network, uncounted), `adoptStaged` on a re-bootstrap, the tail (incomplete fails the attempt), `applyTail`, `ready`. Three attempts, 1 s then 3 s apart; after the third `server` if this open was never ready (the link disposed), else `failed` — which, like `frozen`, keeps the user's own commit responses (and accepts new ones) for the replica `retry()` rebuilds: its re-bootstrap adopts the batches those commits carried, and only their bookkeeping — applied on the first drain, a `duplicate` naming batches still staged — drops them. Every continuation checks a generation token that `stop()` and `open()` move, and every API call carries its own project's base URL (`replicaApi(root)`), so a late call never lands on the next project. Following: feed deltas, snapshot events and the user's own commit responses form ONE queue handled in `rev` order while `ready` (at most 1,000 wait otherwise, past that a catch-up is owed); a delta not past the replica drops without a call unless it is the user's own; `gap` or a snapshot event ahead runs a catch-up through the tail; an incomplete catch-up, `diverged: true`, or the engine's `replica {state: 'diverged'}` event re-bootstraps — `resyncing`, `staged` + `conflicts` read and joined by id (a worker gone cannot be asked: `heldFallback()`, the model store's copy of them, is held instead), the cache row dropped, `close`, the attempts on the SAME worker adopting those batches; a call that finds the worker gone (an `EngineGoneError` from a posted call — the frame disposes the link on a `worker-error`) drops the link and re-bootstraps a `ready` replica on a new worker (a `frozen` one at adoption — meanwhile it refuses calls as `off` does — a `failed` one at `retry()`); a catch-up whose tail FETCH throws tries once more after 1 s first. `feedReset(rev)` (the feed's `reset`: a `rev` bump with no journal row) is a snapshot event ahead, so the tail is incomplete and the replica re-bootstraps; a `reset` or a snapshot event in `off` restarts the open (`server` stays). `retry()` re-bootstraps a `failed` replica with a fresh budget of attempts, adopting the batches it still holds. `beginCommit()` opens a flight BEFORE the POST and the queue holds while any is open; `settle({text, rev, applied, rebound, idMap, batchIds?})` inserts the response at its place by `rev` (`applied: false` — `prev_rev` null — queues nothing), so the echo drops as covered (CT-2); `abandon()` just lets the queue go. An own response that is DROPPED — settled in `off`/`server`, emptied with the queue at `no model` or at a `server` give-up, or dropped by the pump after its one retry — is applied by no replica: its `batchIds` leave the batches the run holds and are filtered out of every re-bootstrap's read until a replica is `ready` without them, and `onAbandoned(batchIds)` tells the model store, so no re-bootstrap (a wake from `off` included) stages a committed batch again. `ownPending()` is true while a flight is open or an own response waits in the queue or is being applied. A `rebind` event or a `rebound` settle FREEZES the replica (`frozen`, `metamodel changed at rev N`) and `metamodelAdopted()` re-bootstraps it onto the metamodel the UI now shows (AD-27). `call(method, params?, {signal?})` is a read answered by the replica, held in the shell until the phase is `ready` and its `rev` has reached `known` — the highest `rev` a `feedCommit`, an applied `settle`, a `feedSnapshot` or a `feedReset` handed it before the call (AD-28) — or at once in `frozen` / `failed`; with `{transition: true}` (the store's `stage` / `unstage`) it is held for the phase alone — posted in `ready` or `frozen`, never held for `known` nor by a commit in flight, held while `opening`, `resyncing` or `failed` so a re-bootstrap's batches are adopted first, and while there is no link — in the SAME list as the reads, a held transition holding every call asked after it; a transition posted to a worker that turns out gone is held again at its place in arrival order for the replica that replaces it; no open, `off`, `server` or `stop()` reject `EngineGoneError`, and so does a read that finds no link or a worker gone. `on('changed', listener)` hands every engine `changed` event (`ChangedEvent`) to listeners kept on the sync, forwarded by each link it adopts until that link is dropped. `setViewPlacement` / `dropViewPlacement` keep a map the sync sends to every new link before any held read goes (`stop()` clears it); `setArtifacts` / `putArtifacts` / `setStagedArtifacts` keep the artifact context the same way — the committed artifacts by id and the staged entries, each call posted to the current link at once and, on a new link, `setArtifacts` then `setStagedArtifacts` right after the placements (each only when non-empty: a new worker starts with none), so an evaluation held across a dead worker resolves every artifact. `stop()` clears both, and it drops the link and with it the worker, whose artifact set would otherwise survive `close` and `open`: no artifact of one project reaches the engine the next `open` builds; `placements.ts`'s `placedElementIds(view)` is what a view places. `ReplicaStatus` is `{phase: off|opening|ready|resyncing|frozen|failed|server, rev, progress: {task, done, total}, attempt, source, isolated, cspViolations, reason}`, a new object on every change; the replica's `rev` comes from the engine's answers and events, never from the shell's arithmetic.
- **`artifacts.ts`** — `createArtifactFollower({sync, payloads, staged})` keeps the sync's artifact context the project's, one follower per started replica. `load()` fetches every payload (`GET /artifacts/payloads`) into `setArtifacts` and remembers each `artifact_rev`; `onEvent` (an `artifact` feed event) puts a `deleted` id away and fetches a `created` / `updated` one only when its rev is past the one remembered; `onCommit({idMap, changed, deletedIds})` (the user's own commit) fetches the changed ids the engine does not hold yet — past 100, everything, filtered — and sends them, the deleted ids and the staged overlay in ONE `putArtifacts` (a commit that moved no artifact only pushes the buffer). Fetches run one at a time in the order asked, so a later answer never lands under an earlier one. A commit's refresh holds the staged mirror: `stagedChanged()` queues one microtask that reads the buffer and pushes it only while no refresh is out, and `hasOverlay()` says whether any held or carried entry lies under the buffer, and the commit path clears the buffer and announces the commit in one run, so the clear's push finds the hold. At the announcement the follower posts ONE `setStagedArtifacts` of the entries the commit carried — the buffer as last read, the clear not yet — plus each created one again under its real id from `idMap`, with the buffer over them; nothing else is pushed until the refresh lands but another commit's own push or a `putArtifacts` that corrects a failed refresh's entries, and each lays the buffer over the held entries (coalesced as the buffer coalesces: an update over a create merges into it). So until the `putArtifacts` lands the engine reads the working copy the commit came from — a created artifact under its temp id AND its real id, a staged update over the old payload — never a state where a committed artifact is neither staged nor committed; a second commit during a refresh adds its own entries beside the first's. `stop()` drops every answer that comes after it and asks nothing more. A failed refresh keeps its entries under the buffer, each only until a fetch brings newer committed news of the artifact it stands for (a create's real id): a later commit's refresh, an `artifact` event's fetch or delete — whose `putArtifacts` then carries the corrected overlay — or a `load()`, which drops them all; and it asks ONE `load()` at once, with no further retry but the feed's next `snapshot` event. Any other failed fetch leaves the context as it was. The feed's next `snapshot` event reloads everything, which heals a missed event too.
- **Surfaces — `lib/api/engine-route.ts`, `surfaces.ts`, `seam.ts`.** The nine model reads of `lib/api` (`getElement`, `getElementsBatch`, `getTreeItemsBatch`, `listElementsPage`, `listElementRelationships`, `getModelSummary`, `listContainmentRoots`, `listExcludedRoots`, `listContainmentChildren`) and the two evaluations (`evaluateNavigation`, `searchModel`) keep signature and schema and pick a side through `route(surface, cfg, engineCall, serverCall)` over an INJECTED seam (`installEngineSeam`; `lib/api` imports nothing of `lib/engine`): no seam, an explicit `baseUrl` or `fetch` (a call that names its server — every MSW test of the server path), or the surface's side `server` → the server; else the engine, whose body passes the same zod schema, an `EngineGoneError` (`gone`) answered by the server instead and any other error the caller's; an optional `shadow` is handed `{surface, method, params, engine, again, server}` after every engine outcome, never awaited, its throws and rejections swallowed. Engine params are flat snake_case (`elementId` → `id`, `viewId` → `view_id`, an id list → `{ids}`) with omitted options left out; `signal` on the option bags reaches the engine as the call's signal and the server as `init.signal`, never the query string. The five read surfaces (`surfaces.ts`, `READ_SURFACES`): `elements` (`getElement`, `getElementsBatch`, `listElementsPage` without a query that is not blank), `search` (with one), `relationships`, `tree` (the tree items and the three containment reads), `summary`; beside them in `SURFACES`, `navigation` (`evaluateNavigation`, params the request body — `definition` or `artifact_id`, `row_element_id`, `limit`, `offset` — with absent keys left out) and `criteria` (`searchModel`, params `{target, criteria, limit, offset}`), each sent as the plain JSON the server is sent (`asSent`: a `$state` proxy cannot cross a `MessagePort`); `SURFACE_DEFAULTS` `engine` for all seven, `readSurfaces(storage?)` overlays the JSON object in `localStorage['dr.surfaces']` (honoured in a build too; anything malformed gives the defaults) — a `staging` key of `engine` forces every READ surface's switch to `engine` AFTER the per-surface overlay runs, so a read-surface-only override needs `staging: legacy` beside it, while `navigation` and `criteria` take whatever the object says — `anyEngineSurface` (any of the seven). The engine refuses an evaluation it must not answer with a 501: `reaches a script` (a navigation that reaches a configured script step) or `reaches an unsupported pattern` (a criterion pattern the regex translator cannot vouch for); `route(surface, cfg, engineCall, serverCall, {mark?})` answers exactly those two (an `ApiError` of status 501 and that message) from the server, hands the value to `mark(value, 'script' | 'pattern')` when given, and runs no shadow probe; any other 501 is the caller's error. `evaluateNavigation` marks its page `fallback: 'script' | 'pattern'` (`ChainPageSchema`'s optional `fallback`); `searchModel` passes no mark. The navigation editor's preview keeps the first page's `fallback` (`null` when the engine answered or the surface is on the server), and `Navigation/ResultsDock.svelte` shows it above the chain table as a one-line muted note, `data-testid="nav-fallback"`: `Reads committed state: this navigation runs a script on the server.` or `Reads committed state: a pattern here runs on the server.` `createEngineSeam(sync, surfaces, shadow?)` (`seam.ts`): a surface's effective side is `engine` iff its switch says so and the phase is neither `off` nor `server`; `call` is `sync.call`. The replica store installs it (below).
- **Shadow comparison — `shadow.ts`, `quiet.ts`.** Dev-only: `shadowEnabled(storage?)` is `import.meta.env.DEV && localStorage['dr.shadow'] === '1'` (absent from a build; a throwing storage or any other value is off). `createShadow({rev, quiet, staged, report})` builds the seam's `shadow`: nothing is compared while `staged()` is true (the replica's answers then hold edits the server has not seen) — asked before `server()` is called, after each `quiet()` and after each re-test round, so a comparison under way ends silently once an edit is staged; the store hands it `anyStaged() || getStagedArtifactDepth() > 0 || hasOverlay()`: `staged-probe.ts`'s `anyStaged`, which asks the engine half's `hasStagedOps()` while it is attached (`attachEngine` sets the probe, `detachEngine` clears it), or an entry in the staged artifact buffer, which the engine's artifact set mirrors and the server has not seen, or the current artifact follower's `hasOverlay()` — after a commit the buffer is empty while the follower still lays the commit's entries (and a created artifact's real-id alias) over the committed artifacts until its refresh lands, or keeps a failed refresh's entries until newer committed news, a state the server does not have. Otherwise it runs `server()` beside the engine's own outcome, compares by deep equality (object key order ignored, array order not) or, for two failures, the same kind (`ApiError.status`, else the error's `name`) — `summary` compares without `issue_counts`/`undo_depth`, since the engine always answers those `null`/`0`. Equal: nothing. Different: `await quiet()`, note `rev()`, run `again()` and `server()` once more, note `rev()` again — moved in between → repeat, three rounds at most, then give up silently (a replica that never rests is not a mismatch); a round whose `rev` held still decides it, reporting ONE line (`report`, `console.error` in the store) on a still-different round: `[shadow] <surface> <method> <params>: engine <short> ≠ server <short>`, each `short` cut at 300 characters. An `AbortError` from either side, or an `EngineGoneError` from the engine side (`again()`, or the engine's own outcome), at any point, ends the comparison silently — a `rev` gone to `null` on a `stop()` must never read as two stable, equal reads. `quiet.ts`'s `addQuietProbe(probe)` / `quiet()` is the small registry other stores add a "still settling" probe to. The replica store reaches `shadow.ts` only through a dynamic `import('../engine/shadow')` behind the same DEV check, so a build holds neither the module nor its `[shadow]` string.
- **The store — `lib/state/replica.svelte.ts`.** `startReplica()` opens the sync and installs `createEngineSeam(sync, readSurfaces())` into `lib/api`, with `sync.settled()` as a quiet probe; `stopReplica()` / `resetReplica()` uninstall both (every read goes to the server again). `subscribeReplicaStatus(listener)` hands every status change with the one before it. With staging on the engine, `startReplica()` also attaches the model store's engine half (`attachEngine(handle)`: the sync's `call` and `on('changed')`, this store's status, `subscribeReplicaStatus`) and `stopReplica()` / `resetReplica()` detach it before the sync stops; with staging on legacy it is never attached (it would move the structure rev on every applied delta, which the legacy half already moves). The switches are read once, at the first start; `resetReplica()` forgets them. In dev, with `dr.shadow` set and some surface on the engine, the seam is installed again with a shadow once the module has loaded (a seam replaced meanwhile is not overwritten). `handReplicaFeed` hands a `reset` event to `feedReset`; the realtime store then does a snapshot event's work minus presence and leases (`refreshSummary()` when ahead, the debounced issues refetch). With `summary` on the engine, `refreshSummary()` keeps the store's issue counts (the engine answers `null`) and asks `refetchIssues()`; `_modelRev` is the answer's either way. `startReplica()` binds the staged artifact buffer to the project it opens (`bindStagedArtifacts`: a buffer staged in another project is dropped silently — no discard listener, which would re-dirty and repoint that project's editor drafts — while the same project's is kept; `boot()` binds it too, beside the other staged families' resets), then builds the artifact follower for the project it opens (its fetches scoped to that project's base, whatever project is active by the time they go), calls `load()`, and pushes the staged buffer when one is kept; `stopReplica()` / `resetReplica()` stop it before the sync stops, and a start for another project replaces it. `handReplicaFeed` hands it every `artifact` event and reloads it on a `snapshot` event; `onArtifactCommit` and `onStagedArtifactsChanged` (both subscribed once, at module level) reach the current one. `artifact-edits.svelte.ts` fires `onStagedArtifactsChanged` from every function that changes its buffer, `clearStagedArtifacts` included, and `stagedArtifactsForEngine()` projects it to `WireStagedArtifact`s with `$state.snapshot` copies of names and payloads, since an editor's draft may be a proxy a `MessagePort` cannot clone. `registerViewPlacement` / `forgetViewPlacement` / `forgetViewPlacements` reach the sync: the view store registers the COMMITTED document's `placedElementIds` from `refreshView()` — the fetched one, never the staged ops on top, and before `setState`, since the tree refetches on `_view`'s identity — forgets the old view on a switch, a 404, no view or a failed load, forgets all in `clearViewState()`, and adds a quiet probe pending while a `refreshView()` is in flight. The three debounced searches (`Sidebar/Search.svelte`, `Navigation/ElementStartPicker.svelte`, `Snippet/ElementContextRow.svelte`) abort a superseded `listElementsPage` through its `signal`; an `AbortError` leaves the results as they were.
- **The model store — `lib/state/model.svelte.ts`, `model-shared.svelte.ts`, `model-legacy.svelte.ts`, `model-caches.ts`.** `model.svelte.ts` is a facade: it re-exports the shared half and, for every entity-half name, dispatches to `model-legacy.svelte.ts` or `model-engine.svelte.ts` by `getStagingSide()` (`replica.svelte.ts`, the `staging` switch in `lib/engine/surfaces.ts`) — `legacy` without a sync, `engine` iff the switch says so and the phase is neither `off` nor `server` (`failed`/`frozen` keep `engine`: a re-bootstrap carries the batches staged there); `resetModelStore` and `validateAll` touch both halves directly, since neither is one entity half's concern, and `setModelApiConfig` always sets the shared half's client config (the engine half has none). `model-shared.svelte.ts` holds what every entity half agrees on — the summary, `model_rev`, the structure-rev counter, the live issue map, rules status and the store error — and `applyDeltaShared(d, has)` is the shared half of a delta's application (the structural formula, the issue splice, the summary patch, `clearOverlay()`), taking a `has(id)` callback so its pre-remap "was this id already cached" check reads the CALLER's cache before the entity half's own remap runs (`structure: false` leaves the structure rev to the caller). `model-legacy.svelte.ts` is the server-mode entity half (the fetched-subset caches, the staged-edits buffer) — frozen, and deleted once the engine half is the only one (sub-project F). `model-engine.svelte.ts` is the engine half, a view over the replica: its caches (the legacy half's names) are filled through the `lib/api` seam — so they hold the staged edits — with none of the legacy guards and no temp-id short-circuit (a temp id the engine 404s is in `getMissingElementIds()`); `emit(op)` / `emitMany(ops)` (one batch, all or nothing; a one-op list coalesces like `emit`) write the op into the caches at once (a create under its temp id with a lite tree item, a delete taking the row out of the tree items too), raise the entity's PENDING count, add a PROVISIONAL entry and post a `stage` transition; nothing the engine says overwrites a pending entity except the `stage` answer that brings its count back to zero (its post-state), so an answer never regresses a newer keystroke, and a refused stage (`getModelError()` `rejected`, the engine's text) reads its entities back and drops what it created. It keeps a mirror of the engine's `staged` / `conflicts` / `stagedDiff`, read again whenever a `changed` event's `staged_version` moves, whenever the replica becomes `ready` (after a re-bootstrap the cached elements the staged and parked batches touch, before and after, are read again: adopting says nothing) and after every `stage` answer — its three calls posted as transitions (in order with the stages, never held for a rev, only in `ready`/`frozen`), a refused read retried once and then REFUSED: a store error, nothing hangs, but `stagedSettled()` rejects with `StagedUnreadableError` and the unstage family (and `popLastStaged()`, false) does nothing until a read lands, since that mirror is not the engine's staged list; the staged-edit readers read the mirror's batches then the provisional entries, an entry leaving when a mirror read issued AFTER its answer lands — and no mirror read starts while an edit waits for its answer (its `changed` comes first), which is what keeps an op from counting twice; `getStagedBatchIds()` / `getStagedConflicts()` are the mirror's, `getStagedDiff()` the engine's committed images against its records. The batches a landed commit carried are COMMITTED (`markLanded`, which checkout calls once the POST answers with `prev_rev` set or `rebound`): every staged-edit reader, `captureStaged()` and `getStagedDiff()` leave them out — the diff drops the entities only they name and a committed delete's cascade — until a mirror read no longer holds them, though a `frozen` or `failed` replica keeps them staged until it is rebuilt and applies the commit's answer; a single property update the engine would merge into one of them (the first staged batch holding an update of that entity) is DEFERRED — cached, pending and shown at once, posted with every edit after it only once the replica has dropped that batch; Undo withdraws the last deferred edit, the reverts and discards the matching ones. `forgetBatches(ids)` (the sync's `onAbandoned`) drops batches no replica will hold from the mirror and keeps them out of the readers until the next replica is `ready` (one before it may still name them, one after may number a new batch alike); `handOverStaged()` (the sync's `heldFallback`) is the mirror's staged and parked batches, each replaced by a later stage answer's, less the committed ones, which it forgets. `stagedSettled()` resolves once every edit but the deferred ones is answered and covered, no mirror read, cache re-read or unstage is in flight or owed — then `getStagedBatchIds()` and `captureStaged()` are exactly the engine's batches and `getStagedOps()` those plus the deferred edits (a deferred edit waits for a rebuilt replica, and nothing waits for it); a detach releases it. The engine's `changed` event is the one path that refreshes it after a transition: deleted ids leave the caches and tree items, cached changed elements are re-read in one `getElementsBatch`, a changed relationship is left to the relationships list's refetch, `structural` moves the structure rev and the event's `rev` becomes `getModelRev()` when past it. Its `applyDelta` runs `applyDeltaShared` with `structure: false` (the structure rev moves on `changed` alone, once per structural delta), re-keys the caches, visit history and selection through `id_map`, and upserts the delta's entities except those a staged batch touches (the mirror's diff) — the replica replays the batch over the delta and re-reads them; a delta older than `getModelRev()` (the replica applied it already, e.g. through a tail catch-up ahead of the feed frames) moves no rev and no entity, only its issues (`applyDeltaShared`'s `rev: false`) and its `id_map` re-keying. The unstage family waits for the edits before it and posts one transition: `popLastStaged()` = `unstage {batch: last}` (a coalesced keystroke lives in its first batch), `revertStagedFor` = `{entity}` (parked batches stay), `revertStagedForElement` = `{entity, incident: true}` plus `{batch}` for each parked batch touching the element, `revertAllStaged` = `'all'`, `revertConflict(id)` = `{batch}`; `clearStaged()` does nothing. The commit (`checkout.svelte.ts`): on the engine side `previewStaged`, `commitStaged` and `validateAll` wait for `stagedSettled()` first (a `StagedUnreadableError` refuses them, nothing posted) and take the model ops with the facade's `captureStaged()` — the ops of the mirror's batches and their ids, read together, so nothing is sent unnamed or named unsent; the commit's flight is settled with those `batchIds`, so the replica drops exactly the batches sent and remaps the rest through `id_map` (an edit staged during the POST stays, a batch of its own), a refused POST abandons the flight and keeps them, a `rebound` commit unstages them by id (`dropStagedBatches`: the frozen replica never applies it, and a re-bootstrap would adopt them again), and a revert names none. While the sync's `ownPending()` holds — a flight open, or an own answer a `frozen`/`failed` replica has not applied — `commitStaged` refuses with `CommitPendingError`, posting nothing: the batches still staged may name temp ids that commit minted. "Reload model" runs the facade's `reloadModelStore()` — on the engine side `discardAllStaged()` (`unstage 'all'`, deferred edits withdrawn, awaited whatever the mirror's state) before `resetModelStore()` — since the reload drops the lock registry the batches' leases were in; the legacy side is `resetModelStore()` alone. The engine merges a single property update into the first staged update of the same entity, so one staged during the POST could be dropped with a batch being committed: `stageProposedOps` waits for checkout's `commitsLanded()` — no commit running, and a landed one applied by the replica (`replicaSettled()`) and taken in by the store — before it stages its list through `emitMany`; the DiffDrawer stays committing and undismissable (Commit/Cancel disabled, no close button, Escape and outside clicks ignored) through the POST and, on a landed commit, until checkout's `commitApplied()` resolves — `commitsLanded()` (while `ready`, once the replica has applied the answer), or the replica `off`/`server`/`failed` — then closes (a `failed` replica keeps the answer and the rebuilt one applies it on its first drain, under the overlay; waiting on in `failed` would also wait on edits and mirror reads held until then; a rebind that freezes the replica before the answer is applied keeps it queued until adoption, the committed batches out of the readers and an update that would merge into one of them deferred meanwhile); `Cmd/Ctrl+S` opens no drawer while `isReplicaBlocked()`; a refused commit frees it at once, and on the legacy side `commitApplied()` is `null` and it closes when the POST answers. `discardConflict(batchId)` drops a parked batch and releases the leases its ops needed that no remaining staged op needs; the element discards read the remaining ops once the unstage has landed, and keep every lease while the staged list is unreadable. `DiffDrawer` renders `getStagedConflicts()` as a section of its own under the entity rows (`data-testid="staged-conflicts"`, headed `N staged edits no longer apply` — always plural — one row per parked batch, `conflict-row-<batchId>`, each op summarised like an entity row plus the engine's `error.detail` verbatim and a ghost Discard calling `discardConflict`), outside its `total` and never part of a commit; `[]` on the legacy side, so the section never renders there. The facade's `emitMany`, `stagedSettled`, `getStagedBatchIds`, `getStagedConflicts`, `revertConflict`, `captureStaged`, `dropStagedBatches`, `markStagedLanded` are, on the legacy side, a loop of `emit`, a resolved promise, `[]`, `[]`, a no-op, the buffer's ops with no batch id, a no-op and a no-op; checkout awaits nothing on that side, so a legacy commit is posted in the tick it is called. `model-caches.ts` holds the pure id-remap helpers (`remapElement`, `remapRelationship`, `remapCaches`) an entity half's `applyDelta` uses to resolve temp ids to canonical ones across its caches.
- **The notice and the block.** `getReplicaNotice()` (some surface on the engine, phase `server`, not dismissed) is a dismissible warning row — `ReplicaFallbackNotice.svelte`, its own `auto` row in `+page.svelte`'s grid — saying the engine could not start, so the tab reads from the server; `dismissReplicaNotice()` clears it until the next `startReplica()`. `isReplicaBlocked()` (some surface on the engine, phase `failed`, or a `retryReplica()` still running through `resyncing`) blocks the workspace behind `ReplicaFailedOverlay.svelte` — a fixed overlay under the progress overlay's z-index, its Retry button taking focus on mount — showing `Retrying…` disabled while `isReplicaRetrying()`; `retryReplica()` calls `sync.retry()`, the same in-place re-bootstrap that adopts the batches the sync still holds, never a reload. - **Raw text.** A feed frame, a commit or revert response body and a tail body reach the engine as the text that arrived, never re-serialized (AD-26): `FeedConfig.onEvent(event, raw)` passes the frame's text, `ApiFetchInit.onText(text)` (on `commitChanges` / `revertToCommit`) hands over a 2xx body before it is parsed, and `lib/api/replica.ts` returns the tail's text with its three envelope fields read off for the shell. `OpsResponseSchema` keeps `prev_rev`.
