# Replica shell (`frontend/src/lib/engine/`)

The app's side of the replica: plain TypeScript, no runes, no `lib/state/*` import (it may import `lib/api/*`). `lib/state/replica.svelte.ts` wires it into the workspace, and `frontend/README.md` ("Replica (engine shell)") has the detail. Every read of `lib/api` the replica can answer is answered by it, from the working copy — staged edits and staged artifacts included — once its gate is open: the nine model reads (elements, fuzzy search, incident relationships, containment tree, summary counts, …) and the navigation and criteria evaluations, the issues, the table pages, the exports, the metamodel previews, the model download, the view warnings and the compare with apply-CR. No server answer stands behind them: `route()` waits for the gate, and a replica that cannot open it — failed, without a model, not started — is an `EngineUnavailableError`; a status-bar indicator (`data-testid="replica-indicator"`) shows its state. The replica also STAGES: the user's edits are ops applied to the working copy, and the model store's engine half (`model-engine.svelte.ts`) is a view over its staged batches, mirrored for the synchronous readers — see "The model store" below and `frontend/README.md`'s "State model".

- **`frame.ts`** — `connectFrame(deps?)` appends a hidden `<iframe>` of `SANDBOX_ORIGIN` (`origins.ts`, `VITE_SANDBOX_ORIGIN`, `http://localhost:5174` by default) with `allow="cross-origin-isolated"` and `sandbox="allow-scripts allow-same-origin"`, waits for `{type: 'sandbox-ready', crossOriginIsolated}`, and answers `{type: 'connect'}` with ONE transferred `MessagePort`; the link carries `isolated` and replays `csp-violation` reports to its `onViolation` listeners. A message counts only when `event.origin === SANDBOX_ORIGIN` and `event.source` is the frame's `contentWindow`. It refuses outright — `FrameError('same-host', 'open the app at http://127.0.0.1:5173')`, no frame built — when the app's hostname is the sandbox's: the two must be different sites (CN-17), which is why every doc says `127.0.0.1:5173`. No `sandbox-ready` within 10 s is a `timeout`; a `worker-error` before it is `worker`, after it ends the link. The window, location, frame factory and channel are injectable, because happy-dom's `postMessage` delivers no ports and an iframe there fetches for real.
- **`client.ts`** — `createEngineClient(port)` is the CT-4 client: ids from 1, an error answer rejects with `errorForStatus` of `lib/api/errors` (so `NotFoundError` / `ConflictError` / `ValidationError`, as after an HTTP call), events go to every `on` listener, an aborted signal posts `{cancel: id}` and rejects with an `AbortError`, `transfer` rides as the transfer list, and `dispose()` rejects everything pending or later with `EngineGoneError`. An `EngineLink` (`client`, `isolated`, `onViolation`, `dispose`) is what `sync.ts` is handed.
- **`cache.ts`** — `createSnapshotCache()`: IndexedDB `datarover-snapshots` v1, store `snapshots`, key path `project_id`, so one row per project (`{project_id, rev, bytes, size, used_at}`). A hit needs the descriptor's exact `rev` and returns a copy; a `put` happens only after the engine's `end` accepted the bytes and evicts least-recently-used rows of OTHER projects down to 64 MiB; a row the engine refuses is dropped. Every call resolves whatever the store does (AD-10): no `indexedDB`, a blocked open, an aborted transaction or a quota error is a miss or a no-op.
- **`sync.ts`** — `createReplicaSync({connect, api, cache, sleep, onStatus, heldFallback?, onAbandoned?})`, the one place that knows the order of things. An open attempt: the snapshot descriptor (`null` → `off`, `no model`), the link (a `connect()` that rejects ends the attempts at once: `unavailable` if this open was never ready, else `failed`), the metamodel document (an `X-Metamodel-Id` other than the descriptor's restarts the attempt for free, three times), `open`, the bytes from the cache (one `chunk`) or streamed from the descriptor's `url` (each chunk transferred exactly — a view is copied first), `end` (its header must be the descriptor's; refused cached bytes are dropped and read again from the network, uncounted), `adoptStaged` on a re-bootstrap, the tail (incomplete fails the attempt), `applyTail`, `ready`. Three attempts, 1 s then 3 s apart; after the third `unavailable` if this open was never ready (the link disposed), else `failed` — which, like `frozen`, keeps the user's own commit responses (and accepts new ones) for the replica `retry()` rebuilds: its re-bootstrap adopts the batches those commits carried, and only their bookkeeping — applied on the first drain, a `duplicate` naming batches still staged — drops them. Every continuation checks a generation token that `stop()` and `open()` move, and every API call carries its own project's base URL (`replicaApi(root)`), so a late call never lands on the next project. Following: feed deltas, snapshot events and the user's own commit responses form ONE queue handled in `rev` order while `ready` (at most 1,000 wait otherwise, past that a catch-up is owed); a delta not past the replica drops without a call unless it is the user's own; `gap` or a snapshot event ahead runs a catch-up through the tail; an incomplete catch-up, `diverged: true`, or the engine's `replica {state: 'diverged'}` event re-bootstraps — `resyncing`, `staged` + `conflicts` read and joined by id (a worker gone cannot be asked: `heldFallback()`, the model store's copy of them, is held instead), the cache row dropped, `close`, the attempts on the SAME worker adopting those batches; a call that finds the worker gone (an `EngineGoneError` from a posted call — the frame disposes the link on a `worker-error`) drops the link and re-bootstraps a `ready` replica on a new worker (a `frozen` one at adoption — meanwhile it refuses calls as `off` does — a `failed` one at `retry()`); a catch-up whose tail FETCH throws tries once more after 1 s first. `feedReset(rev)` (the feed's `reset`: a `rev` bump with no journal row) is a snapshot event ahead, so the tail is incomplete and the replica re-bootstraps; a `reset` or a snapshot event in `off` restarts the open (`unavailable` stays). `retry()` re-bootstraps a `failed` replica with a fresh budget of attempts, adopting the batches it still holds, and connects afresh from `unavailable` (the run, its batches and the dropped link: phase `opening`, attempt 1). `beginCommit()` opens a flight BEFORE the POST and the queue holds while any is open; `settle({text, rev, applied, rebound, idMap, batchIds?})` inserts the response at its place by `rev` (`applied: false` — `prev_rev` null — queues nothing), so the echo drops as covered (CT-2); `abandon()` just lets the queue go. An own response that is DROPPED — settled in `off`/`unavailable`, emptied with the queue at `no model` or at an `unavailable` give-up, or dropped by the pump after its one retry — is applied by no replica: its `batchIds` leave the batches the run holds and are filtered out of every re-bootstrap's read until a replica is `ready` without them, and `onAbandoned(batchIds)` tells the model store, so no re-bootstrap (a wake from `off` included) stages a committed batch again. `ownPending()` is true while a flight is open or an own response waits in the queue or is being applied. A `rebind` event or a `rebound` settle FREEZES the replica (`frozen`, `metamodel changed at rev N`) and `metamodelAdopted()` re-bootstraps it onto the metamodel the UI now shows (AD-27). `call(method, params?, {signal?, transfer?})` is a read answered by the replica, held in the shell until the phase is `ready` and its `rev` has reached `known` — the highest `rev` a `feedCommit`, an applied `settle`, a `feedSnapshot` or a `feedReset` handed it before the call (AD-28) — or at once in `frozen` / `failed`; with `{transition: true}` (the store's `stage` / `unstage`) it is held for the phase alone — posted in `ready` or `frozen`, never held for `known` nor by a commit in flight, held while `opening`, `resyncing` or `failed` so a re-bootstrap's batches are adopted first, and while there is no link — in the SAME list as the reads, a held transition holding every call asked after it; a transition posted to a worker that turns out gone is held again at its place in arrival order for the replica that replaces it; no open, `off`, `unavailable` or `stop()` reject `EngineGoneError`, and so does a read that finds no link or a worker gone. `on('changed', listener)` hands every engine `changed` event (`ChangedEvent`: `rev`, `staged_version`, `issues_version` and `artifacts_version`, which moves whenever the engine's artifact set does, a staged entry included) to listeners kept on the sync, forwarded by each link it adopts until that link is dropped. `setViewPlacement` / `dropViewPlacement` keep a map the sync sends to every new link before any held read goes (`stop()` clears it); `setArtifacts` / `putArtifacts` / `setStagedArtifacts` keep the artifact context the same way — the committed artifacts by id and the staged entries, each call posted to the current link at once and, on a new link, `setArtifacts` then `setStagedArtifacts` right after the placements (each only when non-empty: a new worker starts with none), so an evaluation held across a dead worker resolves every artifact. `stop()` clears both, and it drops the link and with it the worker, whose artifact set would otherwise survive `close` and `open`: no artifact of one project reaches the engine the next `open` builds; `placements.ts`'s `placedElementIds(view)` is what a view places. `ReplicaStatus` is `{phase: off|opening|ready|resyncing|frozen|failed|unavailable, rev, progress: {task, done, total}, attempt, source, isolated, cspViolations, reason, seeded}`, a new object on every change; the replica's `rev` comes from the engine's answers and events, never from the shell's arithmetic. `seeded` says the replica's issue store has been swept whole: the engine's `progress sweep` event with `done === total` sets it, in any phase, but only after the engine's `replica {state: 'ready'}` for the replica the shell opens now — the events keep the engine's order, so an old replica's end of sweep never seeds a new one; every new replica (each open or re-bootstrap attempt sets `opening` / `resyncing`, and a new link) starts `false`, and so does the engine's replica leaving `ready`; a sweep started again (`validateModel`) keeps it through its `done: 0`, since the store is never emptied. `sweep` is never `progress`: the workspace opens at `ready`, and the sweep feeds the gate, not the bar.
- **`artifacts.ts`** — `createArtifactFollower({sync, payloads, staged, parser, pause?, onLoaded?})` keeps the sync's artifact context the project's, one follower per started replica. `load()` fetches every payload (`GET /artifacts/payloads`) into `setArtifacts` and remembers each `artifact_rev` and `kind` (`kindOf(id)`), and each rule set as the engine was handed it; a `validation_rules` item carries the server's parse of its YAML (`rules`), which goes to the engine with it as `WireArtifact.rules` — the document as the TEXT it arrived as, never parsed here — and an item whose `rules` is `null`, or no parse the engine could take, goes without one, which the engine refuses (below). Every staged push — `setStagedArtifacts` and a `putArtifacts`' `staged` — goes through `parser.attach(overlay, kindOf)`: each create, or update with a payload, of a rule set (a create's own `kind`, an update's `kindOf`) carries its parse in `rules`, or `'pending'` while it is out, when the engine keeps the last parse it received for that id (the committed one under an update, none for a create, which then contributes nothing yet); the parser's `onParsed` asks a staged push again (`stagedChanged()`, so a commit's hold still holds it), a load or an `artifact` event that tells the kind of an id a staged update was pushed under unknown pushes the overlay again, and a commit's refresh learns the kinds before its overlay goes. `settled()` also waits for every parse out and the push each brings; `onEvent` (an `artifact` feed event) puts a `deleted` id away and fetches a `created` / `updated` one only when its rev is past the one remembered; `onCommit({idMap, changed, deletedIds})` (the user's own commit) fetches the changed ids the engine does not hold yet — past 100, everything, filtered — and sends them, the deleted ids and the staged overlay in ONE `putArtifacts` (a commit that moved no artifact only pushes the buffer). Fetches run one at a time in the order asked, so a later answer never lands under an earlier one. A commit's refresh holds the staged mirror: `stagedChanged()` queues one microtask that reads the buffer and pushes it only while no refresh is out, and `hasOverlay()` says whether any held or carried entry lies under the buffer, and the commit path clears the buffer and announces the commit in one run, so the clear's push finds the hold. At the announcement the follower posts ONE `setStagedArtifacts` of the entries the commit carried — the buffer as last read, the clear not yet — plus each created one again under its real id from `idMap`, with the buffer over them; a rule set the commit created or updated is not among them: it goes into the COMMITTED layer in that same call, a `putArtifacts` instead, as the commit made it (a create's real id, name, payload and parse; an update laid over the committed copy the follower keeps of every rule set; the rev the commit's `changed` names), so from the announcement on the engine's committed and working rules are the server's and its list tags their issues `on_server` as the delta's splice did — never `uncommitted` again while the refresh is out or after a failed one, and never compiled twice. Its kind is remembered at once, its rev only when the refresh brings the server's copy. One whose parse is still out (or whose rev the commit does not name) is left out of both layers until the refresh or a load brings it, and one the engine already holds at the commit's rev or past it — a peer's `artifact` event fetched first — is left as the engine holds it, since the refresh fetches only what is newer; nothing else is pushed until the refresh lands but another commit's own push or a `putArtifacts` that corrects a failed refresh's entries, and each lays the buffer over the held entries (coalesced as the buffer coalesces: an update over a create merges into it). So until the `putArtifacts` lands the engine reads the working copy the commit came from — a created artifact under its temp id AND its real id, a staged update over the old payload — never a state where a committed artifact is neither staged nor committed; a second commit during a refresh adds its own entries beside the first's. `stop()` drops every answer that comes after it and asks nothing more. A failed refresh keeps its entries under the buffer, each only until a fetch brings newer committed news of the artifact it stands for (a create's real id): a later commit's refresh, an `artifact` event's fetch or delete — whose `putArtifacts` then carries the corrected overlay — or a `load()`, which drops them all; and it asks ONE `load()` at once, with no further retry but the feed's next `snapshot` event. A failed `load()` is asked ONCE more, in the same queue slot, after `pause()` (the store's is 1 s): the retry's own failure is final, so a load never spins; the next trigger (a `snapshot` event, a failed refresh) asks again. Any other failed fetch leaves the context as it was. The feed's next `snapshot` event reloads everything, which heals a missed event too. `loaded()` is true once a load has landed since the follower was made, false once it is stopped — a new follower starts false; `onLoaded()` is called once, as it turns true.
- **`rules-parse.ts`** — `createRulesParser(parse)` over `lib/api/rules.ts`' `parseRules(yaml, cfg?)` (`POST /rules/parse`, `{ok, document, errors}`; `RulesParseSchema` keeps `document` a `string | null`). `attach(entries, kindOf)` returns the entries with `rules` set on every create, or update with a payload, of kind `validation_rules`: the cached parse of `payload.yaml` (a payload without a string `yaml` parses `''`, as the server's does), else `'pending'`, starting ONE parse per distinct text however many entries carry it; any other entry passes through as it is. A parse that lands fires `onParsed`; one that fails — a non-2xx answer, among them the 422 the server gives YAML its loader cannot construct (`x: 2001-13-45`, `!!float abc`), a network error, or a body `engineParse` finds no parse in (`ok` without a `document`, a failure without errors) — is forgotten, never retried on its own and never made up: the next `attach` of its text asks again, and meanwhile the entry stays `'pending'`. Only the texts the last `attach` named are kept, and a parse that lands for a text no longer named is dropped. `busy()` / `settled()` say whether a parse is out. `engineParse` hands the engine `{ok: true, document}` or `{ok: false, errors}`, the document the text it came as (AD-26).
- **Reads — `lib/api/engine-route.ts`, `gate.ts`, `seam.ts`.** Every engine read of `lib/api` is `route<T>(method, params, {signal?, transfer?})` over an INJECTED seam (`installEngineSeam`; `lib/api` imports nothing of `lib/engine`), and answers the engine's body, which the caller parses with its zod schema: `getElement`, `getElementsBatch`, `getTreeItemsBatch`, `listElementsPage`, `listElementRelationships`, `getModelSummary`, `listContainmentRoots`, `listExcludedRoots`, `listContainmentChildren`, `searchModel`, `evaluateNavigation`, `evaluateTable`, `fetchScriptErrors`, `exportTable`, `previewTableJson`, `runExporter`, `runExporterDraft`, `previewTransform`, `getModelIssues`, `validateModel`, `previewCommit`, `diffMetamodel`, `downloadModel`, `viewWarnings`, `compareModel` and `proposeCr`. An `EngineSeam` is `call(method, params, signal?, transfer?)` and `whenReady(signal?)`; `route` awaits `whenReady`, makes the call and returns, so a call made while the replica opens or is not yet swept waits and answers once the gate is open. No seam installed is an `EngineUnavailableError` (`the engine is not running`). A 409 whose detail is `stale staged batches`, `stale base_rev`, `replica is not ready` or `replica closed` — the staged batches, the `base_rev` or the replica moved under the call — awaits `whenReady` again and asks once more with the same params; a second refusal reaches the caller as the `ApiError` of the engine's answer, and so does every other engine error unchanged: a 404, a 409 of another detail, a 422 (a search or table pattern the regex translator cannot take, an unreadable model file or change request, a rebind preview whose staged ops the candidate refuses, …). A call that moves fixed buffers in `transfer` is not asked again, since they are detached once posted; `params` may be a function and `transfer` a function of the params it made, so each attempt gets its own buffers (`compareModel` reads its file again) and the call is asked again like any other. `createEngineSeam(sync, whenReady)` (`seam.ts`): `call` is `sync.call`, the signal and the transfer list its options; an `EngineGoneError` from it (no replica to ask, a worker gone under the call) is an `EngineUnavailableError`. `whenReady` is the replica store's gate, `createGate(read)` (`gate.ts`): `read()` says `open`, `closed` or `unavailable` with a reason; an open gate resolves at once, an unavailable one rejects at once with `EngineUnavailableError(reason)`, and a closed one holds every caller on ONE promise per epoch — from the first caller to a closed gate until the gate leaves `closed` — which `moved()`, called whenever something `read` reads moved, resolves or rejects; a caller's `signal` rejects that caller alone with an `AbortError`. Engine params are flat snake_case (`elementId` → `id`, `viewId` → `view_id`, an id list → `{ids}`) with omitted options left out; `signal` on the option bags is the call's signal. The three evaluations take the request body as params, with absent keys left out: `evaluateNavigation` (`definition` or `artifact_id`, `row_element_id`, `limit`, `offset`), `searchModel` (`{target, criteria, limit, offset}`) and `evaluateTable` (`definition` or `artifact_id`, `offset`, `limit`); the exports `exportTable` (`{definition | artifact_id, format}`), `previewTableJson` (`{definition | artifact_id}`), `runExporter` (`{artifact_id}`), `runExporterDraft` (`{definition, name}`) and `previewTransform` (`{entry}`) add `date` (`lib/util/utc-date.ts`'s `utcDate()`, the UTC day as `YYYYMMDD`) and `project` (the active project's id, which `state/active-project.svelte.ts` pushes into `api/client.ts` beside its base URL, `activeProjectId()`), but for the preview of a table, and everything is sent as plain JSON (`asSent`: a `$state` proxy cannot cross a `MessagePort`). An export's answer `{parts, filename, content_type, truncated}` is `engineExport`'d into `{kind: 'ready', blob: new Blob(parts, {type: content_type}), filename, truncated}`. `downloadModel {}` answers `{parts, filename, content_type}` (`EngineModelFileSchema`), which is `new Blob(parts, {type: content_type})`: the committed model written as `GET /model/download` wrote it, byte for byte, whatever is staged; `TopBar`'s Export opens the save picker within the click and hands `saveResponseToFile` a `Response` over a stream that reads the Blob once it arrives, named `modelFilename ?? 'model.json'`. Beside the table's Export control and the exporter tab's Export button, `data-testid="export-staged-note"`, `Includes staged changes`, shows while `exportsIncludeStaged()` (`state/replica.svelte.ts`: the model store's engine half holds a staged edit, or the staged artifact buffer an entry; reactive) — an export holds the working copy, and the manifest's `model_rev` stays the committed rev. `viewWarnings(view)` is `validateView {view}`, the view as staged, its issues parsed by `IssueListSchema`. `compareModel(file)` is `compareModel {file, created_at}`, `file` the upload's `arrayBuffer()` in the call's transfer list, and `proposeCr(crs)` is `proposeCr {crs, created_at}` with `crs` sent plain; `created_at` is the client's `new Date().toISOString()`; `compareModel`'s result carries `workingCopy: true`, its answer parsed by `EngineCompareSchema`, and a proposal's by `EngineProposeSchema` — the route's body, or `{conflict}` — into `{ok: true, modelRev, cr, ops}` or `{ok: false, modelRev, crIndex, conflicts}`, so a conflict is an answer, not an error; `modelRev` is the replica's committed rev, which `stageProposedOps` checks. The issues: `getModelIssues {}`; `validateModel` without an inline model or a scope is `validateModel {batch_ids}`, the engine's staged batches `ops` are (`batchIds`, required when ops are sent; an inline model, a scope and ops with no batch ids are still `POST /model/validate`); `previewCommit(baseRev, ops, cfg?, local?: {strict, batchIds})` with `local` and no `metamodel.rebind` op is `previewCommit {base_rev, batch_ids, strict}`, the engine's model half from its own staged batches, and when an op is not a model op (artifact, view, `metamodel.move_node`) the server previews those ops alone and the halves merge — counts summed, `structural_blockers` and `issues` concatenated engine first, `would_block` or-ed; no `local` is the server's whole request. With a `metamodel.rebind` op the blob is linted first (`lintMetamodel`, `POST /metamodel/lint`): a blob the lint refuses is the server's whole request, which answers its own 422, and else `previewCommit {base_rev, batch_ids, strict, rebind: {metamodel: document}}` is the whole working copy under the candidate with the committed rules, `would_block: false`, the ops that are neither model ops nor the rebind previewed by the server alone and merged the same way. `diffMetamodel(body)` lints the candidate — `lintMetamodel`'s `document` is the parsed metamodel as `GET /metamodel` serves it, `null` unless `ok` — throws a `ValidationError` 422 `Invalid metamodel` when the lint refuses it or gives no document, and answers `candidateIssues {metamodel: document}`, the model half, the working copy under the candidate with the working rules, joined with `structuralDiff(body)` (`POST /metamodel/structural-diff`, the document half alone) as `structural`. A rule set the engine cannot read is skipped with a reason in `rules_status.skipped`, and a facet pattern it cannot translate is an issue of its value.
- **The store — `lib/state/replica.svelte.ts`.** `startReplica()` opens the sync, installs `createEngineSeam(sync, whenReady)` into `lib/api`, `whenReady` being the store's gate (below), and attaches the model store's engine half (`attachEngine(handle)`: the sync's `call` and `on('changed')`, this store's status, `subscribeReplicaStatus`); `stopReplica()` / `resetReplica()` uninstall the seam (every read is unavailable again, and one waiting on the gate rejects with `EngineUnavailableError`) and detach the engine half before the sync stops. `subscribeReplicaStatus(listener)` hands every status change with the one before it. `handReplicaFeed` hands a `reset` event to `feedReset`; the realtime store then does a snapshot event's work minus presence and leases (`refreshSummary()` when ahead, the debounced issues refetch). `refreshSummary()` keeps the store's issue counts (the engine answers `null`) and asks `refetchIssues()`; `_modelRev` is the answer's. `startReplica()` binds the staged artifact buffer to the project it opens (`bindStagedArtifacts`: a buffer staged in another project is dropped silently — no discard listener, which would re-dirty and repoint that project's editor drafts — while the same project's is kept; `boot()` binds it too, beside the other staged families' resets), then builds the artifact follower for the project it opens (its fetches and its rules parser's `POST /rules/parse` scoped to that project's base, whatever project is active by the time they go), calls `load()`, and pushes the staged buffer when one is kept. The gate the seam waits on (`gateState()`, a `createGate` over it, `moved()` called at every status change, every follower load and stop and every seam install and uninstall) is `open` when the phase is `ready` or `frozen`, the status's `seeded` is true and the current follower's `loaded()` is true — a navigation may name artifacts, a table its own id or its navigations', an export its tables or its exporter, and a store swept part-way is not the model's list; `closed` while the phase is `opening` or `resyncing`, or until the sweep ends and the first artifact load lands (after a stop, until the next follower's lands; a failed first load is asked once more after a second, and until one lands every read waits); `unavailable` when the phase is `failed`, `unavailable` or `off` (its reason is the status's, such as `no model`), when the follower's first load failed for good (`loadFailed()`: the fetch and its one retry; `onLoadFailed` sets the store's `_loadFailure`, which `isReplicaBlocked()` reports — the workspace shows the failure overlay with `getReplicaBlockReason()` — and `retryReplica()` then asks the follower for a new `load()`, the gate waiting again until it lands or fails once more), or no replica is installed. A `frozen` replica keeps `seeded`: its list matches the old-metamodel UI until the adoption re-bootstraps it. `startReplica()` also follows the sync's `changed` events for the tables (`followTables`): one whose `(rev, staged_version, artifacts_version)` differs from the last seen calls the `onTablesMoved` listeners — the table store's `scheduleTablesRepage()` (see `frontend/README.md`, "Tables on the engine") — and `stopReplica()` / `resetReplica()` unsubscribe. A replica built again posts no `changed` for what it holds, so reaching `ready` from `resyncing`, or from `opening` after the sync reported `off`, calls the listeners too and forgets the last tuple seen, and so does the follower's first load (`onLoaded`): a table asked before either waited for the gate. A commit re-pages once, through the replica's `changed`. The view warnings follow the same events (`followViews`): a new `(rev, staged_version, artifacts_version)` calls the `onViewsMoved` listeners — the view store's recompute, so a peer's model-only commit that deletes a placed element warns without a view reload — and so does the views gate opening (the issues' gate with the artifacts loaded), its status half in `onStatus` or the follower's first load; `stopReplica()` / `resetReplica()` unsubscribe. `metamodelIncludesStaged()` (`state/replica.svelte.ts`, re-exported from `state/index.ts`) is `exportsIncludeStaged()`'s twin, and the metamodel editor records it with each preview as its answer lands (`previewIncludesStaged`), so `Metamodel/MetamodelTab.svelte` shows `data-testid="metamodel-staged-note"`, `Includes staged changes`, above the preview panel when the preview on screen was answered with staged edits, whatever is staged since. The live issue list follows the replica once it holds a model and its first sweep has ended: that gate going from closed to open, or the follower's first load (`onLoaded`) while it is open, schedules the issues refetch (`scheduleIssuesRefetch()`, in `model-shared.svelte.ts`: one 300 ms debounce the feed's triggers share, which `stopRealtime()` disarms), and `startReplica()` subscribes the sync's `changed` events: one whose `issues_version` differs from the last seen schedules it while it is open (`stopReplica()` / `resetReplica()` unsubscribe). The version is per worker; a new worker's gate opening refetches regardless. `stopReplica()` / `resetReplica()` stop the follower before the sync stops, and a start for another project replaces it. `handReplicaFeed` hands it every `artifact` event and reloads it on a `snapshot` event; `onArtifactCommit` and `onStagedArtifactsChanged` (both subscribed once, at module level) reach the current one. `artifact-edits.svelte.ts` fires `onStagedArtifactsChanged` from every function that changes its buffer, `clearStagedArtifacts` included, and `stagedArtifactsForEngine()` projects it to `WireStagedArtifact`s with `$state.snapshot` copies of names and payloads, since an editor's draft may be a proxy a `MessagePort` cannot clone. `registerViewPlacement` / `forgetViewPlacement` / `forgetViewPlacements` reach the sync: the view store registers the COMMITTED document's `placedElementIds` from `refreshView()` — the fetched one, never the staged ops on top, and before `setState`, since the tree refetches on `_view`'s identity — forgets the old view on a switch, a 404, no view or a failed load, and forgets all in `clearViewState()`. The three debounced searches (`Sidebar/Search.svelte`, `Navigation/ElementStartPicker.svelte`, `Snippet/ElementContextRow.svelte`) abort a superseded `listElementsPage` through its `signal`; an `AbortError` leaves the results as they were.
- **The model store — `lib/state/model.svelte.ts`, `model-shared.svelte.ts`, `model-engine.svelte.ts`, `model-caches.ts`.** `model.svelte.ts` is a facade: it re-exports the shared half and the engine half's names, and adds `captureStaged`, `validateAll`, `resetModelStore` and `reloadModelStore`, which span both; `setModelApiConfig` (in `model-engine.svelte.ts`) sets the shared half's client config. `model-shared.svelte.ts` holds what the entity half and the facade agree on — the summary, `model_rev`, the structure-rev counter, the live issue map, rules status and the store error — and `applyDeltaShared(d, has)` is the shared half of a delta's application (the structural formula, the issue splice, the summary patch, `clearOverlay()`), taking a `has(id)` callback so its pre-remap "was this id already cached" check reads the CALLER's cache before the entity half's own remap runs (`structure: false` leaves the structure rev to the caller). `model-engine.svelte.ts` is the entity half, a view over the replica: its caches are filled through the `lib/api` seam — so they hold the staged edits — with no temp-id short-circuit (a temp id the engine 404s is in `getMissingElementIds()`) and nothing a read answers can resurrect a staged delete; `emit(op)` / `emitMany(ops)` (one batch, all or nothing; a one-op list coalesces like `emit`) write the op into the caches at once (a create under its temp id with a lite tree item, a delete taking the row out of the tree items too), raise the entity's PENDING count, add a PROVISIONAL entry and post a `stage` transition; nothing the engine says overwrites a pending entity except the `stage` answer that brings its count back to zero (its post-state), so an answer never regresses a newer keystroke, and a refused stage (`getModelError()` `rejected`, the engine's text) reads its entities back and drops what it created. It keeps a mirror of the engine's `staged` / `conflicts` / `stagedDiff`, read again whenever a `changed` event's `staged_version` moves, whenever the replica becomes `ready` (after a re-bootstrap the cached elements the staged and parked batches touch, before and after, are read again: adopting says nothing) and after every `stage` answer — its three calls posted as transitions (in order with the stages, never held for a rev, only in `ready`/`frozen`), a refused read retried once and then REFUSED: a store error, nothing hangs, but `stagedSettled()` rejects with `StagedUnreadableError` and the unstage family (and `popLastStaged()`, false) does nothing until a read lands, since that mirror is not the engine's staged list; the staged-edit readers read the mirror's batches then the provisional entries, an entry leaving when a mirror read issued AFTER its answer lands — and no mirror read starts while an edit waits for its answer (its `changed` comes first), which is what keeps an op from counting twice; `getStagedBatchIds()` / `getStagedConflicts()` are the mirror's, `getStagedDiff()` the engine's committed images against its records. The batches a landed commit carried are COMMITTED (`markLanded`, which checkout calls once the POST answers with `prev_rev` set or `rebound`): every staged-edit reader, `captureStaged()` and `getStagedDiff()` leave them out — the diff drops the entities only they name and a committed delete's cascade — until a mirror read no longer holds them, though a `frozen` or `failed` replica keeps them staged until it is rebuilt and applies the commit's answer; a single property update the engine would merge into one of them (the first staged batch holding an update of that entity) is DEFERRED — cached, pending and shown at once, posted with every edit after it only once the replica has dropped that batch; Undo withdraws the last deferred edit, the reverts and discards the matching ones. `forgetBatches(ids)` (the sync's `onAbandoned`) drops batches no replica will hold from the mirror and keeps them out of the readers until the next replica is `ready` (one before it may still name them, one after may number a new batch alike); `handOverStaged()` (the sync's `heldFallback`) is the mirror's staged and parked batches, each replaced by a later stage answer's, less the committed ones, which it forgets. `stagedSettled()` resolves once every edit but the deferred ones is answered and covered, no mirror read, cache re-read or unstage is in flight or owed — then `getStagedBatchIds()` and `captureStaged()` are exactly the engine's batches and `getStagedOps()` those plus the deferred edits (a deferred edit waits for a rebuilt replica, and nothing waits for it); a detach releases it. The engine's `changed` event is the one path that refreshes it after a transition: deleted ids leave the caches and tree items, cached changed elements are re-read in one `getElementsBatch`, a changed relationship is left to the relationships list's refetch, `structural` moves the structure rev and the event's `rev` becomes `getModelRev()` when past it. Its `applyDelta` runs `applyDeltaShared` with `structure: false` (the structure rev moves on `changed` alone, once per structural delta), re-keys the caches, visit history and selection through `id_map`, and upserts the delta's entities except those a staged batch touches (the mirror's diff) — the replica replays the batch over the delta and re-reads them; a delta older than `getModelRev()` (the replica applied it already, e.g. through a tail catch-up ahead of the feed frames) moves no rev and no entity, only its issues (`applyDeltaShared`'s `rev: false`) and its `id_map` re-keying. The unstage family waits for the edits before it and posts one transition: `popLastStaged()` = `unstage {batch: last}` (a coalesced keystroke lives in its first batch), `revertStagedFor` = `{entity}` (parked batches stay), `revertStagedForElement` = `{entity, incident: true}` plus `{batch}` for each parked batch touching the element, `revertAllStaged` = `'all'`, `revertConflict(id)` = `{batch}`; `clearStaged()` does nothing. The commit (`checkout.svelte.ts`): `previewStaged`, `commitStaged` and `validateAll` wait for `stagedSettled()` first (a `StagedUnreadableError` refuses them, nothing posted) and take the model ops with the facade's `captureStaged()` — the ops of the mirror's batches and their ids, read together, so nothing is sent unnamed or named unsent; the commit's flight is settled with those `batchIds`, so the replica drops exactly the batches sent and remaps the rest through `id_map` (an edit staged during the POST stays, a batch of its own), a refused POST abandons the flight and keeps them, a `rebound` commit unstages them by id (`dropStagedBatches`: the frozen replica never applies it, and a re-bootstrap would adopt them again), and a revert names none. While the sync's `ownPending()` holds — a flight open, or an own answer a `frozen`/`failed` replica has not applied — `commitStaged` refuses with `CommitPendingError`, posting nothing: the batches still staged may name temp ids that commit minted. "Reload model" runs the facade's `reloadModelStore()` — `discardAllStaged()` (`unstage 'all'`, deferred edits withdrawn, awaited whatever the mirror's state) before `resetModelStore()` — since the reload drops the lock registry the batches' leases were in. The engine merges a single property update into the first staged update of the same entity, so one staged during the POST could be dropped with a batch being committed: `stageProposedOps` waits for checkout's `commitsLanded()` — no commit running, and a landed one applied by the replica (`replicaSettled()`) and taken in by the store — before it stages its list through `emitMany`; the DiffDrawer stays committing and undismissable (Commit/Cancel disabled, no close button, Escape and outside clicks ignored) through the POST and, on a landed commit, until checkout's `commitApplied()` resolves — `commitsLanded()` (while `ready`, once the replica has applied the answer), or the replica `off`/`unavailable`/`failed` — then closes (a `failed` replica keeps the answer and the rebuilt one applies it on its first drain, under the overlay; waiting on in `failed` would also wait on edits and mirror reads held until then; a rebind that freezes the replica before the answer is applied keeps it queued until adoption, the committed batches out of the readers and an update that would merge into one of them deferred meanwhile); `Cmd/Ctrl+S` opens no drawer while `isReplicaBlocked()`; a refused commit frees it at once. `discardConflict(batchId)` drops a parked batch and releases the leases its ops needed that no remaining staged op needs; the element discards read the remaining ops once the unstage has landed, and keep every lease while the staged list is unreadable. `DiffDrawer` renders `getStagedConflicts()` as a section of its own under the entity rows (`data-testid="staged-conflicts"`, headed `N staged edits no longer apply` — always plural — one row per parked batch, `conflict-row-<batchId>`, each op summarised like an entity row plus the engine's `error.detail` verbatim and a ghost Discard calling `discardConflict`), outside its `total` and never part of a commit. `model-caches.ts` holds the pure id-remap helpers (`remapElement`, `remapRelationship`, `remapCaches`) the entity half's `applyDelta` uses to resolve temp ids to canonical ones across its caches.
- **Snippet runs and the working stamp — `state/replica.svelte.ts`.** `callEngine(method, params, {signal})` is `_sync.call`, which `api/snippets.ts`'s `runSnippet` uses for the engine's `runSnippet` (`RunSnippetParams` → `RunSnippetResult`, whose `stamp` is `{rev, staged}`); an aborted `signal` rejects the call locally and the engine stops the run's script. `getWorkingStamp()` (reactive) is the `{rev, staged_version}` of the current link's latest `changed` event, `null` before the first and whenever the phase leaves `ready` (the staged version restarts with each worker) or the replica stops; `adoptWorkingStamp` takes a run's stamp only while it is `null`. `scriptsNeedEngine()` is true while the phase is `off` or `unavailable`: the console and the embedded Test panel then show `ScriptsNeedEngine` and call nothing.
- **The block.** `isReplicaBlocked()` (phase `failed` or `unavailable`, the artifacts could not be loaded, or a `retryReplica()` still running through `resyncing` or `opening`) blocks the workspace behind `ReplicaFailedOverlay.svelte` — a fixed overlay under the progress overlay's z-index, its Retry button taking focus on mount — showing the reason (`getReplicaBlockReason()`, `data-testid="replica-blocked-reason"`) and `Retrying…` disabled while `isReplicaRetrying()`; `retryReplica()` calls `sync.retry()`: from `failed` the same in-place re-bootstrap that adopts the batches the sync still holds, never a reload, from `unavailable` a fresh connect; `whenReplicaUnblocked()` resolves when either lands. Both read `_status.phase`, so they move with `getReplicaStatus()`. A project with no model (`off`) is not blocked.
- **Raw text.** A feed frame, a commit or revert response body and a tail body reach the engine as the text that arrived, never re-serialized (AD-26): `FeedConfig.onEvent(event, raw)` passes the frame's text, `ApiFetchInit.onText(text)` (on `commitChanges` / `revertToCommit`) hands over a 2xx body before it is parsed, and `lib/api/replica.ts` returns the tail's text with its three envelope fields read off for the shell. `OpsResponseSchema` keeps `prev_rev`. A feed commit event without its text is not handed to the replica.
