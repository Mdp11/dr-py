# Backend (`src/data_rover/api/`)

Custom validation rules (lint and parse): `../core/README.md`. Snippet facade reference: `../core/script/README.md`. Frontend architecture: `frontend/README.md`.

## Project state and the delta protocol

This is the central design and the thing most likely to surprise you. The model can be **~80 MB**, so the server holds none of it: it loads no model, builds no whole model for a request and runs no whole-model work.

- **`project_state.py`** holds a process-wide `ProjectStateRegistry`: one in-memory `ProjectState` per project id, loaded on first access. It carries what has no durable home or is read on every request, and **no model**: `project_id`, `metamodel` (the one the `ModelRow` points at, frozen once loaded, replaced by a rebind; `None` for a project with no `ModelRow`), `views` (every view by row id, loaded with the project and healed of missing folder ids without bumping `view_rev`), `model_rev` (mirrors `ModelRow.model_rev`), `strict_mode`, and the live coordination state: `write_mutex` (an RLock serializing commit, revert, lock, view and settings writes and eviction), `lock_table`, `hub` (the feed's subscribers), `mirror_mutex` and `last_access`. `ProjectStateRegistry.get` loads the `ModelRow`, its metamodel, the views and the mirrored leases (`lock_mirror.restore_leases`), never a head row, under a per-project init-once lock so racing requests share one state; a project whose head rows were never written still loads (the commit and the descriptor answer 409 `project has no head rows: re-import it`; nothing heals it). `peek` never loads; `evict` and `discard` are described under Check-out/commit. Routes resolve the state per request from the **`/api/v1/projects/{project_id}` path segment** via `project_state.get_project_state`, which depends on `authz.require_membership` so the request is **authorized before the state is touched** (see Tenancy below); `deps.require_metamodel` is the 404 for a state without one. **The database is the source of truth; the client never holds the whole model** — except through the replica (see `frontend/src/lib/engine/README.md`), which holds it and stages the model edits.
- **`routes/ops.py`** is the op applier behind `POST /commits`: clients send small op batches (mirroring `frontend/src/lib/state/ops.ts`). Ops are applied **in place** to a model while inverse ops and first-touch before-images are collected — a commit, a revert and `POST /commits/preview` apply them to a partial model loaded from the head rows (`commit_load.py`, below); a mid-batch failure returns **422** after `_rollback(model, res)` has put every touched entity back from its before-image — properties, `rev` and place in insertion order — in the four passes of the engine's `rewind` (relationships out, elements out, elements in, relationships in), closed by `Model.settle_order()`. Every path that applies a batch and takes it back goes through it — `POST /commits/preview`, `_CommitUnwind`, a persist failure — so none leaves a trace in any `rev`, in entity order or in the state digest. Each accepted batch bumps `model_rev` once. `create_element`/`create_relationship` accept an optional **`id` hint**: the applier reinstates the entity under it via `Model.restore_*` or 422s the batch when the id is taken, and the journal keeps only the canonical `temp_id`, so replay, revert and the commit diff never see the hint.
- **Rev conflicts**: clients echo `model_rev` as `base_rev`; a stale batch gets **409** and the client must reload. The revision a commit judges it against is `ModelRow.model_rev`, read under the row lock inside the commit's transaction; `ProjectState.model_rev` follows it after the commit.
- **The commit delta (CT-2)**: every landed batch — `POST /commits`, `/commits/revert` — answers with `prev_rev` (the `model_rev` before the bump), `state_digest` and `recreated_element_ids` / `recreated_relationship_ids` on `OpsResponse` / `CommitResponse` (`prev_rev` and `state_digest` are `null` on a response that applied nothing); `commit_event` carries the same four, and `Commit.state_digest` (nullable, Alembic `0015`) records the digest on the journal row. The CT-3 digest is folded on `ModelRow.state_digest` (`state_digest.fold_batch`, in O(batch): every before-image out, whatever the batch left behind in; `parse_digest` reads the 16 hex digits back) in the commit's transaction, so a commit that fails persists no digest. The state holds no digest: the digest is the model row's. The shell hands the response's text to the replica.
- **Replica routes (`api/replica.py`, `routes/replica.py`)** — pure rules over journal rows in `replica.py` (no FastAPI; queries stay in `content.py`), the routes in `routes/replica.py`, member-gated GETs and so viewer-allowed.
  - `GET /replica/tail?from_rev=` answers `{from_rev, head_rev, complete, deltas}` (`ReplicaTailOut`): a range is served whole or not at all. `content.commit_tail_marks` reads `(rev, expressible)` for `(from_rev, head]` as scalar SQL — a row is expressible with a `state_digest`, `entity_states`, and neither metamodel-id column set; a Python `None` in a JSON column is stored as JSON `null`, not SQL NULL, so the test is `IS NULL OR CAST(... AS VARCHAR) = 'null'` — and `replica.tail_is_complete` demands every revision present, each expressible, and `0 <= head - from_rev <= TAIL_MAX_REVS` (1,000). Anything else is `complete: false` with no row loaded, and the client re-bootstraps. `head_rev` is `ProjectState.model_rev` read under `write_mutex` (the state's revision moves only after a commit is durable, so every row up to it is in the journal), the same number the feed's `snapshot` event reports — which is how a revision bump with no journal row at head is seen. Each delta is `replica.delta_from_commit`: `feed.commit_event` built from the RAW `entity_states` (non-null `after`s changed, null ones deleted, in the row's key order; `recreated` absent on old rows = none) and `scope_of_ops` over the raw ops — so it is the feed event field for field (`test_replica_tail.py` holds the two together; `create_commit`'s own scope expression is not refactored onto it).
  - `GET /replica/snapshot` (`SnapshotDescriptorOut`: `rev`, `metamodel_id`, `state_digest`, `elements`, `relationships`, `url`) names the snapshot a replica opens from, read off the `Snapshot` row's typed columns — it never touches the blob store. `replica.pick_snapshot` takes the newest v2 row at or below head and accepts it iff `tail_is_complete` over the same marks the tail route reads, so a client that follows a descriptor never meets an incomplete tail; ONE candidate suffices, as an older snapshot's range contains the newest one's. The route needs membership and a `ModelRow`, never a project state or a model: `model_rev` is read from the row. Lock-free fast path first; if it declines, it takes the row lock (`content.lock_model_row`, so no commit moves the head), looks again (a second opener finds what the first wrote) and only then writes a v2 snapshot at head through `snapshot_rows.write_snapshot_from_rows` — a viewer-allowed GET that can fill that cache. A project whose `ModelRow` has no head rows written (`state_digest`/`next_seq` NULL, a pre-head-table project never re-imported) is a 409 `project has no head rows: re-import it`, checked before the writer runs; nothing backfills it. A failed write is a 503 `snapshot store unavailable`; no model is a 404 `No model loaded`. The descriptor's `state_digest` is the digest AT its `rev`, not the live one, and its `url` is a PATH (the request's own, last segment replaced), not an absolute URL.
  - `GET /replica/snapshots/{rev}` answers the stored bytes — `application/gzip`, `Cache-Control: no-store` (the shell caches the bytes itself), and NEVER a `Content-Encoding`, so no client library inflates them; 404 `no v2 snapshot at rev N` when the row is missing, is not v2, or its blob is gone. It depends on `require_membership` alone, so it never loads a project's state. It stands in for signed storage URLs: the descriptor's `url` is all a client follows. A v1 row is invisible to both routes.
  - `GET /metamodel` carries `X-Metamodel-Id` (`ModelRow.metamodel_id`, `""` without a row; CORS `expose_headers` lists it) so a client can pair the document with a descriptor's `metamodel_id`. It is read lock-free: a rebind landing between the two reads is healed by the `rebind_event` the client is already buffering.
  - `GET /artifacts/payloads` (`routes/artifacts.py`, `ArtifactPayloadListOut`) hands the replica's artifact follower the project's artifacts with their payloads, in `content.list_artifacts` order: every one, or with repeated `id` parameters only the named ids the project has — an unknown or foreign id is left out, never an error. Member-gated, so viewer-allowed; declared before `/artifacts/{artifact_id}`, which would read `payloads` as an id. Each item is an `ArtifactPayloadOut`: the `ArtifactOut` keys, then `rules` — `parse_result` of the payload's `yaml` for a `validation_rules` row (a payload without one parses `""`, the empty set), `null` for any other kind.
  - `POST /rules/parse {yaml}` (`routes/rules.py`) answers `RulesParseOut {ok, document, errors}` for a staged rule set the engine compiles. `document` is `rules_document(defn)`: `json.dumps` of `model_dump(mode="python", by_alias=True, exclude_unset=True)`, compact — aliased keys (`in`, `not`), only the fields the author wrote, in field order. It is a STRING that the shell hands on untouched and the engine reads with its exact parser, since `JSON.parse` would lose a float's `.0` and integers past 2^53 (`model_dump(mode="json")` is no substitute: it writes `in_` / `not_` and every unset test as `null`, and `model_dump_json` writes `inf` as `null`). A parse failure is `ok: false`, `document: null` and the one `LintErrorOut` `/rules/lint` gives for the same text (both build it through `_lint_error`); an empty document is `"{}"`. 200 for a string `yaml` the grammar parses or refuses; 422 for a malformed envelope, a `yaml` over `RULES_MAX_YAML_BYTES`, or — as on lint — a YAML scalar PyYAML cannot construct (`2001-13-45`, `!!float abc`), whose `ValueError` escapes `parse_rule_set` unwrapped (`K-67`); the shell counts a 422 as a failed parse. It depends on `require_membership` alone, so it never loads the project's state, and is not in the read-only allowlist: a viewer gets a 403, as on lint.
- **The server reads, validates, evaluates and exports nothing.** The browser engine keeps the full model replica and answers every read, search, validation, table, export and script call (`engine/README.md`); the server's model surface is the replica routes above, `POST /commits`, `/commits/preview`, `/commits/revert` and the commit-history reads. A commit keeps one server check, the structural gate (`api/structural.py`); conformance and rule verdicts are the engine's, reported with the commit.
- **Upload cap** — `max_request_body_bytes` (`DATA_ROVER_MAX_REQUEST_BODY_BYTES`, default 512 MiB, 0 disables) is the ceiling on the body of an upload request. `upload_cap.UploadCapMiddleware` enforces it on `POST /api/v1/projects`, the one multipart upload (Starlette parses the form before the route runs, so the route cannot count): a `Content-Length` over it is a 413 before a byte is read, and the running total is enforced while the parser streams, since the header is client-supplied and absent on a chunked body.

The frontend edits through the check-out/commit flow (staged-edit buffers committed via POST /commits — see frontend/README.md "State model"); the op shapes below are shared by both paths. **`frontend/README.md` documents the frontend architecture in depth — read it before touching `frontend/src/lib/state/`.**

## Tenancy & auth

User/project/membership data lives in a **SQLAlchemy + Postgres** layer, separate from the in-memory `ProjectState`. Tests run hermetic **in-memory SQLite** (`tests/api/conftest.py`); production runs Postgres with the schema owned by **Alembic** (`alembic/`, `pixi run db-upgrade`).

- **`db.py`** — SQLAlchemy 2.0 (sync) engine lifecycle: `Base`, idempotent `init_engine` (in-memory SQLite → `StaticPool`; file SQLite/Postgres → default pool; SQLite gets `PRAGMA foreign_keys=ON`), `get_db` request dependency, `create_all`/`drop_all` (SQLite/dev + tests only — Postgres uses Alembic).
- **`db_models.py`** — `User`, `Project`, `Membership` + `Role` (`owner`/`editor`/`viewer`). FKs cascade (DB `ON DELETE CASCADE` + ORM `passive_deletes`); `role` is `native_enum=False` (VARCHAR+CHECK, portable across SQLite/Postgres). `User.id` is the external identity subject; `User` also carries the local-auth columns `password_hash` (nullable — header/importer users have none), `is_admin`, `is_active`, plus a partial-unique index on `email` excluding the `''` sentinel those passwordless users share.
- **`tenancy.py`** — service functions over the ORM (create/list/get/delete project, member CRUD, `upsert_user`); the single place queries live.
- **`identity.py`** — the **auth seam**: `IdentityProvider.identify(conn) -> Identity` (typed to `HTTPConnection`, the shared base of `Request`/`WebSocket`). Two providers, selected by `DATA_ROVER_IDENTITY_PROVIDER` (default **`cookie`**): `CookieIdentityProvider` (local auth — reads the session-JWT cookie) and `DevHeaderIdentityProvider` (trusts `X-User-Id`/`X-User-Email`, or `?x-user-id=`/`?x-user-email=` on a WebSocket — dev/gateway/tests only); swap via `set_identity_provider`. `get_current_user` is **dual**: the header provider auto-provisions on first sight (zero-setup), the cookie provider does **not** (admin-only provisioning, no self-signup) and 401s when the user is unknown or `is_active=False`.
- **`authz.py`** — `require_membership` (404 unknown project / 403 non-member / 403 viewer-attempting-write), `require_owner` (membership management), and `require_admin` (global-admin gate for the `/admin` routes). Writes are detected by HTTP method with a small allowlist of read-only POSTs (`_READ_ONLY_POST_SUFFIXES`: commit preview, project clone, snippet lint/format, artifact export and its preview).
- **`routes/projects.py`** — project + membership CRUD at `/api/v1/projects` (the only non-project-scoped data routes). All other data routers mount under `/api/v1/projects/{project_id}`. An admin sees **all** projects with a synthesized `role` (picker visibility, not membership — the data/feed routes still enforce `require_membership`).
- **Local auth (`auth.py` + `routes/auth.py`)** — `auth.py` holds the primitives: argon2 (`argon2-cffi`) `hash_password`/`verify_password`, PyJWT session-token `mint_token`/`decode_token` (carries `user_id` + `is_admin`), and `set_session_cookie`/`clear_session_cookie` (HttpOnly, SameSite=Strict, `Secure` per `auth_cookie_secure`). `routes/auth.py` mounts `/api/v1/auth/{login,logout,me,change-password}`; login is timing-equalized against user enumeration. No change-password UI exists yet — the endpoint is the only path.
- **`routes/admin.py`** — router-level `require_admin`; `/api/v1/admin/users` CRUD + `/api/v1/admin/projects/{id}/members` management. This is the only way to create login-capable users under cookie auth (last-admin/last-owner lockout guards live in `tenancy.py`).
- **`csrf.py` (`CSRFMiddleware`)** — defense-in-depth wired after CORS: on an unsafe method, **if** the session cookie is present, require the `X-Requested-With: data-rover` header (else 403). Cookie-less header-auth requests and login (no cookie yet) are exempt.
- **Dev seed & first admin** — `main._ensure_dev_seed` (gated by `settings.dev_seed`, SQLite-only) **only creates the schema** (`create_all`) — no model or user seeding. `_ensure_bootstrap_admin` is the **sole** user-seed path and runs **always** (independent of `dev_seed`): it create-or-promotes `DATA_ROVER_BOOTSTRAP_ADMIN_EMAIL`/`_PASSWORD` as a global admin — the first admin a fresh deploy logs in as. `_guard_prod_secret` refuses to boot the cookie provider with the insecure default `DATA_ROVER_JWT_SECRET` when `dev_seed=false`. The frontend is a real **login + project picker + admin console** (not single-user). Set `DATA_ROVER_DEV_SEED=false` in production.

## Durable persistence

Model content is durable: the head rows are the current state and the journal is the history;
the in-memory per-project `ProjectState` is a **cache of the small things** (metamodel, views,
revision, policy) and the live leases and feed clients, loaded on cache-miss. Snapshots are
written from the head rows.

- **`db_models.py`** adds content tables: `MetamodelRow` (versioned YAML blob),
  `ModelRow` (1:1 with `Project`; carries DB-authoritative `model_rev` + the
  swappable `metamodel_id`), `ViewRow`, `Commit` (PK `(project_id, rev)`; the
  durable op-journal — `ops`/`inverse_ops`/`id_map` as JSON, `author_id` SET
  NULL on user delete), `Snapshot` (PK `(project_id, rev)`; blob `key`; and, for a v2 blob, its header's fields — `format`, `metamodel_id`, `state_digest`, `elements`, `relationships`; all NULL on a v1 row, Alembic `0016`).
- **`storage.py` / `storage_gcs.py`** — the `SnapshotStore` seam. `GcsSnapshotStore`
  (real `google-cloud-storage`) is used in dev (pointed at `fake-gcs-server` via
  `DATA_ROVER_STORAGE_EMULATOR_HOST`) and prod; `MemorySnapshotStore` backs the
  hermetic test suite. One opt-in `integration`-marked test hits the emulator.
  `build_store_from_settings` passes `create_bucket=` **iff** an emulator
  endpoint is set, so the bucket is provisioned at backend boot in dev (docker
  compose owns containers only) while prod never calls `storage.buckets.create`.
  **`snapshot_codec.py`** is the ONE place that knows the blob format — `encode_snapshot` (v1,
  written by no server path, read until F)
  streams a gzip member (level 3) of the COMPACT document (`serialize.iter_model_json_compact`,
  one `json.dumps` per `SNAPSHOT_BATCH` = 2000 entities, byte-identical to a whole-document
  dumps; ~5 % of the indented save-file size), and `decode_snapshot` sniffs the gzip magic and
  falls through to plain `json.loads`, so every row written before compression (indented JSON
  under a `.json` key) still loads: the `.json.gz` key suffix is naming only, readers NEVER
  branch on it, and there is no migration, `encoding` column or backfill. The indented
  `iter_model_json` writes the indented document (`scripts/download_large.py`). `encode_snapshot_v2` writes the line-delimited `datarover.snapshot/v2` form from a model (CT-1: a header line carrying the entity counts, the `metamodel_id` and the `state_digest` of `api/state_digest.py`, then one `serialize.iter_entity_lines` line per entity); it is kept for the contract test and the scripts. Every server writer goes through ONE funnel, `snapshot_rows.write_snapshot_from_rows(project_id)`: it opens its own DB connection (`REPEATABLE READ` on Postgres), reads `ModelRow` (rev, `metamodel_id`, digest, counts), streams `ElementRow` then `RelationshipRow`, each table in `seq` order with `yield_per(2000)`, through `snapshot_codec.encode_snapshot_v2_rows` into the store, and records the `Snapshot` row from the same values. A row's `properties` text is the line encoder's, so a line is concatenated, not re-encoded, and the blob is byte-identical to `encode_snapshot_v2`'s for the same model. It needs no project state, model or `write_mutex`, and raises `LookupError` for a project without a model row. `GcsSnapshotStore.put` streams into `blob.open("wb", content_type="application/gzip", chunk_size=8 MiB)`, with no `content_encoding`. `scripts/snapshot_v2.py` writes one from a model file, inflated, for the engine's benchmark; the engine's `openSnapshot` reads it; and `decode_snapshot` recognizes it by its first bytes, returns the same `{"elements", "relationships"}` document and raises `ValueError` on a line count that disagrees with the header.
- **`content.py`** — service functions over the content tables (the `tenancy.py`
  of model content). The op journal is (de)serialized via `schemas.serialize_ops` /
  `deserialize_ops` (`schemas.OPS_ADAPTER`).
- **`ProjectStateRegistry.evict(project_id)`** drops a state under its `write_mutex` and
  answers whether it did (no snapshot: rows are the durable state); a project with a live
  lease or a connected feed client is refused, and so is one used within the sweeper's TTL
  (`evict(now=, ttl=)`: a request that got the state after the sweeper listed it as idle
  keeps it). The next `get` loads a fresh state and restores the mirrored leases. A lifespan
  idle-sweeper evicts stale states (`DATA_ROVER_IDLE_EVICT_SECONDS`, 0 disables).
- **`POST /commits`** appends a `Commit` and bumps `models.model_rev`, which
  `ProjectState.model_rev` then follows, under the write-mutex. **`POST /commits/revert`**
  appends a *compensating* commit (journal stays append-only; `model_rev` moves
  forward). `POST /metamodel` and the importer persist their content so a
  project survives eviction.
  The every-`snapshot_every` **periodic snapshot** (`routes/ops.py::_maybe_periodic_snapshot`,
  shared by `/commits` and `/commits/revert`) is scheduled on a
  daemon thread (`api/snapshot_job.py`) that runs `write_snapshot_from_rows` for the project,
  at whatever rev the rows are at (any rev at or past the trigger bounds the replay tail
  equally), writes nothing for a project without a model row, and logs-and-drops failures; one
  job per project at a time, in a process-wide slot. `DATA_ROVER_SNAPSHOT_SYNC=true` (the test
  conftest) runs it inline. The rev-0 baseline snapshot of `install_model`, `import_project`
  and `clone_project` goes through the same job (an open that finds none writes it, below);
  the rebind-forced and descriptor-miss snapshots stay synchronous: they are correctness, not
  bounding, and the request waits on them. The importer CLI waits for its job before it exits.
- **Head tables** (`head.py`, Alembic `0018`). `elements`, `relationships` and `entity_refs`
  hold the project's current state as rows, written on every path that changes it. They are
  authoritative and the only copy of the model the server keeps: a commit reads and checks
  only them (`commit_load.py`).
  - `elements` and `relationships` are keyed `(project_id, id)` and carry `type_name`, `rev`,
    `seq` (and `source_id`/`target_id` on a relationship). `properties` is TEXT: the JSON the
    snapshot line encoder writes for the dict (`head.encode_properties`: compact,
    `ensure_ascii=False`, `allow_nan=False`), read back through `parse_model_json`. Text keeps
    `1.0` and integers past 2^53 exact; a float `NaN` arriving by op is refused by the encoder
    and the commit answers 500 with every write rolled back.
  - `seq` orders rows as the model's dict orders its entities, which is the order
    `iter_entity_lines` writes. A batch leaves a surviving entity's `seq` alone; an entity it
    created, or deleted and created again, takes `ModelRow.next_seq` (then increments it), in
    the model's `element_order`/`relationship_order`. A revert's restored entities are
    "created" this way too. A baseline numbers each table from 0 and sets `next_seq` to the
    larger count; the two tables share the one counter, each with its own unique `(project_id,
    seq)`.
  - `entity_refs` has one `(referencer_id, target_id)` row per element-valued property
    reference of an element or relationship (`head.ref_props` mirrors
    `IndexSet._ref_prop_names`: properties whose datatype is an element type), equal to the
    model's referencer index. A row outlives its target; a touched entity's rows are replaced,
    a deleted one's removed, and a rebind rebuilds them all (`rebuild_refs`, paged by `seq`).
  - `ModelRow` gains `state_digest` (the commit's folded digest, or `digest_value` at a
    baseline), `element_count`, `relationship_count` and `next_seq`; NULL `next_seq` means the
    rows are not written.
  - Writers, all in the transaction of the `Commit`/`ModelRow` write and never committing
    themselves: `write_batch` (`POST /commits` and `/commits/revert` through
    `routes/ops._write_head`, after the digest is folded and before `_stage_commit`; it does
    nothing without a `ModelRow` or while `next_seq` is NULL, which a commit answers with 409
    `project has no head rows: re-import it`), `write_empty_baseline` (`POST /metamodel`:
    no entities, digest 0, `next_seq` 0), `write_baseline` (a `Model` to rows; the importer builds no
    model, it streams its rows: see `import_stream.py`). A project whose `next_seq` is NULL (a
    database from before the head tables) is imported again; nothing writes its rows.
- **`Commit.entity_states`** (nullable JSON) is the full before/after state of every model
  entity a batch touched, captured by every journal writer (`POST /commits`, `/commits/revert`) via `api/commit_states.capture_entity_states` — the applier
  snapshots each entity on first touch (`_BatchResult.before_*`), the post-state is read off the
  live model right before `_stage_commit`, and a `recreated` key names the ids the batch deleted
  and created again (`_BatchResult.recreated_*`; absent from older rows). It exists because the inverse ops cannot render a
  `modified` diff entry (an update's inverse patch carries only the touched keys).
  `GET /commits/{rev}/diff` renders the model half from it and answers 409 `diff unavailable
  for this commit` when it is `NULL` (rows older than the column; every commit stores its
  states, with no cap on the batch): the server holds no model to rebuild one from. Baseline
  rows (the importer) store `NULL` on purpose. The per-commit Diff calls `GET
  /commits/{rev}/diff`; the two-revision Compare calls `GET /commits/diff?from=&to=`, which
  folds the states of the rows in `(from, to]` (`api/range_diff.py`: first `before`, last
  `after`, id order; equality is Python `==` on `type_name` and `properties`, plus `source_id`
  and `target_id` for a relationship, never `id` or `rev`, so `1` against `1.0` is no
  change). A rebind row changes no entity (the rebind is refused unless every row already
  conforms), so it does not stop the fold, and a row of it without states contributes
  nothing. A range past `RANGE_DIFF_MAX_REVS` = 1,000 revisions is 422 `range too wide: at most
  1000 revisions`; a gap in the journal or a row without states (not a rebind) is 409 `diff
  unavailable for this range`. Both endpoints depend on `require_membership`, not the
  project state: they read rows only.
- **`importer.py`** (`python -m data_rover.api.importer`) turns
  `(metamodel.yaml + model.json + view.json)` into a project's rev-0 baseline;
  the importer CLI / New Project wizard load `examples/smart-city.*` on demand (no autoload).
  No `Model` is built on any import path.
  - `import_project` runs in ONE transaction: the project, owner, metamodel, `ModelRow`, rev-0
    `import` commit, the head rows from `import_stream.ingest_model`, then artifacts and views. It
    commits only if every check passes, so a refusal (422, `HTTPException`: a bad metamodel, bundle
    envelope, view or model) leaves no project, no rows and no snapshot; the rev-0 snapshot is
    written after the commit. `POST /projects` hands it the model's spooled upload file (never
    `.read()` whole; the small parts are read as text) and does no pre-validation of its own.
    `model_json` is text, bytes or a binary file.
  - `import_stream.ingest_model(db, project_id, metamodel, source)` reads the document with ijson
    (the pure-Python backend: the C one fails on an integer past 2**63, and the conda-forge
    package is noarch anyway, about 5 MB/s) in one pass, `elements` and `relationships` in
    whatever order the file holds them. Per entity: shape (string `id`/`type_name`/ends, object
    `properties`, integer `rev`), no reserved `tmp_` id, a known type, a non-abstract element
    type, only declared property keys; each is written as a row (each table numbered from 0 in
    file order, exactly what `head.write_baseline` writes, and `next_seq` is the larger table's
    size), with its `entity_refs`, and its `(id, rev)` folded into the digest. Refusals are
    collected by check (the first five ids, then a count) and raised after the parse; once one is
    recorded nothing more is written. Duplicate ids within a table are caught per insert chunk
    (a primary-key probe), not with a set of every id. Then SQL checks over the rows, each naming
    its check and the first ids: an id on both an element and a relationship (K-29), a
    relationship end that is no element, a reference to no element
    (`rebind_check.dangling_references`), an element with two containment parents or on a cycle
    (`rebind_check.containment_violations`).
  - Bare `NaN`/`Infinity`/`-Infinity` are not JSON; `parse_model_json` reads them as the strings
    `"NaN"`/`"Infinity"`/`"-Infinity"` and `import_stream._NonFiniteFilter` rewrites them to
    exactly those strings outside strings (a literal in key position is left for the parser to
    refuse), whatever the read boundaries. `1.0` and integers past 2**53 are kept exact
    (`use_float=True`); `1e999` is refused (`-1e999` becomes `-inf`, which no writer emits, and
    is refused as `non-finite number`). ijson also accepts a leading `+` on a number that
    `json.loads` refuses.
  - `clone_project(source_id, project_id, name, owner_id)` copies in one transaction: `INSERT ...
    SELECT` of `elements`, `relationships` and `entity_refs` under the source's model-row lock,
    the source's digest, counts and `next_seq`, a rev-0 commit; artifacts (fresh ids, payload and
    view refs remapped) and views go through the importer's landing, `trust_artifacts=True`; then
    the rev-0 snapshot. A source without head rows is a 409.
  - `install_model(db, project_id, metamodel_yaml=, model_json=)` replaces an existing project's
    metamodel and model at a fresh rev-0 baseline (no history) in one transaction (a refused model
    leaves the project as it was), schedules the rev-0 snapshot and gives a WARM project state the
    new metamodel and rev in place, announcing a `reset` to its feed clients; it has no production
    caller, and API tests seed through it
    (`tests/api/conftest.py::install`, `install_unchecked` for a head the import refuses).

## Check-out/commit + locking

Pessimistic leases gate every durable mutation.

- **`locking.py` — `LockTable`** holds TTL leases keyed by resource id (single-instance in-process, per project state). `acquire` is all-or-nothing. Conflict matrix: SHARED never conflicts; non-DELETE EXCLUSIVE conflicts only with another holder's EXCLUSIVE; DELETE EXCLUSIVE conflicts with ANY other holder's lease (including shared pins — that is how a pin blocks deletion). `expand_targets` turns a lock request into `RequiredLock`s, expanding DELETE-intent exclusives to the full containment subtree; `POST /locks` answers its subtree from the head rows (`commit_load.subtree_ids`, passed in as a function), never a model. `required_locks` derives the lock set from an op batch (delete → subtree; connect → EXCLUSIVE on source + SHARED pin on target); temp/just-created ids within the same batch need no lock. Leases are best-effort write-through mirrored to Redis (`lock_mirror.py` seam: Redis/Memory/Null impls, `DATA_ROVER_REDIS_URL`, empty ⇒ disabled; `lock_mirror_redis.py` isolates the client with 1s timeouts + 30s cooldown) and restored when a project's state loads, with their ORIGINAL tokens, so a client's heartbeat keeps working across a backend restart. The mirror never participates in a conflict decision; a mirror failure degrades (warn), never fails a lock route.
- **`IssueCategory` on `core.validation.issue.Issue`** — two-tier commit gate: `STRUCTURAL` (dangling reference, containment cycle/two-parents) hard-fails at commit with 422, through `api/structural.structural_blockers`; `CONFORMANCE` (endpoint typing, multiplicity, facets, uniqueness, scalar type) and rule verdicts are the engine's to report and never block a commit, strict mode included (the client enforces strict mode). Default is `CONFORMANCE`; only the handful of structural call sites opt in.
- **`routes/locks.py`** — `POST /locks` acquires leases (all-or-nothing; 409 with conflict detail on failure); `POST /locks/release` releases by token; `POST /locks/renew` heartbeat-extends all leases under a token; `GET /locks` lists active leases for the project. Holder = authenticated user; times use `time.monotonic()` (same clock as the sweeper).
- **`routes/commits.py`** — `GET /open` returns `{model_rev, role, element_count, relationship_count, lock_ttl_seconds, strict_mode}` from the `ModelRow` (revision, counts, policy) and the membership, reading no model (404 without a `ModelRow`); `POST /commits/preview` checks `base_rev` against the `ModelRow`, the artifact and view ops dry, and runs the model batch through `load_and_apply` in a transaction it rolls back (all under `write_mutex`; the applier's 422 is its only refusal; with a `metamodel.rebind` it first checks the rows against the candidate and rebuilds the refs inside that transaction, with the rebind's 422s) and answers no issues (`conformance_error_count` 0, empty `issues`/`structural_blockers`, `would_block` false: the engine previews validation) without advancing `model_rev`; `POST /commits` is the durable lock-verified commit (see below).
- **Commit flow** (`POST /commits`, and `/commits/revert`, which runs the same steps on the inverse ops in restore mode): everything happens under `write_mutex` and in one database transaction. The state's metamodel is read under the mutex, never before it: a rebind that is refused swaps the candidate in and out while it holds it.
  1. `SELECT … FOR UPDATE` on the project's `ModelRow` (`content.lock_model_row`: on Postgres the lock holds to the end of the transaction and the row is refreshed; SQLite takes none and the mutex serializes). `model_rev` is read from that row, and the stale-rev check runs here: a future `base_rev` is 409, a behind-head one reads the tail in the same transaction and is judged by the overlap rule below (the overlap check itself runs in step 3, on the partial model). A project with no `ModelRow` has no rows to check against and gets 409. A row whose head rows are not written (`next_seq` NULL) gets 409 `project has no head rows: re-import it`.
  2. **`commit_load.py`** loads the rows the model ops need and builds a partial model (`core/model/partial.py`) from them. `plan_load(db, project_id, metamodel, ops, extra)` names the ids, from the batch alone, and reads them in `IN` lists chunked at 500 and two recursive CTEs (`subtree_ids` down and `ancestor_ids` up the metamodel's containment types, the type list a bound parameter, `UNION` so a containment cycle ends the walk): the named ids (update and delete targets, relationship ends, id hints, the ids element-valued properties name) or their place in `absent`; for each delete root (a `delete_element` target, each id a round missed and, when the batch deletes, the target of every containment relationship it creates, since it may sit below the deleted element by then) its containment subtree, every relationship incident to it with the other end, and the referencers (`entity_refs` by target) of the subtree and of those relationships, the subtree complete in edges and in referencers; the referencers of every hinted or restored create id; for each element the structural check can judge (update targets, relationship ends, referencers) its containment parents and ancestor chain, each complete in parents, and the targets of its references. `load_and_apply` runs, per round on a fresh partial model: the pre-apply checks, the batch, the structural check. A hinted create has two names (its `temp_id` and its hint): the plan treats both as one element, so an op that names either reaches the same delete root and attachment chain. The referencers the structural check judges exclude only what the batch certainly deletes (the subtree walk does not follow relationships the batch deletes; past `MAX_SKIPPED` = 5000 deleted relationships it subtracts the roots alone, which judges more, never less). A read the rows cannot answer raises `NotLoaded`, and every later round plans `thorough`ly: it also judges the referencers inside the deleted subtree (with ancestor chain and reference targets), and nothing else beyond the named, extra and end elements, so a miss does not load the rest of what the plan read and rounds do not grow with the references an element holds; its ids join `extra` (each becomes a delete root: row, subtree, edges, referencers) and the round runs again. `MAX_ROUNDS` = 8; past it, or when a round learns nothing new, the answer is 500 `commit check did not converge`, logged with the batch's op kinds and counts, and nothing was written. A rebind-carrying batch is the same: its metamodel half runs first (below), then its model ops run here, against the candidate, as an ordinary commit.
  3. Before the batch is applied, on the partial model as it stands (and again each round): `required_locks` (temp ids are skipped before the model is read), the stale-rev overlap check (409 `conflicting concurrent commits`), view resolution (422), then lease verification (409 if any expired/missing). Then the batch (422 on mutation-boundary error) and the structural gate: `structural_blockers` over the batch's touched entities, the ends of its touched relationships and the referencers of the elements it deleted, sorted so the answer is stable (structure elsewhere never blocks, and what a schema swap can break in untouched entities is refused over the rows by the rebind itself; no conformance or rule check, no strict-mode gate, no rule recompile). The artifact and view halves are staged after the model half, and a structural refusal (422) comes after them, as before; every refusal rolls the transaction back, which also ends the row lock.
  4. `capture_entity_states` (always), then in this order: the digest folded (`fold_batch` over `ModelRow.state_digest`), `write_batch` (the head rows and `entity_refs`, counts and `next_seq` by delta), `_stage_commit` (the `Commit` row with `message` and the `validation_error_count`/`issues` the client reported, stored as given, and the row's `model_rev` and `state_digest`), `db.commit()`. A failure anywhere rolls the transaction back (500) and leaves no row, journal entry or digest behind.
  5. After the commit: `ProjectState.model_rev` is set to the new revision (a state that had drifted from the row is brought back to it), the snapshot is scheduled, the caller's locks are released and the delta is broadcast inside the mutex. Returns `CommitResponse` with full element/relationship delta and commit metadata.
- **`Commit` row columns** — `message TEXT`, `validation_error_count INTEGER NULL`, `issues JSON` on the `commits` table. The count and issues are client-reported (`CommitRequest.validation_error_count`/`issues`, from the frontend's preview); a revert has no client preview and stores `NULL` and `[]`, which the history shows as "—"; fed by `_stage_commit` via the `_commit_id`/`_message`/`_validation_error_count`/`_issues` kwargs.
- **Lifespan sweepers** — a `lock-sweeper` daemon thread runs every `lock_sweep_seconds` (default 60) calling `LockTable.sweep_expired` on every registered project state; `lock_ttl_seconds` (default 300) is the per-lease TTL refreshed on each `renew` call. Both settings are 0-disableable (tests use 0).
- **Evict-with-live-locks guard** — `ProjectStateRegistry.evict` checks `lock_table.active_leases` under the `write_mutex` before removing the state; if any lease is live, eviction is skipped and the state stays registered.
- **Artifact ops** — `create_artifact`/`update_artifact`/`delete_artifact` join the `OpIn` union: they flow through `POST /commits` (applied, lock-verified — `art:<id>` leases from the typed lock namespace in `locking.py`) and are dry-validated — no lock check, no persistence — by `POST /commits/preview`; `api/artifact_ops.py`'s `split_ops` separates the union so they are applied to `ArtifactRow`s on the request's DB transaction, never to a model (materialized heads, like the views and the metamodel), with full-state inverses so `GET /commits/{rev}/diff` can render them journal-only, like the model half (`api/commit_diff.py`); `/commits/revert` answers a clean 409 for any range containing artifact ops. The kind registry lives in `api/artifact_kinds.py` (`ArtifactKindSpec`: adapter + derived metadata + `extract_deps`/`rewrite_refs`, which drive the import/export closure) — `navigation`, `table`, `code_snippet` and `exporter` are registered; `diagram`/`diagram_kind` stay unregistered and 422 on write. Commit staleness is **overlap-based with a completeness guard**: a stale `base_rev` 409s only when the batch's touched resources intersect the journal tail, but falls back to a strict 409 whenever the tail cannot fully account for the rev gap (something bumped `model_rev` without journaling) or contains an empty-ops/rebind commit; `/commits/preview` keeps strict equality (an empty `POST /commits` is a no-op early return, so a commit can never mint that always-conflict marker itself). Commit feed events carry a `scope` list (`model`/`artifact`). Legacy `PUT`/`DELETE /artifacts/{id}` stay mounted, bumping `artifact_rev` and emitting the same-shaped feed events as the op path. **Lease rule**: `POST /commits` is the only lock-VERIFIED artifact writer, but every other writer HONORS `art:` leases — the legacy PUT/DELETE both 409 while a peer holds one (the caller's own lease never blocks them) — because `UpdateArtifactOp.artifact_rev` is an optional precondition the current client contract omits, which makes the lease, not OCC, the real concurrency control.
- **Named views** — a project holds N views (`ViewRow`: `id`, `name` unique per project, `blob`, `view_rev`), all loaded into `ProjectState.views: dict[id, View]` (complete once the state is loaded — a missing id is a client error, never a cold-cache miss). Selection is **per client**: `routes/views.py` exposes `GET /views` (summaries), `GET /views/{id}` (content), `POST /views` (`{name, view}` → 201; the row's `name` overwrites the document's; 409 duplicate name, 422 malformed), `PUT /views/{id}` (`{view, base_view_rev?}` — whole-document replace, the View menu's JSON editor Save; a differing `name` renames, 409 on a stale rev, duplicate name or a peer lease inside the view, folder ids colliding with another view's are reassigned) and `DELETE /views/{id}` (204; 409 while a PEER holds the view's `view:` lease or any `folder:` lease inside it). Add/replace/delete are DIRECT actions like `POST /metamodel` — under `write_mutex`, never journaled or undoable, broadcast as `view_event(created|updated|deleted)` so peers refresh their list (and refetch an updated active view); the frontend remembers the active view per project in localStorage and stamps it on every staged op.
- **View ops** — folders carry stable uuid ids (`Folder.id`, healed lazily by `core/view/ids.ensure_folder_ids` when the state loads and at import — blob content needs no migration; `views.view_rev` is a real column). Every op of the ten-op `view.*` family (`create/rename/move/delete_folder`, `place/remove/move_element`, `place/remove/move_artifact`) carries a **`view_id`** (`str = ""` — the default exists ONLY so journal rows from before named views still parse; `POST /commits`/`/commits/preview` 422 an empty or unknown id via `view_ops.resolve_view`). The family flows through `POST /commits` only: `api/view_ops.py` applies each `group_by_view` group to the in-memory `state.views[view_id]` with exact inverses (apply-then-inverse restores a byte-identical blob — the invariant revert and `GET /commits/{rev}/diff` lean on; the diff renders view commits journal-only, prior names off the inverse half, each entry stamped with its `view_id`), then every touched view's blob is persisted (`content.upsert_view`) + `view_rev` bumped on the commit's transaction and reported as `CommitResponse.view_revs`. model hydration replay skips it; `/commits/revert` answers 409 across it. Locks: `folder:<id>` leases (`LockTargetIn.type: "folder"`; DELETE intent expands over the folder subtree in the view that OWNS the folder; element placement ops lock only the containing folder) and, for a view's ROOT membership, the view's own `view:<id>` lease (`LockTargetIn.type: "view"`, `locking.container_resource`) — folder ids are uuids, unique across views, so only the root needed view scoping. The conflict backstop compares `folder:`/`view:` resources plus `viewel:<view_id>:<eid>`/`viewart:<view_id>:<aid>` placement-subject markers (the same element placed in two views is no conflict). Element placements never target the root (`VIEW_ROOT_ID = "root"`): an unplaced element renders there, so "move to root" is `remove_element`; artifact refs have a real root list and may sit in many folders. The client commits every `view.*` op through `POST /commits`.
- **Import/export** — `api/artifact_bundle.py` owns the `datarover.artifact-bundle/v1` envelope, the `extract_deps` BFS closure, and the stateless plan→confirm import (`POST /artifacts/{export,export/preview,import/plan,import}`): confirm re-derives the plan, builds fresh-id `create_artifact` ops (refs pre-rewritten to temp/reuse ids; the commit applier resolves the rest) and lands ONE commit via `create_commit` — no leases, 409-with-fresh-plan on any stale decision or apply-time clash (the 409 carries the applier's own detail, never a bare "stale"), and a no-op (never an empty batch) when nothing is created. `extract_deps` is a generic `{"ref": ...}` payload walk, so a REF-valued `transform` (an exporter entry's or a table's) is a bundle dependency it finds and pulls in, while an INLINE `transform` is plain data the walk never sees — an exporter/table using only inline transforms exports bundle-self-contained, one using ref transforms drags its snippet artifacts along. A client `copy_names` rename is vetted against the plan's per-kind taken-name pool (`derive_plan_ex().taken_names`) and rejected by name in `build_import_ops`, since a whole-plan 409 for it would re-derive byte-identically and loop forever. `importer.import_project(artifact_bundle=…)` lands baseline artifacts with id remap + view-blob ref rewrite, and its `trust_artifacts` flag splits its two callers: `clone_project` alone passes it (verbatim copy — unregistered `diagram` rows ride along, because that bundle never left this DB), while the wizard/CLI take the safe default and hold every artifact to what a normal write enforces (registered kind, adapter-valid payload, re-derived `entry_points`), reporting-and-skipping the rest exactly like `derive_plan` — so all three import-from-outside paths accept the same bundle. Duplicate `(kind, name)` inside a bundle is a skip (first wins) on every path; dangling refs, including refs to skipped artifacts, are always tolerated. Export/preview are viewer-allowed read-only POSTs. The frontend exposes this via the TopBar's Artifacts menu (`ArtifactsMenu.svelte` + `ExportArtifactsDialog`/`ImportArtifactsDialog`) and a per-artifact export button in each artifact editor's own toolbar (`ArtifactExportButton.svelte`), and the New Project wizard accepts an optional bundle file and surfaces any `ProjectOut.skipped_artifacts` in a warning panel before navigating to the new project.

## Realtime feed

Server-to-client WebSocket feed.

- **`feed.py` — `FeedHub`** holds a per-`ProjectState` set of `ClientConn`s (each with a bounded `asyncio.Queue`). `broadcast` is sync and thread-safe: it schedules enqueues on the event-loop thread via `loop.call_soon_threadsafe` so it is safe to call while holding the `write_mutex`. A client that falls behind has its queue drained, receives `CLOSE_SENTINEL`, and is dropped; its sender pump closes the socket with 4408 and the client reconnects. The event loop is captured lazily on the first WebSocket connect via `set_loop_if_unset`; `reset_loop` provides test isolation. The event builders (`snapshot_event`, `commit_event`, `reset_event`, `lock_event`, `presence_event`, …) return plain dicts serialized by `ws.send_json`.
- **`routes/feed.py` — `@router.websocket("/feed")`** mounts under the `/{project_id}` prefix. Authentication uses the `IdentityProvider` seam (typed to `HTTPConnection`, the shared base of `Request`/`WebSocket`): the default `CookieIdentityProvider` reads the session cookie the browser sends on the same-origin WS upgrade (no query params); `DevHeaderIdentityProvider` falls back to `?x-user-id=`/`?x-user-email=` query params (dev/tests). Close codes: 4401 (no identity), 4403 (non-member), 4404 (unknown project), 4408 (dropped-behind). On connect: capture the event loop, auth+authz over a short-lived DB session, register `ClientConn`, broadcast a presence-join, send an initial snapshot (current `model_rev` + active leases + connected users), then run a sender pump (`_pump`) alongside a receive loop that only observes disconnect. On disconnect: unregister and broadcast a presence-leave.
- **Broadcast hook sites** — commit delta + lock release after `POST /commits` (in `routes/commits.py`); lock acquire in `POST /locks` and release in `POST /locks/release` (in `routes/locks.py`); lock expiry in the lifespan lock-sweeper (`main.py`); `ProjectState.announce_reset()` — a header-only `reset_event` (`{type, model_rev}`) for a `model_rev` bump that writes no journal row. Three callers: `DELETE /metamodel` right away, and two that announce late, after their durable writes (`POST /metamodel` in a `finally`, so a failed write still announces the bump): `importer.install_model` (through the warm state it refreshes), and `POST /metamodel` after its rows are committed — an earlier event would send a replica to `GET /replica/snapshot` between the bump and those writes, to open from the rows they are about to replace (and, for an upload, to write a second snapshot). `POST /locks/renew` is silent (heartbeat only, no peer-visible state change).
- **`identity.py` (WS detail)** — `identify` is typed to `HTTPConnection`; on a WebSocket the cookie provider reads the session cookie and `DevHeaderIdentityProvider` reads `conn.query_params` instead of `conn.headers` (browsers can't set WS headers). See the auth section above.
- **Evict guard extension** — `ProjectStateRegistry.evict` skips eviction while `state.hub.has_clients()` returns true (mirrors the live-leases guard); `feed_queue_max` setting controls per-client queue depth.

## Live metamodel editing (`routes/metamodel*.py`, `metamodel_ops.py`, frontend `state/metamodel-{editor,diagram,stage}.svelte.ts`)

The metamodel is edited as YAML **in the app** instead of by uploading a file, and both metamodel edits and diagram node positions flow through the **same check-out/commit pipeline** as model/artifact/view edits — there is no separate swap page. Two read-only routes sit beside the commit flow (`POST /metamodel/structural-diff`, `POST /metamodel/lint`); there is no `POST /metamodel/rebind` and no `PUT /metamodel/layout`.

- **`GET /metamodel/raw`** (`routes/metamodel.py`) returns `{blob, source}`: the stored `MetamodelRow.blob` **verbatim** (`source: "stored"` — the author's comments and formatting are the point of this route) or, for a state whose metamodel never landed in a durable row (legacy/test setups, uploads that wrote no content row), a re-serialized `yaml.safe_dump` of the in-memory object tagged `source: "serialized"`. Degrading beats failing here; the client shows a chip saying the comments are gone.
- **`POST /metamodel/lint`** (`routes/metamodel_swap.py`) is parse + metamodel-schema check ONLY — no `ProjectState` dependency (a cold project is not even loaded), no model, no `write_mutex` — cheap enough for a debounced call per keystroke. It is **always 200** with `{ok, errors[]}`, carrying `line`/`column` off the YAML error's `problem_mark`; an undecodable body is just another bad candidate, not a 422. When `ok`, it also answers `document`: the parsed candidate `Metamodel`, serialized exactly as `GET /metamodel` serializes the bound one (the same model, nested), which is what the engine opens as the candidate; `null` when `ok` is false. It is deliberately **NOT** in `authz._READ_ONLY_POST_SUFFIXES` (unlike `/commits/preview`), so a viewer gets a 403: only the owner-gated editing flow lints, and a viewer has nothing to lint.
- **`POST /metamodel/structural-diff`** (`routes/metamodel_swap.py`) diffs the bound metamodel against a candidate: the candidate body is read as YAML, or JSON under a JSON content type, and, `diff_metamodels(bound, candidate)` answered as `MetamodelStructuralDiff` (`response_model=None`, so `FieldChange.from_` goes out as `from`). No model is touched and no mutex taken; the engine computes the model half of a candidate diff itself. A bad candidate is a 422, and so is an undecodable body or a YAML scalar PyYAML cannot construct. Like lint, it is not in the read-only allowlist: a viewer gets a 403.
- **The `metamodel.*` op family** (`schemas.py`'s `MetamodelOpIn` union, `METAMODEL_OP_KINDS`) joins `OpIn` with two members, applied by `api/metamodel_ops.py` (the fourth sibling of the model/artifact/view appliers — full-state inverses, no internal rollback, mirroring the artifact applier's split of responsibilities with `POST /commits`'s unwind):
  - `metamodel.rebind {blob}` — the author's full candidate YAML. At most one per batch (422 otherwise); `POST /commits` **hoists it to apply first** regardless of client order, so every other op in the batch validates against the **new** schema (the point of an atomic migration commit). Inverse carries the prior YAML blob (full-state, self-contained), persisted as a new immutable `MetamodelRow` at `prior_version + 1`. **Rows are checked first** (`rebind_check.py`, in `apply_metamodel_ops` after the candidate parses and before anything swaps): the head rows are streamed in `seq` pages of 1,000 (`rebind_refusals`) and an entity the candidate cannot hold (a type it lacks, an abstract element type, a property key it does not declare) is refused with 422 `rebind leaves {n} entities the new metamodel cannot hold: {first five ids}`; `containment_violations` refuses an element with two containment parents (`GROUP BY target_id HAVING count > 1` over the candidate's containment types) or a containment cycle (a walk over the `(source, target)` pairs of those types, the only thing held beyond a page) with 422 naming the first ids. Then the swap and the staged rows run, `rebuild_refs` rewrites `entity_refs` for the candidate (which properties are references depends on the metamodel), and `dangling_references` (an anti-join of `entity_refs.target_id` against the element rows) refuses a reference that points to no element, 422 naming the first holders. Every refusal rolls the transaction back, refs included, and the ledger puts the swap back. The refusals are over the rows as they are, before the batch's model ops: a rebind that drops a type or property still in use is refused even when the same batch would delete or unset it. The batch's model ops then run as an ordinary commit under the candidate (`load_and_apply` with it; the pre-apply lock and overlap checks read the partial model under the candidate's containment types). The state's metamodel is swapped by `apply_metamodel_ops` and put back by `_CommitUnwind` if the commit does not land; there is no model to swap. **Known limitation, by design, not a bug**: there is deliberately no "old-schema slot" — a model op that references a property the outgoing schema declared but the NEW one doesn't is rejected by `_check_patch_keys` because the swap already happened. So a **property-removal migration cannot be one commit**: the supported shape is unset the property on every affected element in commit N, then rebind (dropping it from the schema) in commit N+1 — two commits, not one atomic migration. The **ADD-a-mandatory-property** direction has no such limitation and IS atomic (rebind + populate in one commit), which is also the direction that actually risks an observable inconsistent state if it weren't atomic.
  - `metamodel.move_node {node, pos: {x,y} | null}` — a per-node write against `metamodel_layouts` (`pos: null` removes the key). Cheap and presentation-only: no metamodel swap, no revalidation.
- **`POST /commits`** treats a rebind-carrying batch specially: gates it on the **owner** role (`metamodel.move_node` alone only needs editor+); hard-verifies the singleton `mm` lease (unlike `POST /metamodel` and `DELETE /metamodel`, which only HONOR the lease — they are the only callers of `_peer_mm_conflict`); runs a **quiet-peers guard** that 409s if any *peer* holds a model-scope lease (the caller's own leases never block — a migration is expected to hold locks on the elements it fixes); **forces a snapshot** at the new rev (so a replica's catch-up tail never spans a rebind boundary; written from the rows); and broadcasts **`rebind_event`** instead of `commit_event` (peers get the reload banner — there is no applyable delta after a schema swap). A layout-only batch is a normal cheap commit: `commit_event` with `"metamodel-layout"` added to the `scope` vocabulary so an open diagram refetches positions. `POST /commits/preview` dry-runs the whole family side-effect-free: the rebind's row checks, the refs rebuilt in a transaction it rolls back, then the model ops on a partial model under the candidate; nothing is swapped.
- **Revert/diff.** `/commits/revert` 409s across the whole family: restore-mode model inverses are schema-checked at the core mutation boundary, and no single replay order is valid both before and after a schema swap without teaching the core a schema-independent restore mode. `GET /commits/{rev}/diff` renders the rebind's structural diff (recomputed from the two immutable `MetamodelRow` blobs, off the commit's `from_metamodel_id`/`to_metamodel_id` columns) beside a journal-only "N nodes moved" layout summary, independent of whether the commit also carried a rebind (`commit_diff.py`).
- **The family is a materialized head, replayed by nothing** (the metamodel comes from `ModelRow.metamodel_id`, positions from `metamodel_layouts`).
- **The conflict backstop uses the single `mm` resource** for the whole family (not per-node markers): every metamodel writer already serializes on the exclusive `mm` lease, so a finer marker could never change an outcome.
- **Frontend** — a singleton `metamodel` workspace tab (`components/Metamodel/`, `state/metamodel-editor.svelte.ts`) with a CodeMirror YAML editor, a localStorage draft, debounced lint and on-demand preview; it composes the surface-agnostic `mm` lease module. The dirty buffer and the diagram's coalesced node moves are the **fourth staged family** (`state/metamodel-stage.svelte.ts`, beside model/artifact/view), committed through the same `commitStaged` as everything else — there is no Rebind button; a dirty draft becomes the batch's `metamodel.rebind` op and staged moves become its `metamodel.move_node` ops. See `frontend/README.md`'s "Live metamodel editing" section.
- **Diagram surface (metamodel diagram editor)** — the same tab toggles to an editable UML class diagram. It adds **no** mutation protocol: `state/metamodel-diagram.svelte.ts` turns every canvas gesture into `parseDraft → applyEdit → serializeDraft` over the current buffer and hands the text back through `editMetamodelBuffer`, so lease/lint/draft/preview are the YAML path's, unbranched; a drag stages a `metamodel.move_node` op instead of a live PUT. The edit core is `frontend/src/lib/metamodel/yaml-edit.ts` — a 22-member `YamlEditCommand` union over the `yaml` package's Document API, because the point of `GET /metamodel/raw`'s `stored` source is the author's comments and re-serializing a plain object would burn them; its `STRINGIFY_OPTS = {lineWidth: 0, flowCollectionPadding: false}` is load-bearing (drop `flowCollectionPadding` and an unedited round-trip of `examples/smart-city.metamodel.yaml` rewrites 126 of 455 lines — a test pins the byte-identity). `diagram-build.ts` derives endpoints from `rel.mappings` ONLY, never the `source`/`target` shorthand, which is a serialization mirror that can go stale. **Node positions are the one exception to "everything durable is journalled"** — they live in the shared `metamodel_layouts` blob, not in a `Commit` row's `ops`, and a rename's position migrates as two `metamodel.move_node` ops (`old → null`, `new → {x,y}`) landing in the SAME commit as the rename, so there is no wire moment where the blob and the draft's names disagree — a peer never observes a half-renamed layout. There is no rename-key deferral: positions only ever land atomically with the rename that caused them.
