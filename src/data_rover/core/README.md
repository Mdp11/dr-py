# Python core (`src/data_rover/core/`)

Snippet facade reference: `script/README.md`. The API layer on top: `../api/README.md`.

## Core layering

- **`metamodel/schema.py` — `Metamodel` is immutable with lazily-built derived caches** (`_Caches`: ancestor chains, effective properties/keys, containment flags, end constraints). Treat it as frozen after load; uploads replace the whole object. If you ever add a mutation path, reset `_cache` to `None` (see `model_copy`). All subtype/effective-property/containment queries go through its cached lookup methods — never re-walk `extends` chains by hand. On a property-name clash along `extends` the ANCESTOR's definition stays (`_effective_props` keeps the first name it sees walking root → leaf), while `key` resolves nearest-first and `key: []` counts as declared; the engine port mirrors both.
- **`model/model.py` — `Model` is the single mutation boundary.** Every create/connect/set_property/delete flows through its methods, which keep `self.indexes` (`IndexSet`, in/out relationship adjacency) in sync. Bulk loaders that populate the dicts directly must call `indexes.rebuild()`. `IndexSet.element_order` (element id → monotonic insertion sequence number; sorting ids by it reproduces `model.elements` order, and ONLY the order is meaningful — the numbers go sparse after churn, a restore re-inserts last) is maintained at that same boundary like `roots_order` and is how the uniqueness validator picks a duplicate group's insertion-first primary without enumerating the model; `verify_consistent` checks it as an order invariant, never by comparing numbers to a fresh rebuild. `relationship_order` is its twin over `model.relationships`, with its own counter, and is what keeps `containment_parents` in relationship insertion order when a relationship comes back under an old number. `set_property`/`delete_property` check the property name against `Metamodel.effective_*_property_names` (cached frozensets on `_Caches`, shared with `routes/ops.py::_check_patch_keys` — never a per-write list copy) and fire `IndexSet.on_properties_changed(entity)`, the whole-entity re-derivation that code writing `entity.properties` directly must call too. `delete_element` cascades through containment children. `insert_element` / `insert_relationship` / `overwrite` are the committed-state methods, the only way an entity is put back as it was: they check no type (a model may hold one its metamodel no longer has), take `rev` as given and fire the same hooks; handed the entity's old sequence number they give it its place back, and `settle_order()` then puts the dicts in that order by REPLACING them — read routes iterate them without `write_mutex`, so never refill one in place and never keep a reference to one across that call. Property values are **replaced wholesale, never mutated in place** — a recorded inverse patch (the commit journal's `inverse_ops`) aliases prior values by reference and depends on this.
- **`validation/pipeline.py` — one sweep, many validators.** The pipeline iterates the model (or a `Scope` subset) once and hands each entity to every `Validator` (`type_conformance`, `multiplicity`, `facets`, `endpoint_typing`, `containment`, `uniqueness`). `default_validators()`/`default_pipeline()` are these six and rule-free; the server runs only the structural subset at commit time (`api/structural.py`), and the engine's port is validated against this pipeline. Per-entity hooks must be O(entity) — use metamodel caches and `model.indexes`, not model scans. Whole-model checks go in `validate_global`. Validators carry mutable per-metamodel memo caches (`MetamodelMemo`, identity-keyed), so **construct one pipeline per request/thread**; never share across threads.

## Custom validation rules (`core/validation/rules/`)

User-defined cross-element rules ("if x has y, then z must have k"), authored as a small **declarative YAML** language and evaluated by the engine (`engine/src/rules/`); the server only parses and lints them.

- **`core/validation/rules/schema.py`** — the pydantic AST + `parse_rule_set(text)`, raising only `RuleSetError`. A rule is `{name, applies_to, severity, disabled, description?, when?, then, message?}`; conditions are `all`/`any`/`not`/property atoms (`exists`/`equals`/`not_equals`/`in`/`gt`/`gte`/`lt`/`lte`/`contains`)/relationship atoms (`type`, `direction`, optional `to`/`where`, `exists` xor `count`), nesting freely. Caps enforce wherever the payload PARSES, never at evaluation time: `RULES_MAX_YAML_BYTES` (64 KiB — a pydantic `max_length` on the string, so characters, matching the `SNIPPET_MAX_CODE_BYTES` precedent), `MAX_RULES_PER_SET` (200), `MAX_CONDITION_DEPTH` (8), and a null operand is refused for every test but `equals`/`not_equals` (`gt: null` would otherwise compile clean and then die per element). **YAML aliases are refused outright** (`_NoAliasLoader`): PyYAML memoizes anchors into a shared-reference DAG that loads in flat time and memory, but pydantic walks that DAG as a tree, so a few hundred bytes of nested aliases expands into gigabytes of validation work **under every one of those caps** — they all measure the source text.
- **`compile.py`** — `compile_rule_sets(sources, metamodel) -> CompiledRules`: parses every source, resolves each `applies_to` to its subtype closure, builds the type → rules dispatch map, and computes per-rule **drift verdicts**. A rule naming an unknown stereotype/relationship/property is **skipped whole** at compile — never evaluated half-blind. `POST /rules/lint` reports the skips as warnings.
- **Storage.** `validation_rules` is an artifact kind (`ArtifactKind.validation_rules`), payload `{schema_version: 1, yaml: "<verbatim text>"}` — the text, not parsed JSON, so author comments and formatting survive, mirroring the metamodel blob. Structural invalidity (unparseable YAML, schema violation) 422s at save; **metamodel drift does not** — the metamodel can change under a committed set regardless. No new artifact routes: commits/locks/bundles are already generic over the kind registry.
- **`POST /rules/lint`** (`routes/rules.py`) is the sibling of `/metamodel/lint`: no write mutex, no model iteration, cheap enough to debounce per keystroke. Parse failures and schema violations are `errors` (`ok: false`); **drift is a `warning` with `ok: true`** (compiled against `session.metamodel` when present). Deliberately NOT in `authz._READ_ONLY_POST_SUFFIXES`, so a viewer gets a 403 — only the editing flow lints. Always 200 for any well-formed envelope; 422 only for a malformed request body (missing/non-string `yaml`, an over-cap `yaml`) — and for a YAML scalar PyYAML cannot construct (`K-67`). Its sibling `POST /rules/parse` hands the engine the parsed rule set as JSON text (`src/data_rover/api/README.md`, "Replica routes").
- **Rule verdicts are conformance, never structural.** A user rule never blocks a commit; the engine reports them, and `schema.py`/`compile.py` stay in step with its port.
- **Deliberately out of scope**: `else` branches; rules on relationship types; property tests on the relationship itself; value-vs-value joins; snippet-backed rules; per-element severity override/muting; STRUCTURAL user rules (permanently out). End to end, `frontend/e2e/eval-rules.spec.ts` drives a rule set from the Rules tab through the Issues panel, a commit and the strict gate.
