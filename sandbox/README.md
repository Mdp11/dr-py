# Sandbox (`sandbox/`)

Commands: `pixi run sandbox-install | sandbox-build | sandbox-start | sandbox-test | sandbox-check` (tasks set cwd = `sandbox`).

A static Vite site, its own npm package, always served as BUILT files (`vite preview`) on `http://localhost:5174` — another site than the app's `http://127.0.0.1:5173`. It hosts the engine in a module worker; the workspace embeds it through the shell (`frontend/src/lib/engine/README.md`).

- **`src/page.ts`** (behind `index.html`, which holds one module script and nothing inline) creates the worker (`new Worker(new URL('./engine-worker.ts', import.meta.url), {type: 'module'})`), reports the worker's `error` event (`{type: 'worker-error', message}`) and every `securitypolicyviolation` (`{type: 'csp-violation', directive, blocked}`) to the parent at `APP_ORIGIN` (`src/origins.ts`, `VITE_APP_ORIGIN` at build time), then posts `{type: 'sandbox-ready', crossOriginIsolated}`. It hands the FIRST acceptable `connect` to the worker as `{type: 'port'}` with the port and keeps no reference to it, so it leaves the data path: `src/handshake.ts`'s `connectPort` accepts a message only from `APP_ORIGIN`, from `window.parent`, of type `connect` and carrying exactly one port; the "only once" rule is the page's. **`src/engine-worker.ts`** runs `createService` over the first port it is given and ignores any other.
- **CSP relay.** A worker's violations fire in the worker's own scope, never on the page. `src/engine-worker.ts` listens for `securitypolicyviolation` on `self` and posts `{type: 'csp-violation', directive, blocked}` to the page; the page's `message` handler on the worker passes it through `handshake.ts`'s `relayedViolation` (which rebuilds the message from its two strings and drops anything else) and reports it to the parent like its own, so the app's violation count covers the worker too. The script worker's violations (an `eval` from a user script, say) fire in ITS scope; it posts them to the engine worker, whose script host re-posts a validated `{type: 'csp-violation', directive, blocked}` to the page through the same path.
- **Pyodide assets.** `pyodide` is a devDependency pinned to an exact version. The script worker loads Pyodide from this origin, never a CDN, under the same policy, so `vite.config.ts` serves exactly the five files in `PYODIDE_FILES` (`pyodide.mjs`, `pyodide.asm.mjs`, `pyodide.asm.wasm`, `python_stdlib.zip`, `pyodide-lock.json`) at `/pyodide/<file>` from `node_modules/pyodide/`. A build copies them to `<outDir>/pyodide/` after every bundle write, `--watch` rebuilds included, and `vite preview` serves that copy as static files; `vite dev` has a middleware that answers those five names only (matched as received: an encoded or dotted path is no name) and 404s anything else under `/pyodide/`. All of them carry the three headers below, and `application/wasm` types the wasm. `test/pyodide-assets.test.ts` builds into a temp directory and starts a real dev server and a real preview over it.
- **`src/host.ts`** — the three things the engine cannot hold, and `portOf(port)`, the engine's `Port` over a `MessagePort` (setting `onmessage` starts the port, which queues whatever was posted before). `inflate` is a `DecompressionStream('gzip')` fed by a pump and read through a `getReader()` loop (not the stream's async iterator, which not every browser has); a failure of the STREAM — a truncated member, trailing bytes, not gzip — is rethrown as `SnapshotError('snapshot bytes do not inflate')`, because the stream's own errors carry an EMPTY message and the service answers anything but a `SnapshotError` with a 500 of that message; a failure of the SOURCE (the service's `ByteQueue`) is rethrown as it is, and the pump never rejects. `createHost()` gives `yieldToHost` as a post on a private `MessageChannel` resolving a FIFO of waiters — a macrotask with no clamp, where a nested `setTimeout(0)` is clamped to 4 ms from its fifth level (about 1.2 s over an open at M) — and `now` as `performance.now()`; its `close()` frees that channel (the worker never calls it; tests must). `host.ts` may use only what a window, a worker and Node 22 share, because the frontend's tests run it.
- **Scripts: the pool, its workers and the bridge.** `ServiceDeps.scripts` is `browserScriptHost` (`src/script-host.ts`), which `src/engine-worker.ts` hands `createService`. It is the engine's pool (`engine/src/script/pool.ts`, documented in `engine/README.md`) over Web Workers: `createBrowserHost({spawn, post, parallelism, warn})` is `createPool(spawn, {cap: poolCap(navigator.hardwareConcurrency), now, onViolation, onWarning})`, `poolCap` being `max(1, min(4, cores - 2))` (one core when the browser says none), and `spawnScriptWorker` makes `new Worker(new URL('./script-worker.ts', import.meta.url), {type: 'module'})` (its own chunk `script-worker-<hash>.js`; a nested worker's message channel to its spawner is already private, so there is no extra `MessagePort`). The engine worker NEVER blocks; a script worker is the only place that calls `Atomics.wait`. The pool, its stops and its snapshot are proved over real Pyodide in the engine's tests; what the sandbox adds is proved in Chromium (below).
  - **One batch per worker.** A worker boots (Pyodide and the guest, no user code), waits as a spare, runs exactly ONE batch and is terminated by the pool, so no interpreter, global or listener of one script reaches another. Workers boot from a memory image of Pyodide with the guest loaded, which one more worker, the maker, takes once per pool and which runs no batch; each worker is posted a COPY of the image (transferred, never shared memory). A boot that cannot use it is cold (about 2 s) and the pool says so once through `onWarning` (`console.warn` here). From the image a boot is about 280 ms in Chromium.
  - **`src/script-worker.ts`** gives `runWorker` (`engine/src/script/worker-main.ts`, the one worker body the Node port runs too) this scope and a Pyodide loaded from this origin. Its loader refuses with `failed` unless `self.crossOriginIsolated`, then `import()`s `/pyodide/pyodide.mjs` (`/* @vite-ignore */`, so the bundle keeps the import; the CSP allows it as `script-src 'self'`, and the wasm as `'wasm-unsafe-eval'`) and calls `loadPyodide({indexURL: '/pyodide/', ...options})`; `runWorker` adds the fixed hash seed, the snapshot and the interrupt buffer. Nothing else is ever fetched. `postMessage`, `addEventListener` and `setTimeout` are bound before any script can run, so a script that rebinds them on its scope does not change how its worker talks. The worker pins its own scope's `Date.now` (and `Date`'s local getters, as UTC), and `crypto.getRandomValues` (`0x42`, which Pyodide's `os.urandom` and the first seed of `random` read), so a script's time and entropy are the server's.
  - **Messages** are the pool's (`engine/src/script/pool.ts`, `worker-main.ts`). Pool → worker: `init {reply, interrupt, limits, snapshot?, make?}` and `run {batch, roots}`; `batch` is the `ScriptBatch` as `engine/src/script/wire.ts` sends it (structured clone keeps an object's fields and drops its class, which would turn a `PyFloat` into a dict, so a float crosses as a one-element `Float64Array`, a type no `Value` holds, and is rebuilt on arrival; ints past 2^53 cross as `bigint`) and `roots[i]` is `bridge.roots(ids)` for call `i`. Worker → pool: `ready {ms, boot}`, `snapshot {bytes}` (the maker), `failed {message}`, `bridge {text}`, `more`, `call-start {i}`, `call-end {i, text}`, `done {results, trips, ms}` and `csp-violation {directive, blocked}`. The pool times each call by its windows and stops a call that outlives it through the 8-byte interrupt buffer (`engine/src/script/interrupt.ts`): the soft stop interrupts the call and the batch goes on in the same worker; `graceMs` later the pool ends the worker (the hard stop) for what the interrupt cannot reach (`time.sleep`, `sum(range(10**10))`, `except BaseException`).
  - **Worker errors.** `spawnScriptWorker` sets `onerror` to `preventDefault()` the event and report it to the pool. Left alone, an uncaught error in a script worker would surface in the engine worker's scope, reach the page's `worker.onerror` as `worker-error` and end the app's link (`frame.ts`). A `messageerror` is reported too. A worker that fails or dies loses only its own batch: the pool answers the calls that had not ended and starts another worker for the next.
  - **`done` is posted one task late.** A script's CSP violations (a `js.eval`) are reported on tasks that follow the one the batch ran in, and the pool ends the worker at `done`; `src/script-worker.ts` posts `done` from a `setTimeout(0)` so the violations go out before it and the page's count includes them. This ordering is best effort, observed in Chromium and not guaranteed by the platform; script timers queued during the batch run before `done`. The Chromium run's control shows one counted for a script that calls `js.eval`.
  - **CSP relay.** The pool calls `onViolation` for each `csp-violation` a worker posts; `violationRelay` cuts both strings to 256 characters, posts `{type: 'csp-violation', directive, blocked}` to the page (which rebuilds it through `relayedViolation`) and never throws into the engine worker. The report is a plain message any script can post, so the count is not authenticated beyond the worker: a script can inflate it or send a made-up one, and a batch the pool ends by a stop before its violations were posted loses them. It is an alarm for the deployment, not a measure of what scripts did.
  - **The reply buffer** (`engine/src/script/bridge-buffer.ts`): one `SharedArrayBuffer` of `REPLY_BUFFER_BYTES` (1 MiB) per worker. Int32 header `[0]` state (0 waiting, 1 chunk ready), `[1]` bytes in this chunk, `[2]` bytes still to come; the payload (the reply's UTF-8 bytes) from byte `HEADER_BYTES` (16), so a chunk holds up to 1,048,560 bytes. The transport is `armReply(buffer)` (state 0), then post `bridge`, then `readReply(buffer, askMore)`, whose bytes are decoded ONCE, with a fatal, BOM-keeping `TextDecoder`, on the whole reply: chunk edges fall inside characters, so chunks are joined as bytes. `readReply` loops: while state is 0, `Atomics.wait(header, 0, 0)`; copy the chunk out to a plain (non-shared) array, which a decoder needs; if bytes remain, store state 0, post `more` and wait again, else return. `ReplyWriter.begin(bytes)` (on `bridge`, answering `bridge.dispatch(text)` encoded to UTF-8 once) writes the first chunk and `more()` the next: length, remainder and payload, then state 1, then `Atomics.notify`. The request text and the reply are never parsed or re-serialized by the host. No timeout: the engine always answers, even "replica is not ready" (`bridge.dispatch` never throws; if it somehow does, the host ends the worker rather than leave it blocked).
  - **Why no wake is lost.** The reader arms BEFORE it posts, so a reply that lands at once is never erased by a late arm; the writer answers only a request or a `more` that reached it, and the reader posts `more` only after storing state 0, so a 0 never follows the writer's 1 for the same chunk and the payload is never rewritten while it is copied; `wait(…, 0)` returns at once when state is already 1, and the loop re-reads the state after every return.
  - **Runs** (`engine/src/service/service.ts`): each run takes the bridge of its own replica epoch and answers that run's worker alone; a replaced or closed replica makes the bridge answer `BridgeError: replica is not ready`, so the script ends by itself and the service refuses the call 409. `dispose()` (the service's `close`) ends every worker and rejects every pending boot and run, and nothing a worker says after it ended is read.
  - **Trust.** A script runs inside its worker's global scope: through Pyodide's `js` module it reaches that scope's globals (`self`, `fetch`, `indexedDB`, `caches`, `BroadcastChannel`, `postMessage`), can post any message (`done`, `failed`, `bridge`, `csp-violation`) and can rewrite what its own worker says. That affects only its own batch: the pool validates every message's shape and its place in the protocol, ends a worker that breaks it, answers a call it did not stop from the results in `done` (the `call-end` texts are used only when a run ends without a `done`), and reads nothing from a worker it ended. A worker has no reference to the engine worker, the page or another script worker: its `postMessage` reaches the pool's slot for it and nothing else, its buffers are its own, and its image is a copy. Under the CSP (`connect-src 'self'`, `worker-src 'self'`) it can fetch this origin's static files and start nested workers (ended with it), and nothing else. **Origin-wide state.** The sandbox origin's IndexedDB, CacheStorage and BroadcastChannel are reachable from every script worker and outlive it. Nothing in this origin reads them: not the engine worker, the page, the snapshot path (the image is made in memory, transferred and never stored), the pool, Pyodide's loader (`pyodide.mjs` has no storage use; `pyodide.asm.mjs` touches IndexedDB only through IDBFS, which nothing mounts) or `host.ts`; the app's own IndexedDB (`datarover-snapshots`) is on the app's origin, which is another site. Registering a service worker is not a vector either: `script-src` and `worker-src` are `'self'` with no `blob:` or `data:`, and the origin serves no same-origin script with attacker-chosen logic. A script can therefore leave something for a LATER script that goes out of its way to read it (or tell a concurrent one over a `BroadcastChannel`), and no one else; a script that does not read it is unaffected. `K-105` is closed for the browser by the one-batch-per-worker rule; the Node port is `K-106`.
  - **Tests.** `test/script-host.test.ts` runs the real pool over scripted workers (`engine/test/script/fixtures/fake-workers.ts`) for what the port adds: the size by `hardwareConcurrency` and the violation relay (cut, forged fields dropped, a throwing post survived). The spawner and `script-worker.ts` need a browser: **`pixi run engine-scripts-browser`** builds the sandbox and runs `frontend/bench/scripts-run.ts` in Chromium (described in `engine/README.md`): every case of the script parity corpus equal to the oracle's, one after another and all at once, the runaway cases with the default limits, the scope-isolation probe, the CSP control and zero CSP violations elsewhere. It needs both ports free, since a sandbox preview left running serves an old `dist/`.
- **Policy.** `vite.config.ts` sets `Content-Security-Policy: default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self'; worker-src 'self'; frame-ancestors <app origin>`, `Cross-Origin-Embedder-Policy: require-corp` and `Cross-Origin-Resource-Policy: cross-origin` on `preview` AND `server`, so `vite dev` is never laxer than what ships. The app origin comes from `loadEnv(mode, process.cwd(), 'VITE_').VITE_APP_ORIGIN`, defaulting to `http://127.0.0.1:5173` like `src/origins.ts`'s own read of it — `loadEnv`, not `process.env`, because the config itself cannot read `import.meta.env`. `appType: 'mpa'`: a missing file is a 404, not the page again. `worker: {format: 'es'}`, `build.target: 'es2022'`.
- **Three tsconfigs** keep the page from seeing worker globals: `tsconfig.json` (the page: ES2023 + DOM), `tsconfig.worker.json` (both workers and what they import: `host.ts`, `script-host.ts`: ES2023 + WebWorker), `tsconfig.test.json` (tests, and `host.ts`, `handshake.ts`, `script-host.ts` and the configs: DOM + `node`; `script-worker.ts` is checked only as a worker). The engine's sources come in through the imports (`../../engine/src/index.ts`), which is why `allowImportingTsExtensions` is on.
